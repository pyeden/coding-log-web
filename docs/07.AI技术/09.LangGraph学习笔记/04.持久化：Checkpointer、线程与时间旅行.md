# 持久化：Checkpointer、线程与时间旅行

## 本章要解决的问题

没有 checkpointer 时，LangGraph 的执行是纯内存的：`invoke` 返回就结束，状态随风而散。一旦加上 checkpointer，同一张图立刻多出三种能力：断点续跑、历史回看、人工修正状态。但同时也多出三类事故：所有人共用默认线程导致**串话**、状态里塞了不可序列化的对象导致落盘失败、误以为每个节点都有一份快照导致恢复精度不符预期。

这一章按「存在哪、按什么分组、怎么读回来、怎么改」四条线讲持久化。读完你应该能为一个线上服务选对 saver，设计出不会串话的 `thread_id` 规则，并能用 `get_state_history` 把一个失败的执行回溯到具体超步。

## 核心概念与术语

| 术语 | 含义 | 工程含义 |
| --- | --- | --- |
| checkpointer | 负责读写状态快照的组件 | 编译时传入，未传则无持久化 |
| thread | 一组连续快照的命名空间 | 会话隔离的基本单位 |
| `thread_id` | 线程标识，放在 `config["configurable"]` 里 | 生成规则决定是否会串话 |
| 快照（checkpoint） | 某个超步结束时的状态副本 | 恢复与时间旅行的最小单位 |
| `checkpoint_id` | 单个快照的标识 | 可指定它从历史某点重新出发 |
| `get_state` | 读当前线程的最新状态 | 断点查看、调试 |
| `get_state_history` | 读该线程的历史快照序列 | 回溯、审计、复现 |
| `update_state` | 手工写入状态更新 | 人工修正、插入修正值 |
| 序列化器 | 把状态转成可存储字节的组件 | 决定能存什么类型 |
| saver 实现 | 内存 / SQLite / Postgres | 决定持久范围与并发能力 |

## 快照存在哪一步

这是最容易被误解的一点：checkpoint 的粒度是**超步（super-step）**，不是节点。运行时在每个超步结束后写一次快照，也就是说：同一超步内并行执行的多个节点，只在它们全部结束后留下一份合并后的状态。

推论有三条。第一，**恢复只能落在超步边界**，如果某个节点执行了三分钟才失败，恢复时这一整个超步要重跑。第二，**节点拆分粒度直接影响恢复成本**，把长任务拆成多个节点，等于把快照点变密。第三，**快照数量与超步数成正比**，一个二十轮的循环就是二十份快照，状态越大存储压力越明显。

还有一条容易踩的细节：节点内部的副作用（发邮件、扣库存、调外部写接口）在恢复时会重放。因为恢复是从上一个超步边界重新执行，节点会再跑一遍。所以**有副作用的动作必须自己做幂等**，或者在执行前用状态标记「已做过」，让重放时短路跳过。

## 三种 saver 的取舍

| 实现 | 存储位置 | 进程重启后是否保留 | 并发能力 | 适用场景 |
| --- | --- | --- | --- | --- |
| `InMemorySaver` | 进程内存 | 否 | 单进程 | 单测、本地调试、演示 |
| `SqliteSaver` | 本地 SQLite 文件 | 是 | 单机、写锁受限 | 单机服务、桌面工具、原型上线 |
| `PostgresSaver` | Postgres 数据库 | 是 | 多实例共享 | 生产环境、多副本部署 |

选型逻辑很直接：**只要是多副本部署，就必须用共享存储，否则请求落到另一个副本就读不到状态**。用 SQLite 做多副本是经典的坑——文件不共享，表现为「有时候能恢复、有时候说线程不存在」，而且随负载均衡概率变化，极难复现。

内存实现的价值被低估了：单元测试里用它，可以让每个用例都拿到干净的线程，跑得快且无需外部依赖。测试里不要复用同一个 saver 跨用例，否则历史快照会互相干扰，断言变得莫名其妙。

还有一个与存储相关的隐性成本：每次写快照都是一次完整状态落盘，而不是增量补丁。状态里如果躺着几万字的对话历史，每个超步就要重复写一遍。省钱的做法不是关掉持久化，而是把状态做薄——长文本落对象存储或业务库，状态里只留摘要与指针。判断标准很朴素：如果一个字段在三个节点里都没被读过，它大概率不该待在状态里。

```python
import sqlite3

from langgraph.checkpoint.sqlite import SqliteSaver

conn = sqlite3.connect("checkpoints.db", check_same_thread=False)
saver = SqliteSaver(conn)
graph = builder.compile(checkpointer=saver)
```

```python
from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string("postgresql://user:pass@host:5432/db") as saver:
    saver.setup()                     # 首次使用需要建表，具体方法名以官方文档为准
    graph = builder.compile(checkpointer=saver)
```

Postgres 实现通常需要先初始化表结构，这一步在部署脚本里做一次即可。连接串属于密钥，不要写进代码仓库，走环境变量或密钥管理。

## thread_id：隔离与串话

所有持久化能力都挂在 `thread_id` 上。同一个 `thread_id` 的多次 `invoke` 被视为同一条会话的连续推进，状态会累积；不同 `thread_id` 之间完全隔离，互相看不到。

```python
config = {"configurable": {"thread_id": "user-42:session-20261029-01"}}
result = graph.invoke({"messages": [{"role": "user", "content": "你好"}]}, config)
```

串话（一个用户的上下文出现在另一个用户的会话里）是这套机制里最高频的事故，根因几乎都是 `thread_id` 生成得太随意：

| 生成方式 | 风险 | 建议 |
| --- | --- | --- |
| 固定字符串调试用 | 所有请求共用一条线程 | 仅限本地，禁止进生产 |
| 只用用户 ID | 同一用户多个会话互相污染 | 用户 ID + 会话 ID |
| 只用会话 ID | 不同用户可能撞号 | 加用户或租户前缀 |
| 时间戳到秒 | 高并发下可能重复 | 时间戳 + 随机后缀或 UUID |
| 从客户端传入且不校验 | 可越权读别人的线程 | 服务端从鉴权信息派生 |

最后一条是安全问题：如果 `thread_id` 直接取前端传来的值，攻击者改一个字符串就能读到别人的历史状态。正确做法是由服务端根据登录身份派生，前端只传会话序号。

## 读回、回溯与修正

带 checkpointer 的编译产物提供三个读取/写入接口，用途差别很大：

- `get_state(config)`：取最新快照，返回状态值、下一步要执行的节点、以及快照元信息。它是「这个会话现在到哪了」的标准答案。
- `get_state_history(config)`：按时间倒序迭代历史快照。用来定位「哪一步开始跑偏」，也用来做审计。
- `update_state(config, values)`：手工写入更新，产生新的快照。常见用途是人工修正字段后继续，或者在测试里构造特定状态。

```python
state = graph.get_state(config)
print(state.values["attempts"], state.next)

for snap in graph.get_state_history(config):
    print(snap.metadata.get("step"), snap.values.get("attempts"))

# 人工把计数清零后继续
graph.update_state(config, {"attempts": 0})
```

时间旅行的标准做法是：从历史里挑一个快照，拿它的 `checkpoint_id` 放进 `configurable`，再 `invoke`。此时执行会从该快照之后继续，等价于「回到那一步重来」。注意这是**分叉**而不是原地重写——原分支的快照仍然在，方便对比两种走法的结果。

## 序列化边界

状态要被写成字节，所以能放什么有硬边界。安全的类型包括字符串、数字、布尔、列表、字典、以及由它们组成的数据；相对安全的是普通数据类与常见时间类型。不安全的是：数据库连接、HTTP 客户端、线程锁、文件句柄、lambda、本地类的实例。

序列化失败的典型表现是：本地跑得好好的，一加 checkpointer 就报错，且报错栈指向写入而不是业务代码。排查顺序是「先看状态里有没有资源对象，再看有没有自定义类」。自定义类要能被正确还原，需要它可导入且构造路径稳定；否则即使写进去了，读出来也可能变成字典或直接失败。

工程上的折中方案是「状态存引用，对象放外面」：状态里存 `doc_id`、`file_path`、`task_key`，节点执行时按引用去取。这样快照小、可移植，也避免了恢复后拿到一个已经失效的连接。

## 常见坑清单

- [ ] 加了 checkpointer 但 `thread_id` 固定不变，所有用户共用一条会话
- [ ] 多副本部署用 SQLite，请求飘到别的实例就报线程不存在
- [ ] 状态里塞了模型客户端或数据库连接，落盘直接失败
- [ ] 以为每个节点都有快照，恢复时发现整段要重跑
- [ ] 有副作用的节点没做幂等，恢复时重复发通知
- [ ] 生产环境用 `InMemorySaver`，一重启全部会话丢失
- [ ] `thread_id` 直接取前端传值，未做归属校验
- [ ] 历史快照无限增长，没有清理策略，库表迅速膨胀
- [ ] 把 `update_state` 当业务写入接口用，绕过正常流程改状态
