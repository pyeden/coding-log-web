# 导读：为什么读 LangGraph

## 本章要解决的问题

大多数团队在做智能体时，第一步都是「让模型调工具」，第二步就卡住了：多轮之后忘了自己在干什么、出错之后只能从头再跑、需要人确认的环节塞不进去、几个角色互相甩锅停不下来。这些都不是模型能力问题，而是**编排问题**。LangGraph 出现的意义，就是给这类「有状态、长流程、需要人插手」的程序提供一套低层原语，而不是再包一层更聪明的 Agent。

这一章回答四个问题：LangGraph 到底处在技术栈的哪一层；它专门解决哪四类痛点；它和 LangChain 的 AgentExecutor、手写 while 循环、Dify、n8n 分别是什么关系；以及什么情况下你**不该**用它。读完这一章，你应该能判断自己手上的需求是不是 LangGraph 的目标场景，再决定要不要继续读后面八章。

## 核心概念与术语

| 术语 | 含义 | 在本套笔记中的位置 |
| --- | --- | --- |
| 图（Graph） | 由节点和边组成的执行结构，描述「先做什么、再做什么」 | 第 02 章 |
| 节点（Node） | 一个普通的 Python 函数或可调用对象，读状态、返回增量更新 | 第 02 章 |
| 边（Edge） | 节点之间的跳转关系，分固定边与条件边 | 第 03 章 |
| 状态（State） | 在节点之间流转的共享数据结构，通常用 `TypedDict` 描述 | 第 02 章 |
| 通道（Channel） | 状态中每个字段的存储与更新单元，reducer 决定合并方式 | 第 02 章 |
| 超步（super-step） | 一次「并行节点全部执行完」的推进单位，checkpoint 以它为粒度 | 第 04 章 |
| 检查点（Checkpoint） | 每个超步后落盘的状态快照，用于恢复与时间旅行 | 第 04 章 |
| 中断（interrupt） | 在节点内部主动挂起，等外部输入后再继续 | 第 05 章 |
| 子图（Subgraph） | 把一张编译好的图当作另一个图的节点使用 | 第 06 章 |
| 编译（compile） | 把图定义校验并转换成可执行对象 `CompiledStateGraph` | 第 02 章 |
| 流式（stream） | 按不同粒度把执行过程吐出来，供前端或日志消费 | 第 07 章 |
| 线程（thread） | 一组连续 checkpoint 的命名空间，会话隔离的基本单位 | 第 04 章 |

## 它是什么：低层有状态编排框架

LangGraph 由 LangChain 团队出品，定位是**低层（low-level）编排框架**。这句话有两个关键词。

「低层」意味着它不替你做决策。它不内置「先思考再行动」的固定范式，不规定你必须用哪种提示词模板，也不替你挑选记忆策略。它提供的是图、状态、边、检查点、中断这些**原语**，流程长什么样由你画。这与 `create_react_agent` 这类预置封装形成对比：预置封装是「给你一个能跑的循环」，LangGraph 核心是「给你搭循环的零件」。

「有状态」意味着执行不是一次函数调用，而是一串可以暂停、可以回看、可以续跑的超步。每一步之后状态都能被持久化，于是「断线重连」「人工审批」「回滚到第三步重来」这些在纯链式调用里很难实现的能力，变成了配置项。

需要强调一点：LangGraph 不是「更聪明的 Agent」。它不会提升模型推理质量，也不会自动规划任务。它解决的是**工程结构**问题——把不确定的模型输出，装进一个确定可控、可观测、可恢复的执行骨架里。如果模型本身做不对任务，换成 LangGraph 依然做不对。

一个最小的心智模型可以用下面这段骨架表示——它不追求完整，只说明「图 + 状态 + 边」三件事如何在代码里落地：

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class S(TypedDict):
    question: str
    answer: str

def draft(state: S) -> dict:
    return {"answer": "初稿：" + state["question"]}

builder = StateGraph(S)
builder.add_node("draft", draft)
builder.add_edge(START, "draft")
builder.add_edge("draft", END)
graph = builder.compile()

print(graph.invoke({"question": "什么是状态机"}))
```

这段代码里没有循环、没有分支、没有持久化，所以它其实更适合用普通函数写。把它写出来只是为了让你看到：LangGraph 的入口是「定义状态 → 注册节点 → 连边 → 编译」，后面所有能力都是在骨架上加减而已。

## 它解决的四个问题

**第一，显式控制流。** 手写 while 循环时，分支逻辑散落在 `if/else` 里，谁也说不清一共有几条路径。图把控制流变成**可声明、可画出来**的结构：有哪些节点、哪些边、在什么条件下走哪条边，全部写在代码的一处。评审时可以直接看 `compiled.get_graph()` 的输出，而不是靠读三百行嵌套判断。

**第二，可恢复状态。** 长任务最怕中途失败。没有检查点时，失败只能从头再跑，前面的 token 和时间全部作废；有检查点时，可以按 `thread_id` 读回最近一次快照继续，也可以读历史快照做时间旅行。代价是状态必须可序列化，这一点会在第 04 章反复出现。

**第三，人在回路。** 真实业务里总有些动作不能全自动：发邮件、下单、改生产数据。LangGraph 用 `interrupt` 在节点内部挂起，把控制权交回调用方，等人工确认后带着 `Command(resume=...)` 恢复。因为挂起依赖 checkpoint，所以这套能力天然与持久化绑定。

**第四，多智能体协作。** 当任务需要多个角色（规划者、检索者、执行者、审核者）时，可以让每个角色成为子图或节点，用一个路由节点决定派活。相比「一个大提示词里塞四个人格」，显式的图结构让上下文隔离和职责边界都更清楚。

## 与相邻方案的边界

| 方案 | 它替你决定什么 | 适合 | 不适合 |
| --- | --- | --- | --- |
| LangGraph | 只决定执行骨架，流程与状态由你定义 | 长流程、需恢复、需审批、多角色 | 一次性问答、简单单次工具调用 |
| LangChain AgentExecutor | 固定「思考—行动—观察」循环 | 快速验证工具调用闭环 | 复杂分支、需要精细控制与恢复 |
| 手写 while 循环 | 什么都不决定，全靠自己 | 极简场景、教学、原型 | 路径一多就失控，无持久化与观测 |
| Dify | 平台化的可视化工作流与知识库 | 业务人员搭流程、快速上线 | 需要深度定制状态与运行时行为 |
| n8n | 通用自动化集成，触发器 + 节点 | 系统间集成、定时与事件驱动 | 以模型推理为核心的有状态智能体 |

这张表的关键不是「谁更强」，而是**抽象层级**。LangGraph 抽象得最薄，所以最灵活，也最需要你自己想清楚；Dify 和 n8n 抽象得厚，上手快，但遇到它们没预设的行为时就要绕路。判断标准很简单：流程是否需要「暂停—人工介入—继续」、是否需要「回到某一步重跑」、是否需要「多个角色共享一份结构化状态」。只要有一条是硬需求，薄抽象的框架就更合适。

## 图优于链的三个场合

**场合一：存在回退与循环。** 链是单向的，图可以有环。检索不到就改写查询再检索、回答不合格就重写再评审，这类「不满意就回去」的逻辑在有环结构里是一等公民，在链里只能靠外部循环包一层。

**场合二：需要并行与汇合。** 同一次请求要同时查三个数据源再汇总，链只能串行或自己写并发代码；图的超步机制天然支持同一步内多节点并行，再在汇合节点统一读取各分支写入的字段。

**场合三：需要持久化与审批。** 只要流程可能要「停下来等人」，就必须有地方存住当前状态。链式调用把状态放在函数栈里，进程一停就没了；图把状态放在 checkpoint 里，进程重启也能续上。

反过来，如果需求是「一次问答」「单轮工具调用」「定时跑个脚本」，用图就是过度设计。工具选型的成本不只是写代码，还包括团队理解和后续维护。

## 版本基线声明

LangGraph 迭代速度很快，包的拆分、参数名、默认值在不同版本之间都发生过变化。本套笔记**不绑定具体版本号**，代码示例只使用官方文档中长期稳定的核心 API：`StateGraph`、`START`、`END`、`add_node`、`add_edge`、`add_conditional_edges`、`compile`、`Send`、`Command`、`interrupt`、`InMemorySaver`、`create_react_agent`、`ToolNode`。凡是你不确定的参数、默认值、是否已废弃，请**以官方文档为准**，不要照抄任何二手教程（包括本套笔记）里的细节。

安装方式通常是一次性装主包与需要的检查点实现，具体包名以官方安装说明为准：

```bash
# 以官方文档为准；不同版本可能需要额外安装 checkpoint 实现
pip install -U langgraph
pip install -U langgraph-checkpoint-sqlite
pip install -U langgraph-checkpoint-postgres
```

## 常见认知坑

- [ ] 以为 LangGraph 会让模型变聪明：它只改变执行结构，不提升推理质量
- [ ] 一上来就用多智能体：单图加几个节点通常更快、更省钱、更好调
- [ ] 没有检查点就设计「人工审批」：`interrupt` 依赖持久化，没 checkpointer 恢复不了
- [ ] 把状态当全局变量随便塞：状态必须可序列化，塞进客户端、连接池会在落盘时炸
- [ ] 只写节点不画终止条件：有环就必须有出口，否则撞 `recursion_limit`
- [ ] 照抄教程里的参数与默认值：版本差异大，一律以官方文档为准
