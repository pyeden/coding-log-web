# 多智能体：Supervisor、Swarm 与子图

## 本章要解决的问题

「多智能体」是这一波 AI 应用里被过度包装最严重的词。很多所谓多智能体系统，本质是把一个大提示词拆成四个小提示词，然后让它们互相转交，结果是：调用次数翻倍、上下文反复重复、出错时不知道是哪个角色的锅。反过来，有些确实需要分工的系统被硬塞进一个节点里，导致上下文超长、职责混乱。

这一章先回答「到底该不该拆」，再讲两种主流结构：Supervisor（中心调度）与 Swarm / handoff（对等转交），最后讲子图如何封装与映射状态。读完你应该能判断一个需求是「一个图加几个节点」够用，还是真的需要多个角色，并能说清两种结构在成本与可控性上的差别。

## 核心概念与术语

| 术语 | 含义 | 与单图的差别 |
| --- | --- | --- |
| 角色（agent） | 承担特定职责的子流程，通常是一个子图 | 有自己的提示词与工具集 |
| Supervisor | 中心路由节点，决定把任务派给谁 | 全局视角，控制流集中 |
| Worker | 被派活的执行者，完成后交回中心 | 职责单一，不互相直连 |
| Handoff | 把控制权连同上下文交给另一个角色 | 去中心，链式转交 |
| Swarm | 对等的 handoff 网络，无固定中心 | 结构灵活，收敛难保证 |
| 子图（subgraph） | 编译后的图作为父图的一个节点 | 可独立测试与复用 |
| 状态映射 | 父子图之间字段的对应关系 | 决定耦合程度 |
| 上下文隔离 | 各角色只看到自己需要的信息 | 降低成本与干扰 |
| 路由抖动 | 两个角色反复互相转交 | 多智能体的典型病症 |

## 先问：真的需要多智能体吗

判断标准不是「任务复不复杂」，而是下面三个条件是否至少满足一个：

| 条件 | 说明 | 单图能否满足 |
| --- | --- | --- |
| 上下文必须隔离 | 不同阶段需要完全不同的资料，混在一起会互相干扰 | 勉强可以，靠字段裁剪 |
| 工具集冲突 | 两个阶段要用截然不同的工具与权限 | 可以，但提示词会膨胀 |
| 需要并行分工 | 多个子任务可同时进行再汇总 | 可以，用 `Send` |
| 需要独立演进 | 不同角色由不同团队维护 | 难，耦合在一个文件里 |
| 需要不同模型 | 规划用强模型、执行用便宜模型 | 可以，节点内切换 |

如果只有「工具多」「提示词长」，优先考虑**单图多节点 + 字段裁剪**。把规划、检索、执行、审核拆成四个节点，各自只读需要的字段，往往比四个互相转交的智能体更便宜、更好调。只有当你需要「独立的对话历史」「独立的工具权限」「不同团队分别维护」时，角色的边界才值得用子图固化下来。

一条经验：**能用状态字段表达的分工，不要用角色表达**。角色会带来额外的模型调用、额外的上下文复制，以及额外的失败面。

还有一个常被忽略的成本：角色越多，**调试信息越碎**。单图出问题时看一条日志就能定位；五个角色互相转交时，要先把五次调用的输入输出按时间线拼起来，才能判断是哪一步把任务带偏了。如果团队还没有成熟的追踪体系（第 07 章会讲），多智能体带来的排障成本往往超过它省下的提示词工程成本。先把单图跑顺，再考虑拆分，顺序不要反。拆分时也不要一次拆五个，从一个 worker 加一个 supervisor 开始，验证完收敛性与成本再加人。

## Supervisor：中心调度

Supervisor 的结构非常直白：一个路由节点读当前状态，决定「下一步派给谁」或「结束」；worker 干完活回到 supervisor，由它再决定下一步。

```python
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command

def supervisor(state: dict) -> Command:
    if state.get("done"):
        return Command(goto=END)
    if not state.get("plan"):
        return Command(goto="planner")
    if state.get("need_search"):
        return Command(goto="researcher")
    return Command(goto="writer")

builder = StateGraph(AgentState)
builder.add_node("supervisor", supervisor)
builder.add_node("planner", planner_graph)     # 子图直接当节点
builder.add_node("researcher", researcher_graph)
builder.add_node("writer", writer_graph)
builder.add_edge(START, "supervisor")
builder.add_edge("planner", "supervisor")
builder.add_edge("researcher", "supervisor")
builder.add_edge("writer", "supervisor")
```

它的优点是**可控**：所有跳转集中在一个函数里，加一条日志就能看清「谁被派了几次」；出问题只需看 supervisor 的决策记录。缺点是**中心节点成为瓶颈**：每一轮都要多一次模型调用来做路由，长任务下这部分开销不可忽视。缓解办法是让 supervisor 尽量用规则做决策，只在真正需要判断时才调模型。

Supervisor 还有一个隐性好处：它天然允许「回到上一步」。writer 写得不满意，supervisor 可以再派给 researcher 补资料，不需要 worker 之间互相认识。

## Swarm 与 handoff：对等转交

Swarm 去掉了中心：每个角色都能把控制权直接交给另一个角色，通常用 `Command(goto=..., update=...)` 实现，并把「当前该谁说话」写进状态。

| 维度 | Supervisor | Swarm / handoff |
| --- | --- | --- |
| 控制结构 | 星型，中心调度 | 网状，对等转交 |
| 转交成本 | 每轮一次路由决策 | 只在转交时决策 |
| 可观测性 | 高，决策集中 | 低，路径分散 |
| 收敛性 | 容易加全局终止条件 | 需要额外的转交计数与熔断 |
| 适合 | 任务可分阶段、需要审核 | 对话式协作、职责边界清晰 |
| 风险 | 中心节点成本高 | 无限互相转交、责任不清 |

Swarm 的风险必须正视：A 交给 B，B 觉得该 A 处理又交回去，如果没有转交计数，这个环会一直转到递归上限。工程上至少要加两样东西：状态里的 `handoff_count`，以及「同一个角色连续被转回超过 N 次就强制收口」的规则。

官方提供了 supervisor 与 swarm 的封装包（`langgraph-supervisor`、`langgraph-swarm`），可以少写样板代码。它们的参数与行为随版本变化，**以官方文档为准**；但结构上的取舍与上面这张表一致，封装不会替你解决收敛问题。

## 子图：封装与状态映射

子图的价值是把一坨节点打包成「一个可测试的单元」。用法有两种：直接 `add_node("name", compiled_subgraph)`，或者在节点函数里手动 `subgraph.invoke(...)`。前者更简洁，后者更灵活（可以自己决定传什么、怎么改）。

用第一种方式时，父子图的状态通过**同名字段**自动衔接：父图调用子图时，把匹配的字段传进去；子图结束时，把匹配的字段回写。字段名对不上就要写一层包装函数做映射。

```python
def research_node(state: ParentState) -> dict:
    # 显式映射：父图字段 -> 子图字段
    sub_out = research_graph.invoke({
        "query": state["question"],
        "docs": [],
        "messages": state["messages"],
    })
    return {"docs": sub_out["docs"], "sources": sub_out.get("sources", [])}

builder.add_node("research", research_node)
```

显式映射虽然多写几行，但换来两个好处：子图可以独立定义自己的状态，不必为了迁就父图而膨胀；父子之间的耦合点集中在一处，重构时只改这个函数。

子图内部的检查点需要注意：如果父子图都用 checkpointer，恢复语义会变复杂（父图恢复到某个超步时，子图内部的进度是否也要恢复）。稳妥做法是**只在最外层挂 checkpointer**，子图作为纯函数式的一段流程执行；确实需要子图独立恢复时，再单独设计线程命名空间，**以官方文档为准**。

## 失败模式与对策

| 失败模式 | 表现 | 对策 |
| --- | --- | --- |
| 路由抖动 | 两个角色反复互交，轮次暴涨 | 转交计数 + 熔断规则 |
| 无限互相转交 | 撞递归上限或超时 | 全局最大轮次 + 强制收口 |
| token 成本失控 | 单请求费用是预估的数倍 | 上下文裁剪、角色用便宜模型 |
| 责任不清 | 出错后不知道哪个角色该修 | 每步写角色名与决策理由 |
| 状态污染 | 一个角色改了别人的字段 | 字段前缀 + 子图隔离 |
| 空转 | 角色收到不属于自己的任务仍照做 | 入口校验职责范围，不合格就交回 |

## 常见坑清单

- [ ] 三个角色其实可以合并成一个节点，纯属增加调用次数
- [ ] Supervisor 每一轮都调模型做路由，成本远超预期
- [ ] Swarm 没有转交计数，A、B 之间来回甩
- [ ] 所有角色共享一份超长上下文，隔离等于没做
- [ ] 子图与父图字段名不一致，静默丢数据
- [ ] 父子图都挂 checkpointer，恢复时状态错乱
- [ ] 角色提示词里没有「什么时候该交回」的规则
- [ ] 没有全局终止条件，靠 `recursion_limit` 兜底
- [ ] 用多智能体解决「提示词太长」的问题，方向就错了
