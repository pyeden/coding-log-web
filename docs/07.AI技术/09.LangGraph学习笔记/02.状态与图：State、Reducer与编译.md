# 状态与图：State、Reducer 与编译

## 本章要解决的问题

LangGraph 里最容易埋雷的地方不是控制流，而是**状态设计**。同样的图，状态字段用默认覆盖语义，上一轮的检索结果就会被下一轮清空；消息列表忘了加 `add_messages`，第二条消息直接把第一条顶掉；节点函数顺手 `state["items"].append(x)`，两个并行分支就丢了一半数据。

这一章要解决四件事：状态 schema 该怎么写（`TypedDict` 还是 `dataclass`）；`Annotated[T, reducer]` 到底改变了什么；节点返回值为什么必须是「部分更新」而不是完整状态；`compile()` 究竟做了什么、产物为什么能直接 `invoke`。读完你应该能一眼看出一个状态定义在该追加的地方有没有用错 reducer。

## 核心概念与术语

| 术语 | 含义 | 常见误用 |
| --- | --- | --- |
| State | 在节点之间流转的共享数据，由 schema 描述 | 当成全局变量随意读写 |
| `TypedDict` | 用类型注解描述字典结构，运行时不做校验 | 以为它会在运行时拦截类型错误 |
| `dataclass` | 带默认值与构造的类式 schema | 塞入不可序列化的字段 |
| `Annotated[T, reducer]` | 声明「该字段的更新如何合并」 | 以为它只是文档注释 |
| reducer | 合并函数，签名大致是 `(旧值, 新值) -> 合并值` | 自定义 reducer 里改入参 |
| `add_messages` | 消息列表专用 reducer，按消息 id 追加或替换 | 消息字段用默认覆盖语义 |
| `MessagesState` | 预置的「只有 messages 字段」的状态类型 | 需要额外字段时忘了继承扩展 |
| 部分更新 | 节点只返回自己改动的字段 | 返回整个状态导致覆盖他人写入 |
| `START` / `END` | 图的虚拟入口与出口 | 把 `END` 当成节点去 `add_node` |
| `compile()` | 校验并生成可执行图 `CompiledStateGraph` | 以为编译后可再改结构 |

## 状态 schema：先定形状，再谈逻辑

状态是图的合同。节点之间不直接传参，全部通过状态通信，所以 schema 一旦定歪，后面每个节点都要绕路。实践中优先用 `TypedDict`：它轻、和字典天然兼容、序列化没有额外负担。`dataclass` 适合需要默认值或少量方法的场景，但要记住它最终仍会被当成结构化数据落盘，方法不会跟着走。

```python
from typing import Annotated, TypedDict

from langgraph.graph.message import add_messages

class ResearchState(TypedDict):
    question: str                                  # 覆盖语义：后写覆盖前写
    messages: Annotated[list, add_messages]        # 追加/按 id 合并
    docs: Annotated[list[str], lambda old, new: old + new]  # 追加
    attempts: int                                  # 覆盖语义
    final: str
```

三个字段三种语义，正好对应三类需求：**单值事实**用覆盖（当前问题、当前答案、计数器要小心）、**累积集合**用追加（检索到的文档、日志、消息）、**需要去重或替换的集合**用专用 reducer（消息）。

关于 `add_messages` 为什么「必须」用于消息列表，值得展开。消息列表不是简单追加：同一条消息可能被后续节点改写（比如给 AI 消息补上工具结果、修正内容），此时应当按消息 id **替换**而不是再追加一条。`add_messages` 同时处理了「新消息追加」与「同 id 消息替换」，还会做基本的类型归一化（把字典转成消息对象）。用默认覆盖语义，第二轮就只剩一条消息；用裸 `lambda old, new: old + new`，改写会变成重复堆积。这就是它在几乎所有官方示例里出现的原因。

## reducer 的合并时机

很多误解来自「reducer 什么时候跑」。答案是：**每个超步结束时，运行时把各节点返回的增量按字段合并**。顺序上，同一超步内多个节点对同一字段的写入，会按 reducer 依次合并；如果字段没有 reducer（默认覆盖），后合并的写入直接覆盖先前的。

这带来三条推论：

1. **并行写同一字段必须给 reducer。** 两个分支都想往 `docs` 里加结果，没有追加 reducer 就只剩一份。
2. **reducer 必须无副作用且可重放。** 恢复执行时可能重复合并，reducer 里若做了网络请求或写文件，会产生重复副作用。
3. **reducer 的入参不要原地修改。** `old.append(new)` 会污染快照，进而让「时间旅行读历史状态」读到被改过的数据。正确写法是返回新对象。

自定义 reducer 的代码量很小，但要守住纯函数这条线：

```python
def merge_unique(old: list[str], new: list[str]) -> list[str]:
    seen = set(old)
    out = list(old)
    for item in new:
        if item not in seen:
            seen.add(item)
            out.append(item)
    return out
```

## 节点返回值：永远是部分更新

节点函数读完整状态、只返回自己改动的字段。这是 LangGraph 与「函数式管道」最大的差别之一：返回值不是新状态，而是**补丁**。

| 写法 | 结果 | 评价 |
| --- | --- | --- |
| `return {"answer": text}` | 只更新 `answer` | 正确，推荐 |
| `return {**state, "answer": text}` | 把所有字段重写一遍 | 危险：并行时会覆盖别人的写入 |
| `state["answer"] = text; return state` | 原地改快照 | 错误：污染历史状态 |
| `return {"docs": [doc]}` | 交给 reducer 合并 | 正确，追加语义 |
| `return {}` | 不更新任何字段 | 合法，但要确认边仍能推进 |

一个容易被忽略的细节：如果节点返回了 schema 里没有的字段，通常会被忽略或报错，取决于版本与配置，**以官方文档为准**。稳妥做法是让状态定义覆盖所有会被写入的键。

## 图：从构造到编译

构造阶段只做三件事：声明状态类型、注册节点、连边。

```python
from langgraph.graph import StateGraph, START, END

def retrieve(state: ResearchState) -> dict:
    return {"docs": ["doc-a"], "attempts": state["attempts"] + 1}

def answer(state: ResearchState) -> dict:
    return {"final": "基于 " + str(len(state["docs"])) + " 篇资料作答"}

builder = StateGraph(ResearchState)
builder.add_node("retrieve", retrieve)
builder.add_node("answer", answer)
builder.add_edge(START, "retrieve")
builder.add_edge("retrieve", "answer")
builder.add_edge("answer", END)

graph = builder.compile()

out = graph.invoke({"question": "为什么需要 reducer", "messages": [], "docs": [], "attempts": 0, "final": ""})
print(out["final"], out["attempts"])
```

`compile()` 做的是校验与打包：检查边指向的节点是否存在、把节点与边装进运行时需要的结构、绑定 checkpointer 与中断点，最后返回 `CompiledStateGraph`。编译后结构不可变——想加节点就重新构造，不要试图改已编译对象。产物的接口很直观：`invoke` 输入初始状态、输出最终状态；`stream` 输出过程；带 checkpointer 时还能 `get_state` / `get_state_history`。

`MessagesState` 是一个便利类型，等价于「只有一个带 `add_messages` 的 `messages` 字段」。需要额外字段时，继承它再补字段通常比从零写更省事：

```python
from langgraph.graph import MessagesState

class ChatState(MessagesState):
    summary: str
    turn: int
```

## 状态的读写边界

状态虽然是共享的，但「谁能读、谁能写」需要在设计阶段就想清楚。默认情况下每个节点都能看到全部字段，这在节点数量少时很方便，节点一多就变成隐式耦合：改一个字段名要翻遍所有节点，某个节点偷偷依赖另一个节点的中间产物也查不出来。

常见的收口办法有三种。一是**按职责拆分字段命名**，例如 `plan_*`、`search_*`、`answer_*` 前缀，让「这个字段归谁维护」一眼可见。二是**在节点入口做断言**，节点开头检查自己依赖的字段是否存在且非空，把上游漏写变成明确报错，而不是带着空值跑到下游才炸。三是**用子图隔离**，把一组互相依赖的节点封进子图，对外只暴露少量字段（第 06 章会展开）。

还有一种反模式值得点名：把状态当成日志仓库，每个节点都往里追加一大段文本，最后几万字的字符串跟着每次 checkpoint 反复落盘。正确做法是状态里只留决策所需的最小信息，长文本放外部存储，状态里存 id 或摘要。这条规则对成本和恢复速度的影响，往往比换模型更明显。

## 状态 schema 设计原则

| 原则 | 说明 | 违反后的症状 |
| --- | --- | --- |
| 扁平优先 | 少嵌套，字段名自解释 | 深层嵌套难合并、难调试 |
| 可序列化 | 只放 JSON/pickle 友好的数据 | checkpoint 落盘报错 |
| 不放资源句柄 | 客户端、连接池、线程锁放在节点外 | 序列化失败、恢复后句柄失效 |
| 一个字段一个语义 | 别让 `data` 同时装三种东西 | reducer 无法统一 |
| 大对象存引用 | 文档存 id 或路径，正文放外部存储 | 快照膨胀、恢复变慢 |
| 显式计数与标记 | 用 `attempts`、`done` 支撑终止判断 | 循环无法收敛 |

第六条值得强调：状态里最好显式保留「已经试了几次」「是否已完成」这类字段，而不是指望从消息数量推断。循环的终止条件写在边上是逻辑，写在状态里才是可观测的事实。

## 常见坑清单

- [ ] 消息字段忘了 `Annotated[list, add_messages]`，第二轮消息覆盖第一轮
- [ ] 节点返回整个状态（`{**state, ...}`），并行时互相覆盖
- [ ] 在节点里原地修改 `state` 的列表，历史快照被污染
- [ ] 把 `requests.Session`、数据库连接放进状态
- [ ] 自定义 reducer 里做网络请求，重放时产生重复副作用
- [ ] 用默认覆盖语义累积文档，最后只剩一份
- [ ] 编译后又想改结构，试图操作 `CompiledStateGraph` 内部
- [ ] 状态字段命名含糊（`data`、`info`），三个月后自己看不懂
