# 流式与可观测：stream、事件与追踪

## 本章要解决的问题

一个跑十秒的智能体，如果前端十秒后才一次性出结果，用户会以为页面卡死；一次线上事故，如果只有「请求失败」四个字，你根本不知道是检索没返回、模型超时，还是路由走错分支。流式与可观测解决的正是这两件事：**把过程吐出来给用户看**，以及**把过程记下来给工程师看**。

这一章先拆 `stream` 的几种模式分别吐什么、什么时候用哪一种；再讲 token 级流式为什么必须用 `messages` 模式；然后讲自定义事件与 `astream_events` 的关系；最后落到追踪方案的选择与日志脱敏。读完你应该能为一个服务设计出「前端有进度、后台有 trace」的最小可观测方案。

## 核心概念与术语

| 术语 | 含义 | 使用时关注 |
| --- | --- | --- |
| `stream` / `astream` | 同步/异步地逐步产出执行结果 | 异步优先，避免阻塞 |
| `stream_mode` | 决定吐什么粒度的数据 | 直接决定前端能显示什么 |
| `values` | 每个超步后的完整状态 | 数据大，适合调试 |
| `updates` | 每个节点返回的增量 | 体积小，适合做进度 |
| `messages` | 模型产生的消息与 token 片段 | token 级打字机效果 |
| `custom` | 节点内主动写出的自定义事件 | 长任务进度、阶段提示 |
| `debug` | 尽可能详细的事件流 | 排障用，别进生产前端 |
| `astream_events` | 基于 LangChain 事件体系的事件流 | 细到每次 LLM/工具调用 |
| trace | 一次请求的完整调用树 | 定位慢在哪、错在哪 |
| span | 调用树中的一个节点（一次 LLM、一次工具） | 看输入输出与耗时 |

## stream_mode 的差异

同一张图，换一个 `stream_mode`，你看到的东西完全不同。理解差别的最好方式是记住「粒度」与「体积」的反比关系。

| 模式 | 产出内容 | 体积 | 典型用途 |
| --- | --- | --- | --- |
| `values` | 每步之后的完整状态 | 大 | 本地调试、状态快照对比 |
| `updates` | `{节点名: 该节点的增量}` | 小 | 进度条、阶段提示 |
| `messages` | `(消息片段, 元信息)` 二元组 | 中 | 打字机效果、逐字显示 |
| `custom` | 节点内 `get_stream_writer()` 写出的任意数据 | 可控 | 长任务进度、工具执行提示 |
| `debug` | 尽可能全的事件（含任务开始/结束） | 很大 | 排障、复现问题 |

`values` 与 `updates` 最容易混。前者是「当前完整状态的快照」，后者是「这一步变了什么」。前端做进度显示时用 `updates`，因为只需要知道「检索完成了、找到 3 篇」；要把中间状态存下来做对比时用 `values`，因为它自带上下文。

```python
for chunk in graph.stream(
    {"messages": [{"role": "user", "content": "介绍一下 checkpointer"}]},
    config,
    stream_mode=["updates", "messages"],
):
    mode, payload = chunk
    if mode == "updates":
        print("节点完成：", payload)
    else:
        msg, meta = payload
        print("token：", getattr(msg, "content", "")[:20])
```

注意同时传多个模式时，产出会带上模式标识，消费端要按标识分流。这一点在文档里有示例，具体返回结构在不同版本可能微调，**以官方文档为准**。

## token 级流式为什么要用 messages

想让前端出现「一个字一个字蹦出来」的效果，必须拿到模型输出的 token 片段。图级别的 `values` / `updates` 只在节点结束时才有数据，节点里的一次 LLM 调用要等全部生成完才返回，所以看不到 token。

`messages` 模式的实现思路是：运行时把节点内发生的模型调用也接进流里，产出消息片段与元信息（包含来自哪个节点、哪条消息）。于是即便你的节点是「一次 LLM 调用 + 后处理」，前端也能边生成边显示。

三个注意点：

1. **片段不是完整消息**。拼接逻辑要放在前端或消费端，按消息 id 归并；直接覆盖显示会只剩最后一个字。
2. **元信息用于分流**。多节点都调模型时，要按元信息里的节点名区分，否则主回答和内部评审的 token 会混在一起。
3. **工具调用与文本可能交替出现**。渲染时要把「正在调用工具」与「正在生成文本」分开处理，否则会出现内容闪烁。

## 自定义事件：让长任务有进度

有些节点要跑很久（批量处理、逐条校验），期间没有任何模型输出。这时用 `custom` 模式配合 `get_stream_writer`，在节点内部主动写进度：

```python
from langgraph.config import get_stream_writer

def batch_check(state: dict) -> dict:
    writer = get_stream_writer()
    total = len(state["items"])
    for i, item in enumerate(state["items"], start=1):
        check(item)
        writer({"stage": "batch_check", "done": i, "total": total})
    return {"checked": total}
```

消费端用 `stream_mode="custom"` 就能收到这些字典。这个机制的价值在于**把「进度」变成正式的输出协议**，而不是靠日志文件或数据库轮询。要注意写入频率：每处理一条写一次，在前端可能造成上千次更新，通常按百分比或每 N 条节流一次。

## astream_events 与追踪体系

`astream_events` 提供的是更细粒度的、基于 LangChain 回调的事件流：一次请求会产出「链开始」「模型开始」「token」「工具开始/结束」等事件，每条带名字、标签与输入输出。它适合两类场景：需要一个统一的「事件总线」同时驱动前端与日志；或者需要统计每次 LLM/工具的耗时。

与 `stream` 的分工可以这样理解：`stream` 是**图视角**的过程输出，`astream_events` 是**调用视角**的事件流。前者回答「流程走到哪了」，后者回答「每一次外部调用花了多久、输入是什么」。构建复杂应用时，常见做法是前端用 `stream`（简单、稳定），后台用事件流或追踪系统记录细节。

LangSmith 是官方的追踪与评测平台，开启方式通常是设置环境变量（变量名随产品更名有过变化，例如 `LANGCHAIN_TRACING_V2` 与 `LANGSMITH_TRACING` 都出现过），**以官方文档为准**：

```bash
export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY="你的密钥"
export LANGSMITH_PROJECT="langgraph-notes-demo"
```

开启后，每次 `invoke` / `stream` 都会生成一条 trace，按图—节点—模型调用分层展开，能直接看到每次调用的输入输出与耗时。对 LangGraph 应用来说，这是最省事的排障手段，代价是数据要出网（或走自托管部署）。

## 自建观测的取舍

| 方案 | 优点 | 代价 | 适合 |
| --- | --- | --- | --- |
| LangSmith | 与框架原生集成、开箱即用 | 数据出境、按量计费 | 快速排障、团队无观测基建 |
| Langfuse 等开源方案 | 可自托管、数据可控 | 需部署与维护 | 有合规要求、想长期存明细 |
| OpenTelemetry | 与现有 APM 打通、标准协议 | 语义约定要自己定 | 已有成熟可观测平台 |
| 自建日志 + 数据库 | 完全可控、成本低 | 结构化与查询全靠自己 | 小规模、只需关键节点记录 |

选择的关键不是工具，而是**你要回答什么问题**。如果问题是「这次请求为什么慢」，需要的是 span 级耗时；如果是「上周这类问题出现几次」，需要的是可聚合的字段与看板；如果是「模型为什么这么答」，需要的是完整输入输出留存。先列问题，再选工具，否则会陷入「接了一堆 SDK 但没人看」的状态。

无论选哪种，有三条底线：**每次请求有唯一 id**（与 `thread_id`、业务单号能对上）、**每个节点记录开始与结束**、**失败要记录异常类型与堆栈摘要**。这三条做到了，剩下的是锦上添花。

## 日志脱敏

追踪系统最容易变成数据泄露的通道。模型输入里常有手机号、身份证、订单号、内部地址；工具调用参数里常有密钥。上线前必须处理：

- [ ] Prompt 与消息内容入库前做正则脱敏（手机号、邮箱、证件号、卡号）
- [ ] 工具参数里的密钥、token、连接串整体替换为占位符
- [ ] 文件路径与内网地址按需截断或哈希
- [ ] 设置留存期，到期自动删除，而不是永久堆积
- [ ] 区分环境：测试数据可以全留，生产默认最小化
- [ ] 访问控制：追踪平台账号纳入统一权限管理
- [ ] 采样：高流量下按比例采样，避免成本与噪声失控
- [ ] 明确告知：涉及用户数据时，确认合规要求与告知义务

还有一条常被漏掉：**异常堆栈里也可能带敏感数据**。捕获异常时不要直接把整个 `locals()` 序列化进去，只记录类型、消息与关键字段。

## 常见坑清单

- [ ] 前端用 `values` 模式，每步推一次完整状态，流量翻十倍
- [ ] 用 `updates` 却期望拿到 token 片段，打字机效果做不出来
- [ ] `messages` 模式拼接时按「最新片段」覆盖，只显示最后一个字
- [ ] `custom` 事件每条都推，前端被上千次更新卡死
- [ ] 生产环境开 `debug` 模式，日志量爆炸且含敏感信息
- [ ] 追踪只记成功请求，失败请求反而没有上下文
- [ ] trace 与业务单号对不上，出事后无法定位到具体用户
- [ ] 采样率设置不当，关键故障恰好被采样掉
