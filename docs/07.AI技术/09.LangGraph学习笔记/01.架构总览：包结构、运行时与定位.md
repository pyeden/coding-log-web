# 架构总览：包结构、运行时与定位

## 本章要解决的问题

第一次装 LangGraph 的人常被一堆包装晕：`langgraph`、`langgraph-checkpoint`、`langgraph-checkpoint-sqlite`、`langgraph-checkpoint-postgres`、`langgraph-prebuilt`、`langgraph-cli`，再加上服务端的 LangGraph Server。到底哪个必须装、哪个是可选、哪个只在生产需要？为什么有的教程 `from langgraph.prebuilt import create_react_agent`，有的又来自别的路径？

这一章给出三层地图：**包的分层**（谁依赖谁、各自职责）、**运行时的执行模型**（一次 `invoke` 从入口到落盘发生了什么）、**与 LangChain 的分工**（组件与编排的边界）。读完你应该能仅凭报错信息判断「缺的是核心包、检查点实现，还是预置组件」，也能解释为什么同一个图在加 checkpointer 前后行为不同。

## 核心概念与术语

| 术语 | 含义 | 对应包/位置 |
| --- | --- | --- |
| 图定义 API | `StateGraph`、`START`、`END`、`add_node`、`add_edge` | `langgraph.graph` |
| 运行时 | 把编译后的图按超步执行、调度并行节点的引擎 | `langgraph` 内部（Pregel 风格） |
| 检查点抽象 | `BaseCheckpointSaver` 接口与内存实现 | `langgraph-checkpoint` |
| 检查点落库 | SQLite / Postgres 的具体实现 | `langgraph-checkpoint-sqlite`、`langgraph-checkpoint-postgres` |
| 预置组件 | `create_react_agent`、`ToolNode`、`tools_condition` | `langgraph-prebuilt` |
| 服务端工具 | 本地跑服务、打包镜像、生成配置的命令行 | `langgraph-cli` |
| LangGraph Server | 托管图、提供线程/流式/后台任务的运行时服务 | 服务端产品，以官方文档为准 |
| 控制原语 | `Send`、`Command`、`interrupt` | `langgraph.types` |
| 配置 | 递归上限、线程号、回调等运行时参数 | `config` 参数（`configurable`、`recursion_limit`） |

## 包的分层

LangGraph 的设计是「核心极薄 + 周边可插拔」。核心只关心图怎么跑，其它能力都拆成独立包，按需安装。这种拆分对部署很友好：只跑内存检查点的原型不需要拖一个 Postgres 驱动，只做静态图校验的 CI 也不需要服务端。

| 层 | 包 | 职责 | 是否必需 |
| --- | --- | --- | --- |
| 图与运行时 | `langgraph` | `StateGraph`、编译、超步调度、`stream`、控制原语 | 必需 |
| 持久化抽象 | `langgraph-checkpoint` | `BaseCheckpointSaver` 接口、`InMemorySaver` 等内存实现 | 用到恢复/中断时必需 |
| 持久化实现 | `langgraph-checkpoint-sqlite` / `-postgres` | 把 checkpoint 落到 SQLite / Postgres | 按存储选一个 |
| 预置构件 | `langgraph-prebuilt` | `create_react_agent`、`ToolNode` 等常用组合 | 可选，省样板代码 |
| 开发与服务端 | `langgraph-cli`（及服务端组件） | `langgraph dev` 本地起服务、打包、按 `langgraph.json` 加载图 | 部署到 Server 时必需 |
| 多智能体扩展 | `langgraph-supervisor`、`langgraph-swarm` | 官方提供的 Supervisor / Swarm 组合封装 | 可选 |

分层带来一个实用推论：**报错信息里的包名就是线索**。`ImportError: cannot import name 'InMemorySaver'` 说明检查点包没装或路径变了；`AttributeError: 'CompiledStateGraph' object has no attribute 'get_state_history'` 往往是没传 checkpointer；`ModuleNotFoundError: langgraph.prebuilt` 则是预置包缺失。按层排查比盲搜快得多。

需要提醒：包的拆分方式与模块路径在不同版本之间调整过，例如内存检查点的导入路径就变过。凡是导入报错，先查官方文档的安装与迁移说明，**以官方文档为准**，不要凭记忆改 import。

## 一次 invoke 的调用链

理解执行模型比记住 API 更重要。把一次 `invoke` 拆成五步：

1. **构图与编译。** `StateGraph(S)` 收集节点与边，`compile()` 做结构校验（是否有不可达节点、是否有环但无出口的明显问题），产出 `CompiledStateGraph`。编译时如果传入 `checkpointer`，后续每次执行都会尝试落盘。
2. **写入初始状态。** `invoke(input, config)` 把输入按状态 schema 写进通道；`config` 里的 `configurable.thread_id` 决定这次执行归属哪个线程。
3. **超步推进。** 运行时按 Pregel 风格执行：同一超步内可并行的节点一起跑，各自读取当前状态快照、返回**部分更新**；运行时把更新按字段的 reducer 合并进通道。
4. **路由。** 固定边直接进入下一个节点；条件边的路由函数读取更新后的状态，返回下一个节点名（或一组 `Send` 做动态分发）。
5. **落盘与终止。** 每个超步结束后写一次 checkpoint（配置了 saver 时），直到某条边指向 `END`；返回值为最终状态。

这个模型解释了三件容易困惑的事。其一，**节点之间不共享内存**，只通过状态通信，所以节点函数不要依赖外部可变全局变量。其二，**同一超步内的并行节点读的是同一份快照**，谁后写谁覆盖取决于 reducer，这就是并行写同一字段会丢更新的原因。其三，**checkpoint 粒度是超步而不是节点**，所以「恢复到第 3 个节点执行到一半」这种精度是拿不到的，只能恢复到某个超步边界。

## 与 LangChain 的分工

一句话概括：**LangChain 提供组件，LangGraph 负责编排与状态。**

| 关注点 | LangChain | LangGraph |
| --- | --- | --- |
| 模型调用 | 统一 ChatModel 接口、消息格式 | 不关心，节点里随便调 |
| 工具定义 | `@tool`、参数 schema、绑定 | 不关心，用 `ToolNode` 时借用 |
| 检索 | Loader、Splitter、VectorStore、Retriever | 不关心，作为节点内部实现 |
| 流程控制 | 链式组合（LCEL）为主 | 图、条件边、循环 |
| 状态管理 | 无统一跨步状态 | 显式 State + reducer + checkpoint |
| 人在回路 | 需自行实现 | `interrupt` + `Command(resume=...)` |
| 观测 | 回调体系、LangSmith 追踪 | 复用同一套回调与追踪 |
| 部署 | 无强制形态 | 可裸跑、可包 FastAPI、可上 LangGraph Server |

因此两者不是替代关系。常见组合是：用 LangChain 的模型封装与工具定义，用 LangGraph 画流程。也可以完全不用 LangChain——LangGraph 的节点就是普通函数，你直接调 SDK 也行，只是会失去统一的回调与追踪。

## 可操作示例：最小服务化骨架

下面演示「编译产物 + 配置 + 状态查询」的组合方式。示例只用稳定 API，参数细节以官方文档为准。

```python
from typing import Annotated, TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver

class State(TypedDict):
    messages: Annotated[list, add_messages]
    step: int

def plan(state: State) -> dict:
    # 节点只返回增量更新，不修改入参
    return {"step": state.get("step", 0) + 1}

def act(state: State) -> dict:
    return {"step": state["step"] + 1}

builder = StateGraph(State)
builder.add_node("plan", plan)
builder.add_node("act", act)
builder.add_edge(START, "plan")
builder.add_edge("plan", "act")
builder.add_edge("act", END)

graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "demo-1"}}
result = graph.invoke({"messages": [], "step": 0}, config)
print(result["step"])          # 2

# 有 checkpointer 才能读状态
state = graph.get_state(config)
print(state.values["step"])    # 2
```

命令行侧，开发与检查通常围绕 CLI 与配置文件进行。部署到 Server 时，配置文件 `langgraph.json` 描述「有哪些图、依赖怎么装」，其字段随版本演进，**以官方文档为准**：

```bash
# 本地开发服务（命令与端口以官方文档为准）
langgraph dev

# 安装与版本确认
pip show langgraph
```

## 运行时特性：并行、持久化与「不自带记忆」

理解运行时还需要澄清三个常被误解的点。

**其一，并行是超步级的，不是线程池级的自由并发。** 当一个节点通过条件边同时分发到多个节点，运行时会在同一超步内并行执行它们，等全部结束再统一合并状态。这意味着并行分支的耗时不等于各自耗时之和，但也意味着**你无法在超步中途读取另一个分支的写入**。如果业务上确实需要「边跑边看」，只能靠流式接口把中间事件吐出来，而不是靠共享变量。

**其二，持久化是「每步一次快照」，不是「每步一次事务」。** 每个超步结束后写一次 checkpoint，写入失败时通常表现为本轮执行报错而不是静默丢更新。这带来两个后果：快照数量与超步数成正比，长循环会明显放大存储；以及恢复点只能落在超步边界。工程上通常用「限制循环次数 + 定期清理旧线程」控制体积，而不是期待框架自动压缩。

**其三，LangGraph 不自带「记忆」概念。** 它提供的是状态与检查点，长期记忆要靠你自己实现：把摘要写回状态字段、把事实存进向量库或数据库、在入口节点做检索注入。很多教程把「checkpointer 等于记忆」混为一谈，实际上 checkpointer 只是把**线程内的状态**存住了，跨线程的知识复用仍是你自己的活儿。

这三个点决定了架构选型时的分工：需要并行就在图里表达分支，需要跨会话记忆就在节点里接外部存储，需要更高恢复精度就要把长节点拆细。

落到代码上有个简单判据：如果一个节点函数超过了「读状态、调一次外部服务、返回增量」这三件事，它就该被拆开。拆开之后并行调度的机会变多，恢复粒度变细，日志里也能看清每一步的耗时。反过来，把整段业务流程塞进一个巨型节点，等于放弃了框架提供的全部结构性能力，只剩下一个带状态字典的函数调用。

## 常见坑清单

- [ ] 只装 `langgraph` 却直接 `from langgraph.checkpoint.memory import InMemorySaver`，缺 `langgraph-checkpoint`
- [ ] 传了 `checkpointer` 但 `config` 里没有 `thread_id`，运行时报缺少线程号
- [ ] 节点函数直接 `state["messages"].append(...)` 改入参，导致并行分支互相污染
- [ ] 以为 checkpoint 粒度是节点，实际是超步，恢复精度不如预期
- [ ] 在节点里创建数据库连接、线程池并塞进状态，落盘时序列化失败
- [ ] 用 `create_react_agent` 后仍手写整套工具循环，重复且难调
- [ ] 看到导入路径报错就照抄旧教程，忽略官方迁移说明
