# 控制流：条件边、循环与 Send

## 本章要解决的问题

画图很容易，画**不会卡死、不会走错路**的图很难。实际项目里最常见的三种翻车是：路由函数返回了一个不存在的节点名，运行时才报错；循环没有写终止条件，一路撞到递归上限；并行分支同时写一个字段，结果只剩一份。

这一章把控制流拆成四个工具讲透：`add_conditional_edges` 做分支路由、环边做循环、`Send` 做动态并行分发、`Command` 把「更新状态 + 跳转」合成一步。同时给出两类硬约束：路由目标必须已声明、循环必须有可观测的出口。读完你应该能把一个「检索—评估—重写」的循环画出来，并说清它凭什么会停。

## 核心概念与术语

| 术语 | 含义 | 关键约束 |
| --- | --- | --- |
| 条件边 | 由函数决定下一步走向的边 | 返回值必须是已注册的节点名 |
| 路由函数 | 读状态、返回目标节点名（或 `Send` 列表）的函数 | 必须纯、快、可预测 |
| 路由表 | 把路由函数的返回值映射到节点的字典 | 可省略，省略时返回值直接当节点名 |
| 环边 | 指向上游节点的边，构成循环 | 必须有终止条件 |
| `Send` | 动态分发：按参数生成多个并行任务，各自指定目标节点 | 目标节点的写字段需要 reducer |
| `Command` | 节点返回 `Command(goto=..., update=...)`，一步完成跳转与更新 | 用了它就不必再为源节点连固定边 |
| `recursion_limit` | 单次执行允许的最大超步数 | 是保护而非逻辑，靠它停说明逻辑有 bug |
| 超步 | 一轮并行调度单位 | 循环每圈至少消耗一个超步 |

## 条件边：把分支写成数据

条件边的写法是「源节点 + 路由函数 + 可选的映射表」。路由函数收到当前状态，返回下一个节点的名字。相比在节点内部 `if/else` 里调用下一步，条件边的价值在于**分支结构对运行时可见**：可以画图、可以做静态检查、可以在流式输出里看到走了哪条路。

```python
from langgraph.graph import StateGraph, START, END

def route_after_check(state: dict) -> str:
    if state.get("score", 0) >= 0.8:
        return "done"
    if state.get("attempts", 0) >= 3:
        return "give_up"
    return "revise"

builder.add_conditional_edges(
    "check",
    route_after_check,
    {"done": "final", "give_up": END, "revise": "revise"},
)
```

映射表不是装饰。它的两个作用是：把「路由函数里的字符串」和「节点名」解耦，改名时只改一处；以及在编译期暴露目标集合，让「返回了不存在的节点」这类错误尽早暴露。省略映射表时，返回值会被直接当作节点名使用，方便但与节点名强耦合。

路由函数要遵守四条纪律：只读状态、不做 I/O、不抛未捕获异常、对未知输入有兜底返回值。最后一条尤其重要——模型输出的枚举值经常带空格、大小写不一致或多一个后缀，路由函数里一个 `state["decision"]` 直接当返回值用，就会得到 `Node 'Approve ' not found` 这种报错。

## 循环：环边 + 出口

LangGraph 表达循环的方式很朴素：把边指向已经执行过的节点。没有专门的 `while` 节点，也不需要。真正需要设计的是**出口**。

```python
def should_continue(state: dict) -> str:
    if state["score"] >= 0.8:
        return "final"
    if state["attempts"] >= state["max_attempts"]:
        return "final"      # 兜底出口：即使不理想也必须停
    return "revise"

builder.add_node("revise", revise)
builder.add_node("check", check)
builder.add_edge("revise", "check")
builder.add_conditional_edges("check", should_continue, {"final": "final", "revise": "revise"})
```

三个设计要点：

1. **计数器放在状态里**，不要靠「消息条数」推断轮次。消息可能被压缩、被裁剪，计数会被动变。
2. **兜底出口必须存在**。理想情况下质量达标就退出，但工程上一定要有「试够次数就带着当前最好结果退出」的分支，否则一次模型抽风就把整个请求拖到超时。
3. **`recursion_limit` 只是保险丝**。它按超步计数，命中后抛错。如果你的流程正常运行时经常接近上限，说明循环设计有问题，调大参数只是延后爆炸。

## Send：动态并行 fan-out

固定边只能连固定数量。当「要处理几个子任务」取决于运行时数据时，用 `Send`。路由函数可以返回一组 `Send`，每个 `Send` 指定目标节点与**该分支看到的私有输入**：

```python
from langgraph.types import Send

def fan_out(state: dict):
    return [Send("worker", {"item": item, "question": state["question"]})
            for item in state["items"]]

builder.add_conditional_edges("plan", fan_out, ["worker"])
```

关键点是：`Send` 传的是**该分支的输入**，不是完整状态的引用。worker 节点拿到的是一份以该输入构造的状态视图，所以各分支天然隔离，不会互相踩。分支结果要回到主状态，就要靠目标节点写入带 reducer 的字段——这是 `Send` 与 reducer 必须成对出现的原因：

```python
def worker(state: dict) -> dict:
    return {"results": [process(state["item"])]}   # results 必须是追加 reducer
```

`Send` 的常见用途是 map-reduce：一次把 N 个文档切片分发出去，每个 worker 独立总结，最后汇合节点读 `results` 做归并。注意 N 很大时要自己控并发与限流，框架负责调度，不负责帮你省钱。

## Command：更新与跳转合成一步

有些节点在执行中才知道下一步去哪，且同时要更新状态。`Command` 把这两件事合成一次返回：

```python
from langgraph.types import Command

def triage(state: dict) -> Command:
    if state["intent"] == "refund":
        return Command(goto="refund_flow", update={"priority": "high"})
    return Command(goto="faq", update={"priority": "low"})
```

与「返回 dict + 加条件边」相比，`Command` 的优点是**决策与跳转写在同一处**，读代码时不用在两处对照；缺点是把控制流从「图的结构」搬回了「节点内部」，图上看不出分支，静态检查也弱一些。实践中的取舍是：分支少且与业务语义强绑定时用 `Command`（比如多智能体 handoff），分支多、需要可视化时用条件边。

如果使用了 `Command`，源节点通常不再需要连固定边，否则会同时存在两条出边产生竞争。这一点在文档里容易漏看，出错时表现为「节点执行了两次」或「走到了预期外的分支」。

## 循环里最容易被忽略的成本

写出一个能停的循环只是及格线，真正决定体验的是**每一圈做了什么**。循环体里如果每一轮都把全部历史消息重新喂给模型，输入 token 会随轮次线性增长，成本和延迟都是平方级的体感；如果每轮都重新检索一遍相同文档，纯属浪费。

两条实用优化。第一，**只让必要的字段参与循环**：把「历史全量对话」与「本轮待修正的草稿」分开，重写节点只读草稿与评估意见，不读完整历史。第二，**给循环体加短路条件**：如果这一轮的输入与上一轮完全相同（例如检索结果没变、草稿没改），就直接走兜底出口，避免同一份输入反复消耗模型调用。

还有一条与调度相关：循环每转一圈至少消耗一个超步，而每个超步结束都会写一次 checkpoint。转二十圈的流程就意味着二十份快照。这本身不致命，但如果状态里塞着几万字文档，存储与恢复时间会迅速失控。把大文本移出状态、在快照里只留引用，是让循环跑得久的前提。

换个角度看，循环的设计质量可以直接用一个问题检验：随便取一个中途失败的时刻，你能说清下一轮会读哪些字段、会不会重复做副作用、要多久才能收敛吗？答不上来就说明控制流还没写清楚，而不是模型不够聪明。把这三个问题写进设计文档，评审时逐条过一遍，比事后在日志里找线索便宜得多。

## 四类常见错误的症状对照

| 错误 | 典型报错/症状 | 根因 | 修法 |
| --- | --- | --- | --- |
| 路由目标未声明 | `Node 'xxx' not found` | 返回了拼错或未注册的名字 | 用映射表 + 兜底分支 |
| 循环无出口 | 递归上限报错、请求超时 | 终止条件只在理想路径成立 | 加计数器与兜底出口 |
| 并行写字段丢数据 | 结果条数少于分支数 | 字段没有追加 reducer | 加 `Annotated[list, reducer]` |
| 用了 `Command` 又连固定边 | 节点重复执行、分支错乱 | 同时声明了动态与固定跳转 | 二选一 |

## 常见坑清单

- [ ] 路由函数直接返回模型原始输出，没做归一化与白名单校验
- [ ] 循环只判断「质量达标」，没有最大轮次兜底
- [ ] 把 `recursion_limit` 当循环终止手段，逻辑上永远不收敛
- [ ] `Send` 分发后，接收字段忘了加 reducer，只剩最后一条
- [ ] `Send` 一次分发上千个任务，没有限流与超时控制
- [ ] 节点返回 `Command` 的同时还保留了固定出边
- [ ] 路由函数里做数据库查询或调用模型，拖慢每一步调度
- [ ] 在条件边里修改状态（只能读，不能写）
