# 人在回路：interrupt、审批与恢复

## 本章要解决的问题

全自动的智能体在演示里很酷，在生产里很危险。发邮件、下单、删数据、改配置，这些动作一旦错了就不可逆，所以业务方一定会要求「执行前让我确认一下」。问题在于：确认可能发生在几秒后，也可能发生在第二天；确认的人可能换了一台设备；而中间这段时间，进程不能一直挂着。

LangGraph 的答案是 `interrupt`：在节点内部主动挂起，把当前状态存进 checkpoint，然后把控制权交回调用方；等外部决定后，用 `Command(resume=value)` 恢复，挂起点会拿到这个值并继续往下跑。这一章讲清三件事：挂起的机制与前提、审批型与编辑型两种用法、以及 Web 服务里「两次 HTTP 请求对应一次挂起」的映射方式。

## 核心概念与术语

| 术语 | 含义 | 要点 |
| --- | --- | --- |
| `interrupt` | 在节点内部调用，挂起当前执行并向外抛出待决值 | 必须在节点函数内调用 |
| 待决值（payload） | 传给外部的数据，通常是「要审批什么」 | 应可序列化、可展示 |
| `resume` | 恢复时传入的值，成为 `interrupt` 的返回值 | 通常经 `Command(resume=...)` 传入 |
| 挂起 | 执行暂停、状态落盘、调用方拿到控制权 | 依赖 checkpointer |
| 审批型 HITL | 让人决定「继续 / 拒绝 / 修改」 | 高风险动作前的闸门 |
| 编辑型 HITL | 让人直接改状态再继续 | 内容创作、参数修正 |
| 重放 | 恢复时从挂起节点开头重新执行 | 副作用必须幂等 |
| 多中断 | 一次执行里出现多个 `interrupt` 调用 | 按顺序逐个恢复 |

## 挂起的机制

`interrupt` 的行为可以概括为「抛出一个带载荷的信号，运行时接住它，把状态存盘，然后把执行交还给你」。它的调用位置很关键：**只能在节点函数内部调用**，不能在节点外的辅助函数里随便调，也不能在路由函数里调。

挂起发生后，调用方能看到两样东西：一是最终返回结果里包含中断信息（通常是一个包含待决值的结构），二是通过 `get_state` 查看时，`next` 指向的正是被挂起的那个节点。恢复时，执行会**从该节点的开头重新进入**，而不是从 `interrupt` 那一行继续。这一点决定了副作用规则：

- `interrupt` 之前不能有不可重入的副作用（否则恢复时又执行一遍）。
- `interrupt` 之后也不要假设自己只执行过一次。
- 需要「只做一次」的动作，用状态字段打标记，或者放到挂起之后的独立节点里。

```python
from langgraph.types import interrupt, Command

def approve_send(state: dict) -> dict:
    # 先做纯计算，再挂起；不要在挂起前发消息
    draft = state["draft"]
    decision = interrupt({"action": "send_email", "draft": draft})

    if decision.get("approved"):
        return {"status": "sent", "final": decision.get("text", draft)}
    return {"status": "rejected", "reason": decision.get("reason", "")}
```

注意 `interrupt` 的返回值就是恢复时传进来的值，所以恢复数据用 `Command` 传即可：

```python
from langgraph.types import Command

config = {"configurable": {"thread_id": "mail-20261029-01"}}

# 第一次执行：跑到 approve_send 里挂起
first = graph.invoke({"draft": "季度报告摘要"}, config)

# 人工确认后恢复
second = graph.invoke(Command(resume={"approved": True, "text": "季度报告摘要（已审）"}), config)
print(second["status"])
```

两个硬前提：编译时必须传 checkpointer；两次调用必须用同一个 `thread_id`。缺任何一个都会得到「找不到可恢复的状态」之类的报错，而不是友好的提示。

## 审批型与编辑型

两种用法的结构相同，差别在于恢复值怎么被消费。

| 用法 | 挂起时给外部什么 | 恢复时外部给什么 | 典型场景 |
| --- | --- | --- | --- |
| 审批型 | 动作名、参数、风险说明 | `approved` 布尔 + 可选拒绝原因 | 发邮件、下单、写生产库 |
| 编辑型 | 当前草稿、可编辑字段说明 | 修改后的完整内容或字段补丁 | 文案生成、SQL 生成、配置变更 |
| 选择型 | 若干候选项 | 选中的选项标识 | 多方案二选一 |
| 澄清型 | 缺失参数与追问 | 用户补充的值 | 表单补全、意图不明时追问 |

**审批型**的关键是把决策点做窄：只让人回答「发不发」，不要在审批页面里再塞一堆可编辑字段，否则审批人会顺手改内容，责任边界就模糊了。拒绝时把原因写回状态，供后续节点调整策略，而不是直接 `END` 掉整个流程——很多时候拒绝只是要求换一种写法重试。

**编辑型**的关键是校验。人改过的内容回到图里就是新的输入，节点必须当它是**不可信数据**：长度、格式、枚举值都要重新校验，越权字段要丢弃。把人工编辑当成「绝对正确」是常见的思维漏洞，尤其在多人协作的系统里。

```python
def edit_then_send(state: dict) -> dict:
    edited = interrupt({"draft": state["draft"], "editable": ["subject", "body"]})
    payload = sanitize(edited)                     # 重新校验，别信任外部输入
    return {"draft": payload["body"], "status": "ready"}

def send(state: dict) -> dict:
    if state.get("status") != "ready":
        return {}
    deliver(state["draft"])                        # 真正有副作用的动作放独立节点
    return {"status": "sent"}
```

把「有副作用的动作」放在挂起之后的独立节点，是整个模式里最重要的工程习惯。这样即使恢复逻辑出错、重复恢复、或者人在两端同时点确认，最坏结果也只是状态错，而不是邮件发两遍。

## Web 场景：两次请求对应一次挂起

服务端集成时，最自然的映射是「一次挂起 = 一次请求结束」。

第一次请求（POST /chat）：服务端生成或取回 `thread_id`，调用 `graph.invoke(...)`。执行到 `interrupt` 时挂起，函数返回一个待确认结构。服务端把它转成前端需要的 JSON（动作、参数、可编辑字段），HTTP 响应返回 200 + `status: "pending_approval"`。

第二次请求（POST /chat/approve）：服务端从鉴权信息里取出用户身份，校验这个 `thread_id` 是否属于该用户，然后调用 `graph.invoke(Command(resume=...), config)`。执行从挂起点继续，可能再次挂起（多级审批），也可能走到 `END`。

| 环节 | 第一次请求 | 第二次请求 |
| --- | --- | --- |
| 输入 | 用户消息 | 审批决定或编辑内容 |
| 服务端动作 | 新建/复用线程后 `invoke` | 同一线程 `invoke(Command(resume=...))` |
| 结束条件 | 遇到 `interrupt` 或 `END` | 再次 `interrupt` 或 `END` |
| 响应 | 待决项 + `thread_id` | 新待决项或最终结果 |
| 校验重点 | 输入合法性 | 线程归属、幂等键 |

几个实践细节。**幂等键**：前端重复提交审批（网络重试、用户连点）会触发重复恢复，服务端应记录「该 `thread_id` 的该次中断已处理」。**超时**：挂起可以停留很久，但业务上往往有时间窗，过期后应主动把线程标记为废弃，而不是等用户某天点开。**状态展示**：`get_state` 能拿到当前状态与 `next`，前端据此判断该显示「等待审批」还是「已结束」，不必自己维护一份状态机。

## 恢复时机与幂等副作用的判断依据

挂起之后不一定要立刻恢复，时机本身也是设计决策：时效敏感的动作（发通知、锁库存）收到审批就恢复，把停留时间压到最短；批量、低风险的修改可攒成一次批量审批，减少打扰。状态里记下待决项的生成时间与有效期，恢复节点先判断是否超时，超时就走「重新生成草稿」的分支，而不是继续执行过期内容。

幂等的判断依据要落在可比较的键上：用 `thread_id` 加中断序号（每挂起一次递增）标识一次决策，恢复前查已处理表，命中就返回上次结果。不要用「时间相近」或「参数相同」判定重复——前者在重试下不可靠，后者会把两次刻意相同的审批误判成同一件事。

## 什么时候不需要 interrupt

不是所有「需要人参与」都该用挂起。如果人只是在流程结束后做验收，那属于业务系统的事，让图正常走到 `END`，把结果写进待办表即可；用 `interrupt` 把线程停在半路，反而要额外维护一堆永不恢复的会话。

同样地，如果确认动作可以在毫秒级完成（比如前端弹窗、内部工具的一次点击），一个同步调用就够了，没必要引入持久化与恢复协议。判断标准是**跨越的时间与进程边界**：确认可能跨请求、跨设备、跨天，才值得用挂起；否则用普通的同步交互更简单，也更容易测试。

反过来，凡是「错了不可逆」且「无法用自动化规则兜住」的动作，都应该走挂起。宁可让流程慢一点，也不要让一个模型幻觉直接写进生产库。这条取舍比任何框架选型都重要。落到评审上，可以要求每个挂起点都写清三件事：谁审批、超时多久、被拒绝后怎么办。三件事答不全，就说明这个挂起点只是「看起来安全」。

## 常见坑清单

- [ ] 编译时没传 checkpointer，`interrupt` 直接报错或无法恢复
- [ ] 恢复时换了 `thread_id`，挂起的执行找不到，实际起了新会话
- [ ] 在 `interrupt` 之前发通知、扣库存，恢复时重复执行
- [ ] 把 `interrupt` 放在路由函数或节点外的工具函数里
- [ ] 恢复值不校验，人工编辑的内容带着非法字段进入下游
- [ ] 同一中断被重复恢复，产生两次副作用
- [ ] 前端自己维护待办状态，与服务端 `get_state` 不一致
- [ ] 挂起线程无超时清理，库里堆着几万条永不恢复的会话
- [ ] 把「拒绝」直接当异常抛出，丢掉拒绝原因
