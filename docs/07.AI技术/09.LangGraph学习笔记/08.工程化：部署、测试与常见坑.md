# 工程化：部署、测试与常见坑

## 本章要解决的问题

前七章讲的是「怎么把图跑起来」，这一章讲「怎么让它别在凌晨三点挂掉」。原型阶段大家都在本地 `invoke`，一旦上线就会遇到完全不同的四类问题：并发下状态互相污染、重启后会话全丢、模型偶发超时把整个请求拖死、以及根本没人写测试——因为「模型输出不确定，测不了」。

这一章按上线顺序展开：先选部署形态，再配 `langgraph.json`，然后建立三层测试，接着处理性能与成本，最后给一份可以逐条打勾的上线清单。读完你应该能把一个本地跑通的图，变成一个有并发隔离、有检查点、有测试、有超时与重试策略的服务。

## 核心概念与术语

| 术语 | 含义 | 工程关注点 |
| --- | --- | --- |
| 部署形态 | 服务怎么跑：裸包 FastAPI、LangGraph Server 等 | 决定并发、线程、流式能力 |
| `langgraph.json` | 描述「有哪些图、依赖怎么装」的配置文件 | 字段随版本演进，以官方文档为准 |
| `langgraph dev` | 本地起开发服务，便于联调 | 端口与参数以官方文档为准 |
| 编译产物 | `CompiledStateGraph`，可被任意 Python 服务调用 | 关注线程安全与生命周期 |
| 节点单测 | 单独测试节点函数的输入输出 | 最快，覆盖纯逻辑 |
| 图级集成测试 | 用假模型跑通整张图 | 覆盖路由与状态合并 |
| 重放测试 | 用固定快照回放中断/恢复流程 | 覆盖 HITL 与恢复逻辑 |
| `recursion_limit` | 单次执行的最大超步数 | 防止死循环拖垮服务 |
| 幂等键 | 保证重复请求不产生重复副作用 | 恢复与重试的前提 |
| 密钥管理 | 模型 key、数据库连接串的存放方式 | 禁止进代码与日志 |

## 部署形态怎么选

| 形态 | 组成 | 优点 | 代价 | 适合 |
| --- | --- | --- | --- | --- |
| FastAPI 包一层 | 自己的 Web 框架 + `CompiledStateGraph` | 完全可控、与现有服务同构 | 线程、流式、后台任务都要自己写 | 已有服务、需深度定制 |
| LangGraph Server | `langgraph.json` + 官方运行时 | 内建线程管理、流式、任务 | 引入额外组件、部署方式受限 | 快速上线、标准化接口 |
| 容器化自托管 | 镜像 + 自己的编排 | 环境一致、易扩缩 | 需维护镜像与依赖 | 中大型团队 |
| 无服务形态（本地脚本） | 定时任务或 CLI | 简单 | 无并发、无状态共享 | 批处理、离线任务 |

一个务实的判断顺序是：先问「是否多副本」，多副本就必须有共享 checkpointer；再问「是否需要标准化的线程/流式接口」，需要就上 Server，不需要就用 FastAPI 包一层；最后问「是否有合规限制」，有限制就自托管。

用 FastAPI 包一层的骨架大致如下。注意两点：用异步接口配合 `astream` / `ainvoke`，避免同步调用阻塞事件循环；把 `thread_id` 从鉴权信息派生，不要直接信任前端。

```python
from fastapi import FastAPI, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

app = FastAPI()

class ChatIn(BaseModel):
    session_id: str
    message: str

@app.post("/chat")
async def chat(body: ChatIn, user_id: str = "demo"):
    thread_id = f"{user_id}:{body.session_id}"      # 服务端派生，防越权
    config = {"configurable": {"thread_id": thread_id}, "recursion_limit": 30}

    async def gen():
        async for chunk in graph.astream(
            {"messages": [{"role": "user", "content": body.message}]},
            config,
            stream_mode="messages",
        ):
            msg, meta = chunk
            text = getattr(msg, "content", "")
            if text:
                yield text

    return StreamingResponse(gen(), media_type="text/plain")
```

生产上还要补：请求级超时、模型调用重试、异常统一包装、以及把 `thread_id` 与业务单号一起写进日志。

## langgraph.json 的关键字段

部署到官方运行时，靠一个 JSON 描述「图在哪、依赖怎么装」：

```json
{
  "graphs": {
    "agent": "./src/agent.py:graph"
  },
  "dependencies": ["."],
  "env": ".env"
}
```

| 字段 | 作用 | 注意 |
| --- | --- | --- |
| `graphs` | 图名到「模块路径:变量名」的映射 | 变量必须指向**已编译**的图 |
| `dependencies` | 依赖声明（本地包或包名列表） | 与 lock 文件保持一致 |
| `env` | 环境变量文件 | 不要提交含密钥的文件 |
| 运行时相关字段 | Python/Node 版本、自定义构建等 | 字段名随版本变化，以官方文档为准 |

常见错误是 `graphs` 指向了一个未编译的 `StateGraph` 构造器，启动时报「不是可执行图」；或者路径写成了相对仓库根之外的位置。另一个高频问题是依赖没装全——本地能跑是因为 `site-packages` 里恰好有，镜像里就缺。

本地联调通常用 `langgraph dev` 起服务，再用官方提供的客户端或 HTTP 接口调用。命令参数与端口在不同版本有过调整，**以官方文档为准**。

## 三层测试

**第一层：节点单测。** 节点本质是「状态进、增量出」的纯函数（理想情况下），直接调用即可断言：

```python
def test_supervisor_ends_when_done():
    out = supervisor({"done": True, "plan": None})
    assert out.goto == END
```

这一层覆盖率应该最高，因为它跑得最快、最稳定，且能锁住所有分支判断。

**第二层：图级集成测试。** 用假模型（固定返回的 stub）替换真实调用，跑通整张图，断言最终状态与经过的节点。关键是**固定输入 + 固定假模型 = 确定输出**，这样测试才可断言。不要在图级测试里调真实模型：一次几毛钱、几十秒，跑几十个用例就没人愿意跑了。

**第三层：重放与恢复测试。** 针对 `interrupt` 流程：先跑到挂起，断言待决内容；再用 `Command(resume=...)` 恢复，断言后续状态；最后断言「重复恢复」不会产生第二次副作用。有 checkpointer 时，还可以用 `update_state` 构造特定状态，测试那些难以自然触发的分支。

| 层级 | 依赖 | 耗时 | 覆盖什么 | 建议比例 |
| --- | --- | --- | --- | --- |
| 节点单测 | 无 | 毫秒 | 分支、边界、格式转换 | 最多 |
| 图级集成 | 假模型 | 秒 | 路由、状态合并、终止 | 中等 |
| 重放/恢复 | 内存 saver | 秒 | HITL、幂等、时间旅行 | 关键路径 |
| 端到端 | 真模型 | 分钟 | 提示词质量、真实工具 | 少量、手动 |

## 性能与成本

**并行。** 能并行的分支就并行：`Send` 分发或同超步多节点，能把「三次检索串行 1.5 秒」压到「并行 0.5 秒」。但要注意下游汇总节点必须等所有分支完成，木桶效应明显，别把一个慢分支和三个快分支并行。

**减少无用节点。** 每多一个节点就多一次状态合并、多一份快照、多一段可观测开销。用小模型能做的判断（分类、格式化）不要用大模型；能规则判断的不要调模型。

**checkpoint 写放大。** 快照是整份状态落盘，不是增量。状态里少放长文本，能显著降低写放大与恢复时间。长循环还要配清理策略。

**`recursion_limit` 调参。** 它按超步计数，默认值通常偏保守。正确姿势是先算出「正常路径最多需要多少超步」，再留一定余量，而不是出一次错就翻倍。频繁触顶说明循环设计有问题。

**超时与重试。** 模型调用要设超时，工具调用要设超时，整个请求也要设总超时。重试只对幂等操作开启，并且要区分「可重试错误」（限流、超时）与「不可重试错误」（参数非法、鉴权失败）。

## 上线前检查清单

- [ ] 状态字段全部可序列化，没有连接、锁、客户端对象
- [ ] checkpointer 已落库（多副本用共享存储），并做了建表初始化
- [ ] `thread_id` 由服务端从身份派生，含用户/租户前缀
- [ ] 所有循环都有计数器与兜底出口，`recursion_limit` 有合理值
- [ ] 有副作用的动作幂等，或在恢复时能短路跳过
- [ ] 模型与工具调用都有超时，重试策略区分错误类型
- [ ] 密钥走环境变量或密钥服务，不进代码、不进日志
- [ ] 关键节点有结构化日志，字段含 `thread_id` 与请求 id
- [ ] 节点单测、图级集成、HITL 重放三类测试都存在且能跑
- [ ] 追踪已接入并验证 trace 可查，采样率与留存期已设定
- [ ] 失败时的降级行为已定义（返回兜底话术还是报错）
- [ ] 有回滚方案：图版本与提示词版本可回退

## 常见坑清单

- [ ] 生产用 `InMemorySaver`，重启后全部会话丢失
- [ ] 只用 `user_id` 当 `thread_id`，同一用户多会话互相污染
- [ ] 同步 `invoke` 塞进异步框架，事件循环被阻塞
- [ ] `graphs` 指向未编译对象，服务启动失败
- [ ] 依赖缺失只在本机能跑，镜像里 import 报错
- [ ] 图级测试调真实模型，慢且不稳定，最后被跳过
- [ ] 重试没有幂等保护，一次超时产生两笔业务
- [ ] 日志里打出完整 prompt，泄露用户与内部信息
- [ ] 没有总超时，一个卡死的工具调用占满连接池
