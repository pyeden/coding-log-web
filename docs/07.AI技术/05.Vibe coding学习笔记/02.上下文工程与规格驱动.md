# 上下文工程与规格驱动

## 本章目标

同一个模型，为什么在你的仓库里表现像两个人？多数时候差别不在提示词措辞，而在**它看到了什么、按什么顺序看到、哪些信息被挤掉了**。这一章讲三件事：怎样给仓库画一张模型能用的地图；怎样用规则文件把隐性约定变成显性约束；怎样用「规格先行」把「写代码」变成「实现一个已经定义清楚的契约」。最后给出一套上下文预算的分配方法，避免把窗口浪费在无关文件上。

## 核心概念与术语

| 术语 | 含义 | 常见误区 |
| --- | --- | --- |
| 仓库地图 | 用一页文字描述目录职责、入口、关键模块 | 以为模型能自己「看懂」仓库 |
| 规则文件 | 放在仓库里的约定：技术栈、命令、禁止项 | 写成愿望清单，没有可执行约束 |
| 任务卡 | 一次改动的最小单元：目标、范围、验收、禁止 | 只写目标，不写范围，diff 失控 |
| 规格（spec） | 行为契约：输入、输出、错误、边界 | 把实现方案当规格 |
| 验收标准 | 可判定的通过条件 | 写「体验流畅」这种不可测描述 |
| 上下文预算 | 一次会话可用的信息容量 | 把所有文件都塞进去 |
| 检索（retrieval） | 按需取回相关片段 | 一次取回几十个文件，噪声淹没信号 |
| 压缩（compaction） | 对话过长时对历史做摘要 | 压缩后丢失关键约束 |

## 为什么「上下文」比「提示词」更重要

提示词决定模型怎么回答，上下文决定它基于什么回答。一个措辞普通但信息完整的请求，产出通常好于一个措辞精巧但缺关键文件的请求。原因很直接：模型无法访问你的仓库、你的约定、你的历史决策，它只能从你给的材料里推断。材料缺失时，它用训练数据里的「平均项目」填补，于是出现「代码能跑但不是你的代码」。

上下文工程因此不是「写更长的提示词」，而是**决定哪些信息进入窗口、以什么结构进入、什么时候该换一个干净的窗口**。它包含四个动作：选材（哪些文件相关）、组织（地图、规则、任务卡）、压缩（长会话摘要）、隔离（按任务切会话）。

这四件事都不依赖模型升级，却直接决定同样的模型能否稳定产出。把它们做成仓库里的静态资产后，换工具、换模型都不必从头再教一遍，这是上下文工程相对于「调提示词」的最大优势。

## 仓库地图：让模型先学会找路

大仓库里最高频的失败是「改错文件」：模型打开了一个同名但不同层的模块，改完发现线上没变化。解决办法不是更强的模型，而是一张地图。地图不需要详尽，只要回答四个问题：这个仓库有哪几层；每层的职责边界；关键入口在哪；改某类需求通常要动哪些目录。

```markdown
# 仓库地图（放在 AGENTS.md 顶部）
- apps/web/      前端应用，路由在 src/router，接口封装在 src/api
- apps/api/      后端服务，routes/ 只做参数校验与编排，业务逻辑在 services/
- packages/shared/ 前后端共享类型，改这里要同时跑两端测试
- migrations/    数据库迁移，只增不改
- scripts/       运维脚本，禁止在业务代码中引用

## 常见需求的落点
- 新增接口：apps/api/routes/ + apps/api/services/ + 对应测试
- 新增页面：apps/web/src/views/ + 路由表 + api 封装
- 改共享类型：packages/shared/ 后跑 pnpm -r test
```

这张地图的价值在于「缩小搜索空间」。模型读完它，就不会去 `apps/web` 里找数据库迁移。地图也会随仓库演进而过期，所以最好由 CI 或例行检查提醒：目录新增时同步更新地图，过期地图比没有地图更危险。

## 规则文件：把隐性约定变成显性约束

规则文件（不同工具叫法不同，常见如 `AGENTS.md`、编辑器自带的规则目录）是上下文工程里投入产出比最高的一项。它把「老员工才知道」的东西写下来：用什么包管理器、测试怎么跑、哪类文件不许动、错误怎么抛、日志怎么打。

写法上有三条经验。第一，**只写可执行的约束**：「代码要优雅」没用，「接口层禁止写 SQL」有用。第二，**给出命令而不是描述**：「提交前跑 `pnpm typecheck && pnpm test`」比「注意类型安全」有效。第三，**写清禁止项**：模型很擅长「顺手优化」，明确列出不许改的目录能挡掉大部分越界。

```markdown
# AGENTS.md 片段
## 必须
- 新增依赖前先提 issue，禁止直接改 package.json
- 所有对外接口必须有错误码，复用 src/errors/codes.ts
- 改动 services/ 后必须运行 pnpm test <module>

## 禁止
- 禁止修改 migrations/ 下已存在的文件
- 禁止在日志中输出用户手机号、身份证、token
- 禁止使用 any 绕过类型检查；确需使用需注释说明
```

规则文件不是越长越好。超过一两百行后，模型会开始忽略中段内容。更稳的结构是「根目录放通用规则，子目录放局部规则」，让工具按当前路径加载，而不是把所有约定堆在一个文件里。

## 规格驱动：先定义「对」，再让模型写

「先写规格再写码」不是形式主义，它解决的是**验收标准缺失**。没有规格时，模型只能猜你要什么，你只能凭感觉判断它猜对没有，来回几轮后双方都疲惫。有了规格，实现变成「满足契约」，评审变成「对照契约」。

一份够用的规格包含五块：背景（为什么要做）、行为（输入到输出的映射）、错误（失败时返回什么）、边界（空值、超长、并发、权限）、非目标（这次不做什么）。最后一项最容易被忽略，却最能防止范围蔓延。

```markdown
## 规格：优惠券核销
### 背景
下单时使用优惠券，需在支付前锁定，支付成功或超时后释放。

### 行为
- 输入：couponId、orderId、userId
- 成功：返回锁定结果与抵扣金额
- 幂等：同一 orderId 重复调用返回同一结果

### 错误
- 券不存在 / 已使用 / 已过期 / 不属于该用户 → 对应错误码
- 并发锁定时，后到请求返回「锁定中」，不报系统错误

### 边界
- 抵扣金额不得为负，不得超过订单金额
- 锁定超时时间可配置，默认值以配置中心为准

### 非目标
- 本次不实现退款返还，仅记录待返还流水
```

规格写完后，任务卡就可以从规格里「裁剪」出来：只取这次要做的切片，附上相关文件与验收命令。

## 任务卡：控制范围的开关

任务卡是规格与实现之间的桥。它比规格短，比一句话需求长，核心作用是**限定边界**。一张合格的任务卡包含四行：目标、范围、验收、禁止。范围要具体到目录或文件，验收要具体到命令，禁止要具体到「不许做什么」。

```markdown
## 任务卡：优惠券核销接口
- 目标：实现 POST /coupons/redeem，按规格完成锁定与幂等
- 范围：apps/api/routes/coupons.ts、services/coupon.ts、对应测试
- 验收：pnpm test coupon 全绿；并发用例通过；错误码与 codes.ts 一致
- 禁止：不改数据库 schema；不新增依赖；不改动支付模块
```

任务卡还有一个隐性作用：它是**会话切分点**。一张卡对应一个会话，做完就结束。这样上下文不会被上一个任务的残留污染，压缩也更容易做。

## 规格与任务卡的分工

两者容易混为一谈，其实职责不同。规格是**长期契约**，回答「这个能力应该怎样表现」，一张规格可以对应多次迭代；任务卡是**一次性切片**，回答「这一轮改哪里、改到什么程度」。规格写得粗，任务卡就会被迫承担定义行为的责任，结果是一次改动反复返工；规格写得细，任务卡可以很薄，只保留范围与验收。

一个可操作的判断是：如果这次改动会改变对外行为（接口、错误码、数据结构），先改规格再写码；如果只是内部重构、性能优化、补测试，规格不动，直接写任务卡。把这条规则写进团队约定，能省掉大量「边写边改需求」的争论。

规格评审也有成本，所以要控制粒度：一张规格只描述一个能力，不超过两页。超过两页通常说明它包含多个能力，应该拆开。拆开的好处是每个切片都能独立验收，模型也更容易在一次会话里做完。

## 上下文预算怎么分配

上下文窗口是有限资源，需要像内存一样分配。一个可用的经验比例是：规则与地图占一成，任务相关代码占五成，测试与错误信息占两成，对话历史占两成。超过这个比例，通常意味着选材有问题——要么塞了不相关文件，要么会话拖太久。

| 内容 | 建议占比 | 超支时的处理 |
| --- | --- | --- |
| 规则文件 + 仓库地图 | 10% | 拆分规则，子目录局部加载 |
| 相关源码 | 50% | 只保留调用链上的文件，其余用摘要 |
| 测试与报错 | 20% | 贴关键堆栈，不贴全量日志 |
| 对话历史 | 20% | 到阈值就摘要并开新会话 |

压缩时要保住三类信息：约束（不许做什么）、决策（为什么选这个方案）、未完成项（下一步做什么）。可以丢的是探索过程：试过哪些错路、看过哪些无关文件。一个实用做法是让模型自己输出「交接摘要」，你审一遍再粘到新会话开头。

## 上下文中毒与噪声

有两类信息会主动伤害产出。第一类是**过期文档**：README 里写着旧的启动命令，模型照做后报错，然后开始自行编造替代命令。第二类是**矛盾示例**：仓库里同时存在两种错误处理风格，模型随机选一种，评审时又要返工。

处理办法是「单一事实源」：命令只在规则文件里写一次；风格以一处参考实现为准，并在规则里指明「参考 src/services/order.ts 的写法」。模型很擅长模仿，给它一个好样例，胜过给它十条抽象原则。

还有一个低成本技巧：在任务卡里附上「反例」。明确写一句「不要像 legacy/order_old.ts 那样在 controller 里拼 SQL」，比只给正例更能防止模型沿用过时写法。正例定方向，反例划红线，两者一起才构成完整的上下文。维护成本上，反例只需要保留一条，多了反而变成新的噪声；挑选标准是「最近一次真实事故里的错误写法」，既有说服力，也不容易过期。每隔一个季度复查一次规则与反例，把已经修掉的坑删掉，保持材料短小。

## 风险与常见坑

- [ ] 规则文件写成价值观，没有可执行约束
- [ ] 仓库地图过期，指向已删除的目录
- [ ] 任务卡只写目标，范围留空，diff 蔓延到无关模块
- [ ] 规格里混入实现方案，锁死了模型的合理选择
- [ ] 把整个仓库塞进上下文，关键信息被噪声淹没
- [ ] 长会话不做摘要，早期约束被逐渐遗忘
- [ ] 同一会话连做多个任务，上下文互相污染
- [ ] 用「参考现有实现」代替具体路径，模型参考了错误的文件
