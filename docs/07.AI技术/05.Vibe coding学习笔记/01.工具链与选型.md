# 工具链与选型

## 本章目标

这一章解决一个具体问题：面对 IDE 补全、AI 编辑器、终端 agent、通用 agent 这几类形态，怎么按任务选，而不是按热度选。读完后你应该能画出自己团队的选型决策树，知道每种工具的上下文从哪里来、能执行什么动作、在哪些任务上会失控，以及为什么「同一家公司出的两个产品」也可能属于完全不同的形态。

## 核心概念与术语

| 术语 | 含义 | 选型时的意义 |
| --- | --- | --- |
| 交互形态 | 补全、对话、终端命令、常驻服务 | 决定它能否主动读文件、跑命令 |
| 上下文来源 | 光标附近、打开的文件、索引、显式引用 | 决定它「知道多少」，也决定噪声多少 |
| 可执行动作 | 只输出文本、可改多文件、可执行 shell | 决定风险等级与所需护栏 |
| 索引（index） | 对仓库做的向量或符号索引 | 大仓库检索质量的关键，需关注更新时机 |
| 工具调用 | 模型请求执行读文件、搜索、运行命令 | 能力上限的来源，也是权限风险的来源 |
| 沙箱 | 限制文件与网络访问的执行环境 | 决定「跑坏了」的影响范围 |
| 审批（approval） | 人对高风险动作逐次确认 | 把不可逆操作留在人手里 |
| 会话（session） | 一次连续的上下文容器 | 跨任务复用会污染上下文 |

## 先分清形态，再挑品牌

同样是「输入自然语言、输出代码」，不同形态的差别不在模型智商，而在**它能看见什么**和**它能做什么**。只能看见光标的工具，注定给不出跨模块的重构；能执行命令的工具，注定需要沙箱与审批；常驻服务型 agent 能接消息渠道与定时任务，也就意味着它的权限边界比一个编辑器窗口大得多。

一个实用的判断顺序是：先问这次任务需要多少上下文，再问需要多大执行权，最后才看品牌与价格。反过来做——先选工具再找用途——几乎一定会买贵或用错。

## 六类工具的能力边界

下表按「交互形态 / 上下文来源 / 可执行动作 / 适合任务 / 主要风险」对比。产品迭代很快，具体能力以官方文档为准，这里只描述形态层面的稳定差异。

| 工具 | 交互形态 | 上下文来源 | 可执行动作 | 适合任务 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| GitHub Copilot | IDE 内补全与对话 | 当前文件、打开的文件、仓库索引 | 建议代码、局部编辑 | 逐行编写、样板、测试骨架 | 片段脱离整体设计；跨文件重构弱 |
| Cursor | AI 原生编辑器 | 打开文件、代码库索引、显式 @ 引用 | 多文件编辑、终端命令（需确认） | 中等规模功能开发、边写边改 | 索引过期导致改错位置；易产生大 diff |
| Claude Code | 终端里的 agent | 仓库文件、命令输出、显式引用 | 读写文件、执行命令、跑测试 | 跨文件改造、排障、脚本化任务 | 命令副作用；长会话上下文漂移 |
| OpenAI Codex CLI | 终端里的 agent | 仓库文件、命令输出 | 读写文件、执行命令 | 本地任务委派、批量修改 | 与现有工具链集成需自行约束 |
| Aider | 终端配对编程 | 显式加入的文件、git 仓库 | 编辑文件并自动提交 | 小步重构、按 git 历史推进 | 依赖人工控制文件集合；大仓库需精选 |
| OpenClaw | 常驻 agent 网关 | 工作区文件、技能、记忆、渠道消息 | 工具调用、脚本、定时任务、多 agent | 长期自动化、跨系统协作 | 权限面大；需要审批与沙箱策略 |

**GitHub Copilot** 的强项是「不打断」。它把建议嵌在打字节奏里，适合已经想清楚要写什么、只需要少敲键盘的场景。它的弱点是缺乏全局设计视角：补全基于局部上下文，容易写出「语法正确但和项目约定不一致」的代码。把它当作高级模板引擎，收益稳定；指望它完成跨五个文件的重构，会失望。

**Cursor** 把对话、编辑与代码库索引放在同一个界面里，适合「边聊边改」的中等任务。它的关键变量是索引质量：索引没更新时，模型会基于旧代码给建议，表现为「改了但没生效」。使用时要养成习惯：改动后确认引用的是最新文件，跨模块任务显式把相关文件加入上下文，而不是指望索引自动找全。

**Claude Code** 是终端形态的 agent，能读文件、跑命令、看测试输出，因此特别适合排障与跨文件改造：它能自己发现「测试挂了是因为某个导出名改了」。代价是命令副作用——它会执行你没想到的命令，所以沙箱、审批与「先计划后动手」的约束不能省。它也更依赖仓库里的规则文件，因为没有规则时它会按通用最佳实践猜你的约定。

**OpenAI Codex CLI** 同样是终端 agent，定位接近「把任务丢给本地助手」。它与既有工具链的集成需要自己设计：怎么限定可改目录、怎么复用项目的测试命令、怎么在失败时停止而不是反复试错。适合已经有一套清晰工程规范的团队，规范越明确，产出越稳定。

**Aider** 的特点是「显式 + 可回滚」：你明确告诉它哪些文件参与，它改完自动提交，每一步都能用 git 回退。这让它非常适合小步重构与教学式协作——你能清楚看到每一轮改了什么。缺点是它不会主动帮你找全相关文件，大仓库里需要人工精选上下文，否则容易改漏。

**OpenClaw** 不是编辑器插件，而是常驻的 agent 网关：接聊天渠道、跑定时任务、调用工具、协调多个 agent。它适合「长期运行的自动化」而不是「写一个函数」：比如每天检查依赖更新、把 issue 分类、在多个仓库间同步文档。能力越大权限面越大，因此审批白名单、工作区隔离与审计日志是使用前提，而不是可选项。

## 选型决策树

把上面的差异压缩成可执行的判断流程：

```text
任务需要跨 3 个以上文件，或需要跑测试才能确认？
├─ 否 → 只是补几行 / 写样板？
│        ├─ 是 → IDE 补全（Copilot 类）
│        └─ 否 → 单文件内的对话式修改（编辑器内对话）
└─ 是 → 需要反复执行命令、看输出再决定？
         ├─ 否 → 编辑器多文件编辑 + 显式引用相关文件
         └─ 是 → 终端 agent
                  ├─ 需要严格可控的提交粒度与回滚 → Aider 类
                  ├─ 需要长期驻留、接消息/定时/多系统 → 常驻 agent（OpenClaw 类）
                  └─ 一次性本地任务 → 终端 agent（Claude Code / Codex CLI 类）
```

决策树里有两条隐含规则。第一，**能用低权限形态解决就不要升级**：补全能搞定的不要开终端 agent。第二，**任务越靠近不可逆操作，越要选「默认不执行」的形态**：涉及生产数据、部署、删除的，宁可多一步人工确认。

## 配置示例：把约定写进工具

无论选哪种工具，第一步都是把仓库约定固化。下面是编辑器与终端 agent 都能读的最小规则文件片段：

```markdown
# AGENTS.md（节选）
## 技术栈
- 前端 Vue 3 + TypeScript；后端 FastAPI + SQLAlchemy
- 包管理统一用 pnpm / uv，禁止混用 npm / pip 安装

## 目录约定
- 接口层 src/api/，业务逻辑 src/services/，禁止在接口层写 SQL
- 测试与被测文件同目录，命名 *.test.ts

## 命令
- 单测：pnpm test <path>
- 类型检查：pnpm typecheck
- 提交前必须两者都通过

## 禁止
- 不新增依赖（需先提 issue）
- 不修改 migrations/ 下已合并的文件
- 不打印或提交任何密钥、内网地址
```

终端 agent 的工作流可以固定成三步，减少它自由发挥的空间：

```bash
# 1. 让它先读、先计划（不写代码）
claude "阅读 src/services/order.ts 与相关测试，输出改动计划，先不要改文件"

# 2. 计划确认后限定范围执行
claude "按计划只修改 src/services/order.ts 与对应测试，改完运行 pnpm test order"

# 3. 人工审查后提交，保持单一目的
git diff --stat
git add src/services/order.ts src/services/order.test.ts
git commit -m "fix(order): 修正金额汇总的边界条件"
```

如果工具支持项目级规则目录（例如编辑器自带的规则文件机制），把同样的内容同步一份，避免「换工具就换约定」。规则只写一份、多处引用，是这个环节最重要的工程习惯。

## 组合搭配：三层工具栈

实际团队很少只用一个工具。更稳的做法是按「权限递进」搭三层，每层有明确的进入条件：

| 层 | 工具形态 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| 第一层：补全 | IDE 插件 | 默认开启 | 需要跨文件修改时升级 |
| 第二层：编辑 | AI 编辑器 / 编辑器内对话 | 已明确目标文件与验收 | diff 超过单文件规模时拆分 |
| 第三层：执行 | 终端 agent / 常驻 agent | 需要跑命令、看输出、多步验证 | 任务完成或触发高风险动作需人工确认 |

这个结构的好处是「默认低权限」。大部分日常改动停在第一、二层，只有真正需要执行与多轮验证时才进第三层。它也让成本可控：最高权限的额度留给排障与迁移这类高价值任务，而不是用来改文案。

三层之间需要共享同一份规则文件与同一套命令。否则会出现「补全按 A 风格写、agent 按 B 风格改」的撕裂。一个可执行的做法是：规则文件放仓库根目录，编辑器规则目录用软链接或脚本同步，CI 里加一条检查，确保两份内容一致。

还要注意「工具不是越多越好」。每增加一个能改代码的入口，审查面就扩大一分。团队规模小于十人时，两层足够；只有当自动化需求（定时、跨系统、消息驱动）真实出现时，才引入常驻 agent。

## 成本与治理

成本不只看订阅费。真正的成本包括：审查时间（diff 越大越贵）、返工时间（上下文漂移导致）、以及事故成本（权限过大导致）。一个常见误判是给所有工程师开最高权限的终端 agent，结果审查能力没跟上，合并质量下降，最后又退回补全——问题不在工具，在于治理顺序反了：应该先有测试与规则，再放开执行权。

另一个被忽略的成本是**切换成本**。团队里三种工具混用、规则文件各不相同，会导致同一份代码被不同风格改写。可行的做法是：允许个人在「低权限形态」上自由选择，但「能改仓库、能跑命令」的形态统一到一套规则与一套审批策略上。

最后要提醒的是，工具的能力边界会随产品迭代变化，本文描述的是形态差异，不是功能清单。采购或推广前，用自己仓库里的真实任务做一次小规模对照：同一张任务卡分别交给候选工具，比较「首次 diff 可读性、返工次数、总耗时」。这个测试比任何评测榜单都更接近你的实际收益。

## 风险与常见坑

- [ ] 用补全工具做跨模块重构，改漏调用点
- [ ] 编辑器索引未更新，模型基于旧代码给建议
- [ ] 终端 agent 没有沙箱，误删或误改工作区文件
- [ ] 多个工具各有一份规则文件，内容互相矛盾
- [ ] 让 agent 自行安装依赖，引入未审计的包
- [ ] 把「能自动提交」当成「可以不用看 diff」
- [ ] 在同一个会话里连续处理多个不相关任务
- [ ] 只看生成速度，不统计返工与缺陷
