# 导读：Vibe coding 是什么

## 本章目标

读完这一章，你应该能回答四个问题：Vibe coding 与「让 AI 补全一行代码」到底差在哪里；它在哪些任务上收益最高、在哪些任务上必须绕开；一次正常的协作回合里，人和模型各自承担什么责任；以及当模型开始「自信地胡说」时，用哪几道闸门把错误挡在合并之前。这一章是整套笔记的地基，后面四章分别展开工具选型、上下文工程、工作流与质量体系。

## 核心概念与术语

| 术语 | 含义 | 为什么重要 |
| --- | --- | --- |
| 意图（intent） | 你真正想达成的用户价值与约束 | 模型只能优化你写清楚的目标，模糊意图必然换来模糊实现 |
| 规格（spec） | 把意图翻译成可验证的行为描述 | 没有规格就没有「对错」，评审会退化成审美争论 |
| 任务卡（task card） | 一次改动的最小工作单元：目标、范围、验收、禁止项 | 控制上下文规模，也控制 diff 规模 |
| 上下文窗口 | 模型单次能看到的全部输入 | 决定它能理解多少代码；超出后开始遗忘与臆造 |
| 上下文漂移 | 长对话中模型逐渐偏离最初约束 | 表现为改着改着动了不该动的文件 |
| 幻觉 | 模型编造不存在的 API、配置项或文件路径 | 编译或运行才会暴露，成本高 |
| diff | 一次改动的逐行差异 | 人审查的唯一有效单位，diff 越大审查质量越低 |
| 人在回路（HITL） | 在关键节点插入人的判断 | 把「不可逆」的动作留在人手里 |
| 验收标准 | 可执行的通过条件：测试、构建、手工检查项 | 让「完成」可被机器与人共同判定 |
| 护栏（guardrail） | 类型检查、lint、测试、权限沙箱等自动约束 | 把模型的自由度限制在可回滚范围内 |

## 定义：把「说」变成「可合并的改动」

Vibe coding 指的是用自然语言描述意图，由模型生成或修改代码，人负责定义目标、提供上下文、审查结果，并对最终质量负责。它强调「以对话推进实现」而不是「按行敲代码」，但并不意味着人不看代码。恰恰相反：人从「生产者」变成「意图定义者 + 验收者 + 风险承担者」，看书的时间从写之前挪到了合并之前。

三个要素缺一不可。第一是**明确的意图**：要解决谁的什么问题，边界在哪里。第二是**足够的上下文**：模型需要知道仓库结构、既有约定、相关实现，否则只能按训练数据里的「平均写法」猜。第三是**可执行的验收**：能跑的测试、能过的构建、能复现的手工步骤。缺任何一项，产出都会退化成「看起来像代码的文本」。

与相邻概念的区别可以用一张表说清：

| 形态 | 人的输入 | 模型的输出 | 人的角色 | 典型风险 |
| --- | --- | --- | --- | --- |
| 代码补全 | 正在写的几行 | 接下来的一小段 | 逐行作者 | 低，但收益也有限 |
| 对话问答 | 一个问题 | 解释或片段 | 学习者 | 片段脱离仓库语境 |
| Vibe coding | 任务 + 上下文 + 验收 | 一个可评审的 diff | 意图与验收负责人 | 大 diff、上下文漂移 |
| 自主 agent | 一个目标 | 多轮工具调用后的结果 | 监督者与审批者 | 副作用不可控、难复现 |

越往右，杠杆越大，对护栏的要求也越高。很多团队失败不是因为选了太弱的工具，而是用「补全」的治理方式去管「自主 agent」的产出。

## 收益：杠杆来自哪里

收益主要有三处。其一是**启动成本**：把「新建一个模块、补齐 CRUD、写测试脚手架」这类结构清晰的活儿从小时级压到分钟级。其二是**探索成本**：让模型同时给三种实现思路，人只做取舍，比自己在脑子里比较更快。其三是**重复劳动**：改命名、迁移 API、批量补类型这类机械改动，模型的稳定性往往高于疲劳的人。

但有三件事常被高估。第一，模型不会替你想清楚需求；需求模糊时它只会更快地生产错误。第二，模型不掌握你仓库的隐性约定，除非你写进规则文件或示例。第三，生成速度不等于交付速度，评审、测试与返工才是瓶颈。把「生成了两千行」当成绩，是最典型的度量错位。

## 四类风险

**幻觉**。模型会编造配置键、函数签名、文件路径，而且语气笃定。防御方式是让它在动手前先读文件、动手后必须跑构建与测试；凡是「引用了不存在的符号」的改动，一律视为未完成。

**上下文漂移**。对话越长，早期约束越容易被稀释：说好只改 A 模块，改到第五轮顺手重构了 B。防御方式是把约束写进任务卡、把会话按任务切分、每轮结束复查 diff 涉及的文件清单。

**不可审查的大 diff**。一次生成八百行，评审者只会看个开头就点通过。防御方式是设定单次改动上限（例如单文件、单职责），超出就拆任务；先给计划再动手，避免「边想边写」把探索过程也写进提交。

**安全与许可**。模型可能引入来源不明的代码片段、把密钥硬编码、给接口加上不必要的宽权限，或者生成有已知漏洞的依赖用法。防御方式是依赖白名单、密钥扫描、最小权限沙箱，以及默认不执行来自模型的安装命令。

## 人在回路的三道闸门

**第一道：计划闸门**。动手前要求模型输出「改哪些文件、为什么、怎么验证」的计划，人确认后再写。计划的成本是几十秒，返工的成本是几小时。计划里出现「重构整个模块」「顺便升级依赖」这类扩权表述，直接驳回。

**第二道：diff 闸门**。按文件审查，不看总结看差异；重点看边界条件、错误处理、并发与资源释放、以及对既有行为的破坏。单次 diff 控制在可读完的规模，读不完就拆。

**第三道：验证闸门**。构建、测试、静态检查全绿才算完成；没有自动化测试的路径，必须留下可复现的手工验证步骤。三道闸门都过，才允许合并。

## 一套最小可用流程

先写任务卡，再开对话。任务卡不需要复杂模板，四行就够：

```markdown
## 任务卡：为订单列表增加按状态筛选
- 目标：GET /api/orders 支持 status 参数，非法值返回 400
- 范围：仅 src/orders/ 下的 controller 与 service；不改数据库 schema
- 验收：单测覆盖合法/非法/缺省三种情况；`npm test -- orders` 通过
- 禁止：不新增依赖；不改动公共错误码定义
```

把任务卡原样贴进对话，并附上「先计划后动手」的指令：

```text
你是本仓库的协作工程师。请先阅读 src/orders/ 下的 controller、service 与现有测试，
然后输出一份计划：要改哪些文件、每个文件改什么、如何验证。
暂时不要写代码。计划里如果发现需要改动范围外的文件，先停下来问我。
```

计划确认后再让它实现。每次提交保持单一目的，提交信息写清「为什么」：

```bash
git add src/orders/order.controller.ts src/orders/order.service.ts
git commit -m "feat(orders): 支持按状态筛选并校验非法值"
npm test -- orders && npm run build
```

如果实现跑偏，不要在原对话里继续打补丁，直接 `git checkout -- .` 回到干净状态，把新学到的约束补进任务卡，重开一轮。回滚比重写便宜。

## 适用与不适用边界

适合：有明确输入输出的业务逻辑、脚手架与样板代码、测试补齐、批量重命名与迁移、文档与注释、把一次性脚本写规范。

不适合：没有验收标准的模糊需求、强依赖领域隐性知识的核心算法、涉及资金与权限的关键路径（可以辅助，但必须逐行审）、线上故障的紧急热修（先止血，再让模型参与复盘）、以及许可证不明的代码搬运。

## 一次协作回合的拆解

把一次典型的改动摊开看，人和模型的分工其实很清楚。假设要给一个已有接口加参数校验。

**回合开始**，人做三件事：确认现象（现在的接口对非法参数返回 500），确认目标（返回 400 并带错误码），确认边界（只动这一层，不顺手改日志格式）。这三件事模型都做不了，因为它不知道业务上什么算非法、也不知道线上监控怎么消费错误码。

**第一个模型动作是读**，不是写。让它先列出相关文件、现有校验方式、错误码定义位置。这一步的产出是「事实清单」，人能立刻判断它有没有找错地方。很多事故源于模型在读错文件的前提下自信地写完了整段逻辑。

**第二个动作是计划**。计划里应该出现具体的函数名与分支条件，而不是「优化参数校验」这种空话。计划越具体，实现越可控；计划里出现「顺便抽取一个通用校验器」这种扩权，就应该在这一步砍掉。

**第三个动作才是写**。写的时候要求它保持最小改动：沿用既有错误码、沿用既有日志格式、不引入新依赖。写完后由模型自己跑一次目标测试，把失败信息贴回来。

**第四个动作是自查 diff**。让人看的是四件事：新增分支是否覆盖了缺省值；错误码是否复用了既有常量；有没有顺手改格式；测试是否真的断言了行为而不只是「不抛异常」。这四条里任何一条不过，退回重做，而不是在评论里打补丁。

**回合结束**，人做两件事：跑完整构建与相关测试，把任务卡的验收项逐条勾掉；写提交信息，说明「为什么改」而不是「改了什么」——diff 已经说明了改了什么。

这个流程听起来比「直接让它写」慢，但它把返工从「事后发现」提前到「事前拦截」。熟练之后，一个中小改动从任务卡到合并大约十几分钟，其中模型生成只占一两分钟，剩下的是人的判断。这也是为什么 Vibe coding 的瓶颈通常不是模型速度，而是人的验收能力。

## 团队引入的最小动作

如果团队想试，不要一上来就定规范。先做三件成本极低的事：在仓库根目录放一份规则文件，写清技术栈、目录约定、测试命令与禁止事项；把「先计划后动手」写进默认提示词；要求所有 AI 参与的改动单独提交，提交信息里标注来源。这三件事让产出可追溯、可对比、可回滚，之后再谈评审标准与度量。

一个常见误区是把工具当成「人力替代」。更准确的定位是「把资深工程师的判断力复制到更多地方」：规则文件是判断力的固化，任务卡是范围的固化，测试是验收的固化。三者都在，模型越强收益越大；三者都不在，模型越强事故越大。

## 风险与常见坑

- [ ] 把「模型说完成了」当成完成，没有跑构建与测试
- [ ] 一次任务跨了三个模块，diff 大到没人愿意读完
- [ ] 没有任务卡，靠聊天记录回忆约束，第五轮开始跑偏
- [ ] 允许模型自行安装依赖，引入未审计的包
- [ ] 把密钥、内网地址、客户数据贴进对话
- [ ] 用「生成了多少行」衡量效果，而不是返工率与缺陷率
- [ ] 在同一个会话里连续做五件不相关的事，上下文互相污染
