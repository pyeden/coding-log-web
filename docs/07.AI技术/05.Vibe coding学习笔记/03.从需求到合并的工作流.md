# 从需求到合并的工作流

## 本章目标

Vibe coding 的效率不取决于「一次生成多少代码」，而取决于**每次改动是否可被快速验证**。这一章给出一条六步闭环：需求 → 规格 → 计划 → 小步实现 → 自测与评审 → 合并。每一步都明确人机分工，并给出可直接复用的提示词模板、分支与提交策略、diff 审查清单与回滚方法。读完后你应该能把一个模糊需求，稳定地推进成一个可合并的提交。

## 核心概念与术语

| 术语 | 含义 | 在工作流中的位置 |
| --- | --- | --- |
| 需求 | 用户问题与业务目标 | 第一步，人负责 |
| 规格 | 行为契约，含错误与边界 | 第二步，人主导、模型补漏 |
| 计划 | 改哪些文件、怎么验证 | 第三步，模型产出、人批准 |
| 小步实现 | 单次可评审的改动 | 第四步，模型执行、人监督 |
| 自测 | 构建、单测、静态检查 | 第五步，模型跑、人复核 |
| diff 审查 | 按文件读差异 | 第五步，人负责 |
| 回滚 | 撤销到已知良好状态 | 任一阶段失败时 |
| 合并 | 进入主干并可发布 | 第六步，人负责 |

## 六步闭环与分工

| 步骤 | 人的动作 | 模型的动作 | 通过标准 |
| --- | --- | --- | --- |
| 1 需求 | 写清背景、用户、成功指标 | 追问歧义、列出假设 | 能一句话说清「为谁解决什么」 |
| 2 规格 | 定义行为、错误、边界、非目标 | 补边界用例、指出矛盾 | 每条行为都可判定 |
| 3 计划 | 审范围、砍扩权 | 列出文件、步骤、验证方式 | 计划不超出任务卡范围 |
| 4 实现 | 盯范围、随时叫停 | 最小改动、沿用既有约定 | 单次 diff 可读完 |
| 5 自测评审 | 看 diff、跑关键路径 | 跑测试、修失败、解释改动 | 构建与测试全绿 |
| 6 合并 | 写提交信息、合并、观察 | 无（或生成发布说明） | 主干可构建、可回滚 |

这张表最重要的一列是「通过标准」。没有标准的步骤会自然退化成「看起来差不多」，而 Vibe coding 的所有事故几乎都发生在「差不多」的地方。

## 第一步：把需求压缩成一句话

需求阶段人最容易犯的错是「边想边写」。更有效的做法是先写一句话：**为谁、解决什么问题、怎么判断成功**。例如「为运营同学提供按状态筛选订单的能力，使日常核对从导出 Excel 改为页面筛选，成功指标是核单耗时下降」。这句话里已经包含用户、问题、边界与指标，后面的规格才有依据。

模型在这个阶段的价值是「追问」：让它列出它认为模糊的点，通常能暴露你没想到的边界（权限、分页、排序、导出）。但不要让它直接给方案——方案会过早锁定实现，掩盖需求本身的问题。

## 第二步：规格写「行为」，不写「实现」

规格的写法在上一章已经展开，这里补充工作流视角的两个要点。第一，**每条行为都要有可判定的结果**：「支持筛选」不可判定，「传入非法 status 返回 400 与错误码 INVALID_STATUS」可判定。第二，**显式写非目标**：这次不做导出、不做批量操作、不改权限模型。非目标是对模型的硬约束，也是对评审者的保护。

规格完成后让模型做一次「反例检查」：请它列出会让规格自相矛盾或无法实现的场景。模型在这类挑错任务上表现通常不错，因为它不需要创造性，只需要一致性推理。

## 第三步：先要计划，再要代码

计划是整个工作流的分水岭。没有计划，模型会边探索边写，探索过程全部变成 diff；有计划，探索发生在文本里，diff 只剩结论。

一份合格的计划包含：涉及文件清单（含新增）、每个文件的改动要点、验证命令、风险点。人审计划时只做三件事：范围是否越界、验证是否充分、有没有更小的做法。发现越界就当场砍掉，不要指望「写完再删」——删的时候往往会带走正确的部分。

```text
请先不要修改任何文件。基于下面这张任务卡：
1) 列出需要改动的文件（含新增文件）与每个文件的改动要点；
2) 给出验证方式（具体命令与预期结果）；
3) 指出你认为的风险点与不确定项。
如果发现必须改动任务卡范围外的文件，请停下来说明原因，等我确认。
```

## 第四步：小步实现

小步的含义是「一次只做一件可独立验证的事」。判断标准很简单：如果这个 diff 无法用一句话描述，它就太大了。常见拆分方式：先加测试（红），再改实现（绿），最后清理；或者先加接口与类型，再补实现；或者先改一个调用点验证方向，再批量替换其余调用点。

分支策略上，一个任务一个分支，分支名带任务标识；提交保持单一目的，提交信息写「为什么」。不要把格式化、重命名、功能改动混在一个提交里，否则回滚时无法只撤其中一项。

```bash
git switch -c feat/coupon-redeem
# 每一轮改动后
git diff --stat
git add apps/api/services/coupon.ts apps/api/services/coupon.test.ts
git commit -m "feat(coupon): 实现核销锁定与幂等"

# 方向错了就整轮丢弃，不要在脏状态上继续打补丁
git restore --staged . && git restore .
```

最后一条命令值得强调：模型跑偏时，最便宜的动作是回到干净状态重来，而不是在错误的基础上继续对话。重来一轮的成本通常低于审查一个被补丁覆盖的复杂 diff。

## 第五步：自测与 diff 审查

自测由模型执行，人复核结果。最低要求是：构建通过、相关测试通过、静态检查通过。没有测试的路径，要求模型给出可复现的手工步骤，人照着走一遍。注意「测试通过」不等于「行为正确」：模型可能改了测试来适配实现，所以审查时要单独看测试文件的 diff。

diff 审查按风险排序，而不是按文件顺序：

| 审查重点 | 具体看什么 | 常见问题 |
| --- | --- | --- |
| 边界条件 | 空值、超长、并发、权限 | 只处理了正常路径 |
| 错误处理 | 错误码、日志、向上抛出 | 吞异常、返回模糊错误 |
| 数据一致性 | 事务边界、幂等、重复提交 | 部分成功未回滚 |
| 兼容性 | 接口字段、默认值、旧数据 | 改了字段含义未迁移 |
| 测试质量 | 断言行为而非实现 | 只断言「不抛异常」 |
| 范围 | 是否动了无关文件 | 顺手格式化、顺手重构 |

审查时优先读「删除的行」。新增代码容易博得好感，删除的代码才暴露行为变化：删掉的校验、删掉的日志、删掉的默认值，往往是线上问题的源头。

## 第六步：合并与观察

合并前确认三件事：主干能构建、变更可回滚、提交信息能让人看懂为什么。合并后观察关键指标（错误率、延迟、告警），不要假设「测试过了就没问题」。对于高风险改动，采用小流量或灰度发布，把回滚成本降到一次配置切换。

回滚要提前想清楚：是 revert 提交，还是回退发布版本，还是关开关。三种手段的恢复时间不同，团队应在变更前就约定。最糟的情况是出了问题才开始讨论怎么回滚。

```bash
# 代码回滚（保留历史）
git revert <sha> --no-edit

# 发布回滚：把 current 指回上一个 release（以团队脚本为准）
# 开关回滚：关闭功能开关，保留代码
```

## 可复用的提示词模板

把上面的步骤固化成模板，能显著降低每轮沟通成本：

```text
【任务卡】
目标：<一句话>
范围：<目录/文件>
验收：<命令与预期>
禁止：<不改 schema / 不加依赖 / 不动 X 模块>

【本轮要求】
1. 先读 <相关文件>，用三句话总结你理解的现状；
2. 给出计划（文件、改动、验证），不要写代码；
3. 我确认后，按计划实现，保持最小改动；
4. 实现后运行 <命令>，把失败输出原样贴回；
5. 最后列出你改了哪些文件、哪些地方你不确定。
```

模板里「用三句话总结现状」这一步很关键：它迫使模型先建立事实基础，也让你能提前发现它读错了文件。最后一句「哪些地方不确定」则把幻觉从「隐藏」变成「显式」，方便重点审查。

## PR 检查清单

```markdown
- [ ] diff 能用一句话描述，且只做这一件事
- [ ] 没有改动任务卡范围外的文件
- [ ] 构建、单测、静态检查通过
- [ ] 新增分支有测试覆盖，测试断言的是行为
- [ ] 错误码与日志符合既有约定
- [ ] 无密钥、内网地址、调试输出
- [ ] 无新增依赖（或已单独评审）
- [ ] 提交信息说明「为什么」，必要时附回滚方式
```

## 并行协作：多人与多 agent 同仓

当多个 agent 或多个同事同时改一个仓库时，工作流需要额外两条规则。第一，**按文件划分所有权**：同一时间只让一个执行者改同一个文件，尤其是导航配置、路由表、依赖清单这类「所有人都要动一行」的聚合文件。冲突不是最可怕的，最可怕的是自动合并后语义错误——两边各加一行，语法没问题，顺序却乱了。

第二，**提交前先同步**：拉取远端、检查是否有新提交，再决定合并或变基。共享 checkout 里尤其要按文件逐个暂存，不要用「全部添加」，否则会把别人未完成的改动卷进自己的提交。

```bash
git fetch origin
git log --oneline HEAD..origin/main
# 有更新则先同步，再重新验证
git rebase origin/main
pnpm test && pnpm build
```

如果冲突发生在生成物或锁文件上，不要手工「猜」一个结果：重新生成（安装依赖、重新构建）通常比手工合并更可靠。生成物冲突是信号，说明有人提交了本不该提交的产物。

协作中还有一个容易被忽略的点：**agent 之间不要共享会话**。每个执行者用独立会话、独立分支，通过提交与 PR 交流，而不是通过聊天记录传递上下文。聊天记录不可审计，提交可以。

## 度量这套流程是否有效

不要用「生成了多少代码」衡量。更有意义的四个指标是：一次通过率（首次提交即通过 CI 的比例）、返工轮次（同一任务的平均修改次数）、diff 中位数（是否稳定在小步范围）、以及合并后缺陷率。前两个衡量流程质量，后两个衡量产出质量。

如果一次通过率低但返工轮次也低，说明验收标准写得太松；如果两者都高，说明任务卡范围过大或上下文不足。指标的作用是定位环节，不是考核个人——一旦用于排名，人们会开始拆小任务刷数据，反而破坏流程。

## 风险与常见坑

- [ ] 跳过计划直接生成，探索过程变成不可读的 diff
- [ ] 一个提交混入格式化与功能改动，无法单独回滚
- [ ] 模型改测试来让测试通过，人未复核测试 diff
- [ ] 在脏工作区上继续对话，补丁叠补丁
- [ ] 合并后不观察指标，问题延后暴露
- [ ] 高风险改动没有灰度与开关
- [ ] 提交信息只写「update」，三个月后无人能懂
- [ ] 任务跨多个模块却坚持一次做完
