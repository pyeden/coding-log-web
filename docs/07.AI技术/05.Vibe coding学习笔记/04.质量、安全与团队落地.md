# 质量、安全与团队落地

## 本章目标

前四章讲的是「怎么让模型写出想要的代码」，这一章讲「怎么保证写出来的东西可以上线」。模型可以显著提高产出速度，但它不会自动带来质量：它会把你的测试缺口、权限松散、依赖混乱原样放大。本章从五个维度给出可执行的护栏——测试、静态检查、依赖与许可、密钥与沙箱、评审与度量，最后给出一条分三阶段的团队落地路线，以及一份常见失败模式清单与可勾选的自查项。

## 核心概念与术语

| 术语 | 含义 | 与 AI 协作的关系 |
| --- | --- | --- |
| 测试护栏 | 单测、契约测试、端到端测试 | 让「改坏了」立刻可见 |
| 契约测试 | 校验接口输入输出约定 | 防止模型擅自改字段语义 |
| 静态检查 | 类型、lint、格式、复杂度 | 低成本拦截一类错误 |
| 供应链风险 | 依赖来源、许可证、已知漏洞 | 模型可能推荐不明来源的包 |
| 密钥泄露 | 凭证进入代码或日志 | 模型容易把配置写死 |
| 沙箱 | 限制文件、网络、命令执行 | 限制 agent 的破坏半径 |
| 评审制度 | 谁看、看什么、何时放行 | 决定 AI 产出的准入标准 |
| 度量 | 采纳率、返工率、缺陷率 | 判断投入是否真的有效 |

## 测试护栏：先有网，再走钢丝

Vibe coding 的第一个前提是「有测试」。没有测试时，模型的每次改动都无法被机器验证，人只能靠读代码判断，成本极高且不稳定。测试护栏按三层建设：

| 层级 | 覆盖对象 | 建设成本 | 对 AI 的价值 |
| --- | --- | --- | --- |
| 单元测试 | 纯函数、业务规则、边界 | 低 | 改完立刻知道有没有破坏行为 |
| 契约测试 | 接口输入输出、错误码 | 中 | 防止字段语义被悄悄改写 |
| 端到端 | 关键用户路径 | 高 | 防止跨模块组合失效 |

优先级建议是「先补业务规则的单元测试，再补接口契约，最后才是端到端」。原因很实际：单元测试跑得快、定位准，模型能在一次会话里自己跑完；端到端慢且易碎，更适合作为合并前的门禁，而不是迭代中的反馈。

还有一个反模式要警惕：**模型改测试来适配实现**。审查时必须单独看测试文件的 diff，确认断言的是行为而不是实现细节，确认删除的用例有正当理由。一个实用规则是：测试的修改要与实现的修改分开提交，让评审者能独立判断。

## 静态检查与类型

静态检查是性价比最高的护栏，因为它不需要理解业务。类型检查能拦住「字段名写错」「返回值可能为空」这类高频错误；lint 能拦住未使用变量、危险的相等比较、遗留的调试输出；格式检查则让 diff 只包含语义变化，避免格式化噪声淹没真正的改动。

```bash
# 提交前的最小闭环（命令按仓库实际调整）
pnpm typecheck
pnpm lint --max-warnings=0
pnpm test -- --run
```

关键是**不要允许跳过**。一旦「这次先跳过，下次再补」成为习惯，护栏就等于不存在。如果某条规则确实不合理，改规则并说明理由，而不是临时绕过。对 AI 生成代码尤其如此：模型会模仿它看到的做法，一次绕过会被复制到后续所有改动里。

## 依赖与许可

模型最常见的越界行为之一是「顺手装个包」。它可能引入维护状况不明的库，或使用与项目许可证不兼容的依赖。防线有三道：规则文件明确「新增依赖需先评审」；CI 检查依赖清单的变更；定期扫描已知漏洞与许可证。

```bash
# Node 生态示例，其他生态用对应工具，具体参数以官方文档为准
npm audit --omit=dev
npx license-checker --summary

# Python 生态示例
pip-audit
pip-licenses --format=markdown
```

审查新增依赖时问四个问题：是否真的需要（标准库或现有依赖能否替代）、维护是否活跃、许可证是否兼容、体积与安全记录如何。四个问题里任何一个答不上来，就不合并。这条规则对人和模型一视同仁，才不会变成「AI 写的就放宽」。

## 密钥与权限沙箱

密钥泄露是 AI 协作里最昂贵的事故类型，因为模型会把「看起来能跑」的配置直接写进代码：数据库连接串、第三方 token、内网地址。防线要放在三个位置。

第一，**入口**：规则文件与提示词明确禁止粘贴密钥，敏感信息通过环境变量注入。第二，**提交前**：用钩子扫描常见密钥模式，命中即阻断。第三，**运行时**：agent 使用最小权限凭证，网络访问限定在必要域名。

```yaml
# pre-commit 配置示意（工具与字段以官方文档为准）
repos:
  - repo: local
    hooks:
      - id: secret-scan
        name: scan staged files for secrets
        entry: gitleaks protect --staged
        language: system
        pass_filenames: false
      - id: typecheck
        name: typecheck
        entry: pnpm typecheck
        language: system
        pass_filenames: false
```

沙箱的粒度按风险分级：只读任务给只读挂载；需要改代码的任务给仓库目录写权限，但不给家目录；需要跑测试的任务允许本地回环网络，但不允许外网任意访问。终端 agent 默认应该跑在容器或受限用户下，而不是你的主账户。

## 日志与可观测性

AI 参与的改动同样需要可观测性，甚至更需要：因为改动速度快，出问题时定位窗口更短。三条最低要求：关键路径有结构化日志（含请求标识）；错误日志包含足够上下文但不含个人信息；新功能有对应的指标或告警，否则「上线成功」只是没人发现而已。

一个容易忽略的点是**日志本身也是泄露面**。模型可能把整个请求体打进日志，包括手机号与 token。审查时看到 `log.info(request.body)` 这类写法要停下来，改成白名单字段。

## 评审制度

评审是唯一能同时覆盖「机器测不到」和「机器测得出但没人看」的环节。建议按风险分级：低风险改动（文案、注释、测试补充）单人快速过；中风险（业务逻辑、接口字段）要求熟悉该模块的人审；高风险（权限、支付、数据迁移、依赖升级）要求两人审并附回滚方案。

评审时给出明确指令，比笼统的「看看有没有问题」有效得多：请重点检查边界条件、错误处理、是否改动范围外文件、测试是否断言行为。把这份清单放进 PR 模板，评审质量会稳定很多。

## 上线门禁：把护栏接进流水线

护栏如果只写在文档里，执行率取决于当天的忙碌程度。有效做法是把它们接进流水线，让「不合规」在合并前就无法通过。门禁分三道：提交前（格式、密钥、类型）、合并前（单测、契约测试、依赖扫描）、发布前（构建、端到端冒烟、变更说明）。

```yaml
# CI 门禁示意（平台与字段以官方文档为准）
stages: [check, test, build]
check:
  script:
    - pnpm lint --max-warnings=0
    - pnpm typecheck
    - gitleaks detect --no-banner
test:
  script:
    - pnpm test -- --run
    - npm audit --omit=dev
build:
  script:
    - pnpm build
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```

门禁设计要注意两点。第一，**快速失败**：把最便宜、最容易失败的检查放最前面，减少等待。第二，**可解释**：失败信息要指向具体文件与规则，而不是一句「检查未通过」。模型读不懂模糊报错时会开始猜，猜的结果往往是绕过检查。

对 AI 参与的提交，可以额外加一条元数据要求：提交信息标注「AI 辅助」，并附上任务卡编号。这不是为了追责，而是为了在复盘时能区分「哪类任务用 AI 收益高、哪类总是返工」。没有这层数据，团队只能凭感觉调整策略。

## 度量：别用行数骗自己

| 指标 | 定义 | 说明什么 | 误用风险 |
| --- | --- | --- | --- |
| 采纳率 | 被合并的 AI 参与改动占比 | 工具是否真的进入流程 | 高采纳不代表高价值 |
| 一次通过率 | 首次 CI 通过比例 | 上下文与验收是否清晰 | 可通过拆碎任务刷高 |
| 返工率 | 合并后需修复的比例 | 评审与测试是否有效 | 统计口径要统一 |
| 缺陷密度 | 每千行新增缺陷数 | 质量趋势 | 小样本波动大 |
| 交付周期 | 从任务卡到合并耗时 | 真实效率 | 受任务难度影响 |

度量用于定位瓶颈，不用于排名。一个健康信号是：交付周期下降，同时返工率与缺陷密度不上升。如果周期下降但返工上升，说明省下的时间被转移到了事后修复，整体并没有变好。

## 团队落地路线

**阶段一：个人试点（两到四周）**。选一到两个愿意折腾的工程师，在一到两个非关键仓库试用。目标不是提效数字，而是收集「哪些任务适合、哪些不适合」的具体案例。产出是一页纸的经验：有效任务类型、失败模式、必要的规则文件片段。

**阶段二：小队规范（一到两个月）**。把试点结论固化成团队规范：统一的规则文件、任务卡模板、PR 清单、评审分级。选一个仓库做完整落地，包括测试补齐与 CI 门禁。这个阶段的成功标准是「新人按规范做，产出质量不依赖个人水平」。

**阶段三：组织基线（持续）**。把规范上升为组织基线：依赖白名单、密钥扫描、沙箱策略、审计日志、度量看板。同时建立例外流程——允许团队申请偏离基线，但必须记录理由与复审时间。基线评审每季度一次，只增删必要项，避免规则膨胀到无人阅读；每次评审记录「新增了哪条、因为哪次事故」，让规则始终有据可查。基线的作用是设下限，不是消灭差异。落地过程中要留一个「反馈口」：一线遇到规则不合理时，能在一个工作日内得到回应，否则规范会迅速失去信任。

三个阶段不要跳。没有试点就直接推组织基线，通常会得到一份没人执行的文档；试点做完不固化，经验会随人员流动消失。

## 常见失败模式

- **只买工具不改流程**：工具装上了，评审还是「看一眼就过」，问题照旧。
- **用 AI 补测试缺口**：让模型生成大量断言实现的测试，覆盖率上去了，保护力没上去。
- **权限一步到位**：直接给 agent 生产凭证，第一次事故就是最后一次试点。
- **度量变成考核**：一旦按生成行数排名，团队会开始制造无意义代码。
- **规范过度**：规则文件几百行，模型忽略中段，人也不维护。

## 风险与常见坑

- [ ] 没有测试就大规模使用 agent 改核心逻辑
- [ ] 允许模型修改测试以通过 CI，且未单独审查
- [ ] 依赖新增无人评审，许可证与漏洞未扫描
- [ ] 密钥写入代码或日志，未配置提交前扫描
- [ ] agent 以主账户权限运行，无沙箱与网络限制
- [ ] 高风险改动单人评审、无回滚方案
- [ ] 用生成行数或采纳率作为绩效指标
- [ ] 规范只写不查，落地三个月后无人遵守
