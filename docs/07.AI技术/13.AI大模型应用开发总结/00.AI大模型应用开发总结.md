# AI大模型应用开发总结

## 写在前面：这篇总结从哪里来

过去两周，我在 MacBook 节点上连续推进了几类项目：PanguVerse 自动化工作台（探索式智能体、LLM 规划、任务编排）、coding-log-web 的 AI 技术笔记与站点发布链路、简历维护助手、接单报价系统，以及旅行助手。它们的技术栈不同，但真正让人加班的问题高度相似：**大模型不是一个更聪明的本地函数，而是一个有概率、有预算、有外部依赖、还会悄悄返回半成品的远程服务。**

这篇总结不复述 prompt 技巧，而是按“故障面”复盘我实际踩过的坑。每个坑都给出当时的症状、根因、修复方式和可复用的检查项。文中的数字来自项目日志与实测，不编造版本号和参数；涉及供应商能力时，以官方文档为准。

## 一、先建立一张故障面地图

AI 应用出问题，第一反应往往是“prompt 写得不好”。实际排查下来，prompt 只占一小部分，更多问题分布在下面六层。

| 层级 | 典型症状 | 常见根因 | 第一动作 |
| --- | --- | --- | --- |
| 模型层 | 返回空、截断、答非所问 | 推理 token 吃光输出预算、模型能力不匹配 | 看 `finish_reason`、usage 与 effort 配置 |
| 请求层 | 偶发 5xx、超时、重试后更慢 | 超时与总预算不联动、重试不区分错误类型 | 按剩余预算设超时，只重试瞬时错误 |
| 上下文层 | 模型看不到关键文件、答非所问 | 沙箱可见性、上下文裁剪、权限边界 | 检查模型实际能读到的目录与片段 |
| 规划层 | 计划很完整，但一执行就 404 | 把模板假设当成观察事实 | 先探索取证，再生成计划 |
| 验证层 | 模型说成功，用户一用就失败 | 用自然语言自述替代可执行校验 | 落成断言、脚本、产物检查 |
| 产品层 | 错误提示不可行动、默认值误导 | 错误码与降级路径设计缺失 | 把“为什么失败、下一步做什么”写进契约 |

排查顺序应当反过来：**先看产品层能否解释失败，再看验证层有没有证据，再看请求层和模型层。** 直接盯着 prompt 改，往往会错过真正的断点。

## 二、坑一：把推理模型当成普通对话模型

这是我在 PanguVerse 上遇到的第一个硬坑。项目使用 `deepseek-v4-flash`，它默认带有较高的 reasoning effort。一次 2.9KB 的探索式 JSON 请求，实测耗时 52.6 秒，completion 只有 547 tokens，但 reasoning 有 2015 个字符。并发三次也要 6.2–9.7 秒。单看“模型没挂”，但交互体验已经不可用。

更隐蔽的是第二个问题：我给 OpenAI 兼容分支加了 `max_tokens=2048`，本意是限流，结果推理 token 先耗尽了输出预算，`content` 为空、`finish_reason=length`，HTTP 仍然是 200。上层只看到“响应中没有 JSON”，很容易误判为解析 bug。

修复分三步：

1. JSON 类调用显式关闭或降低 reasoning，把预算留给最终 JSON；
2. 把 JSON 输出预算提高到 4096，并允许用环境变量覆盖；
3. 把 `finish_reason=length` 单独识别为“输出被截断”，不再报“没有 JSON”。

```python
resp = client.chat.completions.create(
    model=model,
    messages=messages,
    max_tokens=4096,
    response_format={"type": "json_object"},
    reasoning_effort="none",  # 是否支持、可选值以供应商文档为准
    timeout=remaining_budget,
)

choice = resp.choices[0]
if choice.finish_reason == "length":
    raise TruncatedOutput(
        f"输出被截断: finish_reason=length, usage={resp.usage}"
    )
if not choice.message.content:
    raise EmptyContent("HTTP 200 但 content 为空")
```

这条经验可以推广：**凡是“模型返回空/格式不对”的问题，先看 usage 和 finish_reason，再看解析器。** 推理模型时代，`max_tokens` 不是“回答长度”，而是“推理 + 回答”的总预算。

## 三、坑二：重试次数和总预算各算各的

PanguVerse 的探索接口默认允许 50 步、总时长 300 秒；单次 LLM 决策实测 5–100 秒；客户端默认超时 120 秒、重试 2 次。把这些数字放在一起就能看出：**这个任务在预算内不可能跑完。** 实际会话里，有的在 288 秒时遇到上游 500，有的 0 步就失败，有的跑了 6 步、318 秒后以“总时长超过 300 秒”收尾。

更糟的是，上游还会返回 HTTP 200 但响应体为 `null`，或者没有 `choices`。如果重试逻辑只认 5xx，这些都会被当成“成功但没内容”，然后进入一个没有出口的解析失败分支。

修复原则是“预算联动”：

- 每次调用的超时取 `min(客户端超时, 剩余总预算 - 1 秒)`；
- `max_steps` 按 `total_timeout / 单步预算` 封顶，而不是让用户随便填 50；
- 剩余预算低于 15 秒时，不再发起新决策，直接用已有产物收尾；
- 5xx、空响应、`null`、非 JSON 都归为可重试，退避 2 秒、4 秒并加抖动；
- 错误里保留供应商的 `request_id`，否则无法和上游对账。

```python
remaining = deadline - monotonic()
if remaining <= 15:
    return finalize_with_existing_artifacts()

timeout = min(client_timeout, max(1.0, remaining - 1.0))

for attempt in range(3):
    try:
        return call_llm(timeout=timeout)
    except TransientLLMError as exc:
        if attempt == 2:
            raise
        sleep((2 ** attempt) + random.uniform(0, 0.5))
```

这里的关键认知是：**超时不是单次请求的参数，而是全链路预算的一部分。** 重试次数、单步超时、总时长、最大步数必须一起设计，否则“多试几次”只会把失败推迟到最后一秒。

## 四、坑三：JSON 模式不等于“一定返回 JSON”

我一度以为传了 `response_format={"type": "json_object"}` 就万事大吉。实际遇到的响应形态包括：

| 响应形态 | 判定 | 处理 |
| --- | --- | --- |
| HTTP 200，`choices` 为空 | 上游异常或代理改写 | 按瞬时错误重试 |
| HTTP 200，`content` 为空 | 输出预算被推理耗尽 | 检查 `finish_reason`，调整预算 |
| HTTP 200，`content` 是 Markdown 代码块 | 模型没有遵守 JSON 约束 | 提取代码块后再解析 |
| HTTP 200，`content` 是解释文字 | 指令冲突或模型能力不足 | 用错误反馈做一次修复重试 |
| HTTP 500 / `null` | 上游故障 | 退避重试并记录 request_id |

工程上要分三层处理：**严格解析 → 容错提取 → 带错误反馈的修复重试**。修复重试只做一次，且要把解析错误、期望 schema、上一轮输出一起给模型；再失败就进入确定性兜底，不能无限循环。

```python
def parse_json_response(text: str) -> dict:
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        block = extract_json_block(text)  # ```json ... ``` 或首个平衡花括号
        if block is None:
            raise
        return json.loads(block)

try:
    data = parse_json_response(content)
    validate_schema(data)
except (json.JSONDecodeError, SchemaError) as exc:
    data = repair_once(messages, content, exc)  # 只修一次
```

还有一个容易被忽略的点：**不同供应商、不同代理对 `response_format` 的支持程度不一样。** 接入前要验证，接入后要保留“不支持 JSON 模式”的降级路径，而不是把整个功能绑死在一个可选参数上。

## 五、坑四：让模型“先观察”，不要“先编计划”

这是 PanguVerse 最贵的一课。最初的 plan-first 逻辑是“意图 → 计划 → 画布”，听起来很顺，但模型还没接触现实就开始编步骤：

- 模板把健康检查地址写成 `${env.BASE_URL}/api/health`，实际站点没有这个路径，调试直接 404；
- 用户说“打开百度网页，获取今天的热点新闻”，前端默认包是 `api_testing`，后端又无条件尊重显式包，于是生成了 19 个 health/login/order 节点，和意图完全无关；
- 缺 URL 时返回 `capability_gap`，还把已经存在的原子列为缺失，用户看到的是“能力不够”，实际只是“少一个输入”；
- 没有配置 LLM 时仍然生成 `llm_summarize` 节点，运行必然 `missing_llm`。

更根本的是沙箱可见性：探索会话的工作目录就是会话目录，`fs_list(".")` 只能看到 `session.json / trace.jsonl / artifacts / scripts`。模型看不到项目仓库，却被要求“给项目所有 API 生成用例”，它只能反复列自己的文件。这不是模型笨，是**我们给它的世界太小**。

后来的 explore-first 闭环改成：

1. **Explore**：模型在沙箱里真实执行，优先调用已有原子，不够用时写脚本；
2. **Verify**：用确定性检查证明成功标准，不信模型自述；
3. **Crystallize**：把成功轨迹回溯成原子步骤，参数用真实调用值；
4. **Replay**：脱离 LLM 重放，必须同样成功；
5. **Canvas**：把已验证的流程投影到画布。

成功标准必须落成可执行检查，例如：

```json
{
  "intent": "列出当前目录文件并生成 reports/list.md",
  "success_criteria": [
    {"type": "file_exists", "path": "reports/list.md"},
    {"type": "text_contains", "target": "reports/list.md", "value": "session.json"}
  ]
}
```

配套的产品规则也很重要：站点别名是数据表，不是 if/else；显式 URL 优先于别名；未知站点必须返回 `missing_inputs`，**绝不编造 URL**；模板里的端点要标成 `assumption`，不能伪装成已验证事实。

一句话总结：**事实来自观察，计划来自事实。** 让模型先跑一遍，比让它先写五十步计划可靠得多。

## 六、坑五：模型说“成功了”不算成功

在探索式智能体里，最容易犯的错是拿模型的自然语言结论当验收。PanguVerse 后来把成功定义成三类可执行检查：文件存在、状态码匹配、文本包含。任一必检项失败，探索就不算成功；固化后的流程还要在不调用 LLM 的情况下重放一遍，失败就标记 `replay_failed`，不允许发布。

```python
checks = run_checks(criteria, artifacts)
if not all(c.ok for c in checks if c.required):
    return Verdict.failed(checks)

replay = run_graph(graph, env={}, llm=None)
if not replay.ok:
    draft.status = "replay_failed"
    block_publish(draft)
```

这条原则不仅适用于智能体，也适用于所有“AI 生成 + 自动执行”的系统：**LLM 负责探索与提议，确定性校验负责证明。** 两者混在一起，系统就会变成“模型觉得自己对，产品觉得能上线”。

## 七、坑六：没有 LLM 时的降级路径不是可选项

PanguVerse 工作台最早在没有配置 LLM 的情况下，仍然生成了 `llm_summarize` 节点，调试结果 4 passed / 1 failed `missing_llm`。用户并没有要求总结，系统却强行加了一个依赖外部 key 的节点。

修复后，无 LLM 时走 `web_open → web_get_text`，产出正文并用断言校验状态码；有 LLM 时才允许追加总结节点。实测“打开百度网页，获取今天的热点新闻”能跑出 5 条当天热搜，不需要任何模型 key。

这个选择在另外两个项目里也出现过：

| 任务 | 是否用 LLM | 实际方案 |
| --- | --- | --- |
| 接单报价 | 不用 | 确定性报价引擎，同一输入同一结果 |
| 简历知识库 | 不用 | 结构化 Markdown + 固定 schema 生成 |
| 网页正文提取 | 可不用 | 原子抓取 + 文本提取 + 断言 |
| 意图理解/探索 | 用 | LLM 提议，确定性校验兜底 |

结论很朴素：**能用规则、模板、检索解决的，不要用 LLM。** LLM 应该是最后一块拼图，而不是第一块。尤其涉及价格、权限、合规、可复现结果时，确定性方案优先。

## 八、坑七：上下文、沙箱与权限是一体三面

我一开始把“上下文工程”理解成 prompt 里塞多少资料。实际调试后发现，真正决定效果的是三件事：

1. **模型能看到什么**：沙箱目录、只读挂载、工具返回的摘要；
2. **模型能做什么**：脚本执行、网络访问、文件写入是否显式授权；
3. **模型能带走什么**：日志、产物、密钥是否脱敏。

PanguVerse 的 8KB prompt 上限一度被怀疑是 500 的原因，实测并不是；真正的问题是沙箱里没有项目代码。另一个风险是网页内容进入上下文后的提示注入：抓回来的 HTML 里可能藏着“忽略之前的指令”。因此，外部内容必须标注来源、限制长度、与系统指令隔离，涉及写操作时加人工闸门。

```python
context = {
    "system": system_rules,
    "repo_map": repo_map(top_k=20),
    "task_card": task,
    "observations": summarize(trace, max_chars=6000),
    "untrusted": {"web_excerpt": excerpt, "source": url},
}
```

**给模型看什么，是权限设计，不只是 prompt 设计。** 只读挂载、路径校验、脚本能力白名单、密钥打码，这些看起来不“AI”，却决定了系统能不能上线。

## 九、坑八：可观测性缺失，让“老是报错”无法归因

PanguVerse 用户反馈“LLM 老是报错”时，服务日志里几乎没有 LLM 错误行。我们只能从会话 JSON 和 trace 里反推，才分清三类原因：上游 5xx、单次调用逼近超时、总预算必然超时。没有结构化记录，这三件事会被混成一句“模型不稳定”。

后来每次 LLM 尝试都写入一条 `llm_call` 事件，至少包含：

| 字段 | 用途 |
| --- | --- |
| `step` / `attempt` | 定位是哪一步、第几次 |
| `payload_bytes` | 判断是否上下文过大 |
| `elapsed_ms` | 区分慢调用与网络故障 |
| `status` / `finish_reason` | 区分 5xx、空响应、截断 |
| `request_id` | 与供应商对账 |
| `max_tokens` / `effort` | 复盘预算配置 |

排查时按四层归因：

1. **上游**：5xx、限流、区域故障；
2. **本地配置**：key、base_url、代理、模型名；
3. **预算**：超时、步数、输出长度、并发；
4. **产品逻辑**：意图路由、模板假设、错误码。

**一条结构化调用记录，比“再试一次”有用得多。**

## 十、坑九：产品层的隐性失败最容易被忽略

有些问题不在模型，也不在请求，而在产品契约：

- 前端默认 `domain_pack=api_testing`，用户不选包就被强行路由；
- 显式包与意图矛盾时后端不纠正，静默生成无关套件；
- `capability_gap` 和 `missing_inputs` 混用，用户不知道该补什么；
- `param_gaps` 把带默认值的环境变量也标成缺口，一次报 9 条噪声；
- 单节点调试引用上游变量时抛 `TemplateError`，而不是提示“请用 from_start”；
- replan 应用后元数据仍是旧草案，页面显示旧假设。

修复的共同方向是：**错误要可行动，默认值要可解释，变更要可追溯。** API 契约里应该明确返回 `error_code`、`missing_inputs`、`missing_atoms`、`assumptions`、`autofilled`、`param_gaps`，前端才能给出“缺什么、去哪补、为什么”的提示，而不是一句“失败了”。

## 十一、上线前检查清单

- [ ] 每个 LLM 调用都有明确超时，且超时不超过剩余总预算。
- [ ] `max_tokens` 覆盖 reasoning + content，JSON 调用单独设预算。
- [ ] 识别并单独上报 `finish_reason=length`、空 `content`、空 `choices`。
- [ ] 只对瞬时错误重试，退避带抖动，保留供应商 `request_id`。
- [ ] `max_steps` 与 `total_timeout` 联动，剩余预算不足时能优雅收尾。
- [ ] JSON 解析有严格模式、容错提取、一次修复重试和确定性兜底。
- [ ] 模板中的端点、参数、域名标记为 assumption，不冒充已验证事实。
- [ ] 探索/生成前先观察真实环境，沙箱按最小权限只读挂载。
- [ ] 成功标准落成可执行检查，固化后能在无 LLM 情况下重放。
- [ ] 无 LLM、无网络、无外部 API 时都有明确降级路径。
- [ ] 每次调用写结构化 trace，能区分上游、配置、预算、产品四类原因。
- [ ] 外部内容标注为不可信，写操作有权限校验和人工闸门。
- [ ] 价格、权限、合规等确定性场景不使用 LLM 生成最终结果。
- [ ] 错误码可行动，默认值有说明，replan/变更后元数据同步更新。

## 十二、一个最小可用的架构

把上面的经验收拢，AI 应用的最小闭环可以写成：

```text
请求入口
  → 意图与输入校验（缺什么就明确说）
  → 上下文装配（规则 + 仓库地图 + 任务卡 + 观察摘要）
  → 模型调用（预算、超时、重试、结构化输出）
  → 工具/沙箱执行（最小权限、只读优先）
  → 确定性验证（断言、文件、状态码）
  → 产物与 trace 落盘
  → 人工审阅 / 发布
```

其中模型只占中间一段。前面是产品契约，后面是验证与可观测性。把这三段做扎实，模型换供应商、换版本、偶发 5xx，都不会让系统失去可控性。

## 结语：三条原则

1. **先观察，后计划。** 不要让模型在没看过真实环境时编步骤。
2. **模型提议，系统证明。** 成功必须由确定性校验证明，不能由模型自述定义。
3. **预算是系统属性。** 超时、重试、步数、输出长度、并发要一起设计。

大模型应用开发的难点，从来不是“会不会写 prompt”，而是能不能把一个概率性的远程服务，放进一个可解释、可验证、可回滚的工程系统里。坑踩得越多，越会发现：**真正让 AI 产品可靠的，是模型之外的那些确定性。**
