# 07 扩展机制：插件、渠道、技能与自动化

一个 Agent 框架能不能长期演进，取决于它把“新增能力”放在哪里。每来一个模型厂商、一个聊天平台、一个内部系统就改一次内核，最后一定变成无法维护的分支集合。OpenClaw 的扩展策略是：内核定义能力契约，插件实现厂商与渠道，技能承载流程知识，自动化负责时间维度。

## 要解决的问题

第一，渠道差异巨大：Telegram 是 bot token，WhatsApp 要 QR 配对，iMessage 走本地桥，Slack 有 Socket Mode 和 HTTP 两种入口。第二，模型与媒体能力差异更大，而且会持续变化。第三，流程知识不适合写进代码：同一套“如何做代码评审”的步骤，应该能被不同 Agent 复用、按需加载。第四，时间维度的工作（提醒、日报、巡检）需要持久化、可恢复、可观测，不能靠 Agent 自己 sleep。

## 机制拆解

**插件的四层。** 第一层 manifest + discovery：从配置路径、workspace、全局插件根、内置插件发现候选，读取 `openclaw.plugin.json` 或 bundle manifest。第二层 enablement + validation：内核决定插件是启用、禁用、阻断，还是占用 memory 这类独占 slot；这一步尽量只依赖 manifest/schema 元数据，不执行插件代码。第三层 runtime loading：原生插件在进程内加载并把能力注册到中央 registry；managed 实例通过 Node 加载 JS，必要时编译 TS；兼容 bundle 被规范化为 registry 记录，不导入运行时代码。第四层 surface consumption：内核其余部分从 registry 读取，暴露 tools、channels、provider setup、hooks、HTTP routes、CLI commands、services。

关键边界是：manifest/config 校验不执行插件代码；原生能力发现可以加载受信任的入口代码来构建“非激活”快照；真正的运行时行为来自 `register(api)` 且 `api.registrationMode === "full"`。失败注册会回滚并留在诊断里，不阻塞健康插件。

**能力所有权。** 插件是所有权边界，不是大杂烩。公司插件通常拥有该公司所有 OpenClaw 表面（模型、embedding、语音、图像、搜索）；功能插件拥有完整功能面，但消费核心能力契约，而不是直接 import 厂商插件。分层是：核心能力层负责编排、策略、回退、配置合并、投递语义与类型契约；厂商插件层负责具体 API、认证、模型目录；渠道/功能插件层负责把能力呈现在某个表面。新增一个领域时，第一问不是“哪个厂商硬编码”，而是“核心契约是什么”。

**渠道。** 渠道可以是 bundle、官方插件或外部插件；Gateway 拥有连接与账号状态，渠道插件负责协议适配。一个渠道可以有多个 `accountId`，binding 按 `(channel, accountId, peer)` 路由到 Agent，最具体匹配优先；多账号场景下 `accountId` 是隔离边界。群聊默认要求 mention 或 allowlist，私聊用 allowlist 与配对控制谁能进来。渠道插件应消费共享能力（语音、媒体、消息投递），而不是各自重造一套。

**技能。** 技能是 `SKILL.md` 指令包，加载优先级从高到低是：workspace `skills/`、workspace `.agents/skills`、个人 `~/.agents/skills`、managed/local、workshop、bundled、extraDirs 与插件技能。同名时高优先级胜出。`SKILL.md` 至少要有 `name` 和 `description`；系统提示只放 name/description/location 的目录，正文要等模型按需 `read`。所以技能不是“越多越好”：每个技能条目都占提示预算，长流程应放在正文而不是描述里。技能还支持 gating、agent allowlist、快照刷新与沙箱同步；工作区技能在沙箱里读的是物化副本，不是宿主原路径。

**自动化。** cron 运行在 Gateway 进程内，不是模型里；Gateway 不在，计划不会触发。Job 定义、运行状态、历史都存在共享 SQLite，重启不丢。它支持一次性 `--at`、间隔、cron 表达式与入站 webhook；一次性任务成功后自动删除，失败则保留为 disabled 供检查。每个 run 有 wall-clock 预算：agent-turn 默认由调度器 60 分钟看门狗兜底，命令任务 10 分钟，脚本 5 分钟。heartbeat 是系统拥有的环境监控自动化，默认每 30 分钟跑一次 main-session turn，可以用很小的 scratch 上下文提示需要关注的事；它不是通用调度器，独立计划应建独立 job。

Webhook 是外部服务调用 OpenClaw 的 HTTP 入口，默认关闭；启用后要配专用 token、路径、允许的 Agent，并建议用 `Idempotency-Key`。`/hooks/agent` 返回 200 只代表接纳，不代表模型完成；需要终态可加 `waitForCompletion: true`。内部 hook（`HOOK.md`）则是 Gateway 进程内的事件脚本，和 webhook、插件 hook 是三套不同机制。

**节点。** node 以 `role:"node"` 连同一台 WS 服务器，声明 caps/commands/permissions，暴露 `camera.*`、`screen.record`、`location.get`、`device.*` 等命令。配对是设备级的，审批在设备配对存储里；node 还能托管 MCP server、技能和本地模型推理，或承载 worker 会话。节点扩展了 Agent 的物理触达，也扩大了攻击面，所以有 command policy、平台默认 allowlist 和危险命令 opt-in。

## 设计取舍

插件在进程内运行，换来了低延迟和直接访问 registry，代价是信任边界与 Gateway 相同：一个恶意插件可以做进程能做的任何事。所以文档反复强调“安装前审查代码”“只装可信来源”，这不是客套话，而是架构事实。

技能用“目录常驻、正文按需”换 token，代价是模型可能不读、或读错技能；描述写得越模糊，按需加载越不可靠。渠道与厂商插件用能力契约换可组合性，代价是核心团队要维护契约的稳定性，插件作者要理解分层。

cron 放在 Gateway 内，换来了零外部依赖和统一恢复，代价是 Gateway 停机就不触发，且不适合跨机分布式调度。node 换来了设备能力，代价是配对、权限、版本偏移和网络可达性都变成运维问题。

## 实践建议

第一，把插件当依赖管理：固定版本、审查来源、关注 manifest 权限，生产环境不要 `--link` 任意本地目录。第二，新增厂商能力时先找核心契约，不要在渠道插件里直接调厂商 SDK。第三，技能描述写“何时用”，正文写“怎么做”，长示例放正文；定期清理不再使用的技能，减少目录开销。第四，周期任务用 cron，不要用 `exec` sleep 循环或反复轮询；需要未来提醒就建一次性 job。第五，webhook 用独立 token、限制 allowedAgentIds、带幂等键，并区分“已接纳”和“已完成”。第六，node 命令按平台最小化 allowlist，摄像头、屏幕、位置这类能力要有明确的使用边界。
