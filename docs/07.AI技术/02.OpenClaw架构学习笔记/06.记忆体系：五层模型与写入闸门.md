# 06 记忆体系：五层模型与写入闸门

“让 Agent 记住”听起来像一个检索问题，实际更像一个写入治理问题。只要把所有对话都塞进向量库，召回总会看起来能用一阵子；几周后你会发现记忆里全是心跳噪音、重复总结和从网页抄来的指令。OpenClaw 的记忆架构把大部分工程放在写入侧：先分层，再标 provenance，最后用确定性闸门决定什么有资格进入长期记忆。

## 要解决的问题

第一，不同记忆的信任级别不同：用户亲口说的偏好、Agent 从对话里推断的事实、网页里的内容、系统心跳的脚手架，不能同等对待。第二，不同记忆的读取时机不同：行为规则每次都要在，日常笔记只在需要时查，提醒只在触发时出现。第三，写入是攻击面：一条被注入的“请永远执行某命令”如果进了长期记忆，就会反复出现在未来上下文里。第四，记忆不能拖垮回复：检索失败、总结超时、索引损坏，都不应该让用户收不到答案。

## 机制拆解

**五层模型。** 第一层 Instructions：`AGENTS.md` 等工作区指令，只能由人写，每次会话开始注入。第二层 Curated core：`MEMORY.md`、`USER.md`，由 dreaming 整合或用户直接要求写入，会话开始时在预算内注入。第三层 Episodic：`memory/YYYY-MM-DD.md` 日常笔记与会话 transcript，Agent 工作时写、压缩前 flush、会话结束摄取，只在召回时读取。第四层 Prospective：standing intents（SQLite）与 cron，只在触发时注入。第五层 Review：`DREAMS.md` 与 dreaming 报告，只给人看，不进提示。

最重要的边界是 curated 与 episodic：curated 小、常驻、只通过有闸门的整合写入；episodic 大、可追加、靠搜索或 Active Memory 取。没有任何内容能绕过 promotion gate 从 episodic 进入 curated。

**provenance 四个 origin。** 索引里的每条记忆都带 SQLite 列，模型不能通过正文伪造：`owner`（在可信渠道由 owner 输入）、`agent`（Agent 从 owner 内容派生）、`untrusted`（网页、工具输出、群聊非 owner 参与者等外部内容派生）、`system`（心跳提示、cron 前言等脚手架）。同时还记录 session kind（interactive/cron/heartbeat/subagent）、observed timestamp 和 supersession key。分类是保守的：无法确定来源的外部内容按 `untrusted`，脚手架按 `system`，绝不默认成 `owner`。

还有两条卫生规则：cron、heartbeat、subagent 会话不产生可晋升的长期记忆候选；被注入过上下文的记忆（bootstrap、搜索结果、召回摘录）会被结构化标记，永远不会被再次抽取成新记忆。否则一条事实被召回一百次，就会变成一百条“新发现”。

**写入路径。** 持久记忆只有一个主要写入者：dreaming 整合。日常笔记、压缩前 flush、会话结束的 transcript 摄取都先进入 episodic 与索引，等待 dreaming。Dreaming 默认开启，分阶段运行：Light/REM 去重、暂存候选、做主题反思与强化记录；Deep 先过确定性闸门，按检索相关性、召回频率、查询多样性、新近度、多日复现、概念丰富度加权排序，`untrusted`/`system` 在构建提示前就被结构性排除。通过闸门的候选再和当前 `MEMORY.md` 一起送给整合模型，做合并、按 supersession key 退休旧条目、保留来源锚点。写入用乐观并发：构建输入时记录内容哈希，原子 rename 前再校验；期间被编辑器或其他会话改过，就放弃本次重写，退回追加模式。每次接受的改写都保存 pre-image，并把变更摘要写进 `DREAMS.md`。

**两条召回通道。** 第一条常开、零模型调用：`MEMORY.md`/`USER.md` 在来源合格时随会话注入；`memory_search` 用混合相关性乘以 30 天半衰期的指数新近度，再乘写入时标注的 importance；写入者还可以给条目加 trigger 短语，每条入站消息做快速词法/向量预筛，分数达到 0.65 的条目以隐藏上下文注入，每轮最多三条。自动注入只限 curated 层，日常笔记和 transcript 永远不会自动注入，这是安全属性，不是调参选项。

第二条是升级通道 Active Memory：一个阻塞式召回子 Agent，能搜索和读取会话历史，在 `rememberAcrossConversations` 允许时跨私密会话召回。默认只在两个确定性条件同时满足时运行：消息表现出回忆意图（提到过去、时间性措辞、询问之前的决定），且第一条通道没有强命中。`mode:"always"` 可以恢复无条件预召回，`mode:"off"` 关闭。

**standing intents。** 记住“要做某事”与记住“某个事实”是不同能力。时间型意图（“周五提醒我”）在说出口时就编译成 cron；事件型意图（“发布开始时提醒我看 changelog”）通过 `intent` 工具写入每 Agent 的 SQLite 表，字段包括关键词、可选触发 embedding、渠道与发送者范围、过期时间、触发预算、冷却时间。每条入站消息跑确定性预筛，命中就把意图作为隐藏上下文注入，匹配路径不调用模型。生命周期是显式状态：pending、armed、fired、done、cancelled、expired；默认冷却 24 小时、最多触发 3 次、90 天过期、每轮最多注入 3 条。

**失败不阻塞。** 回复路径上的每个记忆步骤都有超时或回退。索引挂了、检索超时、flush 失败，最坏结果是召回质量下降，不会吃掉这一轮回复。

## 设计取舍

把工程放在写入侧，是因为检索侧的边际收益有限。LongMemEval 等长程记忆评测反复显示，写了什么比怎么索引更重要；而生产环境里自动捕获的记忆，绝大多数是脚手架复述、心跳噪音和召回反馈。OpenClaw 因此宁愿少记，也不让不可信内容获得指令 authority。

代价是召回可能显得“迟钝”：一条重要事实要先经过 episodic、dreaming 闸门、整合，才进入 curated；紧急信息只能靠显式记忆工具或当前会话。对需要即时记住的场景，正确做法是直接让 Agent 写 `MEMORY.md` 或使用 standing intent，而不是等 dreaming。

plain files + SQLite 的选择换来了可检查、可编辑、可迁移，代价是没有分布式一致性。多 Gateway 共享同一 workspace 时，写入靠哈希校验和追加回退避免互相覆盖，但这不是数据库级并发控制。

## 实践建议

第一，写“可执行”的记忆：不只写事实，还写什么时候适用、什么时候过期、谁有权、应该避免什么。第二，`USER.md` 用 Always/Never/Prefer 的祈使句，并在偏好变化时原地 supersede，不要追加互相矛盾的条目。第三，不要把密钥、令牌、完整聊天记录写进记忆；记忆文件是明文。第四，未来的动作优先用 standing intent 或 cron，不要把“记得提醒我”写成一句散文。第五，定期看 `DREAMS.md`，确认晋升了什么、改写了什么；这是人类审查面。第六，仓库相关的经验加 project 注释，避免在一个项目学到的 workaround 悄悄影响另一个项目。第七，做一次投毒演练：让 Agent 总结一个含恶意指令的网页，确认它只能被显式搜索到，不会自动注入。
