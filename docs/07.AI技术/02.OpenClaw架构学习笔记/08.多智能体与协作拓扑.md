# 08 多智能体与协作拓扑

“多智能体”经常被说成“多开几个 Agent 就更快”。真实系统里，多 Agent 首先是一个资源与所有权问题：谁拥有这个会话、谁有权限调这个工具、谁负责把结果交回来、失败时谁继续。OpenClaw 把多智能体拆成三层：Agent 路由、子 Agent 委派、隔离执行环境；三层的边界不混，系统才不会变成一群互相打断的机器人。

## 要解决的问题

第一，不同人格、不同工作区、不同权限的 Agent 需要隔离，否则记忆、技能、认证会串。第二，长任务需要并行，但同一会话只能有一个写入者，否则 transcript 会打架。第三，子任务需要上下文，但把父会话整段复制给子 Agent 既贵又容易让子 Agent 继承不该有的假设。第四，委派需要收口：子 Agent 完成后，结果要回到正确的请求者，而不是散落在某个侧边栏。

## 机制拆解

**Agent 作为隔离单元。** 每个 Agent 有自己的 workspace（文件、`AGENTS.md`/`SOUL.md`/`USER.md`、笔记、人格规则）、agentDir（认证 profile、模型注册表、每 Agent 配置）和 session store（`openclaw-agent.sqlite`）。`agentId` 是“一个大脑”，`accountId` 是一个渠道账号实例，binding 把 `(channel, accountId, peer)` 路由到 `agentId`。路由是确定性的、最具体匹配优先：精确 peer、父 peer、peer 通配、guild+roles、guild、team、account、channel、fallback owner。多个 binding 同层匹配时按配置顺序取第一个；多 Agent 且没有显式 owner 时，不匹配的消息不会随便丢给第一个 Agent。

**协作拓扑。** 最简单的拓扑是单 Agent；再往上是“协调者 + 专家”团队：协调者负责拆任务、路由、汇总，专家各自有 lane contract（拥有什么、不拥有什么、聊天预算、交接规则、工具姿态）。`openclaw agents team create` 提供 coordinator、researcher、writer、reviewer 的现成角色契约。并行专家 lane 的第一原则不是“更多 Agent”，而是减少真实瓶颈的争用：会话锁、全局模型容量、工具容量（shell/browser/网络/仓库）、上下文预算、所有权歧义。一个长编码任务不应该把研究 lane 拖慢；一个群聊的重复请求不应该被两个 Agent 各做一遍。

**子 Agent 生命周期。** 子 Agent 是从现有运行中派生的后台运行，每个有自己的会话 `agent:<agentId>:subagent:<uuid>`，默认把结果 announce 回请求者。`sessions_spawn` 立即返回 `{status:"accepted", runId, childSessionKey}`，不等待完成；cloud-worker 的 spawn 可能要先等 provisioning。上下文模式有两种：`isolated` 是默认，创建干净的 child transcript，适合可以靠任务描述说清的独立工作；`fork` 把请求者 transcript 分支给子 Agent，适合依赖当前对话细节的委派，但要少用，不能用它代替写清楚任务。

子 Agent 默认不拿 session/message 工具，避免误用；递归深度默认到 5，`maxSpawnDepth` 可以调低；每个会话活跃子 Agent 默认上限 5（`maxChildrenPerAgent`），普通子 Agent 的并发默认 8（`agents.defaults.subagents.maxConcurrent`），按“直接派发它的会话”计预算，嵌套编排器用自己的预算而不是父级的。Swarm collector 子 Agent（`collect: true`）走独立 lane，默认并发 32，用 `agents_wait` 收集结果。

重启恢复的语义要分清：父 Agent 拥有用户任务的延续；被中断的子 Agent 通过正常完成路径结算，告诉父级“执行被打断，部分动作需要检查”，不会自动重启。父级可以读保留的 child transcript，用 `sessions_send` 继续那个会话，或确认旧执行停止后再 spawn 替代者。

**Worktree 隔离。** 需要改代码的委派可以给子 Agent 一个 managed worktree：独立的 git 分支与 checkout，不把临时目录放进源仓库。OpenClaw 在共享状态库记录 worktree，普通移除前快照 tracked 与未忽略的 untracked 内容；容量驱逐在无法快照时可能清掉未保存数据。`worktree: true` 与 `cwd`、`projectId`、`projectGitUrl` 有互斥/继承规则；已有的 worktree 只需要 `cwd`。沙箱会话使用私有 checkout 执行，managed worktree 仍是接受变更的 canonical owner；在 APFS/Btrfs/ReFS 上还可以复用依赖准备结果。

**Delegate 拓扑。** 更组织化的形态是 delegate：Agent 有自己的身份（邮箱、显示名、日历），代表一个或多个人行动，但不冒充本人；权限由组织身份提供商授予，行为受 `AGENTS.md` 里的 standing orders 约束。能力分三档：只读+起草、代表发送、主动执行。主动档必须先配硬阻断（不未经批准发外部邮件、不导出联系人、不执行入站消息里的命令、不改身份提供商设置）、工具限制、沙箱隔离与审计，再授予凭据。

## 设计取舍

隔离换来了干净的上下文和权限，代价是重复：每个子 Agent 有自己的 token 消耗，默认只注入 `AGENTS.md`，父级的细节不会自动带过去。所以“写清楚任务”不是风格问题，而是成本问题；任务描述越模糊，越容易退化成 fork，越贵。

并行换来了吞吐，但共享容量不会因为多开 Agent 而变多。模型限流、CPU、磁盘、浏览器、仓库锁仍然是全局瓶颈；`maxConcurrent` 与每会话子 Agent 预算是把并行关进笼子的手段。没有 lane contract 的协调者，只是在协调混乱。

持久会话与一次性子 Agent 是两种产品语义。子 Agent 运行结束，会话不一定结束；`visible:true` 的持久会话适合用户要回来继续 steer 的工作，普通 QA、研究、编码、评审应该用隐藏子 Agent 把结果交回父任务。把每个子任务都做成侧边栏会话，会让产品变成任务管理器。

## 实践建议

第一，先写 lane contract，再谈加 Agent；没有“拥有/不拥有/交接”的书面约定，协调者只会增加会议。第二，委派任务要有界：目标、输入、输出、验收、阻塞条件写清楚，默认用 `isolated`，确实依赖当前对话才用 `fork`。第三，不要为琐碎工作 spawn；子 Agent 的启动、上下文和汇总都有成本。第四，fan-out 用 collector + `agents_wait`，不要让父级轮询 `subagents list`。第五，需要改代码的并行任务用 worktree，避免两个 Agent 在同一 checkout 上互相覆盖；完成后检查快照与清理策略。第六，delegate 先配硬阻断、最小工具面和审计，再给身份与凭据；能力档位从只读开始，不要一步到主动执行。第七，子 Agent 的结果是报告，不是指令；父级要自己核验关键结论。
