# 05 工具、沙箱与权限边界

Agent 的能力来自工具，风险也来自工具。一个能读文件、跑 shell、发消息、操作浏览器的 Agent，如果权限边界只写在提示词里，那么一次提示注入就可能让它越过所有约定。OpenClaw 的做法是把“在哪里跑”“能调用什么”“能不能提权”拆成三个独立控制面，并让运行时而不是提示词来做最终裁决。

## 要解决的问题

第一，工具的风险不同：读网页和删数据库不是一回事，不能用一个“允许/禁止”一刀切。第二，执行位置不同：同样一个 `exec`，在 Gateway 主机、沙箱容器、配对 node 上跑，影响面完全不同。第三，审批体验不同：全自动、白名单、每次询问、完全禁止，适用于不同信任级别。第四，工具目录会膨胀：几十上百个 schema 全塞进提示，既贵又容易误选。

## 机制拆解

**三层控制。** 文档把边界拆得很清楚：Sandbox 决定“工具在哪里跑”；Tool policy 决定“哪些工具可用/可调用”；Elevated 是仅针对 `exec` 的“逃出沙箱”开关。三者独立，不能互相替代。Sandbox 由 `agents.defaults.sandbox.mode` 控制：`off` 不沙箱，`non-main` 只沙箱非 main 会话（群聊/频道常落在这里），`all` 全部沙箱；`workspaceAccess` 决定沙箱能看到 `none`、`ro` 还是 `rw`。如果 operator role 要求 `sandbox:"required"`，它覆盖 Agent 配置，且不能用 elevated 或 host 覆盖绕过，沙箱起不来就失败关闭。

**Tool policy 的五层。** 依次是 tool profile、provider tool profile、全局/每 Agent 的 `allow`/`deny`、provider 级 `allow`/`deny`、沙箱内 tool policy。规则很简单但容易记反：`deny` 永远赢；`allow` 非空时，其余全部视为禁止；tool policy 只按名字过滤工具，不检查 `exec` 内部的副作用。也就是说，允许了 `exec`，再禁止 `write`/`edit` 并不会让 shell 变成只读。常用简写是 `group:*`，例如 `group:runtime` 包含 `exec`、`process`、`code_execution`，`group:fs` 包含读写补丁工具；只读 Agent 必须同时 deny `group:runtime`，否则 shell 仍可写文件。

**exec 审批。** `tools.exec.mode` 是首选的策略面：`deny` 禁止主机 exec；`allowlist` 只跑白名单；`ask` 用白名单并在未命中时询问；`auto` 对确定性白名单直接放行，对合格未命中做 `allow`/`deny`/`ask` 审查；`full` 不做常规策略提示。`exec.ask` 另有 `off`、`on-miss`、`always`，`askFallback` 决定没有 UI 或超时时怎么办，默认 `deny`。审批不是每用户认证边界，也不是只读策略；它降低误执行风险，但一旦批准，命令仍按目标主机的文件权限执行。

审批流程也做了防篡改：Gateway 审批的命令会绑定每个解析出的命令段可执行文件，审查前记录、启动前复核；受保护可执行文件用真实路径身份，可写可执行文件还加内容哈希。node 的审批请求带 canonical `systemRunPlan`，包含 command、cwd、session 上下文；批准后 Gateway 转发存储的计划，调用方事后修改 command/cwd/agentId/sessionKey 会被丢弃，env 变更会被判为不匹配。脚本和解释器调用还会尽量绑定一个具体本地文件操作数，文件在批准后变化就拒绝执行。

**deferred tools 与 tool search。** 当工具有很多时，OpenClaw 默认启用结构化 Tool Search：模型先看到一份受策略过滤的能力目录，再用 `tool_search`、`tool_describe`、`tool_call` 按需发现和调用。目录按名字排序、限制 18000 字符，只包含已授权目录项；直接工具和核心编码原语仍然可见。好处是提示更小、误选更少；代价是多出发现轮次，小目录反而可能更贵，所以文档明确建议小目录可以设 `tools.toolSearch: false`。

**钩子拦截。** 插件可以在 `before_tool_call` 里检查参数并返回 `{ block: true }`，这是终态，会阻止更低优先级 handler；`{ block: false }` 是空操作，不会清除之前的 block。`before_prompt_build` 可以在支持的运行时用 `toolsAllow` 收窄本轮工具面；`message_sending` 的 `{ cancel: true }` 同样是终态。内部 hook 是受信任代码，以 Gateway 进程权限运行，不是沙箱脚本。

## 设计取舍

把权限放在运行时而不是提示词，是这套设计最重要的选择。提示词可以告诉模型“不要删库”，但只有 tool policy、sandbox、审批能真正阻止。代价是配置复杂：五层策略、多个 mode、按 Agent/按 provider 的覆盖，很容易配出一个“以为禁了其实没禁”的组合。`openclaw sandbox explain` 和 `exec-policy show` 就是为这个复杂度准备的。

审批换来了安全，但牺牲了自动化流畅度。`auto` 模式试图折中：确定性白名单直接跑，只有边缘情况才审查；它适合可信操作员，不适合把 Gateway 暴露给不可信用户。`full` 最省事，但它不是“更聪明的安全”，而是把风险转移给部署边界。

Tool Search 是用轮次换 token。目录越大越划算，目录越小越可能倒贴；它不适合对延迟极敏感、工具很少的场景。沙箱则用隔离换性能：容器启动、文件投影、依赖准备都有成本，因此它更适合高风险或不信任的会话，而不是每一次普通对话都强行套上。

## 实践建议

第一，按信任级别分层：面向外部内容的 Agent 开沙箱，面向内部自动化的 Agent 用 allowlist，交互式个人助手才考虑 `auto`。第二，只读 Agent 同时 deny `group:runtime` 和写文件工具；不要只禁 `write` 而留下 `exec`。第三，`exec` 白名单要配 `argPattern` 之类的参数约束，否则“允许 git”可能等于允许任意 git 子命令。第四，不要把 `gateway.auth.mode:"none"` 和宽松 exec 策略一起用在非私有入口，也不要把控制面端口直接映射到公网。第五，用 `openclaw logs` 查 `agents/tool-policy` 审计条目，确认是哪条规则挡了工具，而不是反复改提示词；日志里会给出规则标签和配置键。第六，插件 hook 能看消息与工具参数，安装前要像审查代码一样审查它，并优先使用官方签名或固定版本的插件。
