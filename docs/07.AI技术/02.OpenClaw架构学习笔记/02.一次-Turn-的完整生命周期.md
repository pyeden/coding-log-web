# 02 一次 Turn 的完整生命周期

在聊天框里按下发送，看起来只是一次请求。但在 Agent 系统里，这条消息要经过受理、排队、恢复工作区、组装上下文、调用模型、执行工具、流式回传、整形回复等多个阶段，任何一段都可能超时、失败或被取消。理解 turn 的生命周期，是定位“为什么它卡住了”“为什么回复重复了”“为什么工具没执行”的前提。

## 要解决的问题

Agent 运行有三个不同于普通 API 的特征。第一，它很长：一次运行可能几十秒到几小时，不能用一个 HTTP 请求包住。第二，它会行动：工具调用有副作用，失败重试不能简单重放。第三，它会流式输出：用户期望看到进度，但增量事件可能乱序、重复或中断。

因此需要一条明确的运行主线，把“受理”和“完成”分开，把“等待”和“执行”分开，把“可重试的错误”和“终态失败”分开。OpenClaw 的 agent loop 就是这条主线。

## 机制拆解

**第一阶段：受理。** 客户端调用 `agent` RPC。服务端校验参数、解析会话（`sessionKey` 或 `sessionId`）、持久化会话元数据，然后立刻返回 `{ runId, acceptedAt }`。这个返回值只表示“已受理”，不表示模型已经开始，更不表示任务完成。`agent.wait` 是另一个入口，用来等待某个 `runId` 的终态。

**第二阶段：命令层。** `agentCommand` 负责这一轮 turn：解析模型与 thinking/verbose/trace 默认值，加载 skills 快照，调用 `runEmbeddedAgent`；如果内嵌循环没有发出 lifecycle 的 end/error，它负责补一个兜底的 lifecycle 事件。这一层是“策略与装配”，不直接跑模型。

**第三阶段：内嵌运行时。** `runEmbeddedAgent` 做几件事：通过 per-session 与全局队列串行化运行；解析模型与认证 profile；构建 OpenClaw 会话；订阅运行时事件；把 assistant/tool 增量转成事件；执行运行超时并在到期时中止；最后返回 payload 与 usage 元数据。对于 Codex app-server 的 turn，provider 的存活与 `turn/completed` 由原生 Codex 负责，静默期和 assistant 输出都不会提前结束 turn。

**第四阶段：事件桥接。** `subscribeEmbeddedAgentSession` 把运行时事件映射到 `agent` 流：工具事件进 `stream:"tool"`，assistant 增量进 `stream:"assistant"`，生命周期进 `stream:"lifecycle"`，phase 为 `start`、`finishing`、`end`、`error`。客户端看到的是这三条流，而不是模型的原始 SSE。

**第五阶段：会话与工作区准备。** 运行前会解析并创建工作区；沙箱运行可能把工作区重定向到 sandbox 根目录；加载或复用 skills 快照并注入环境与提示；解析 bootstrap/context 文件并注入系统提示；在开始流式输出前准备好 transcript 目标与 writer claim。后面的重写、compaction、截断都要经过同一个事务内的 writer-claim 校验。

**第六阶段：prompt 组装。** 系统提示由基础提示、skills 提示、bootstrap 上下文和本轮覆盖项组成，并受模型上下文上限与 compaction reserve 约束。历史消息、工具结果、附件和运行时上下文一起进入模型请求。这里的原则是：能在运行前确定的稳定内容放前面，易变的每轮内容放后面，以利于前缀缓存。

**第七阶段：工具执行与回复整形。** 工具参数先按 schema 校验；执行过程发出 start/update/end 事件；结果在记录和发送前会做大小与图片载荷的清洗。消息类工具的发送会被跟踪，以避免 assistant 的确认文本与真实发送重复。最终 payload 由 assistant 文本、可选的 reasoning、工具摘要和错误文本组成；精确的 `NO_REPLY` 会被过滤，重复的消息工具结果会被移除。若一轮在工具批次结束后仍没有可交付答案，运行时会做一次不重复执行工具的 finalization pass。

**超时与重试。** 这里有四个容易混淆的时间：`agent.wait` 默认 30 秒，只是等待超时，不会停止底层运行；Agent runtime 默认 172800 秒（48 小时），是执行预算，到期会 abort；模型 idle timeout 云端默认 120 秒、自托管 300 秒；provider HTTP 超时由 `models.providers.<id>.timeoutSeconds` 控制。重试按请求而不是按整个流程：限流最多 10 次总尝试，其他瞬时故障在 90 秒窗口内最多 8 次重试，退避从约 1 秒开始指数增长并加抖动；已完成的有副作用步骤不会因为重试被重放。

## 设计取舍

把受理与完成分开，是为了让客户端在长任务里保持可交互：先拿到 `runId`，再通过事件流和 `agent.wait` 观察。代价是客户端必须理解“accepted 不是 done”，并处理“受理成功但执行失败”的中间态。

流式输出换来了体验，但带来了顺序与去重问题。OpenClaw 用每个 run 独立序号、快照纠正和终态事件来解决；相邻文本增量可以合并，但快照、内容块变化、reasoning、工具和终态事件必须保持边界。这个设计不适合把增量当唯一事实来源的客户端，正确做法是“增量用于展示，历史用于对账”。

超时分层是为了让不同故障在正确的层级被处理：等待超时不该杀任务，模型空闲超时该重试，执行预算到期才该 abort。很多系统把这三个时间合成一个，结果要么误杀长任务，要么让卡死的请求永远占着车道。

## 实践建议

第一，调用 `agent` 后不要轮询数据库猜状态，用 `agent.wait` 或事件流；等待超时后可以再次 wait 同一个 `runId`，不要重新发一条消息。第二，给长任务设置合理的 `agents.defaults.timeoutSeconds`，不要用无限预算掩盖卡死；慢的本地模型优先调 provider 超时，而不是直接放大整个运行预算。第三，工具要尽量幂等，尤其是发送、写入、支付这类操作；重试策略只能保证“当前步骤重试”，不能替你消除副作用。第四，客户端要把 lifecycle 的 `end` 与 `error` 都当终态，并在断线后重新拉取历史对账。第五，排障时先分清是排队、准备、模型还是工具阶段，再看对应日志，不要一上来就怀疑模型。
