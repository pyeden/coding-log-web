# 02 工作流模型：节点、连接与表达式

工作流是 n8n 里唯一被完整持久化的「源文件」。它是一段 JSON：节点列表、连接表、若干设置。看懂这段 JSON，你就能回答一连串平时只能靠猜的问题——为什么导入后某条线断了、为什么 IF 的 false 分支从不执行、为什么表达式在第一个 item 上正常、在第二个 item 上取到空值。这一章把这份「图纸」拆成三部分：节点（做什么）、连接（谁交给谁）、表达式（参数怎么算出来）。

## 要解决的问题

**为什么手动改 JSON 后工作流「线断了」？** 因为连接表的键是节点名，不是节点 id。改了 `nodes[].name` 却没同步 `connections` 的键，图里就出现孤儿节点，画布上看起来节点还在，但没有入边。

**为什么一个分支只处理了部分数据？** 因为 n8n 的执行单位是 item 数组，不是「一次运行」。节点输出多少个 item、以什么顺序、哪些 item 被条件过滤掉，全都体现在节点的输入输出数组里，而不是在连线本身。

**为什么表达式有时是字符串、有时是数字？** 因为 <code v-pre>{{ }}</code> 里执行的是 JavaScript 表达式，返回值保留类型；而整个参数如果是纯文本夹表达式，结果会被拼成字符串。这个差别在拼接 URL、比较数字、传布尔开关时会直接改变行为。

## 核心概念与术语

| 术语 | 在 JSON 中的位置 | 说明 |
| --- | --- | --- |
| 节点数组 | `nodes[]` | 每个元素是一个节点实例，顺序不代表执行顺序 |
| 节点名 | `nodes[].name` | 图内的唯一标识，连接表用它做键，重名会出错 |
| 节点类型 | `nodes[].type` | 形如 `n8n-nodes-base.if`，决定加载哪个实现 |
| 类型版本 | `nodes[].typeVersion` | 参数语义的版本锚点，升级节点即迁移语义 |
| 参数 | `nodes[].parameters` | 该节点的配置，值可以是固定值或表达式 |
| 位置 | `nodes[].position` | 画布坐标 `[x, y]`，只影响可读性 |
| 凭据引用 | `nodes[].credentials` | 形如 `{ "类型": { "id": "...", "name": "..." } }` |
| 连接表 | `connections` | 源节点名 → 输出槽 → 目标节点列表 |
| 输出槽 | `connections[x].main[i]` | `i` 是输出的序号，0 起 |
| 设置 | `settings` | 执行顺序、时区、错误工作流等 |
| 表达式 | <code v-pre>{{ ... }}</code> | 在运行时用 JS 求值，能访问内置变量 |

一个容易忽略的事实：**`nodes[]` 的数组顺序与执行顺序无关**。执行顺序由连接拓扑和 `settings.executionOrder` 决定，画布上的左右位置只是视觉排序。把节点拖到左边不会让它先跑。

## 机制拆解：连接表是三层数组

先看最小骨架：

```json
{
  "name": "order-sync",
  "nodes": [
    {
      "id": "n1",
      "name": "Webhook",
      "type": "n8n-nodes-base.webhook",
      "typeVersion": 2,
      "position": [0, 0],
      "parameters": { "path": "order", "httpMethod": "POST" }
    },
    {
      "id": "n2",
      "name": "IF",
      "type": "n8n-nodes-base.if",
      "typeVersion": 2,
      "position": [220, 0],
      "parameters": {}
    },
    {
      "id": "n3",
      "name": "Paid",
      "type": "n8n-nodes-base.set",
      "typeVersion": 3,
      "position": [440, -80],
      "parameters": {}
    },
    {
      "id": "n4",
      "name": "Unpaid",
      "type": "n8n-nodes-base.set",
      "typeVersion": 3,
      "position": [440, 80],
      "parameters": {}
    }
  ],
  "connections": {
    "Webhook": {
      "main": [
        [{ "node": "IF", "type": "main", "index": 0 }]
      ]
    },
    "IF": {
      "main": [
        [{ "node": "Paid", "type": "main", "index": 0 }],
        [{ "node": "Unpaid", "type": "main", "index": 0 }]
      ]
    }
  },
  "settings": { "executionOrder": "v1" }
}
```

`connections` 的结构可以读成三层：

```text
connections[源节点名] = {
  main: [                      // 输出类型；绝大多数节点只有 main
    [ 目标A, 目标B ],           // 输出 0 的全部目标（这里就是「扇出」）
    [ 目标C ]                   // 输出 1 的全部目标（IF 的 false 分支）
  ]
}
```

三层各有语义，混淆任何一层都会得到「看起来连上了但数据没到」：

1. **第一层（键）是节点名**。改名必须同步，否则断链；同名节点不允许存在。
2. **第二层（`main` 的下标）是源节点的输出序号**。IF、Switch 这类节点有多个输出，序号即分支。
3. **第三层（数组内元素）是目标列表**。同一个输出连多个节点，就是扇出，每个目标都会收到同样的 item 副本；元素的 `index` 是目标节点的**输入**序号，多输入节点（如 Merge）才用得上。

扇出还有一个常被误解的细节：连到多个目标的不是「同一份 item 的引用」，而是会被各自消费的数据副本。上游节点只执行一次，输出一次；下游每个目标节点各自收到这批 item，并各自产生自己的输出。因此「一个输出接三个节点」不等于「三份独立计算」，而是「一次产出、三处消费」。如果其中一个目标修改了 item 的字段，默认不会影响另一个目标看到的数据，但共用二进制引用时要小心内存与清理时机。

分支的执行并不保证并行。n8n 会按一定顺序逐个推进分支，遇到需要汇聚的节点（如 Merge）会等待。`settings.executionOrder` 的取值改变了这个顺序语义（旧版与新版的差异正是这里的坑），迁移老工作流时要确认它。

表达式是第二块拼图。关键前提是：**表达式是按 item 求值的**。一个节点收到 100 个 item，它的参数表达式会被求值 100 次，每次的 `$json` 指向当次 item。因此 <code v-pre>{{ $json.id }}</code> 天然是「批量映射」，不需要你写循环；写成 <code v-pre>{{ $items()[0].json.id }}</code> 反而会让 100 个 item 全部拿到第一条的值，这是批处理里最典型的数据错位。求值发生在节点执行前，上下文里可用的内置变量大致如下：

| 变量 | 含义 | 典型用法 |
| --- | --- | --- |
| `$json` | 当前 item 的 `json` 字段 | <code v-pre>{{ $json.email }}</code> |
| `$node["名"].json` | 指定节点输出中对应 item 的数据 | <code v-pre>{{ $node["Webhook"].json.body.id }}</code> |
| `$items()` | 取某节点（缺省为直接上游）的全部 item | <code v-pre>{{ $items().length }}</code> |
| `$now` / `$today` | 当前时间（Luxon 对象） | <code v-pre>{{ $now.toISO() }}</code> |
| `$workflow` | 工作流元信息 | <code v-pre>{{ $workflow.name }}</code> |
| `$execution` | 本次执行元信息 | <code v-pre>{{ $execution.id }}</code> |
| `$vars` | 实例级变量（可用性随版本/版本权限而异） | <code v-pre>{{ $vars.region }}</code> |
| `$env` | 环境变量（可被配置关闭） | <code v-pre>{{ $env.MY_FLAG }}</code> |
| `$parameter` | 当前节点其它参数的值 | 跨参数引用 |
| `$runIndex` / `$itemIndex` | 第几次运行 / 当前 item 下标 | 分页与批量控制 |

三个使用原则。**第一，优先用 `$json`，谨慎用 `$node[...]`**：前者跟随数据流，后者是跨节点硬引用，节点改名或断链时会静默失效。**第二，表达式里不要写副作用**：它不是脚本执行环境，写 `console.log` 或改全局对象不会按你预期工作，也会让调试变难。**第三，注意类型**：<code v-pre>{{ 1 + 1 }}</code> 得到数字 2，<code v-pre>{{ "1" + 1 }}</code> 得到字符串 `"11"`；在「固定值/表达式」开关关闭时，<code v-pre>{{ }}</code> 只是普通文本。

既然连接表用名字做键，命名就不再是审美问题，而是结构问题。建议在项目里固定一套约定：节点名体现「做什么」而不是「是什么」（`拉取待发货订单` 优于 `HTTP Request1`），分支出口用同一前缀加条件（`已支付` / `未支付`），跨工作流复用的子工作流节点带上用途前缀。这样做的收益在半年后显现：读 JSON 就能还原业务，而不是打开画布逐个点开参数。

工作流 JSON 适合进版本库，但要接受它的两个特性：一是编辑器保存会改写 `position`、`id` 等与语义无关的字段，会产生噪音 diff；二是凭据只保存引用，换环境必须重新绑定凭据。实践上建议只对「稳定工作流」做导出归档，diff 时先忽略空白与坐标，重点看 `nodes[].parameters` 与 `connections` 两块。

参数面板上的「表达式」开关，本质是把该参数标记为可求值。关闭后即使写了 <code v-pre>{{ }}</code> 也不会求值——这是导入他人工作流后「变量不生效」的常见原因。

最后一个容易踩的细节是 `parameters` 的形状。不同 `typeVersion` 的同一节点，参数结构可能完全不同：旧版可能把字段平铺在参数顶层，新版改为嵌套的 `assignments.assignments` 数组。这意味着「照抄别人的 JSON 片段」比「照抄界面操作」更容易出错。判断依据只有一个：看该节点当前 `typeVersion` 对应的参数定义，在编辑器里把参数配好后导出比对，是最省事的校准方式。

## 可操作示例：用表达式做一次字段整形

假设 Webhook 收到 `{ "order": { "id": 42, "amount": "19.90", "currency": "CNY" } }`，需要一个规范化后的条目。可以用 Set 节点，也可以用 Code 节点；先用 Set 说明表达式的边界：

```text
字段            值
order_id        {{ $json.body.order.id }}
amount_cents    {{ Math.round(Number($json.body.order.amount) * 100) }}
currency        {{ ($json.body.order.currency || 'CNY').toUpperCase() }}
received_at     {{ $now.toISO() }}
summary         order {{ $json.body.order.id }} / {{ $json.body.order.amount }} {{ $json.body.order.currency }}
```

对应的参数结构大致是这样（Set 节点的字段定义随 `typeVersion` 变化，字段名以当前版本为准）：

```json
{
  "assignments": {
    "assignments": [
      { "name": "order_id", "type": "number", "value": "={{ $json.body.order.id }}" },
      { "name": "amount_cents", "type": "number", "value": "={{ Math.round(Number($json.body.order.amount) * 100) }}" },
      { "name": "currency", "type": "string", "value": "={{ ($json.body.order.currency || 'CNY').toUpperCase() }}" }
    ]
  },
  "options": {}
}
```

在 JSON 里，表达式值以 `=` 开头，这是「该参数是表达式」的标记；在界面上对应那个开关。手工编辑 JSON 时漏掉 `=`，参数就会被当成字面量，得到 <code v-pre>{{ ... }}</code> 原文。

调试表达式有个成本很低的办法：先用一个 Set 节点把中间值写出来，再逐段替换成表达式。表达式报错时，错误信息里通常带着出错节点与表达式片段，配合执行记录里该节点的输入数据，能定位到具体是哪个字段为空。另一个办法是把复杂逻辑挪到 Code 节点，那里有真正的 JS 调试空间——第 06 章会讲取舍。

还有一件事值得提前建立直觉：**节点可以改变 item 的数量**。过滤类节点把 100 条变成 3 条，拆分类节点把 1 条变成 100 条，聚合类节点把 100 条变成 1 条。所谓「分支只处理了部分数据」，多数时候不是连线问题，而是上游某个节点已经把数量改了，而你没有在执行记录里核对每个节点的输出条数。养成看「输入 N 条 / 输出 M 条」的习惯，能省掉大量猜测，也比对着画布反复重连有效。

## 常见坑

- [ ] 改节点名不同步 `connections`：断链，且画布可能不报错。
- [ ] 以为 `nodes[]` 顺序是执行顺序：实际由拓扑与 `executionOrder` 决定。
- [ ] 在 JSON 里手写表达式忘了前缀 `=`：参数变成字面量。
- [ ] 用 `$node["旧名"]` 硬引用：改名后静默取到 undefined，下游把空值写进数据库。
- [ ] 把数组当对象用：`$json.items.name` 取不到值，应使用 `$json.items[0].name` 或 `$items()`。
- [ ] 在 IF 条件里比较字符串与数字：JS 的隐式转换会让 `"0"` 与 `0` 的判断结果出乎意料。
- [ ] 多输出节点只连了一个输出：未连的输出对应的 item 会被丢弃，且不会报错。
- [ ] 把大对象塞进 `settings` 或节点参数：工作流 JSON 会变得难以审阅，也会拖慢编辑器加载。
