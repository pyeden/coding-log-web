# 08 运维与安全：可观测性、备份与升级

前七章讲的是 n8n 怎么工作，这一章讲它怎么坏、怎么发现、怎么恢复。自动化平台的运维有个特点：它平时很安静，安静到你会忘记它的存在；等到有人问「为什么昨天的日报没发」，才发现它已经失败了两周。所以运维的第一目标不是「修得快」，而是「失败得响」。这一章从三个观测面讲起，然后收敛到暴露面、备份与升级这三件必须提前决定的事。

## 要解决的问题

**第一，怎么知道它是健康的？** 进程活着不等于工作流能跑。一个实例可能 HTTP 200、编辑器能打开，但 worker 全部卡死、队列积压几万条。健康检查要分两层：进程与依赖（数据库、Redis）可用，以及业务层面的执行成功率与队列深度。

**第二，失败为什么没人发现？** 因为默认的失败出口是「执行记录里的一条红色状态」，而没有人会主动去看。必须有一条主动推送的链路：错误工作流把失败发到告警渠道，或者外部监控定期查询执行表。前者实时，后者能兜住「错误工作流本身也挂了」的情况。

**第三，暴露面到底有多大？** 编辑器登录页、Webhook 路径、公开 API、以及工作流里那些「可以访问任意 URL」的节点。前三个是你能看见的门，最后一个是看不见的通道——攻击者只要能影响工作流参数，就能让服务端去请求内网地址。这是 SSRF 的典型场景。

## 核心概念与术语

| 术语 | 说明 | 用途 |
| --- | --- | --- |
| `/healthz` | 健康检查端点 | 负载均衡探活、容器健康检查 |
| `/metrics` | Prometheus 格式指标 | 监控与告警 |
| 指标开关 | 控制是否暴露指标 | 生产建议开启 |
| 日志级别 | 控制日志详细程度 | 排障时临时调高 |
| 公开 API | 带 API Key 的 REST 接口 | 外部系统编排工作流 |
| API Key 权限 | 按范围授权 | 最小权限原则 |
| 用户与角色 | 实例内的账号体系 | 区分所有者与成员 |
| 单点登录 | 企业身份集成 | 集中账号治理 |
| SSRF | 服务端请求伪造 | 通过节点访问内网 |
| 备份 | 数据库 + 密钥 + 二进制 | 恢复的唯一依据 |

## 机制拆解：三个观测面

```text
① 探活（是否活着）
   GET /healthz → 200
   容器编排用它重启实例，但它不检查业务

② 指标（是否健康）
   GET /metrics → Prometheus 文本
   关注：执行总数/失败数、执行时长、队列深度、进程内存

③ 日志（为什么坏）
   标准输出 / 文件
   关注：错误堆栈、凭据解密失败、数据库连接、Redis 超时
```

三个面解决不同问题，缺一不可。只有探活会出现「活着但没用」；只有指标会出现「知道变慢但不知道为什么」；只有日志则是事后翻找，永远慢半拍。

指标层面，值得优先接入的几类信号如下：

| 信号 | 含义 | 告警建议 |
| --- | --- | --- |
| 执行失败数 | 业务失败量 | 连续 N 分钟大于阈值 |
| 执行时长分位 | 性能退化 | P95 超过基线两倍 |
| 队列深度 | 消费能力不足 | 持续增长或超过阈值 |
| 进程内存 | 泄漏或大对象 | 接近容器上限 |
| 数据库连接 | 连接池耗尽 | 接近上限 |
| Webhook 5xx | 入口异常 | 任一非零即关注 |

日志方面，最需要提前知道的两类信息是：**凭据解密失败**（通常是密钥不一致或迁移遗漏）和**数据库/Redis 连接错误**（通常是网络或限额）。这两类错误在日志里通常有成串的堆栈，但在执行记录里只表现为「执行失败」，不看日志很难定位。

安全边界则要按「谁能到达哪里」来画：

| 面 | 暴露对象 | 主要风险 | 常规做法 |
| --- | --- | --- | --- |
| 编辑器 | 内部成员 | 弱口令、会话劫持 | HTTPS、强口令、限制来源 IP、启用 SSO |
| Webhook | 公网或合作方 | 伪造请求、重放、刷量 | 鉴权头、签名、限流、去重 |
| 公开 API | 自动化系统 | Key 泄露、越权 | 最小权限、定期轮换、按来源限制 |
| 出站请求 | 内部网络 | SSRF、数据外带 | 白名单出口、禁用内网网段、审计 |
| 凭据 | 数据库 | 泄露后可直接调用第三方 | 加密密钥独立保管、最小授权 |

公开 API 的鉴权方式很直接：请求头带 API Key，路径以 `/api/v1` 开头。最小权限的落地方式是「一个用途一把 Key」，而不是全员共用一把管理员 Key：

```bash
# 查询工作流列表（示例结构，字段以官方 API 文档为准）
curl -sS 'https://n8n.example.com/api/v1/workflows?limit=10' \
  -H "X-N8N-API-KEY: $N8N_API_KEY" \
  -H 'Accept: application/json'
```

Webhook 侧的防护比 API 更容易被忽略，因为它常常是「为了让第三方调通」而开放的。至少要做三件事：鉴权（Header/Basic/JWT 或签名）、去重（业务主键）、限流（在反向代理层做，别指望应用层）。签名校验的具体实现见第 04 章，关键是**用原始请求体计算**。

再看备份。n8n 的状态分布在三个地方，缺一不可：

| 组成 | 内容 | 备份方式 | 丢失后果 |
| --- | --- | --- | --- |
| 数据库 | 工作流、执行记录、用户、凭据密文 | 定期 dump | 全部配置丢失 |
| 加密密钥 | 解密凭据的根密钥 | 密钥管理系统 | 凭据全部失效 |
| 二进制存储 | 附件、导出文件 | 卷快照或对象存储版本化 | 历史执行详情残缺 |

只备份数据库是最常见的错误：恢复后工作流都在，但所有凭据都解不开，需要逐个重新授权。密钥要独立于数据库保管，并且至少两人可见——否则单点人员离职就是灾难。

升级节奏建议固定成「月度窗口 + 紧急补丁」两条线。升级前的检查清单应该包含：读发布说明里的破坏性变更、确认节点 `typeVersion` 是否需要迁移、备份三件套、在预发跑三条关键工作流、准备回滚方案（镜像 tag + 数据库快照）。升级后观察一小时：执行成功率、失败类型分布、队列深度、内存曲线。任何一项异常就回滚，不要在生产上「边观察边修」。

## 可操作示例：一套最小可用的监控接线

先确认端点可用，再决定接哪个监控系统：

```bash
# 探活
curl -sS -o /dev/null -w '%{http_code}\n' https://n8n.example.com/healthz

# 指标（需要实例开启指标暴露）
curl -sS https://n8n.example.com/metrics | head -40
```

指标开启通常靠一个环境变量开关（`N8N_METRICS` 一类，具体名称与可选子项以官方监控文档为准）。开启后可在 Prometheus 侧抓取：

```yaml
scrape_configs:
  - job_name: n8n
    metrics_path: /metrics
    static_configs:
      - targets: ["n8n.internal:5678"]
```

如果指标端点不方便暴露到公网，可以让 Prometheus 走内网，或在反向代理层加访问控制。不要为了省事把 `/metrics` 直接开到公网——它会暴露实例规模、工作流数量等信息。

日志侧最实用的一条规则是：给容器日志加轮转。默认的 json-file 驱动不限制大小，一个高频报错的工作流能在几小时内写满磁盘，然后引发一连串与根因无关的故障：

```yaml
services:
  n8n:
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "5"
```

备份脚本则应该把「数据库 + 密钥 + 二进制」当成一个整体对待，并在恢复演练中验证。一个只有备份、没有演练的方案，在真正需要时失败的概率极高：

```bash
#!/usr/bin/env bash
set -euo pipefail
STAMP="$(date +%F-%H%M)"
pg_dump -Fc -h "$DB_HOST" -U "$DB_USER" "$DB_NAME" > "/backup/n8n-$STAMP.dump"
tar -czf "/backup/n8n-files-$STAMP.tgz" -C /srv/n8n data
# 密钥不在数据库里，单独由密钥管理系统备份，切勿写进同一份归档
echo "backup done: $STAMP"
```

最后是升级演练的最小闭环：在预发实例导入生产导出、跑三条关键工作流、核对执行记录与附件可读、再执行一次「恢复演练」（用备份起一个新实例）。这套动作每季度做一次，比任何文档都更能暴露问题。

用户管理这一块常被拖到最后才做，因为「先让业务跑起来」总是更紧急。但账号体系的欠债会以两种方式回来：一是离职人员仍能登录，二是所有人都用同一个管理员账号，审计形同虚设。自托管版本提供了基本的用户与角色能力，更细的权限、集中身份认证（SSO 一类）与组织级治理属于另一档产品能力，边界随版本与授权变化，选型时以官方文档与商务说明为准，不要假设社区版具备企业版的能力。

SSRF 的防护需要具体一点。工作流里能发请求的节点很多（HTTP、Webhook 响应、部分集成节点），它们默认可以访问实例网络能到达的任何地址，包括云主机的元数据地址与内网管理端口。可行的缓解手段是分层的：在容器/网络层限制出站（只允许白名单域名与网段），在节点层避免把用户输入直接拼进 URL，在审计层记录出站请求的目标域名。三层都做成本不低，但只做其中一层，通常刚好漏掉真正的入口。

## 常见坑

- [ ] 只用 `/healthz` 做监控：进程活着但 worker 全挂，照样「健康」。
- [ ] 错误工作流把告警发到同一个已经挂掉的渠道：失败静默。
- [ ] 公开 API 用一把全员共享的 Key：泄露后无法定位来源，也无法单独吊销。
- [ ] Webhook 无鉴权、无限流：被扫描到就是免费的算力入口。
- [ ] 允许工作流访问任意 URL：内网元数据接口、管理端口都成了可达目标。
- [ ] 备份只备数据库：恢复后凭据全废。
- [ ] 密钥只存在某个人电脑上：人员变动即不可恢复。
- [ ] 容器日志不轮转：磁盘写满导致数据库写入失败。
- [ ] 升级不读破坏性变更：节点参数静默失效，几天后才发现数据不对。
- [ ] 没有恢复演练：备份文件存在，但从未验证能否启动。
