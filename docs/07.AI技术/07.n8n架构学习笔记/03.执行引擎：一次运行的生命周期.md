# 03 执行引擎：一次运行的生命周期

工作流定义是静态的，真正让人头疼的是运行时：为什么这条执行一直挂在「运行中」、为什么失败后重试会重复发消息、为什么错误工作流里拿不到出错节点的名字。要回答这些，需要知道一次执行在引擎里被拆成了哪些阶段，每个阶段失败会发生什么。这一章沿着「触发 → 建执行 → 逐节点执行 → 落库」走一遍，并把错误处理的三件套拆开讲清楚。

## 要解决的问题

**第一，执行不是「一口气跑完」。** 引擎按连接关系逐节点推进，每个节点拿到上游的 item 数组，产出一个新的二维数组（按输出槽分组）。中间任何一步都可能抛出错误、进入等待、或者被取消。理解这个推进方式，才能判断「为什么后面的节点没跑」——多半不是没连上，而是上游返回了空数组，而空数组不会让下游节点执行。

**第二，重试的语义比想象中粗。** 引擎级的重试是「重跑整个执行」，不是「从失败节点继续」。这对幂等性的要求极高：如果你的工作流在第 5 步发了通知，第 6 步失败后重跑，通知就会发第二次。凡是带外部副作用的步骤，都必须自带去重键。

**第三，错误处理的三个层次解决的是不同问题。** 节点级设置解决「这一个节点失败怎么办」，执行级重试解决「抖动要不要再试」，错误工作流解决「失败之后谁来收尸」。三者混用会觉得机制很复杂，分开看则各司其职。

## 核心概念与术语

| 术语 | 说明 | 影响 |
| --- | --- | --- |
| 执行 | 一次运行实例，带 id、状态、开始与结束时间 | 排障入口、审计依据 |
| 手动执行 | 在编辑器里点「执行」触发 | 通常不写入正式的生产记录或可单独区分 |
| 触发执行 | 由 Webhook、定时、轮询等触发 | 只有激活的工作流才会发生 |
| 重试 | 对已有执行重新发起运行 | 整条重跑，副作用会重复 |
| 错误工作流 | 在 `settings` 里指定的兜底工作流 | 接收失败通知，做告警与清理 |
| 节点错误策略 | `onError` 三个取值 | 决定失败是中断、继续还是走错误分支 |
| 节点重试 | `retryOnFail` / `maxTries` / `waitBetweenTries` | 处理短时抖动，不解决逻辑错误 |
| 数据溯源 | `pairedItem` | 把输出 item 映射回输入 item |
| 子工作流 | Execute Sub-workflow 节点 | 复用逻辑，产生独立的执行记录 |
| 部分执行 | 从选中节点开始跑 | 调试用，不等价于生产行为 |

一个常被问到的点：**执行状态**。常见的有新建、运行中、成功、失败、取消、等待中、崩溃（不同版本命名略有差异）。看到「等待中」不要以为卡死，它通常意味着工作流里有一个等待类节点或人工审批节点，引擎主动释放了执行上下文。

## 机制拆解：五个阶段与一张状态图

```text
① 触发
   手动点击 / Webhook 请求 / 定时到点 / 轮询命中
        │
        ▼
② 创建执行
   生成 execution 记录（状态=运行中）
   载入 workflow 定义快照、解密所需凭据
        │
        ▼
③ 图遍历
   从触发节点出发，按连接推进
   每个节点：取上游 item → 执行 → 得到 outputs[输出槽][]
        │
        ├─ 成功 → 继续推进后继节点
        ├─ 等待 → 状态置为等待中，释放上下文
        └─ 失败 → 按 onError / retryOnFail 决策
        │
        ▼
④ 收尾
   写回每个节点的运行数据、状态、耗时
   触发错误工作流（若配置）
        │
        ▼
⑤ 持久化结果
   状态=成功/失败/取消
   受保留策略约束（见第 05 章）
```

第 ③ 步有两个容易被误读的细节。

**其一，节点执行是「批量」的。** 引擎把上游输出的 item 数组整体交给节点，节点内部可能逐条处理（很多集成节点就是循环调用 API），也可能一次处理完（Code 节点的 all items 模式）。因此一个节点在 UI 上只显示一次，实际可能发起了 50 次 HTTP 请求。

**其二，空输入不等于跳过执行。** 上游输出 0 条 item 时，下游节点通常不会执行，也不会有输出；这在画布上表现为「节点没有变绿」，但执行仍然可以成功结束。这解释了为什么「明明成功了但数据库没数据」——链路中某处过滤掉了全部数据。

错误处理三件套的职责边界，用一张表对齐：

| 机制 | 配置位置 | 触发条件 | 适用场景 | 不适用 |
| --- | --- | --- | --- | --- |
| `onError` | 节点设置 | 该节点抛错 | 单点容错、错误分支 | 需要跨节点补偿 |
| `retryOnFail` / `maxTries` / `waitBetweenTries` | 节点设置 | 该节点抛错 | 网络抖动、限流 | 参数错误、鉴权失败 |
| 错误工作流 | 工作流 `settings` | 整个执行失败 | 告警、清理、工单 | 精细化重试 |

`onError` 的三个取值可以这样理解：中断整个工作流（默认思路）、继续并输出空/常规结果、继续但把错误信息送到一个专门的错误输出，供后续节点处理。第三种是「错误分支」的实现方式，配合 IF 或 Switch 可以做降级。

再看数据溯源。`pairedItem` 是 item 上的一个字段，记录「这条输出来自哪条输入」。它有三个实际用途：执行记录里点击某个输出能定位到对应输入；某些节点（如聚合、合并）依赖它做正确配对；出错时能告诉你「第 7 条数据在处理第 5 条时炸了」。它不会自动出现在所有节点上——自定义节点如果返回了新构造的 item，需要自己补上，否则溯源链断在这里。

子工作流是另一个高频结构。它的价值在于复用与隔离：主工作流负责编排，子工作流负责一段可测试的逻辑。代价是**每次调用都会产生一条独立执行记录**，主流程里只看到一个节点。排障时要顺着子工作流的执行 id 往下钻，而不是在主执行里找细节。

## 可操作示例：把容错配置写进 JSON

节点级的容错写在节点对象上，不在参数里，这一点常被搞混：

```json
{
  "name": "调用库存服务",
  "type": "n8n-nodes-base.httpRequest",
  "typeVersion": 4,
  "position": [520, 0],
  "parameters": {
    "method": "POST",
    "url": "https://inventory.internal/api/reserve",
    "sendBody": true,
    "specifyBody": "json",
    "jsonBody": "={{ { \"sku\": $json.sku, \"qty\": $json.qty } }}"
  },
  "retryOnFail": true,
  "maxTries": 3,
  "waitBetweenTries": 2000,
  "onError": "continueErrorOutput"
}
```

`waitBetweenTries` 是毫秒级固定间隔，不是指数退避。三次重试加两秒间隔，意味着最坏情况下一个 item 会阻塞六秒；批量 100 条时会非常明显。如果接口支持幂等键，应该在请求体里带上，让重试安全；如果不支持，就该把重试交给下游的幂等设计，而不是靠引擎硬重试。

工作流级的兜底则写在 `settings` 里：

```json
{
  "settings": {
    "executionOrder": "v1",
    "errorWorkflow": "<error-workflow-id>",
    "timezone": "Asia/Shanghai",
    "saveManualExecutions": true
  }
}
```

错误工作流本身也是一份普通工作流，通常以 Error Trigger 节点开头，后面接通知节点。它能拿到的信息包括出错的工作流名、执行 id、错误消息等；具体字段以官方 Error Trigger 文档为准，不要凭记忆写表达式。

调用子工作流时，主流程只保留一个节点：

```json
{
  "name": "生成日报",
  "type": "n8n-nodes-base.executeWorkflow",
  "typeVersion": 1,
  "position": [760, 0],
  "parameters": {
    "source": "database",
    "workflowId": "<workflow-id>",
    "mode": "once"
  }
}
```

“等待子工作流完成”这类开关决定主流程是同步拿到返回值还是并行推进，选错会让下游拿不到数据。建议默认等待，除非你明确需要异步。

排查执行时可以按这个顺序走：先看执行状态与总耗时，再逐节点看「输入条数 / 输出条数」，然后展开报错节点的输入数据，最后才去读节点参数。多数问题在第二步就能定位——数量对不上，说明问题在上游；数量对得上但值不对，才是表达式或参数的问题。

还有一个只在事故中才会被注意到的阶段：进程重启。执行状态保存在数据库里，但运行上下文在内存里。实例重启后，重启前处于「运行中」的执行通常不会自动续跑，而是被标记为异常结束——它既没有完成，也没有正常失败，容易被监控漏掉。所以关键工作流要么设计成可安全重入，要么在启动后主动巡检这类历史执行并人工决策。取消同理：取消只是让引擎停止推进，已经发出的外部请求无法撤回。这类「半完成」状态是分布式系统里最贵的状态，设计时应假设它一定发生，并让下游能够识别与补偿。

## 常见坑

- [ ] 用「重试执行」替代幂等设计：重跑会重复发送通知、重复写库。
- [ ] 把 `retryOnFail` 当成万能：鉴权失败、参数错误重试一百次也没用。
- [ ] 只配错误工作流、不配节点容错：一个非关键节点失败就拖垮整条链路。
- [ ] 在错误工作流里再抛错：没有任何兜底，失败会静默。
- [ ] 认为空输出是错误：0 条 item 是合法结果，需要额外的「无数据」分支处理。
- [ ] 子工作流里改共享数据：多个调用方并发时互相覆盖。
- [ ] 用部分执行验证生产逻辑：部分执行不经过完整触发链路与鉴权。
- [ ] 忽略 `pairedItem`：自定义节点返回新 item 后，溯源与合并行为会变得不可预测。
- [ ] 不巡检重启前的残留执行：它们既不算成功也不算失败，最容易被静默漏掉，建议每次发布后手工核对一次。
