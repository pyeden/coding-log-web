# 09 架构心得：可复用的 AI 应用设计原则

读完前八章，真正能迁移到别处的，不是 OpenClaw 的某个配置键，而是它面对模型不确定性时做出的结构选择。下面十条原则，每条都对应前面章节的具体机制，并标注适用边界与反模式。它们不是 checklist，而是做取舍时的提问方式。

## 1. 控制平面与数据平面分离

**OpenClaw 的做法**：Gateway 负责接入、路由、会话、配对、审批与状态，是控制平面；模型推理、工具执行、流式输出发生在 runtime，是数据平面；node 只是受控外设。控制面不直接跑模型，数据面不持有渠道连接。

**适用边界**：多入口、长任务、需要统一鉴权与审计的系统。**反模式**：把模型调用塞进网关的请求处理函数，让一个慢请求拖住所有渠道；或者每个渠道各自建会话，最后无法回答“这个人到底聊过什么”。

## 2. 按会话串行化，按资源并行

**OpenClaw 的做法**：每个 `session:<key>` 一条车道，保证同一会话只有一个运行；不同会话进入全局 `main` 车道并行，用 `agents.defaults.maxConcurrent` 限流；transcript 写入再用 `activeWriterRunId` 做 fence，被取代的运行不能提交过期数据。

**适用边界**：有共享 transcript、记忆或工具状态的系统。**反模式**：全局一把大锁，吞吐归零；或者完全不加锁，两个 turn 同时改同一份历史，靠“模型会自己处理”兜底。

## 3. 上下文预算优先

**OpenClaw 的做法**：系统提示分层，稳定内容放缓存边界之上，易变内容放下；bootstrap 有单文件与总字符上限；技能只常驻目录，正文按需读；接近上限时 compaction，保留最近消息与工具配对，压缩前 flush 记忆。

**适用边界**：长会话、工具多、提示会持续增长的 Agent。**反模式**：把所有文档塞进系统提示，用更大窗口掩盖浪费；或者一超限就报错，而不是设计可降级的压缩路径。

## 4. 工具即权限面

**OpenClaw 的做法**：sandbox 决定在哪里跑，tool policy 决定能调用什么，elevated 只影响 exec 且不能绕过强制沙箱；`deny` 永远赢；exec 审批绑定命令、cwd、可执行文件与内容哈希。提示词可以鼓励行动，但最终裁决在运行时。

**适用边界**：任何能产生副作用的 Agent，尤其是能跑 shell、发消息、操作浏览器的。**反模式**：只在提示词里写“不要删库”；或者只禁 `write` 却留着 `exec`，以为文件就只读了。

## 5. 写路径决定记忆质量

**OpenClaw 的做法**：记忆分五层，只有 dreaming 能把候选晋升到 curated core；每条记忆带 `owner`/`agent`/`untrusted`/`system` 四类 provenance；不可信内容在进入整合提示前就被结构性排除；召回循环内容不会被再次抽取。

**适用边界**：长期运行、跨会话、会接触外部内容的系统。**反模式**：把全部对话无差别向量化；让模型“觉得重要”就直接写长期记忆；用召回频率给不可信内容加权。

## 6. 确定性闸门 + 模型判断

**OpenClaw 的做法**：binding 路由、队列模式、阈值、standing intent 预筛、dreaming 评分都是确定性代码；模型只在闸门内部做语言判断，例如整合摘要、写记忆条目。路由和权限不交给模型猜。

**适用边界**：高风险或高噪音的决策链，尤其是权限、路由、晋升、触发。**反模式**：让模型决定“这条消息该给哪个 Agent”或“这个用户能不能执行”；反过来，全规则、零模型，也会把语言理解做成一堆脆弱正则。

## 7. 失败降级不阻塞回复

**OpenClaw 的做法**：记忆检索与 flush 失败不阻塞回复；自动 compaction 摘要超时会提交无摘要结果继续本轮；provider 重试有预算与窗口；某个工具失败只在“否则用户没有任何回复”时加 fallback 警告。

**适用边界**：用户面向的多阶段长链路。**反模式**：一个辅助步骤失败就返回 500；或者无限重试，把一次卡顿放大成整条车道堵死。

## 8. 可观测性内建

**OpenClaw 的做法**：lifecycle/assistant/tool 三条事件流；审计 ledger 只投影元数据与结果码，不复制 prompt、消息、工具参数与结果；`session_state_events` 记录会话变更信号；`/context`、队列诊断、cron run history 都可在运行时查看。

**适用边界**：多阶段、多 Agent、需要事后复盘的部署。**反模式**：只记录最终答案；或者把完整 prompt 和工具输出写进日志，制造新的泄露面。

## 9. 扩展点优先于改内核

**OpenClaw 的做法**：插件四层（发现、校验、加载、消费），manifest 校验不执行插件代码；核心定义能力契约，厂商插件实现，渠道插件消费；技能承载流程知识；hook 提供生命周期拦截。新增渠道或模型时，优先加插件而不是改主流程。

**适用边界**：多厂商、多渠道、需要长期演进的平台。**反模式**：每来一个集成就在内核加 if/else；或者插件没有契约，直接改全局状态，升级即碎。

## 10. 部署形态决定运维成本

**OpenClaw 的做法**：单 Gateway、单状态目录、每 Agent SQLite、workspace 文件、launchd/systemd 监督；需要隔离时才多 Gateway，且端口、配置、状态、workspace 全部独立；worktree 与 node 把执行扩展到仓库与设备，但不改变控制面。

**适用边界**：从个人助手到小团队。**反模式**：把单机方案硬扩成多租户分布式，忽略状态目录锁与会话所有权；或者反过来，把分布式消息队列、服务网格塞进一个个人助手，运维成本吃掉全部收益。

## 最后三条自检

设计自己的 Agent 应用时，可以反复问：第一，状态的所有者是谁，失败后谁来恢复？第二，模型能做什么，是由提示词决定，还是由运行时闸门决定？第三，新增一个渠道、模型或工具，需要改内核，还是加一个扩展点？这三个问题答清楚，架构就不会太差。

架构不是把功能堆齐，而是把失败模式收拢。OpenClaw 的可借鉴之处，不在于它每个选择都最优，而在于它清楚地知道每个选择把复杂度放在了哪里。
