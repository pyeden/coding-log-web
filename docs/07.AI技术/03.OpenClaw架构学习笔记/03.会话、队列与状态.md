# 03 会话、队列与状态

Agent 系统最容易被低估的部分，是“同一条消息应该落到哪里，以及它要和谁排队”。模型再强，如果两个请求同时改同一个会话，或者用户的新消息在旧任务跑到一半时被静默丢弃，体验就会崩。OpenClaw 用 `sessionKey` 做路由，用车道做串行化，用 writer claim 做写入隔离，再用 SQLite 和重启恢复兜住持久性。

## 要解决的问题

第一，多渠道、多用户、多群组会产生大量对话，必须有确定的归属规则，否则私聊内容可能串到别人群里。第二，同一个会话不能并发跑两个 turn，否则工具调用和 transcript 会互相覆盖；但不同会话又应该并行，否则一个长任务会堵住所有人。第三，断线、重启、重复投递都会发生，系统必须知道哪些输入已经持久化、哪些 turn 可以恢复、哪些绝对不能重放。

## 机制拆解

**sessionKey 路由。** 每条入站消息先按来源决定会话：私聊默认共享同一个 main 会话；群聊默认按群隔离；房间/频道按房间隔离；cron 每次运行新建会话；webhook 按 hook 隔离。`session.dmScope` 可以改成 `per-peer`、`per-channel-peer` 或 `per-account-channel-peer`，多用户部署应至少用 `per-channel-peer`，否则 Alice 的私聊会进入 Bob 也能看到的同一上下文。`session.identityLinks` 用于把同一个人在不同渠道的身份映射到一个 canonical peer。多 Agent 场景下，`agentId` 决定“哪个大脑”，`accountId` 决定“哪个渠道账号”，binding 决定消息路由到哪个 Agent。

**四种队列模式。** 当会话已有 active run 时，新消息的行为由 `/queue` 决定：

- `steer`（默认）：把消息注入当前运行，包括工具执行期间。正在跑的工具会完成；顺序执行的后续工具若还没开始，可以被跳过，并收到一条合成的“已跳过”结果，保证 transcript 里工具调用与结果仍然配对。并行批次不会被跳过，等批次结束后再检查 steer。
- `followup`：不打断当前运行，等它结束后再开新 turn。
- `collect`：同样不打断，但在 debounce 窗口内把兼容的消息合并成一个 followup turn。
- `interrupt`：中止当前运行，再执行最新消息；被中止的 turn 不会通过重启恢复续跑。

默认参数是 500ms debounce、`cap: 20`、`drop: "summarize"`。队列是 lane-aware FIFO：每个 `session:<key>` 一条车道，保证同一会话串行；之后进入全局 `main` 车道，并发由 `agents.defaults.maxConcurrent` 控制。前台任务对普通任务有最多 15 秒的优先级领先，对后台任务最多 30 秒，超过后新来的前台消息不能无限插队，避免饿死旧任务。

**writer claim。** 在开始流式输出前，被接纳的运行会记录一个持久的 `activeWriterRunId`。之后每次 transcript 追加或重写都要带上 `expectedWriterRunId`，同步提交事务会校验它是否仍匹配当前 claim。这样被取代的旧运行无法把过期数据写进 transcript。SQLite 写入队列按 Agent 排序，Gateway 状态目录锁则防止另一个 Gateway 或 `openclaw agent --local` 同时拥有同一状态目录。

**状态与恢复。** 运行时会话行与 transcript 默认在 `~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite`；归档 transcript 在 `~/.openclaw/agents/<agentId>/sessions/`。会话行区分 `sessionStartedAt`、`lastInteractionAt`、`updatedAt`：daily reset 看第一个，idle reset 看第二个，列表和清理看第三个。Gateway 重启时，被中断的 main-session turn 会在启动几秒后被重新派发，恢复会保留已记录的工具调用与结果，复用原用户消息，并给会话发一条“上次被重启打断，请从现有 transcript 继续”的系统消息。恢复预算默认三次；一旦真正的后端 turn 开始，预算会刷新。子 Agent 不会被自动重启，而是把中断结果交给父级决定；cron 由调度器按计划重跑；Gateway 终端 PTY 不恢复。

## 设计取舍

按会话串行化是最重要的取舍。它牺牲了单会话内的吞吐，换来了状态一致性：工具不会并发改同一份 transcript，模型不会看到一半旧一半新的上下文。为了不让串行化变成全局瓶颈，系统再把不同会话放到全局车道并行，并用 `maxConcurrent` 限制总资源。

四种队列模式把“用户想怎么打断”变成了显式策略。`steer` 体验最好，但实现最复杂：要在工具边界检查、要给被跳过的工具补结果、要保证每条 steer 输入有自己的回复。`interrupt` 最简单，但会丢失正在进行的工作，所以不适合默认开启。`collect` 适合群聊刷屏，但只合并路由、授权、执行设置兼容的消息；Discord/Telegram 这类有独立持久入口的消息不会被合并。

持久化选择 SQLite 而不是外部消息队列，是为了让单机部署零依赖、事务边界清晰。代价是横向扩展受限：多 Gateway 共享同一个状态目录是不被允许的，跨进程通知也不在 v1 的能力里。它适合“一台机器一个助手/一个小团队”，不适合把它当分布式任务平台。

## 实践建议

第一，多用户部署先设 `session.dmScope: "per-channel-peer"`，再谈其他优化。第二，按渠道选择队列模式：私聊用 `steer`，群聊用 `collect`，自动化或批处理用 `followup`，只有明确要“换掉当前任务”时才用 `interrupt`。第三，长任务不要占满 `maxConcurrent`；给后台任务单独的 cron 车道，避免阻塞入站回复。第四，工具要可重入，尤其是写文件、发消息、下单；恢复会重放 turn 的决策，但不会替你消除已经发生的副作用。第五，定期预览 `openclaw sessions cleanup --dry-run`，理解 `pruneAfter`、`maxEntries` 和归档策略，不要等磁盘满了才处理。第六，升级或迁移前备份 `openclaw-agent.sqlite` 与 workspace，恢复逻辑依赖这些状态。
