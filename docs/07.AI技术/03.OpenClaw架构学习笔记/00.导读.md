# 00 导读：为什么要读一个 Agent 框架的架构

大多数人学 Agent，是从一段 prompt 模板、一个工具调用示例、一个“能跑通”的 demo 开始的。demo 到产品之间，差的不只是模型能力，而是一整套让不确定的模型行为变得可运营的工程结构：消息从哪里进来、一次 turn 怎样被串行化、上下文超了怎么办、工具调用如何被授权、记忆写坏了能不能回滚、多个 Agent 抢同一个会话时谁说了算。

这份笔记不打算复述功能清单，而是把 OpenClaw 当成一个可拆解的 AI 应用系统，沿着“请求如何流动、状态放在哪里、边界由谁守”三条线读它的设计。

## 要解决的问题

第一，为什么一个聊天入口可以长期在线，而自己写的 Agent 脚本跑几天就乱？差别通常不在模型，而在会话、队列和恢复机制。第二，为什么同一个模型换一个框架，工具调用的稳定性差很多？差别在上下文怎么组装、工具 schema 怎么暴露、失败如何重试。第三，为什么功能越加越多，系统开始互相干扰？差别在扩展点是插件、钩子还是直接改内核。

OpenClaw 的定位是自托管的 Gateway：把一个常驻进程放在自己的机器或服务器上，连接多个聊天渠道与 AI Agent。官方文档把它概括为 self-hosted、multi-channel、agent-native、open source 四点（`docs/index.md`）。它不是一个模型，也不是一套 prompt 库；它更像 Agent 应用的“操作系统外壳”：负责接入、路由、会话、工具、记忆与多智能体的公共设施。

## 机制拆解：一张文字版分层图

```text
接入层   聊天渠道 / WebChat / CLI / 自动化 / 外部 webhook
             │  统一消息与账号、权限、mention 规则
协议层   Gateway（单进程，默认 127.0.0.1:18789）
             │  WebSocket：connect → req/res + event
             ├─ operator 客户端：CLI、Web Control UI、macOS App
             └─ node 设备：macOS/iOS/Android/headless，role=node
运行时层 agent RPC → agentCommand → runEmbeddedAgent
             │  会话车道 → 工作区/技能准备 → prompt 组装
             │  → 模型推理 → 工具调用 → 流式输出 → 回复整形
能力层   tools / skills / plugins / memory / cron / nodes
状态层   每 Agent SQLite + workspace 文件 + openclaw.json
执行层   Gateway 主机 / sandbox / 配对 node
```

这张图最重要的不是分层本身，而是每层只承担一种责任：Gateway 是控制平面，模型运行时是数据平面，SQLite 与 workspace 是持久层，node 是外设而不是第二个 Gateway。后面九章基本都在解释这些边界为什么这样划。

阅读路径有两条。想建立完整心智模型，按 01→09 顺序读：先看 Gateway 全景，再跟一次 turn 的生命周期，然后理解会话与队列；接着进入上下文、工具权限、记忆三块硬骨头；最后看扩展机制、多智能体与可复用原则。想尽快改代码，可以走 01→02→05→07：先知道请求怎么进来，再看工具权限和插件挂载点，足以定位大多数接入问题。

还有三个容易被忽略的事实。其一，Gateway 同时承载 WebSocket 控制面、HTTP API、插件路由与 Control UI，端口只有一个，但信任边界是同一个；所以“把端口藏起来”不是安全策略，认证与设备配对才是。其二，事件不是消息队列，Gateway 明确不重放事件，客户端遇到序号缺口只能主动刷新状态（`docs/concepts/architecture.md` 的 Invariants）。其三，Agent 的“记忆”与“上下文”是两件事：上下文是这一轮模型能看到的窗口，记忆是落在磁盘、下一轮可以被召回的内容。把两者混为一谈，后面的压缩与召回都会设计错。

从工程角度看，这套结构把不确定性收拢到了两个地方：模型推理和工具副作用。其余部分——路由、排队、权限、持久化——都尽量做成确定性的。读架构时只要盯住这条主线，就不会被功能名淹没。

## 设计取舍

OpenClaw 选择单进程 Gateway，而不是一上来拆微服务。好处是会话、队列、渠道连接共享同一份内存状态，调试链路短；代价是单点故障和资源竞争，所以它用 per-session 车道、全局并发上限和重启恢复来补。它选择 WebSocket 长连接和类型化协议，而不是纯 HTTP，因为 Agent 运行是长任务，需要服务端推送事件；代价是客户端必须处理断线重连和事件不重放。

它还把“简单”优先给了存储：记忆先用 Markdown 文件加一个 SQLite 索引，而不是默认引入向量数据库。这样做可检查、可编辑、可迁移，但把复杂度转移到了写入治理上——也就是后面会反复出现的 provenance 与 dreaming。理解这些取舍，比记住配置键更有价值。

另一个值得注意的取舍是“可检查性优先”。OpenClaw 把系统提示、工作区文件、记忆条目都做成可读文本或可查询记录，代价是这些表面会随功能增长而膨胀。它用 bootstrap 字符上限、工具 schema 预算和 compaction 来对冲，而不是把一切塞进一个不可见的托管服务。这个选择适合自托管与团队审计，但不适合追求零运维的纯 SaaS 场景。

## 实践建议

读这份笔记时，建议带着三个问题：这个机制解决的是哪类失败？它把复杂度转移到了哪里？如果我要在自己的产品里复用它，最小实现是什么？每读完一章，可以回到自己系统里找一处对应：会话表、任务队列、工具白名单、上下文裁剪、记忆写入。能映射上，说明真的读懂了；映射不上，往往只是记住了名词。每章末尾的参考文档不多，但都是理解该章机制的最小集合，建议至少打开其中两篇对照阅读。
