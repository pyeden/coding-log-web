# 04 上下文工程与压缩

同一个模型，为什么有时候像记得所有约定，有时候又像失忆？多数时候不是模型退化，而是上下文工程不同：系统提示里放了什么、工作区文件注入了多少、技能说明是常驻还是按需加载、历史超限后怎么压缩。上下文是 AI 应用最贵的资源，也是最容易被浪费的资源。

## 要解决的问题

一次模型请求能带的 token 有限，但 Agent 需要的东西很多：行为规则、工具定义、技能目录、工作区约定、用户偏好、长期记忆、最近对话、工具结果、附件。全塞进去会超限、变慢、让模型抓不住重点；塞得太少又会丢约束、重复犯错。更麻烦的是，上下文不是静态的：它会随对话增长，必须在某个点做压缩，而压缩本身会丢信息。

所以上下文工程要同时回答三个问题：什么内容应该在现场？什么内容应该按需取？超限时牺牲哪一部分、保留哪一部分？

## 机制拆解

**系统提示的三层装配。** OpenClaw 没有运行时默认提示，每次运行都自己构建。`buildAgentSystemPrompt` 是纯渲染器，只根据显式输入生成文本，不直接读全局配置；`buildConfiguredAgentSystemPrompt` 在其上应用配置驱动的开关（owner 展示、TTS 提示、模型别名、记忆引用模式、子 Agent 委派模式）；运行时适配器（embedded、CLI、导出预览、compaction）负责收集实时事实：工具、沙箱状态、渠道能力、上下文文件、provider 贡献。这样导出的提示与真实运行保持一致，又不会把所有运行时细节塞进一个巨型 builder。

提示的结构是固定的：Tooling、Execution Bias、Promised Work、Care、Runtime Context、Skills、OpenClaw Control、Messaging、Workspace、Documentation、Workspace Files、Sandbox、Temporal Context、Assistant Output Directives 等。稳定的长内容（Project Context、静态记忆召回指令）放在内部缓存边界之上；易变的每轮内容（UI 展示、Messaging、Runtime、Temporal Context、当前 elevated 级别）放在边界之下，让支持前缀缓存的后端可以复用稳定前缀。

**bootstrap 注入。** 工作区里的 `AGENTS.md`、`SOUL.md`、`IDENTITY.md`、`USER.md`、`BOOTSTRAP.md`、`MEMORY.md` 会按生命周期注入。单文件上限 `agents.defaults.bootstrapMaxChars` 默认 20000 字符，总上限 `bootstrapTotalMaxChars` 默认 60000；`USER.md` 另有 4000 字符预算。超限时文件本身不丢，但注入副本被截断，并在提示里加一条不可配置的提示，要求模型直接读原文件。子 Agent 只注入 `AGENTS.md`，其他 bootstrap 文件被过滤，以控制子上下文大小。`memory/*.md` 日常笔记不进入常规 bootstrap，只通过 `memory_search`/`memory_get` 按需读取。

**技能与工具的成本。** 系统提示里的技能目录只包含 name、description、location，真正的 `SKILL.md` 指令要等模型需要时再读。工具则有两份成本：提示里的工具列表文本，以及发给模型的 JSON schema。`/context detail` 会把最大的工具 schema 和技能条目列出来，方便判断是谁在吃预算。

**compaction。** 当会话接近模型上下文上限，或 provider 返回上下文溢出错误时，OpenClaw 会把较早的对话总结成一条 compact entry，写回 transcript，并保留最近消息。选择切分点时会保证 assistant 的工具调用与对应 `toolResult` 不被拆开；如果切在工具块中间，会把边界移开。内置总结一次请求处理旧历史，输入上限 160000 字符（约 40000 token），或按总结模型自己的窗口取更小值；超出时按“最新消息原文一半、用户消息四分之一、最旧消息十分之一、其余均匀采样”的方式填充，并在缺口处标注遗漏条数。中文、日文、韩文字符按近似 token 权重计算。默认 `mode: "safeguard"` 会做摘要质量审计，不合格只允许有限次纠正；仍不合格就不写 transcript，保留原历史。

压缩前可以触发一次静默的 memory flush，把尚未写入的持久信息落到日常笔记；flush 失败不会阻塞回复。自动压缩的摘要如果超时（deadline 或 HTTP 408/504），系统会提交一个没有摘要的压缩结果，保留最近消息和原请求，继续本轮，而不是让会话永久卡住。溢出的恢复还可以在工具结果已结算后，从记录结果继续，不重放已完成动作。

**ContextEngine。** 内置 `legacy` 引擎是默认：ingest 空操作，assemble 直通，compact 委托给内置总结。插件可以实现 `kind:"context-engine"` 并通过 `plugins.slots.contextEngine` 选择，参与四个生命周期点：ingest、assemble、compact、after turn；可选 `maintain()` 做 transcript 维护。`assemble` 返回消息、估算 token 和可选的 `systemPromptAddition`；`ownsCompaction: true` 时由引擎负责 `/compact`、溢出恢复和主动压缩，`false` 时仍要通过 `compact()` 正确委托，不能空实现。子 Agent 还有 `prepareSubagentSpawn` 与 `onSubagentEnded` 两个可选钩子，`contextMode` 为 `isolated` 或 `fork`。

## 设计取舍

稳定前缀与动态内容的分离，是为了缓存命中率。代价是提示被切成很多段落，维护者必须知道每段该放哪里；放错位置不会立刻报错，只会让缓存失效或让模型看到过期信息。OpenClaw 用“稳定内容在上、易变内容在下”的规则和 prompt 快照测试来降低这个风险。

compaction 是用信息换空间。它保留最近消息和工具配对，但早期的细微约束、语气、临时决定可能被摘要掉。safeguard 模式试图用质量审计减少损失，代价是额外的模型请求和失败路径。对需要精确引用的任务，正确做法不是关闭压缩，而是把关键事实写进 memory 或外部文档，让压缩后仍能检索回来。

ContextEngine 的可插拔性换来了实验空间，但也把正确性责任转移给插件作者。`ownsCompaction: false` 不会自动回退到 legacy，空的 `compact()` 会直接破坏 `/compact` 与溢出恢复；这是很多自定义引擎踩过的坑。

## 实践建议

第一，用 `/context list` 和 `/context detail` 定期看预算，先砍最大的工具 schema 和重复的 bootstrap 内容，再考虑换更大窗口的模型。第二，`AGENTS.md` 写“怎么做”，`MEMORY.md` 写“记住什么”，日常细节放 `memory/*.md`，不要把 `MEMORY.md` 当日志。第三，技能说明尽量短，把长流程放进 `SKILL.md` 让模型按需读；技能目录本身也是成本。第四，需要精确回忆的事实写进记忆并带 trigger/importance 注释，不要指望 compaction 摘要替你保留。第五，压缩后做一次回归：问几个依赖早期决策的问题，确认摘要没有把关键约束弄丢。第六，自定义 ContextEngine 先从 `ownsCompaction: false` 加正确的 `compact()` 委托开始，再考虑接管压缩。
