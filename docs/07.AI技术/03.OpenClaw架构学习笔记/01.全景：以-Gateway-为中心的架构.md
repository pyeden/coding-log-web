# 01 全景：以 Gateway 为中心的架构

假设你同时从 Telegram、Web 控制台和命令行给同一个助手发消息，又在手机上让它拍一张照片。谁来决定这三条消息属于哪个会话？谁持有 Telegram 的连接？谁把“拍照”这个动作路由到手机？答案都指向同一个进程：Gateway。

## 要解决的问题

多入口系统最先遇到的不是模型问题，而是一致性问题。每个渠道各自维护连接、账号、重试和会话，最后一定会出现“网页里说过的话，手机上看不到”“同一个群两条消息并发处理，状态互相覆盖”。第二个问题是设备能力：摄像头、屏幕录制、位置这些能力天然在终端设备上，不在服务器上。第三个问题是远程访问：既要从外网连回来，又不能把控制面直接暴露在公网。

Gateway 的设计就是围绕这三个问题：把连接与状态收拢到一个常驻进程，把设备变成受控的外设，把远程接入建立在认证与配对之上。

## 机制拆解

**单进程控制面。** 一个长期存活的 Gateway 拥有所有消息面：WhatsApp、Telegram、Slack、Discord、Signal、iMessage、WebChat 等。文档明确写了一个不变量：每台主机上恰好一个 Gateway 控制一个 Baileys 会话（`docs/concepts/architecture.md`）。它同时在一个端口上提供 WebSocket 控制/RPC、HTTP API（如 `/v1/models`、`/v1/chat/completions`）、插件 HTTP 路由和 Control UI。默认绑定 `127.0.0.1:18789`，也就是默认只对本机开放。

**两类连接者。** operator 客户端（CLI、Web UI、macOS App、自动化）用 `role: operator` 连接，发 `health`、`status`、`send`、`agent` 等请求；node 设备（macOS/iOS/Android/headless）用 `role: node` 连接同一台 WS 服务器，在 `connect` 里声明 caps、commands、permissions，暴露 `camera.*`、`screen.record`、`location.get` 等命令。node 是外设，不跑 Gateway 服务，渠道消息也不会落到 node 上。

**握手与帧。** 第一帧必须是 `connect`，否则硬关闭。握手成功后，客户端拿到 `hello-ok`，其中 `snapshot` 包含 presence、health、stateVersion、uptimeMs，`policy` 包含 `maxPayload`、`maxBufferedBytes`、`tickIntervalMs` 等限制。之后的帧只有两种：请求 `{type:"req", id, method, params}` 得到 `{type:"res", id, ok, payload|error}`；服务端推送 `{type:"event", event, payload, seq?, stateVersion?}`。`send`、`agent` 这类有副作用的方法要求幂等键，服务端用短期去重缓存避免重试造成重复发送。健康检查也遵循同一套协议：`health` 是 WS 请求加 `hello-ok` 快照，不是单独的 HTTP 探针；生产环境应把 `gateway status` 与 `channels status --probe` 一起看，前者证明进程在，后者证明渠道真的可用。

**事件模型。** 常见事件有 `agent`、`chat`、`session.message`、`session.tool`、`presence`、`health`、`heartbeat`、`cron`，以及配对/审批生命周期事件。Agent 运行是两段式：先立即返回 `{ runId, acceptedAt }` 的受理 ack，再通过 `agent` 事件流式输出，最后给出 `status:"ok"|"error"` 的终态。关键限制是：事件不重放。客户端发现序号缺口，必须重新拉取 `health`、`system-presence` 或会话历史，而不能假设补发。

**配对与远程接入。** 所有 WS 客户端都带设备身份；新设备需要配对审批，之后用 Gateway 签发的 device token 重连。本机 loopback 可以自动批准以保持体验，局域网、Tailnet 以及同机的 tailnet 绑定仍要显式批准。连接要签 `connect.challenge` 的 nonce，签名载荷 v3 还绑定 platform 与 deviceFamily；已配对元数据变化需要重新配对。远程访问首选 Tailscale/VPN，次选 SSH 隧道；但隧道不绕过 Gateway 认证，token/password 仍然要带。

**调度与关停。** Gateway 内核持有唯一的 `GatewayScheduler`，维护类任务和 cron 唤醒都注册到它上面；持久化的是截止时间，启动时由各 owner 重建调度，而不是再存一份调度器状态。`beginClose()` 关闭调度准入并取消待唤醒，`stop()` 等待已运行回调与异步作用域收敛。这个设计让“睡眠后迟到的唤醒”只会对每个到期任务派发一次，错过的 tick 会合并。

## 设计取舍

单进程换来了简单的一致性模型：会话、队列、渠道连接共享同一份状态，排障链路短。代价是爆炸半径大，任何一个插件或渠道连接把进程拖垮，所有入口一起受影响。OpenClaw 用监督进程（launchd/systemd）、重启恢复、每会话车道和并发上限来对冲，而不是拆成多个服务。

单端口换来了部署简单，但也意味着控制面、数据面和 UI 共享同一个信任边界。所以它默认 loopback、默认要求认证、对非本机连接要求配对；`gateway.auth.mode:"none"` 只适用于私有入口，公网使用是明确反对的。

WebSocket + 类型化 schema 换来了长任务的服务端推送和跨语言代码生成（TypeBox → JSON Schema → Swift 模型），代价是客户端要自己处理重连、快照和序号缺口。事件不重放是刻意选择：维护一个可回放的事件日志会把 Gateway 变成消息中间件，复杂度和存储成本都不划算；把“刷新状态”的责任交给客户端，是更轻的契约。代价是客户端代码更难写，尤其是移动端断线频繁的场景，必须把“快照 + 增量”当成基本能力，而不是异常分支。

## 实践建议

第一，把 Gateway 当作控制平面，不要把它当业务数据库。会话与运行状态可以从 SQLite 和 API 恢复，业务事实应该落在自己的系统里。第二，不要直接把 18789 暴露到公网；远程优先 Tailscale，其次 SSH 隧道，并且保留认证。第三，同一台机器上运行多个 Gateway 只在需要隔离或救援机器人时使用，且必须分别设置 `gateway.port`、`OPENCLAW_CONFIG_PATH`、`OPENCLAW_STATE_DIR` 和 `agents.defaults.workspace`，否则状态会串。第四，写客户端时把每次重连当成一次新的投影：重新订阅、拉历史、采纳 `inFlightRun`，不要复用旧的事件游标。第五，升级时同时固定客户端与 Gateway 的协议版本，并在预发环境跑一遍握手与事件回放测试，`hello-ok.features` 只是发现元数据，不是完整方法清单。
