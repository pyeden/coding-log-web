# 01 全景：从应用到 LLMOps 平台

第一次打开 Dify 的工作台，很容易把它理解成一个“可视化 prompt 工具”。但只要看一眼 `docker/docker-compose.yaml`，这个印象就会碎掉：除了 API 和 Web，还有 worker、beat、sandbox、plugin_daemon、ssrf_proxy、nginx、元数据库、Redis、向量库。一个能演示的聊天页面，背后是一套完整的应用运行环境。

这一章先不追请求细节，而是把平台摊平：它由哪些部分组成，各部分为什么分开部署，单机 compose 与生产拆分之间的差距在哪里。

## 本章目标

读完本章，你应该能画出 Dify 的六层结构图；能说清 compose 里每个服务的职责；能判断哪些服务可以合并、哪些不能；能根据团队规模选择单机、分离部署或托管方案。你不需要记住所有环境变量，但要记住“哪些状态必须持久化”。

## 平台定位：它不是模型，也不是纯框架

Dify 的官方定位是开源的 LLM 应用开发平台。这个定位包含三层含义：面向构建者的工作台、面向运行时的应用引擎、面向运维的部署单元。三者共用一套后端代码，但入口和生命周期不同。

它和“纯编排框架”的差别在于，框架通常只给你图执行和节点抽象，会话、知识库、发布、多租户、审计都要自己补；Dify 把这些做进了平台。它和“直接调模型 API”的差别更直接：后者只有一次推理，前者管的是一次应用运行的完整上下文。

代价是抽象成本。你要理解 AppMode、Workflow、Dataset、Plugin 这些领域对象，才能改到正确的位置。好消息是这些对象在代码里有清晰的边界，不在一个巨型 service 里。

还有一层容易被忽略：Dify 同时服务两类“用户”。构建者关心拖拽、调试、发布；终端用户关心对话、文件上传、历史记录。两者看到的是同一个应用，但走的是不同入口、不同鉴权、不同限流。平台化意味着这两套体验必须共享同一份运行时定义，否则“工作台里好好的，WebApp 里不对”会变成常态。读源码时先分清自己在看哪一侧，能省很多时间。

从演进角度看，Dify 先有“应用”这个核心对象，再围绕它长出数据集、插件、工作流与触发器。理解这个生长顺序，就能理解为什么很多表都以 `app_id` 或 `tenant_id` 为外键：应用是聚合根，租户是隔离边界。

## 代码组织：一个 monorepo 的六个部分

| 目录 | 技术栈 | 职责 | 读它的理由 |
| --- | --- | --- | --- |
| `api` | Python / Flask | 控制器、服务、core 能力层、Celery 任务、迁移 | 绝大多数架构问题在这里 |
| `web` | Next.js | 构建端工作台与 WebApp 前端 | 理解草稿、发布、SSE 消费 |
| `packages/dify-ui` | 前端组件库 | 共享 UI 组件 | 一般不需要改 |
| `docker` | Compose / nginx | 部署拓扑、环境变量模板 | 上线与排障必读 |
| `sdks` | 多语言 | 对外 API 客户端 | 对接方视角 |
| `e2e` | 端到端测试 | 关键流程回归 | 改核心逻辑时的安全网 |

`api` 内部再分层：`controllers` 只做参数校验与响应组装，`services` 编排业务用例，`core` 提供应用运行时、工作流、RAG、模型、插件等能力，`models` 与 `repositories` 负责持久化。这个分层不是装饰，它决定了依赖方向：controller 可以调 service，service 可以调 core，反过来不行。读代码时如果看到 core 反向 import controller，基本可以判断是历史遗留或临时补丁。

## 六层文字图

```text
① 接入层   浏览器 / 外部系统 / WebApp 终端用户 / webhook 触发器
              │
② 控制层   Flask application factory + blueprint
              /console/api   /v1   /api   /inner/api   /files   /mcp
              │
③ 运行时层 core/app（六种 AppMode）+ core/workflow（图执行）
              │
④ 能力层   RAG / model_manager / plugin / tools / agent / memory
              │
⑤ 状态层   PostgreSQL 或 MySQL / Redis / 向量库 / 对象存储 / 插件库
              │
⑥ 执行层   Celery worker + beat / sandbox / plugin_daemon / nginx
```

六层里，① 和 ② 是“请求怎么进来”，③ 和 ④ 是“能力怎么组合”，⑤ 和 ⑥ 是“状态与副作用放在哪里”。很多架构讨论只盯着 ③，结果忽略了 ⑤ 的一致性问题和 ⑥ 的隔离问题。

一个典型例子：代码节点在 sandbox 里执行，网络出口默认经过 ssrf_proxy。如果你的流程需要访问内网服务，却只改了代码节点的超时，没有检查代理和网络策略，那么失败会以“连接超时”的形式出现，看起来像代码 bug，实际是部署边界问题。

## compose 拓扑：每个服务只做一件事

单机部署的核心服务如下（以仓库 `docker/docker-compose.yaml` 为准）：

| 服务 | 作用 | 关键点 |
| --- | --- | --- |
| `api` | Flask HTTP 服务 | 健康检查 `/health`，挂载存储目录 |
| `worker` | Celery worker | 处理索引、邮件、异步工作流等队列 |
| `worker_beat` | Celery beat | 定时任务调度，只能有一个实例 |
| `web` | Next.js 前端 | 构建端与 WebApp 静态资源 |
| `db_postgres` / `db_mysql` | 元数据库 | 二选一，保存应用、会话、配置 |
| `redis` | broker 与缓存 | 队列、限流、部分运行时状态 |
| `sandbox` | 代码执行沙箱 | 独立镜像，限制网络与依赖 |
| `plugin_daemon` | 插件守护进程 | 安装、签名校验、运行插件 |
| `ssrf_proxy` | 出站代理 | 收敛外部请求，降低 SSRF 风险 |
| `nginx` | 统一入口 | 反向代理、静态资源、超时配置 |
| 向量库 | 可选 | weaviate、qdrant、milvus、pgvector 等 |

这张表最重要的读法是“谁有状态”。`api`、`worker`、`web` 都可以水平扩容，因为它们的状态在数据库、Redis 和对象存储里；`worker_beat` 不能多副本，否则定时任务会重复触发；`sandbox` 和 `plugin_daemon` 属于执行环境，扩容要考虑依赖缓存与插件安装目录。

## 关键配置：把拓扑落到文件

compose 里 `api` 与 `worker` 使用同一个镜像，通过 `MODE` 区分角色。这是理解部署成本的关键：它们共享代码与依赖，但运行形态不同。

```yaml
services:
  api:
    image: langgenius/dify-api:1.13.3
    environment:
      MODE: api
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5001/health"]

  worker:
    image: langgenius/dify-api:1.13.3
    environment:
      MODE: worker

  worker_beat:
    image: langgenius/dify-api:1.13.3
    environment:
      MODE: beat
```

向量库与元数据库通过环境变量选择，`.env.example` 的默认值是 weaviate：

```bash
# 元数据库类型：postgresql / mysql 等
DB_TYPE=postgresql

# 向量库类型，默认 weaviate
VECTOR_STORE=weaviate

# 插件守护进程与内部回调
PLUGIN_DAEMON_PORT=5002
PLUGIN_DIFY_INNER_API_URL=http://api:5001
```

改这些值不是“改一个开关”那么简单。换向量库要考虑集合初始化、维度和距离度量；换元数据库要走迁移；改内部回调地址要同时检查网络别名与密钥。生产环境建议把 `.env` 纳入配置管理，但不要把真实密钥提交进仓库。

## 单机 compose 与生产拆分

| 维度 | 单机 compose | 生产拆分 |
| --- | --- | --- |
| 适用规模 | 试点、内部工具、低并发 | 多团队、对外服务、高可用 |
| 数据库 | 容器内 PostgreSQL | 托管数据库，独立备份与监控 |
| Redis | 容器内单实例 | 托管 Redis 或哨兵/集群 |
| 对象存储 | 本地卷 | S3/MinIO/云对象存储 |
| 向量库 | 容器内单节点 | 独立集群，按数据量扩容 |
| worker | 单进程处理多队列 | 按队列拆分，独立扩缩容 |
| 入口 | nginx 容器 | 负载均衡 + WAF + TLS 终止 |
| 升级 | `docker compose pull` | 蓝绿/滚动，先迁移后切流 |

单机不是“低配版”，而是“把复杂度换成了单点”。它对内部工具完全够用，但有三条硬限制：本地卷丢失就是数据丢失；worker 与 api 抢同一台机器的 CPU 和内存；升级时必然有停机窗口。只要其中一条不可接受，就该进入拆分路径。

拆分的第一刀通常不是微服务化，而是把**状态**拿出去：元数据库、Redis、对象存储、向量库先独立。第二刀是把**执行**拿出去：worker 按队列拆，sandbox 与 plugin_daemon 独立节点。第三刀才是入口与多副本。顺序反过来，会先遇到状态一致性，再遇到容量问题，排查成本高得多。

容量估算可以从四个量入手：日活会话数、单次请求的上下文长度、知识库文档总量与更新频率、插件调用的外部延迟。前两个决定 api 与模型配额，第三个决定向量库与索引 worker，第四个决定超时与重试策略。没有这四个数，谈“要几台机器”只能拍脑袋。

还有一个经常被忽略的维度是**备份恢复**。单机部署时，备份往往只做了数据库 dump，忘了对象存储里的上传文件、插件目录、sandbox 依赖缓存；恢复时应用能启动，但历史附件全丢。生产拆分后，每一类状态都要有独立的备份策略与恢复演练记录。

网络与证书也应该在拓扑阶段定下来。单机 compose 默认把 nginx 放在前面，TLS 可以终止在 nginx，也可以交给上游负载均衡；一旦拆分，就要明确哪一层做 TLS、哪一层做限流、哪一层记录访问日志。否则上线后会出现“证书在 A、日志在 B、限流在 C”的碎片化，排障时找不到完整链路。

## 设计取舍与风险

Dify 把“可自托管”作为核心卖点，因此选择了较重的运行时：Python/Flask、Celery、独立插件守护进程、独立沙箱。好处是边界清楚、可审计、可替换；代价是资源占用和运维面比“一个 Node 服务 + 一个数据库”大得多。

第二个取舍是**插件外置**。模型、工具、触发器都不编进主进程，而是通过插件守护进程运行。这让主进程升级与插件升级解耦，但也引入了新的故障点：插件守护进程不可用时，所有依赖插件的模型调用都会失败。生产环境要把它当成核心服务监控，而不是可选组件。

第三个风险是**默认配置的安全惯性**。compose 的默认密钥、默认端口、默认网络策略适合本地体验，不适合直接暴露公网。上线前至少要改密钥、收紧网络、确认 sandbox 的出站策略、给 nginx 配置合理的超时与请求体上限。

第四个风险是**许可与能力边界**。仓库中 `api/enterprise/` 承载企业版能力，社区版可以完整跑通应用与工作流，但组织级功能（更细的权限、审计与部分治理能力）需要评估版本差异。选型时不要假设“源码里有就一定能用”，先确认许可与功能开关。

- [ ] 能指出 compose 中哪些服务有状态、哪些可以水平扩容
- [ ] 明确 `worker_beat` 只能单实例，避免定时任务重复
- [ ] 生产环境已把元数据库、Redis、对象存储、向量库移出单机
- [ ] 插件守护进程与 sandbox 已纳入监控和资源限制
- [ ] 默认密钥、默认端口、出站网络策略已复核
- [ ] 升级前完成数据库备份与迁移演练
