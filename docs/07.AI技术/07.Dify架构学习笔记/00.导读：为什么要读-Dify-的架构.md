# 00 导读：为什么要读 Dify 的架构

把一个大模型接进产品，第一天通常很顺利：写好 prompt，调一次接口，页面能出字。第二周开始出现另一批问题——知识库更新后回答变差、多人同时提问时任务排队、某个工具超时把整条流程卡死、老板问“上周谁改了这个应用”。这些问题都不在模型里，而在模型外面那层工程结构里。

Dify 是一套开源的 LLM 应用开发平台，官方把它归类为 LLMOps。它真正有价值的部分，不是“能拖拽一个聊天机器人”，而是把从 demo 到可运营应用之间缺失的几段工程能力补齐了：应用形态、编排引擎、知识库、模型与工具接入、异步任务、多租户与部署边界。这份笔记沿着源码读它的架构，而不是复述功能菜单。

## 本章目标

读完这一章，你应该能回答四个问题：第一，Dify 到底解决了“demo 到生产”之间的哪几段；第二，它的代码为什么按 `controllers → services → core → models` 分层；第三，读这套笔记应该走哪三条线；第四，什么场景不该用 Dify。

本章不要求你装好 Dify。它是一张地图，后面的章节才会逐层展开。阅读时建议把“请求怎么流动、状态放在哪里、扩展点在哪里”这三个问题带在身边，每读完一章都回到这三个问题上对一次。

## 从 demo 到可运营应用，缺的到底是哪几段

第一段是**入口**。一个 prompt 脚本通常只有一个调用方；真实产品要同时面对工作台里的构建者、对外 API 的调用方、WebApp 的终端用户，还要区分草稿调试和线上版本。这三类人、两种版本，鉴权边界完全不同。

第二段是**编排**。单轮问答之外，真实需求往往是“先检索、再判断、再分支、再调用工具、最后生成”。一旦有了分支和循环，就需要图、变量、执行状态、失败重试，而不是一段 if-else。

第三段是**知识与能力**。文档要解析、切分、向量化、召回、重排；模型供应商有十几家；工具可能来自内置、自定义、插件或 MCP。这些能力的生命周期、凭据和错误形态都不一样。

第四段是**运营**。索引是长任务，要异步；应用要发布版本；调用要计量；故障要能追踪；多租户数据要隔离。没有这一段，系统只能演示，不能交付。

把这四段放在一张表里对比，会更清楚 Dify 的定位：

| 做法 | 谁负责入口与鉴权 | 谁负责编排 | 谁负责知识与工具 | 主要短板 |
| --- | --- | --- | --- | --- |
| 直接调模型 API | 自己写 | 自己写 | 自己接 | 每加一个能力都要改业务代码 |
| 纯编排框架/库 | 自己写 | 框架 | 自己接 | 没有工作台、版本、多租户与运维面 |
| Dify 这类平台 | 平台 | 平台 | 平台 + 插件 | 平台边界内的自由度，深度定制要读源码 |

Dify 的取舍很清楚：它把公共设施做成平台，把差异化留给“应用配置 + 插件 + 少量代码节点”。代价是你要接受它的抽象，比如 AppMode、变量池、插件协议；收益是你不用从零实现会话、流式、索引和发布。

## 三条阅读线

这套笔记不按功能菜单组织，而按三条线推进：

| 阅读线 | 关注的问题 | 对应章节 |
| --- | --- | --- |
| 请求流 | 一条消息从哪个入口进来，经过哪些层，怎么流式返回 | 02、03 |
| 状态 | 会话、消息、变量、索引、任务状态分别存在哪里 | 02、03、04、06 |
| 扩展边界 | 模型、工具、插件、触发器如何挂进来，失败如何隔离 | 05、06 |

第一条线回答“它是怎么跑起来的”，第二条线回答“重启之后还剩下什么”，第三条线回答“我能不能改、改在哪里”。三条线交汇的地方，就是这套系统最容易出故障的地方。

举个具体例子：用户抱怨“同一个问题，昨天答得好，今天答得差”。沿请求流查，可能发现命中了不同的应用版本；沿状态查，可能发现知识库索引还在异步构建，召回的是旧分段；沿扩展边界查，可能发现 embedding 模型插件升级后维度变了，旧向量没有重建。三个方向都走一遍，比盯着 prompt 改十遍有效。

再比如“工具调用偶发超时”。请求流会告诉你是同步等待还是流式；状态会告诉你任务是否可恢复；扩展边界会告诉你超时是插件守护进程、sandbox 还是外部 HTTP 造成的。架构阅读的价值，就是把这类模糊故障拆成可验证的假设。

从代码结构看，这三条线对应得很直接：`api/controllers/` 是请求流入口，`api/core/` 是运行时与能力层，`api/models/` 与 `api/repositories/` 是状态，`api/extensions/` 与 `api/core/plugin/` 是扩展边界。把它们混在一起读，会被文件名淹没；分开读，结构就出来了。

## 一张文字版分层图

```text
接入/控制面   /console/api 工作台   /v1 Service API   /api WebApp
                     │                  │                │
              controllers（Flask blueprint，按信任域拆分）
                     │
服务层         services：应用、会话、数据集、模型、插件、账号
                     │
能力层         core：app 运行时 / workflow / rag / model_manager
                     │        plugin 桥接 / tools / agent / memory
                     │
状态层         models + repositories：PostgreSQL/MySQL、Redis
                     │        向量库、对象存储、插件库
执行层         Celery worker/beat、sandbox、plugin_daemon、nginx
```

这张图里最值得记住的是“控制面与执行面分开”。构建端在 `/console/api` 下改配置、调模型、跑草稿；终端用户在 `/api` 下聊天；外部系统走 `/v1`。三者共用一套 `core`，但入口、凭据、限流和审计是分开的。后面讲多租户和安全边界时，这条线会反复出现。

分层之外还有一条“配置装配”的线。`api/app_factory.py` 从 `dify_config` 装载配置，注册请求前后的钩子与扩展；数据库、Redis、Celery、登录、存储、Socket.IO、OTEL、Sentry、迁移都在 `api/extensions/` 里统一初始化。这意味着读任何一个子系统，都要先确认它依赖的扩展是否启用。很多“本地能跑、线上不行”的问题，最后都落到某个环境变量或扩展开关上。

另一个容易忽略的点是：`core` 不是一个包，而是一组能力层目录。`core/app` 负责应用运行时，`core/workflow` 负责图执行，`core/rag` 负责检索，`core/model_manager` 负责模型实例，`core/plugin` 负责与插件守护进程通信。它们之间通过实体和接口耦合，而不是互相 import 具体实现。这个约束决定了你能不能只替换其中一层。

## 关键代码：一次最小调用与一次目录浏览

先看外部调用方看到的样子。Service API 的聊天入口是 `/v1/chat-messages`，用应用自己的 API Key 鉴权，`response_mode` 决定阻塞还是流式：

```bash
curl -X POST 'http://localhost/v1/chat-messages' \
  -H 'Authorization: Bearer app-xxxxxxxxxxxxxxxx' \
  -H 'Content-Type: application/json' \
  -d '{
    "inputs": {},
    "query": "用一句话解释什么是 LLMOps",
    "response_mode": "streaming",
    "conversation_id": "",
    "user": "reader-001"
  }'
```

这段请求背后会发生什么，是第 02 章的主题。这里只需要注意两点：`conversation_id` 为空表示新建会话，`user` 是终端用户标识而不是登录账号。把这两个概念混用，是多租户场景下最常见的数据串号来源。

再看仓库结构。Dify 是 monorepo，后端与前端同仓管理：

```text
dify/
├── api/            Python / Flask 后端，控制器、服务、core、任务
├── web/            Next.js 构建端与 WebApp 前端
├── packages/       前端共享包（dify-ui 等）
├── docker/         compose 编排、环境变量模板、nginx 配置
├── sdks/           多语言客户端 SDK
├── e2e/            端到端测试
└── docs/           项目内文档
```

读源码时建议从 `api/app_factory.py` 进，再看 `api/extensions/`，最后按 `controllers → services → core` 往下追。反过来从某个 controller 往上翻，很容易在 service 层迷路。

## 设计取舍与风险

Dify 选择“平台化”而不是“库化”，最直接的代价是**升级耦合**。你的应用配置、插件版本、数据库迁移都跟着平台走；跨大版本升级时，要先读 release note，再在副本环境演练。第二个代价是**抽象泄漏**：当需求超出节点能力时，你最终还是要写代码节点或自建插件，这时必须理解变量池和插件协议。

还有一个隐形成本：**插件与镜像的供应链**。模型供应商、工具、触发器都以插件交付，插件运行在独立守护进程里，安装时可校验签名；但一旦允许团队自由安装插件，就要承担版本兼容与安全审计的责任。生产环境应固定插件版本、限制来源，并把插件库纳入备份范围。

第三个风险是**把平台当万能**。Dify 适合“以 LLM 为中心、流程可枚举”的应用；不适合强实时、强事务、超低延迟的场景，也不适合把复杂业务逻辑全部塞进工作流。判断标准很简单：如果一条流程里有大量领域计算和事务回滚，把它放在业务服务里，Dify 只负责调用和编排。

阅读源码时还要注意版本。本笔记基于 1.13.3 的代码，Dify 迭代很快，目录和类名可能变化；涉及具体字段时以官方文档和当前代码为准，不要背结论。

- [ ] 能说清 Dify 补齐的是入口、编排、知识与运营四段，而不是“模型能力”
- [ ] 能区分 `/console/api`、`/v1`、`/api` 三个入口的信任域
- [ ] 读代码时先看 `app_factory.py` 与 `extensions/`，再进 `controllers`
- [ ] 遇到版本差异，先确认 `git describe`，不凭记忆写参数
- [ ] 能判断一个需求该用工作流、代码节点还是外部服务

## 阅读路径

想建立完整心智模型，按 01 到 07 顺序读：先看全景与部署拓扑，再跟一次请求；然后进入 Workflow 引擎和 RAG 两块硬骨头；最后看模型插件、数据运维和可复用原则。

想尽快定位问题，可以走 01 → 02 → 05 → 06：先知道服务怎么部署，再看请求链路，然后查插件与任务，最后看存储与安全边界。这条路径覆盖了大多数线上故障。

想评估“要不要用 Dify”，读 00、01、07 即可：定位、拓扑、取舍。技术选型不需要背 API，需要知道边界在哪里。

读源码不必一次求全。第一遍只看装配与主链路，遇到不认识的类先记下来；第二遍带着具体问题回去查，比如“流式是怎么断的”“索引失败后状态是什么”；第三遍再横向对比，看同一职责在不同形态里如何实现。每遍都有明确产出，比从头到尾通读更有效。
