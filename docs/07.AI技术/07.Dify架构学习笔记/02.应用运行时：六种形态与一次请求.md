# 02 应用运行时：六种形态与一次请求

在 Dify 里新建应用，第一步不是写 prompt，而是选形态：聊天助手、文本生成、Chatflow、Agent、工作流、知识库 Pipeline。这个选择决定了后端用哪个 generator、消息如何存、前端如何渲染、API 返回什么事件。很多人把形态当成“模板”，改起来才发现它绑定了整条运行时链路。

这一章跟着一次对话走：从 `/v1/chat-messages` 进入，经过控制器、应用生成器、队列管理器、模型与工具，最后以 SSE 事件流回到客户端；同时解释六种形态的差异，以及草稿与发布版本为什么必须分开。

## 本章目标

读完本章，你应该能：根据业务选择正确的 AppMode；画出一次聊天请求的完整链路；说清 generator、runner、queue manager 三者的分工；理解 SSE 事件的含义与断线后的处理方式；区分会话、消息、标注三类数据；知道草稿调试为什么不能直接影响线上。

## 六种应用形态

`api/models/model.py` 里用 `AppMode` 枚举定义了应用形态。除了用于渠道的 `channel`，面向构建者的主要是下面六种：

| 形态 | 枚举值 | 典型场景 | 运行时特征 |
| --- | --- | --- | --- |
| 文本生成 | `completion` | 翻译、摘要、单次写作 | 无会话，输入到输出一次完成 |
| 聊天助手 | `chat` | 客服问答、知识库问答 | 有会话与多轮消息，可挂知识库 |
| Chatflow | `advanced-chat` | 带分支/工具/检索的对话流程 | 图执行 + 会话，支持流式节点事件 |
| Agent | `agent-chat` | 需要自主选择工具的对话 | 模型驱动工具循环，步数与超时受限 |
| 工作流 | `workflow` | 批处理、表单式自动化 | 无会话，输入表单到输出结果 |
| 知识库 Pipeline | `rag-pipeline` | 文档清洗、切分、索引流水线 | 面向数据加工，不直接面向终端用户 |

选择时先问三个问题：是否需要多轮上下文？是否需要把流程画成图？输出是给终端用户还是给下游系统？三个答案基本能定位形态。常见错误是用 `chat` 硬扛复杂流程，然后在 prompt 里写“如果……则……”，最后不可维护；或者用 `workflow` 做多轮对话，却发现没有会话记忆，只能自己拼历史。

`advanced-chat` 与 `workflow` 共享同一套图执行内核，差别在会话与交互：前者有会话变量、消息历史、流式回复；后者更像一次函数调用，输入输出都走表单。`agent-chat` 则把“下一步做什么”交给模型，适合工具集合稳定、任务边界清晰的场景；如果任务步骤可以预先枚举，用 Chatflow 更可控、更便宜。

形态还影响 API。`completion` 走 `/v1/completion-messages`，聊天类走 `/v1/chat-messages`，工作流走 `/v1/workflows/run`。用错端点不会“差不多能跑”，而是参数校验直接失败。对接前先确认应用形态，比事后改代码便宜。

## 一次聊天请求的完整链路

下面这条链路以聊天类应用为例，标注了每一层实际发生的事情：

```text
客户端
  │ POST /v1/chat-messages  (Authorization: Bearer app-xxx)
  ▼
Flask app_factory
  │ before_request：请求上下文、日志上下文、（企业版）License 校验
  ▼
controllers/service_api/app/completion.py :: ChatApi
  │ 校验应用、终端用户、参数；取已发布的应用配置
  ▼
core/app/apps/chat/app_generator.py :: ChatAppGenerator
  │ 组装 prompt、历史消息、知识库检索、模型参数
  ▼
AppQueueManager（message-based）
  │ 生成 task_id，把生成任务交给 worker 线程/进程
  ▼
core/model_manager → provider 插件 → 模型服务
  │ 流式 chunk 回到队列
  ▼
generate_response_converter
  │ 转成 SSE：message / message_end / error / ping
  ▼
客户端逐事件消费
```

这条链路里有三个“边界”值得记住。第一，控制器不生成内容，它只做鉴权、参数与应用解析；第二，生成是异步的，HTTP 连接只是事件流的载体，任务本身由队列管理器持有；第三，模型调用不直接发生在 controller 线程里，而是通过模型管理器拿到 provider 实例，再由插件进程执行。

这也解释了一个常见现象：客户端断开后，任务不一定立刻停止。是否停止取决于队列管理器是否收到停止信号，以及生成器是否在下一个 chunk 检查取消。对长任务来说，“断线”和“取消”是两件事，产品上要分别处理。

## generator、runner、queue manager 的分工

| 组件 | 位置 | 职责 | 不该做的事 |
| --- | --- | --- | --- |
| Generator | `core/app/apps/*/app_generator.py` | 组装输入、调用 runner、把结果转成事件 | 不直接写数据库业务 |
| Runner | `core/app/apps/*/app_runner.py` | 执行一次应用逻辑（含工作流） | 不负责 HTTP 响应 |
| Queue Manager | `core/app/apps/*/app_queue_manager.py` | 持有任务、转发停止信号、管理事件队列 | 不组装 prompt |
| Response Converter | `*/generate_response_converter.py` | 把内部事件映射为对外 SSE | 不改业务状态 |
| Task Pipeline | `advanced_chat/generate_task_pipeline.py` | 串联工作流事件、消息保存、流式输出 | 不重复鉴权 |

分层的意义在于可替换。比如你想在 Chatflow 的每个节点后插入审计日志，正确位置是 pipeline 或事件转换层，而不是在每个节点里写。再比如你想改流式协议，只动 converter，不动 runner。反过来，如果把业务逻辑塞进 controller，升级时会被上游改动反复冲突。

`MessageBasedAppGenerator` 是聊天类应用的共同基类，负责消息相关的公共逻辑；`WorkflowBasedAppRunner` 则把工作流执行接进应用运行时。理解继承关系，能快速定位“这个行为是聊天独有还是工作流通用”。

会话历史与上下文预算是另一个容易被低估的点。聊天应用会把历史消息拼进 prompt，但模型上下文有限，必须截断或摘要。截断策略决定了“聊久了会不会忘事”，摘要策略则多一次模型调用与延迟。生产环境应把最大历史轮数、最大 token、超限后的处理方式写成明确配置，而不是依赖默认值；否则一次长对话就可能把成本推高数倍，或让模型丢掉关键前提。

## 关键代码：请求与事件流

阻塞模式适合后台任务或不需要逐字显示的场景：

```bash
curl -X POST 'http://localhost/v1/chat-messages' \
  -H 'Authorization: Bearer app-xxxxxxxxxxxxxxxx' \
  -H 'Content-Type: application/json' \
  -d '{
    "inputs": {},
    "query": "总结这份制度文档的三条要点",
    "response_mode": "blocking",
    "conversation_id": "",
    "user": "employee-042"
  }'
```

流式模式返回 `text/event-stream`，客户端按事件名处理。下面是聊天应用常见的事件序列（字段以实际版本为准）：

```text
event: message
data: {"event":"message","task_id":"...","message_id":"...","conversation_id":"...","answer":"根据"}

event: message
data: {"event":"message","task_id":"...","answer":"文档，"}

event: message_end
data: {"event":"message_end","task_id":"...","message_id":"...","conversation_id":"...","metadata":{...}}
```

Chatflow 还会穿插 `workflow_started`、`node_started`、`node_finished`、`workflow_finished` 等事件，用于展示节点进度。客户端不应该假设事件顺序固定，也不应该依赖某个中间事件一定出现；正确做法是以 `message_end` 或 `workflow_finished` 作为完成信号，并处理 `error` 与心跳。

`ping` 事件的意义常被误解。它不是业务事件，而是保持连接与探测存活；把它当成“模型还在思考”的进度指示，会在网络抖动时误导用户。真正需要展示进度时，用节点事件或前端自己的计时器。

## 草稿、发布与会话数据

应用有两套配置：草稿与已发布版本。工作台里调试的是草稿，可以随时改 prompt、换模型、加节点；对外 API 与 WebApp 读取的是已发布版本。这个分离避免了“编辑中的配置直接影响线上”，但也带来一个常见疑问：为什么工作台里效果变了，线上没变？答案通常是忘了发布。

| 对象 | 作用 | 生命周期 |
| --- | --- | --- |
| 应用草稿 | 构建者调试 | 可反复修改，不影响线上 |
| 应用发布版本 | 对外提供服务 | 发布时固化配置 |
| 会话（conversation） | 一段多轮对话 | 按终端用户与应用隔离 |
| 消息（message） | 一轮问答 | 关联会话，可含检索引用 |
| 标注（annotation） | 人工修正的问答对 | 可被检索命中，用于提升回答 |

会话与终端用户是两个维度。`user` 是调用方传入的终端用户标识，`conversation_id` 是一段对话；同一个用户可以有多个会话，同一个会话只属于一个用户。做数据隔离时，两个字段都要校验，不能只信 `conversation_id`。

标注是运营手段，不是训练数据管道。它把人工确认的问答对存下来，在相似问题出现时优先命中。它适合高频、答案稳定的场景；不适合把大量文档直接灌进去，那应该走知识库。

还有一层是**流式链路的代理配置**。SSE 经过 nginx 或云负载均衡时，如果开启了响应缓冲，客户端会看到“最后一次性吐出全部内容”；如果读超时短于模型生成时间，连接会在中途被切断。排查这类问题不要先怀疑模型，先看代理的 buffering、read timeout 与 HTTP/1.1 配置。

对事件流的压力也不能忽视。一个客户端消费慢，服务端的事件队列就会积压；并发高时，内存与连接数会先于模型配额成为瓶颈。生产环境应限制单用户并发会话、设置事件缓冲上限，并在客户端做节流渲染，避免每个 token 都触发一次重排。

## 设计取舍与风险

Dify 选择 SSE 而不是 WebSocket，原因是单向流式、易穿透代理、实现简单。代价是客户端不能在同一连接上发控制指令，“停止生成”要另发一个请求；弱网下重连也只能靠客户端补齐状态。对大多数问答产品够用，对强交互场景则要自己加一层。

第二个取舍是**生成与 HTTP 解耦**。好处是长任务不被连接生命周期绑死；代价是任务状态需要额外管理，客户端断线后可能出现“后台还在跑、前端已放弃”的浪费。生产环境应设置任务超时、最大 token、并发上限，并为停止接口做幂等。

第三个风险是**事件语义漂移**。不同形态、不同版本的事件字段不完全一致，客户端如果硬编码解析，会在升级后静默失败。建议只依赖稳定字段（`event`、`answer`、`conversation_id`、`message_id`），其余字段做可选处理。

- [ ] 已根据“是否多轮、是否图编排、输出给谁”选定 AppMode
- [ ] 对外接口使用已发布版本，调试后已执行发布
- [ ] 客户端以 `message_end`/`workflow_finished` 判断完成，并处理 `error`
- [ ] 停止生成接口做了幂等，断线不会导致任务无限运行
- [ ] 会话与终端用户双重校验，避免跨用户读取
- [ ] 对 SSE 字段做容错，升级前回归事件解析
