# 04 RAG 与知识库：从文档到召回

知识库最容易给人错觉：上传文档、点一下索引、问问题有答案，似乎就完成了。真正的坑在后面——文档更新后旧分段还在、切分粒度不合适导致答非所问、换了 embedding 模型但旧向量没重建、召回一堆相似内容却没有一条能回答问题。RAG 不是一个“向量检索接口”，而是一条从文档到答案的流水线，每一段都有自己的失败模式。

这一章沿 `api/core/rag/` 拆这条流水线：解析、切分、索引、召回、重排、生成，并解释为什么索引必须异步、检索方法怎么选、元数据过滤在哪里生效。

## 本章目标

读完本章，你应该能：画出文档到召回的完整链路；根据文档类型选择解析与切分策略；理解三种索引处理器与四种检索方式的差异；说清索引任务为什么异步、失败后如何补偿；识别 RAG 最常见的五类坑，并用检查清单在上线前拦住它们。

## 全链路：从一份 PDF 到一段引用

```text
上传文档
  │ 存对象存储，元数据入元数据库
  ▼
extractor 解析（PDF/Word/HTML/CSV/Excel/Markdown…）
  │ 得到纯文本 + 结构信息
  ▼
splitter 切分（固定长度 / 递归分隔符）
  │ 得到 chunk（分段）
  ▼
indexing_runner 异步索引任务
  │ 选择索引处理器：段落 / 父子 / QA
  ▼
index_processor 写入
  │ 向量索引 + 关键词索引 + 摘要索引（按配置）
  ▼
retrieval 召回
  │ 语义 / 关键词 / 混合 + 元数据过滤 + top_k
  ▼
rerank 重排（可选）
  │ 交叉编码器或模型打分
  ▼
data_post_processor 整理
  │ 去重、截断、拼上下文
  ▼
LLM 生成回答 + 引用
```

这条链路里，任何一段“看起来正常”都可能埋雷。解析丢了表格结构，切分再合理也救不回来；切分把一条完整规则拆成两半，召回再准也只能答一半；索引任务失败但文档状态显示“已完成”，后面所有检索都建立在残缺数据上。

## 核心概念与目录

| 概念 | 作用 | 代码位置 |
| --- | --- | --- |
| Extractor | 把不同格式文档转成文本 | `core/rag/extractor/` |
| Splitter | 把长文本切成可检索分段 | `core/rag/splitter/` |
| Indexing Runner | 组织索引任务、更新状态 | `core/rag/indexing_runner.py` |
| Index Processor | 按索引类型写入向量/关键词/摘要 | `core/rag/index_processor/` |
| Retrieval | 召回候选分段 | `core/rag/retrieval/` |
| Rerank | 对候选重新排序 | `core/rag/rerank/` |
| Data Post Processor | 召回后处理 | `core/rag/data_post_processor/` |
| DocStore | 文档与元数据存取 | `core/rag/docstore/` |

`extractor` 覆盖 PDF、Word、HTML、CSV、Excel、Markdown 等格式，复杂格式可能依赖外部解析服务。`splitter` 提供固定长度切分与递归分隔符切分；前者可控、后者更尊重段落结构。`index_processor` 目前有段落索引、父子索引、QA 索引三类处理器，分别适合普通文档、需要“小块召回、大块生成”的场景、以及问答对语料。

## 切分：最影响效果的一步

| 策略 | 适用 | 优点 | 风险 |
| --- | --- | --- | --- |
| 固定长度 | 结构松散的长文 | 实现简单、块大小可控 | 容易切断句子与表格 |
| 递归分隔符 | 有标题/段落的文档 | 尽量保持语义完整 | 块大小不均匀 |
| 父子分段 | 需要上下文完整的问答 | 召回小块、生成大块 | 存储与索引成本更高 |
| QA 分段 | 已有问答对 | 命中精度高 | 依赖语料质量 |

切分大小没有通用最优值。经验上，问答型知识库可以把块控制在几百字，保留适量重叠；流程型文档要按章节切，宁可块大一点，也不要把一步操作拆开。重叠（overlap）不是越大越好，过大会让同一段内容反复命中，挤占上下文预算。

表格和代码是切分的难点。纯文本切分器不理解表格结构，容易把表头和数据行分开；可行的做法是先把表格转成“表头: 值”的文本，或在解析阶段保留 Markdown 表格，再按行切。代码块则应按函数/段落切，并保留文件路径作为元数据，方便引用。

## 索引：为什么必须异步

一份几百页的 PDF，解析、切分、embedding、写入向量库可能耗时几分钟到几十分钟。如果放在 HTTP 请求里同步执行，连接会超时，用户会重复点击，任务会重复创建。因此 Dify 把索引做成 Celery 任务，文档先落库并标记状态，再由 worker 处理。

`api/tasks/` 下可以看到与索引相关的任务：`document_indexing_task.py`、`document_indexing_update_task.py`、`add_document_to_index_task.py`、`batch_create_segment_to_index_task.py`、`generate_summary_index_task.py` 等。它们覆盖新增、更新、批量、摘要等场景；清理与禁用也有独立任务。任务拆分得细，是为了让失败可以局部重试，而不是整库重建。

| 索引类型 | 写入内容 | 适合的检索 | 注意点 |
| --- | --- | --- | --- |
| 向量索引 | embedding 向量 | 语义检索 | 换模型必须重建 |
| 关键词索引 | 分词后的词项 | 关键词/混合检索 | 中文分词与停用词影响大 |
| 摘要索引 | 分段摘要 | 长文档概览 | 增加一次模型调用成本 |

异步带来两个必须处理的问题：状态一致性与幂等。文档状态要能区分“排队中、索引中、已完成、失败”，失败要保留原因并可重试；同一个文档的重复任务要能去重，否则并发写同一批分段会产生重复数据。生产环境还应监控队列积压与单任务耗时，避免索引把 worker 全部占满。

## 召回：四种检索方式怎么选

`RetrievalMethod` 定义了 `semantic_search`、`full_text_search`、`hybrid_search`、`keyword_search` 四种方式。它们不是互斥的产品功能，而是不同的候选生成策略：

| 方式 | 原理 | 适合 | 不适合 |
| --- | --- | --- | --- |
| 语义检索 | 向量相似度 | 同义表达、自然语言提问 | 精确编号、专有名词 |
| 关键词检索 | 词项匹配 | 型号、条款号、人名 | 口语化改写 |
| 混合检索 | 两路召回后融合 | 大多数生产场景 | 需要调权重与去重 |
| 全文检索 | 倒排索引匹配 | 大段文本、日志 | 语义泛化 |

实践中，混合检索通常是默认起点：语义负责“意思相近”，关键词负责“字面精确”。融合时要处理分数尺度不一致的问题，不能简单相加；常见做法是分别归一化后加权，或按排名融合。`top_k` 与 `score_threshold` 要一起调：阈值太高会漏召回，太低会把噪声塞进上下文。

元数据过滤是另一个维度。给文档打上部门、版本、生效日期、密级等标签，检索时先过滤再算相似度，既能提升准确率，也能防止越权。注意过滤必须发生在召回阶段或索引查询里，不能等召回后再在前端隐藏——那时数据已经进入了模型上下文。

## 关键配置：向量库与检索参数

向量库通过环境变量选择，默认是 weaviate；不同库的连接参数与索引参数不同，切换前要确认维度、距离度量与集合初始化方式：

```bash
# 元数据库
DB_TYPE=postgresql

# 向量库：weaviate / qdrant / milvus / pgvector / chroma / opensearch ...
VECTOR_STORE=weaviate

# 以 weaviate 为例的连接配置
WEAVIATE_ENDPOINT=http://weaviate:8080
WEAVIATE_API_KEY=
```

检索配置通常保存在应用或知识库的配置里。下面是一个示意结构，字段名与可选值以当前版本和官方文档为准：

```json
{
  "retrieval_model": {
    "search_method": "hybrid_search",
    "reranking_enable": true,
    "top_k": 5,
    "score_threshold": 0.5,
    "score_threshold_enabled": true
  },
  "metadata_filtering": {
    "enabled": true,
    "conditions": [
      { "name": "department", "value": "legal" },
      { "name": "status", "value": "effective" }
    ]
  }
}
```

把这份配置当成“检索契约”：谁改了 `top_k`、谁关了 rerank、谁调整了阈值，都应该有记录。否则效果波动时无法回溯，只能靠猜。

## 常见坑与排查顺序

第一坑是**切分过大或过小**。过大导致召回一段里只有一句相关，模型被无关内容干扰；过小导致条件与结论分离。排查时先看命中分段的原文，而不是只看最终回答。

第二坑是**embedding 不一致**。换模型、换维度、换归一化方式后，旧向量必须重建；只改配置不重建，会出现“新问题召回旧空间”的荒谬结果。升级前先确认索引版本与模型版本绑定。

第三坑是**召回无重排**。向量召回擅长“找相似”，不擅长“找最有用”。候选有十几条时，rerank 往往比调 top_k 更有效；但它会增加延迟与成本，是否启用要看场景。

第四坑是**权限越界**。知识库按 workspace 隔离，但应用内的检索还要考虑文档级权限。把无权文档召回给模型，等于把数据泄露给提问者；元数据过滤与检索前鉴权必须同时做。

第五坑是**只看答案不看引用**。RAG 的价值之一是可追溯。上线前应检查引用是否指向正确文档与分段，而不是只评估“回答像不像”。没有引用的 RAG，很难定位错误来源。

- [ ] 文档解析保留了标题、表格与页码等结构信息
- [ ] 切分策略按文档类型选择，并检查过命中分段原文
- [ ] 更换 embedding 模型后已全量重建索引
- [ ] 检索方式与 top_k、阈值经过离线评测，不是拍脑袋
- [ ] 元数据过滤在召回阶段生效，权限校验不依赖前端
- [ ] 索引任务状态可区分排队/进行/失败，并支持重试
- [ ] 回答带引用，且引用能定位到具体文档与分段

## 设计取舍与风险

Dify 把 RAG 做成“知识库 + 检索节点”的组合，而不是一个黑盒问答接口。好处是可以在工作流里控制召回时机、拼接方式与重排；代价是构建者要理解每个参数。对简单场景，这会显得繁琐；对需要治理的场景，这是必要的透明度。

第二个取舍是**多向量库适配**。通过统一接口支持十余种向量库，降低了锁定，但也意味着不能依赖某一家的高级特性。需要稀疏向量、混合检索原生能力或特殊过滤语法时，要确认当前适配层是否暴露。

第三个风险是**成本被低估**。索引要调用 embedding，摘要索引还要调用 LLM，检索重排也可能调用模型；文档量一大，成本与延迟都会上升。上线前应按“文档总量 × 更新频率 × 检索次数”估算，并设置配额与缓存。

评估 RAG 效果时，建议先建一个小型评测集：几十条真实问题，每条标注“应该命中的文档/分段”和“可接受的回答要点”。每次改切分、换模型、调阈值，都跑一遍评测，记录命中率与回答质量。没有评测集，所有“感觉好多了”都无法验证，也无法在回归时发现退化。
