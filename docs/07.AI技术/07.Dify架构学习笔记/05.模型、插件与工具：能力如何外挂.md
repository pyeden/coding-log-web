# 05 模型、插件与工具：能力如何外挂

模型供应商每隔几周就有新版本，工具生态从 REST 长到 MCP，企业内部还有一堆只在内网可用的系统。如果这些能力都编进主进程，Dify 的发布节奏会被拖死。它的解法是把能力“外挂”：模型、工具、Agent 策略、数据源、触发器都以插件交付，由独立的插件守护进程安装和运行，主进程只负责编排与桥接。

这一章讲三件事：模型运行时如何抽象六类模型；插件守护进程的边界在哪里；工具从哪几种来源进入工作流，以及失败时如何降级。

## 本章目标

读完本章，你应该能：说清六类模型的统一接口；理解 provider 插件与模型配置的关系；画出一次插件调用的往返路径；区分内置工具、自定义工具、插件工具与 MCP 工具；判断插件故障会影响哪些功能；知道一个最小插件需要哪些文件。

## 模型运行时：六类能力的统一封装

`api/core/model_manager.py` 的 `ModelManager` 负责按租户、供应商、模型类型获取模型实例。它不直接实现推理，而是通过 provider 管理器拿到插件提供的运行时。这样上层节点只需要说“我要一个 LLM 实例”，不需要知道背后是 OpenAI、通义还是本地模型。

| 模型类型 | 典型用途 | 输入/输出 | 常见坑 |
| --- | --- | --- | --- |
| LLM | 对话、生成、分类 | 消息/文本 → 文本或流 | 上下文长度、停止词、计费口径 |
| Text Embedding | 文档与查询向量化 | 文本 → 向量 | 维度、归一化、模型变更需重建 |
| Rerank | 召回结果重排 | 查询 + 候选 → 分数 | 候选数量与延迟 |
| Speech2Text | 语音转写 | 音频 → 文本 | 采样率、格式、长音频切分 |
| TTS | 文本转语音 | 文本 → 音频 | 音色、流式、并发限制 |
| Moderation | 内容审核 | 文本 → 判定 | 误杀、区域合规差异 |

统一抽象带来两个好处：一是节点配置可以跨供应商迁移，二是用量、错误、重试可以在一层内归一化。代价是“最小公倍数”问题——某家模型支持的特殊参数，未必能通过通用接口暴露；需要深度定制时，只能写自定义 provider 或在代码节点里直连。

模型配置按 workspace 管理，凭据也存在租户维度。这意味着同一个应用换 workspace 部署时，模型凭据不会跟着走；迁移应用要同时迁移或重配凭据。多租户系统里，凭据泄露的影响面是整个 workspace，不是单个应用，所以密钥轮换要按租户做。

## Provider 插件：模型能力的交付单元

模型供应商以插件形式提供。插件里声明 provider 的凭据 schema、支持的模型列表、模型能力（对话、工具调用、视觉、流式等）与参数规则。主进程根据这些声明渲染配置表单、校验参数、选择调用方式。

| 层次 | 负责 | 不负责 |
| --- | --- | --- |
| 前端表单 | 根据 schema 渲染凭据与参数 | 不校验真实连通性 |
| 主进程 ModelManager | 选择实例、归一化错误、计量 | 不实现推理协议 |
| Provider 插件 | 鉴权、请求外部 API、解析响应 | 不管理应用会话 |
| 插件守护进程 | 安装、签名校验、进程隔离 | 不编排工作流 |

这个分层解释了一个常见问题：为什么“模型列表里没有某个新模型”？因为 provider 插件版本还没更新，或者该模型没有在插件声明里暴露。解决方式不是改主进程，而是升级插件或自建 provider。

## 插件守护进程：边界与代价

插件运行在独立服务 `plugin_daemon` 中。compose 默认镜像为 `langgenius/dify-plugin-daemon:0.5.3-local`，默认端口 5002，使用独立数据库 `dify_plugin`，并通过 `/inner/api` 回调主进程。关键配置包括：

```yaml
plugin_daemon:
  image: langgenius/dify-plugin-daemon:0.5.3-local
  environment:
    DB_DATABASE: dify_plugin
    SERVER_PORT: 5002
    SERVER_KEY: ${PLUGIN_DAEMON_KEY}
    DIFY_INNER_API_URL: http://api:5001
    DIFY_INNER_API_KEY: ${PLUGIN_DIFY_INNER_API_KEY}
    FORCE_VERIFYING_SIGNATURE: "true"
    PLUGIN_REMOTE_INSTALLING_PORT: 5003
    PLUGIN_STORAGE_TYPE: local
```

这里有几个安全与运维要点。第一，`SERVER_KEY` 与内部 API Key 必须改成强随机值，默认值只适合本地。第二，签名校验默认开启，生产环境不要为了装来路不明的插件而关掉它。第三，远程调试端口 5003 只应在开发环境暴露，公网开放等于给攻击者一个装插件的入口。第四，插件库与插件文件目录要纳入备份，否则恢复后所有插件都要重装。

独立进程的代价是故障域变多：插件守护进程挂了，所有依赖插件的模型与工具都会失败；插件进程卡死，可能拖慢调用方。因此它必须像核心服务一样被监控——健康检查、错误率、调用延迟、安装队列，一个都不能少。

## 工具的四类来源

`api/core/tools/` 把工具分成四类，再由 `tool_engine` 统一调度：

| 来源 | 目录 | 适合 | 约束 |
| --- | --- | --- | --- |
| 内置工具 | `builtin_tool/` | 搜索、网页抓取等通用能力 | 随平台版本发布 |
| 自定义工具 | `custom_tool/` | 快速接一个内部 REST API | 需要写 OpenAPI schema |
| 插件工具 | `plugin_tool/` | 可复用、可分发的工具包 | 需要打包与签名 |
| MCP 工具 | `mcp_tool/` | 接 MCP Server 的工具生态 | 依赖 MCP 服务可用性 |

此外还有 `workflow_as_tool`，把一条工作流发布成工具供其他应用调用。它适合把稳定的内部流程封装成能力，但要注意递归调用与超时；一个工作流调用自己，可能形成无限循环。

自定义工具是落地最快的方式：给一份 OpenAPI schema，填鉴权，平台就能生成调用界面。它的风险是 schema 与真实接口漂移——参数改了、字段类型变了，工具在运行时才报错。建议把 schema 纳入接口契约管理，接口变更时同步更新。

MCP 工具把外部工具生态接进来，好处是协议统一、可复用；代价是多了一层网络依赖与鉴权配置。接入前要确认 MCP Server 的信任边界：它能看到哪些数据、能执行哪些副作用、失败时是否可重试。

## 一次工具调用的往返

```text
工作流工具节点 / Agent
   │ 选择工具、填参数
   ▼
core/tools/tool_engine.py
   │ 解析工具类型 → 取对应 provider
   ▼
plugin_tool / mcp_tool / custom_tool / builtin_tool
   │ 组装请求、注入凭据
   ▼
插件守护进程 / 外部服务
   │ 执行、返回结果或错误
   ▼
tool_engine 归一化
   │ 成功：结构化结果回变量池
   │ 失败：错误类型 + 可重试标记
   ▼
下游节点 / 模型
```

注意“归一化”这一步。不同工具的错误形态差异很大：HTTP 404、鉴权过期、超时、返回空结果。如果直接把这些字符串丢给模型，模型可能会“编一个合理答案”。正确做法是把错误转成明确的状态，让工作流走失败分支或重试，而不是让模型猜。

## 失败降级：别让一个插件拖垮整条流程

| 故障 | 影响 | 降级策略 |
| --- | --- | --- |
| 模型 provider 不可用 | 该模型的所有调用失败 | 切换备用模型/供应商，提示降级 |
| 插件守护进程不可用 | 所有插件能力失败 | 熔断，走非插件路径或返回明确错误 |
| 单个工具超时 | 当前节点失败 | 节点级重试 + 超时，避免拖垮 run |
| MCP Server 不可用 | 该 Server 的工具不可用 | 标记工具不可用，不让模型反复尝试 |
| 凭据过期 | 调用被拒 | 提前告警，按租户轮换 |

降级的核心是“可判定”。工作流里要有明确的条件分支：主模型失败后是否切备用、工具失败后是否用缓存、检索失败后是否退化为纯生成。没有这些分支，所谓降级只是把错误往后传。

另一个原则是“不要静默降级”。用户应该知道答案来自备用模型或缺少实时数据；否则一次降级会被当成正常结果，长期积累成信任问题。

## 最小插件结构

一个插件至少包含清单、provider 声明与入口代码。下面是结构示意，字段与目录以官方插件模板为准：

```text
my_tool/
├── manifest.yaml
├── main.py
├── requirements.txt
└── provider/
    └── my_tool.yaml
```

```yaml
# manifest.yaml（示意）
version: 0.0.1
type: plugin
author: example
name: my_tool
label:
  en_US: My Tool
description:
  en_US: A minimal tool plugin
resource:
  memory: 268435456
  permission:
    tool:
      enabled: true
plugins:
  tools:
    - provider/my_tool.yaml
meta:
  version: 0.0.1
  arch: [amd64, arm64]
  runner:
    language: python
    version: "3.12"
    entrypoint: main
```

写插件时先把“输入 schema、输出结构、错误码、超时”四件事定清楚，再写实现。插件不是脚本，它会被模型调用、被工作流编排、被多个租户使用；没有稳定契约，后面每加一个调用方都要改一次。

## 设计取舍与风险

插件化的最大收益是**解耦发布节奏**：模型供应商更新不必等主进程发版，企业内部工具也能独立迭代。代价是**供应链复杂度**：插件来源、版本、签名、依赖、权限都要治理。生产环境应建立插件准入清单，禁止随意安装来源不明的包。

第二个取舍是**进程隔离**。插件跑在独立守护进程里，崩溃不会直接带崩 API，但也带来 IPC 开销与调试难度。排查插件问题时，要同时看主进程日志、插件守护进程日志与插件自身日志，缺一不可。

第三个风险是**能力蔓延**。工具越多，模型越容易选错；权限越大，误操作影响越大。应按最小权限授予工具，按场景裁剪工具集，并给高风险工具加人工确认。

第四个成本是**版本漂移**。同一插件在不同 workspace 可能装着不同版本，模型参数与工具 schema 随之变化；排障时必须先对齐版本，再谈复现。

- [ ] 模型凭据按 workspace 管理，轮换流程已定义
- [ ] 插件守护进程已监控，签名校验保持开启
- [ ] 远程调试端口未暴露公网
- [ ] 工具按最小权限授予，高风险操作有人工确认
- [ ] 模型/工具失败有明确降级分支，且对用户可见
- [ ] 自定义工具的 schema 与真实接口同步更新
- [ ] 插件目录与插件库已纳入备份

插件生命周期也要治理。安装、升级、禁用、卸载都会影响正在运行的应用；升级前应在测试 workspace 验证，确认模型列表、工具 schema、凭据字段没有破坏性变更。生产环境建议固定插件版本，关闭自动升级，把“什么时候升级”变成一次有记录的变更，而不是随缘。
