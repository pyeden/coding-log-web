# 03 Workflow 引擎：图、变量池与执行

工作流是 Dify 最像“编程语言”的部分。表面上是拖拽节点、连线、配置表单；底层是一张有向图、一个变量池、一个执行引擎，以及一套节点生命周期。很多人会画流程，却说不清“变量从哪来、到哪去”“迭代和循环差在哪”“失败后会不会重跑整个图”。这些问题不解决，流程一旦变复杂就会失控。

这一章拆 `api/core/workflow/` 与它依赖的 `graphon` 包：图怎么表示、引擎怎么调度、变量怎么解析、节点怎么注册、失败与人工输入怎么处理。

## 本章目标

读完本章，你应该能：用节点、边、变量池描述一张工作流；说清 `GraphEngine` 与 `GraphRuntimeState` 的职责；理解变量引用的解析规则与类型约束；区分分支、迭代、循环与子流程；知道超时、重试、人工输入分别在哪一层处理；能画出一条 workflow run 的时序。

## 图模型：节点、边与变量池

Dify 1.13 把图执行内核抽到了独立包 `graphon`，`api/pyproject.toml` 中声明为 `graphon~=0.2.2`。后端负责把 Dify 的工作流配置转换成图，再交给引擎执行。这个拆分的好处是执行内核可以独立演进、独立测试；代价是读代码时要在两个仓库/包之间跳。

| 概念 | 含义 | 在 Dify 中的载体 |
| --- | --- | --- |
| 节点（Node） | 一个可执行单元 | 节点配置 + 节点类（LLM、代码、检索等） |
| 边（Edge） | 节点之间的依赖与数据流 | 图配置中的 source/target |
| 变量池（VariablePool） | 运行时所有可引用值的集合 | `graphon.runtime.VariablePool` |
| 图状态（GraphRuntimeState） | 一次运行的进度、变量、上下文 | 引擎创建并持有 |
| 引擎（GraphEngine） | 调度节点、处理并发与事件 | `graphon.graph_engine.GraphEngine` |
| 节点工厂（NodeFactory） | 根据类型创建节点实例 | `DifyNodeFactory` |

一张图不是“脚本的另一种写法”，而是“依赖关系的声明”。引擎根据边决定哪些节点可以并行、哪些必须等待。节点只声明自己需要哪些变量、产出哪些变量，不直接调用下游。这个约束让暂停、恢复、子图复用成为可能。

变量池是这张图的“全局内存”。每个节点执行前，引擎把它的输入从池里解析出来；执行后，把输出写回池里，并带上节点 ID 作为命名空间。下游通过 <code v-pre>{{#node_id.variable#}}</code> 这样的引用取值。引用写错不会在保存时报错，而是在运行时解析失败，所以变量命名要当成接口来设计。

## 引擎组装：从配置到可执行图

`api/core/workflow/workflow_entry.py` 是主要入口。它创建变量池、注入系统变量、构建运行状态，再用节点工厂和引擎配置组装 `GraphEngine`：

```python
from graphon.graph import Graph
from graphon.graph_engine import GraphEngine, GraphEngineConfig
from graphon.runtime import GraphRuntimeState, VariablePool
from core.workflow.node_factory import DifyNodeFactory
from core.workflow.variable_pool_initializer import add_variables_to_pool
from core.workflow.system_variables import default_system_variables

variable_pool = VariablePool()
add_variables_to_pool(variable_pool, default_system_variables())

graph_runtime_state = GraphRuntimeState(
    variable_pool=variable_pool,
    start_at=time.perf_counter(),
    execution_context=capture_current_context(),
)

engine = GraphEngine(
    workflow_id=workflow_id,
    graph=graph,
    graph_runtime_state=graph_runtime_state,
    command_channel=command_channel,
    config=GraphEngineConfig(
        min_workers=dify_config.GRAPH_ENGINE_MIN_WORKERS,
        max_workers=dify_config.GRAPH_ENGINE_MAX_WORKERS,
        scale_up_threshold=dify_config.GRAPH_ENGINE_SCALE_UP_THRESHOLD,
        scale_down_idle_time=dify_config.GRAPH_ENGINE_SCALE_DOWN_IDLE_TIME,
    ),
    child_engine_builder=child_engine_builder,
)
```

这段代码里有四个关键点。第一，变量池先注入系统变量，再注入用户输入与环境变量；顺序决定同名变量谁覆盖谁。第二，`GraphRuntimeState` 带 `start_at` 与执行上下文，后者用于追踪与取消。第三，引擎有最小/最大 worker 与扩缩容阈值，说明节点可以并发执行，但并发度受配置约束。第四，`child_engine_builder` 让子图可以复用同一套运行时，而不是另起一套。

`DifyNodeFactory` 负责把配置里的节点类型解析成具体类。节点通过注册表暴露，常见类型包括：开始、结束、LLM、知识检索、知识索引、代码、HTTP 请求、工具、Agent、条件分支、问题分类、迭代、循环、变量聚合、模板转换、参数提取、数据源，以及 webhook、schedule、plugin 三类触发器。新增节点通常要同时改节点类、工厂解析和前端面板；只改后端会出现“配置能存、画布不认”的情况。

## 变量：系统、环境、会话与节点输出

| 变量类型 | 来源 | 生命周期 | 常见误用 |
| --- | --- | --- | --- |
| 系统变量 | 引擎注入（如会话、应用、用户标识） | 单次运行 | 与业务字段重名导致覆盖 |
| 环境变量 | 应用/环境配置 | 跨运行 | 把密钥写进普通变量 |
| 会话变量 | 会话读写 | 跨多轮 | 在无会话的 workflow 里引用 |
| 节点输出 | 节点执行结果 | 单次运行 | 引用不存在的字段，运行时才报错 |
| 用户输入 | 开始节点表单 | 单次运行 | 未做类型校验直接进代码节点 |

变量引用是工作流的“接口协议”。推荐做法是：节点 ID 用语义化命名，输出字段保持稳定，变更时保留旧字段一个版本；在代码节点入口处做一次显式校验，不要把 `None` 直接传给下游。变量聚合节点适合合并分支输出，但要注意各分支的字段结构必须一致，否则下游仍然要写兼容逻辑。

类型问题在工作流里比在普通代码里更隐蔽。表单输入是字符串，代码节点可能期望数字；知识检索返回的是文档对象列表，模板节点却按字符串拼接。引擎会在部分节点做类型转换，但不会替你做业务语义校验。涉及金额、日期、枚举时，最好在代码节点里统一转换并抛出可读错误。

## 一次 workflow run 的时序

```text
调用方 / 工作台
   │ 提交 inputs
   ▼
WorkflowEntry
   │ 建 VariablePool → 注入系统变量 → 建 GraphRuntimeState
   ▼
GraphEngine
   │ 找出入度为 0 的节点（通常是开始节点）
   ▼
NodeFactory → Node.execute()
   │ 解析输入变量 → 调用能力（LLM/检索/代码/HTTP）
   │ 产出 outputs → 写回 VariablePool
   ▼
GraphEngine 收到节点完成事件
   │ 更新边状态 → 解锁下游节点 → 可并行则并行
   ▼
结束节点 / 回答节点
   │ 汇总输出
   ▼
事件流：node_started / node_finished / workflow_finished
```

这张时序图解释了三件事。其一，开始节点不是形式，它负责把用户输入写进变量池；其二，节点完成事件既用于前端展示，也用于引擎推进图；其三，结束节点只是“收敛输出”，真正的完成信号由引擎发出。

## 分支、迭代、循环与人工输入

条件分支（IF/ELSE）按条件选择一条边，未选中的分支不会执行。问题分类节点用模型做意图判断，再路由到不同分支；它适合类别稳定的场景，不适合把开放式生成当分类器用。

迭代（Iteration）对列表逐项执行子流程，输出是一个列表；循环（Loop）按条件反复执行，直到满足退出条件或达到上限。两者最容易混淆：迭代的次数由输入长度决定，循环的次数由条件决定；迭代适合批处理，循环适合“反复改写直到合格”。无论哪种，都要设置最大次数或超时，否则一个错误条件就会拖垮 worker。

人工输入（Human-in-the-loop）把流程暂停，等待外部提交后再继续。它依赖运行状态持久化与恢复能力，不是“在前端弹个框”那么简单。设计时要考虑：超时怎么办、提交人如何鉴权、恢复后变量是否仍然有效、同一任务能否被重复提交。

子流程/子图把一段逻辑封装成可复用单元。它共享父级变量池还是独立变量池，取决于实现；共享则方便传参，独立则隔离更好。无论哪种，都要明确输入输出契约，避免子图直接读写父级的隐式变量。

并发也是容易踩坑的地方。引擎会在依赖满足时并行推进多个节点，这意味着两个分支可能同时写同一个外部系统。若下游是数据库或第三方接口，要在流程层做去重或串行化，而不是假设“图上没连线就一定不会同时发生”。

## 失败、重试与超时

| 失败类型 | 典型原因 | 处理位置 |
| --- | --- | --- |
| 变量解析失败 | 引用不存在的节点/字段 | 节点执行前 |
| 模型调用失败 | 限流、凭据、超时 | 模型管理器/节点 |
| 工具失败 | 外部服务错误、参数不合法 | 工具节点 |
| 代码节点失败 | 语法、依赖、沙箱超时 | sandbox |
| 图级失败 | 节点重试耗尽、取消 | GraphEngine |

重试要区分“可重试”和“不可重试”。限流、网络抖动可以退避重试；参数错误、鉴权失败重试多少次都没用，只会放大故障。副作用型节点（发消息、写数据库、扣款）默认不应自动重试，除非外部接口支持幂等键。

超时也要分层：单节点超时、单次运行超时、HTTP 连接超时。只设最外层超时，会出现“连接已断、后台还在跑”的浪费；只设节点超时，又可能让整个 run 超过业务可接受时间。生产环境建议三层都设，并在超时后给出可区分的错误码。

## 设计取舍与风险

把执行内核抽成 `graphon` 是一次明显的工程取舍：Dify 主仓不必背负调度器的演进，内核也能被独立测试；但调试跨包问题时，调用栈会变长，版本兼容要额外关注。升级 `graphon` 前应跑一遍包含分支、迭代、子图、人工输入的回归流程。

第二个取舍是**变量池作为唯一契约**。它让节点解耦、支持并行与恢复，但也让“隐式依赖”变得容易：一个节点引用了上游某个字段，图上却看不出强依赖。团队应约定变量命名与输出 schema，把关键字段写进文档，而不是靠记忆。

第三个风险是**图膨胀**。当一张图超过几十个节点，调试、review、复用都会变难。此时应拆子图或把稳定逻辑下沉为工具/插件。图不是越直观越好，超过一定规模后，代码反而更易维护。

- [ ] 节点 ID 与输出字段命名稳定，变更保留了兼容期
- [ ] 所有循环与迭代都设置了最大次数或超时
- [ ] 副作用节点没有盲目自动重试，或外部接口支持幂等
- [ ] 子图输入输出契约明确，不依赖隐式父级变量
- [ ] 人工输入有超时、鉴权与重复提交保护
- [ ] 升级 `graphon` 前跑过分支/迭代/子图回归

测试工作流时，不要只测“顺利路径”。至少准备四类用例：正常输入、缺字段、类型错误、下游超时；再补一个“取消运行”的用例，确认停止信号能传到正在执行的节点。很多图在正常路径上完美，一旦模型返回空内容或工具超时，就会卡在某个节点，既不报错也不结束。
