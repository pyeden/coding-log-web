# 06 数据、任务与部署：后台作业与运维边界

一个 LLM 应用上线后，最容易出问题的往往不是模型，而是“后台”。索引排了两个小时、worker 内存被大文档撑爆、Redis 一重启队列全丢、升级后插件库没迁移、备份恢复了数据库却丢了附件。这些问题在功能演示时一个都看不到，但它们决定了系统能不能长期跑。

这一章从状态出发：元数据库、Redis、向量库、对象存储各存什么；Celery worker 与 beat 承担哪些任务；多租户与鉴权边界怎么划；sandbox、ssrf_proxy、nginx 各自守什么；最后给一份可执行的运维检查清单。

## 本章目标

读完本章，你应该能：画出四类存储的职责边界；按任务类型拆分 Celery 队列；说清多租户模型下哪些数据按租户隔离；理解 sandbox 与 ssrf_proxy 的安全意义；制定备份、升级与容量方案；用指标与日志定位“慢”和“错”。

## 四类存储：谁是真相源

| 存储 | 存什么 | 是否可重建 | 丢失后果 |
| --- | --- | --- | --- |
| 元数据库（PostgreSQL/MySQL） | 租户、账号、应用配置、会话、消息、文档元数据、任务状态 | 否 | 平台数据全丢，最严重 |
| Redis | Celery broker、缓存、限流、部分短期状态 | 部分可重建 | 队列任务丢失、缓存击穿 |
| 向量库 | 分段向量、关键词/摘要索引 | 可从文档重建 | 检索失效，需全量重索引 |
| 对象存储 | 上传文件、生成文件、插件包、部分日志 | 否 | 附件与插件丢失 |

判断“能不能重建”很重要。元数据库和对象存储是真相源，必须做可靠备份与恢复演练；向量库理论上可重建，但重建成本随文档量线性上升，不能当作“随时可丢”；Redis 里的队列任务介于两者之间，丢了不会导致数据错误，但会让正在进行的索引或异步工作流中断。

一个常见误区是只备份元数据库。恢复后应用配置都在，但用户上传的 PDF 没了，知识库指向空文件；或者插件包没了，模型供应商全部不可用。备份清单必须覆盖四类存储，并且记录版本号与配置。

## Celery：把长任务移出请求链路

Dify 用 Celery 处理异步任务，`worker` 消费队列，`worker_beat` 负责定时调度。`api/tasks/` 下的任务可以按用途分成几组：

| 任务组 | 代表任务 | 触发方式 | 失败影响 |
| --- | --- | --- | --- |
| 文档索引 | `document_indexing_task`、`document_indexing_update_task` | 上传/更新文档 | 知识库不完整 |
| 分段索引 | `add_document_to_index_task`、`batch_create_segment_to_index_task` | 新增/批量分段 | 单条或批量检索缺失 |
| 清理 | `clean_dataset_task`、`clean_document_task`、`batch_clean_document_task` | 删除知识库/文档 | 残留数据占空间 |
| 摘要 | `generate_summary_index_task` | 摘要索引 | 概览检索缺失 |
| 异步工作流 | `async_workflow_tasks` | 长流程/触发器 | 运行中断，需补偿 |
| 账号与邮件 | `delete_account_task`、邮件类任务 | 账号操作 | 通知延迟 |
| 人工输入超时 | `human_input_timeout_tasks` | 定时扫描 | 流程长期挂起 |

任务拆得细，是为了让失败局部化。一个文档索引失败，不应该让整个知识库重来；一个清理任务失败，不应该阻塞新文档入库。对应地，运维要能按任务类型看积压、失败率与耗时，而不是只看“worker 是否活着”。

`worker_beat` 只能有一个实例。多副本会导致定时任务重复触发，例如重复扫描超时的人工输入、重复做队列监控。如果要做高可用，应该用带锁的调度器或把 beat 做成主备，而不是简单加副本。

## 多租户与鉴权面

Dify 的数据模型以 workspace/tenant 为隔离边界，下面是 account、app、dataset 等对象。应用有草稿与发布版本，对外有 Service API Key，WebApp 有终端用户。理解这些边界，才能判断一个查询该带哪些条件。

| 对象 | 归属 | 鉴权方式 | 越界风险 |
| --- | --- | --- | --- |
| 工作台账号 | workspace | 登录会话/SSO | 跨 workspace 读取应用 |
| 应用 | workspace | 成员角色 | 低权限成员改配置 |
| Service API | 应用 | Bearer API Key | Key 泄露导致滥用配额 |
| WebApp 终端用户 | 应用 | 终端用户标识/会话 | 伪造 user 读取他人会话 |
| 知识库 | workspace | 成员角色 + 文档权限 | 召回无权文档 |
| 插件 | workspace | 安装权限 | 安装恶意插件 |

三类入口的信任域不同：`/console/api` 面向构建者，`/v1` 面向外部系统，`/api` 面向终端用户。它们共用 service 与 core，但鉴权中间件、限流与审计应该分开。把工作台接口暴露给终端用户，或者把 Service API Key 写进前端，都是典型的边界错误。

多租户还有一个容易忽略的点：**后台任务也要带租户上下文**。worker 执行索引时，如果只按文档 ID 查询而不校验租户，理论上不会串数据，但一旦有代码缺陷就会放大。任务参数里应显式携带 tenant_id，并在数据访问层做二次校验。

## 安全边界：sandbox、ssrf_proxy、nginx

| 组件 | 守什么 | 默认行为 | 加固建议 |
| --- | --- | --- | --- |
| `sandbox` | 代码节点执行 | 独立镜像、限制依赖、默认走代理 | 限制网络、设超时与内存、固定依赖源 |
| `ssrf_proxy` | 出站请求 | 收敛外部访问 | 配置允许列表，禁止访问元数据地址 |
| `nginx` | 入口 | 反向代理、TLS、静态资源 | 限制请求体、超时、上传类型 |
| `plugin_daemon` | 插件运行 | 独立进程、签名校验 | 关闭公网调试端口、固定插件来源 |
| 元数据库 | 数据 | 默认账号密码 | 独立账号、最小权限、加密连接 |

代码节点是最需要警惕的能力。它让构建者可以执行任意 Python，因此必须跑在 sandbox 里，并通过代理限制出站。生产环境不要为了“方便调试”把 sandbox 的网络完全放开；也不要让沙箱与主应用共享文件系统。

SSRF 是 LLM 应用的高频风险：用户可以让模型去访问一个 URL，如果服务端没有限制，就可能读到云厂商元数据、内网管理接口。`ssrf_proxy` 的价值是把出站流量收口，配合允许列表与 DNS 解析校验，降低这类攻击面。

nginx 则是第一道流量边界。除了 TLS，还要设置 `client_max_body_size`、代理读超时、SSE 缓冲策略。上传大文件时请求体上限太小会 413，太大又会被滥用；流式接口如果开了缓冲，用户会感觉“卡住很久然后一次性出结果”。

## 关键操作：健康检查与备份

部署后先确认服务角色与健康状态。api 的健康检查端点是 `/health`，sandbox 与插件守护进程也各有健康检查；不要只看容器“running”，要看健康状态与日志。

```bash
# 查看服务状态与健康
docker compose ps

# 查看 api 健康检查
curl -fsS http://localhost:5001/health

# 查看 worker 日志中的任务失败
docker compose logs --tail=200 worker
```

备份要覆盖元数据库、对象存储、插件目录与配置。下面以 PostgreSQL 为例，实际命令按部署方式调整：

```bash
# 元数据库逻辑备份
docker compose exec -T db_postgres \
  pg_dump -U postgres -d dify -Fc > backup/dify-$(date +%F).dump

# 对象存储/本地卷：打包上传目录与插件目录
tar -czf backup/storage-$(date +%F).tar.gz \
  docker/volumes/app/storage \
  docker/volumes/plugin_daemon

# 记录版本，便于恢复时对齐
git -C /path/to/dify describe --tags > backup/version.txt
```

恢复演练比备份本身更重要。至少每季度做一次：在隔离环境恢复数据库与对象存储，启动同版本服务，验证登录、打开应用、检索知识库、调用一次模型。没有演练的备份，只能算“心理安慰”。

## 容量与可观测性

容量估算看四个量：并发会话数、平均上下文长度、文档总量与更新频率、外部工具延迟。前两个决定 api 与模型配额，第三个决定向量库与索引 worker，第四个决定超时与重试。

可观测性至少覆盖三层：请求层（QPS、延迟、错误率、SSE 断连率）、任务层（队列积压、任务耗时、失败率）、依赖层（数据库连接、Redis 延迟、向量库查询、插件守护进程健康）。Dify 内置 OpenTelemetry 追踪与 Sentry 接入，请求会带 `X-Trace-Id`/`X-Span-Id`，排障时应把这三层用 trace id 串起来。

日志要区分“业务错误”和“系统错误”。模型返回 400 是业务参数问题，数据库连接池耗尽是系统问题；前者改配置，后者扩容或修连接管理。混在一起看，会得出错误结论。

## 设计取舍与风险

Dify 选择 Celery + Redis 作为异步骨架，成熟、易接、生态好；代价是任务可见性依赖额外工具，失败重试要自己配。对中小规模足够，对超大规模需要更细的队列拆分与独立调度。

第二个取舍是**多存储**。元数据库、向量库、对象存储各司其职，查询效率高；代价是备份与一致性复杂。跨存储事务不存在，只能靠状态机与补偿任务保证最终一致。删除文档时，元数据、向量、对象文件要分别清理，任何一步失败都要能重试。

第三个风险是**升级顺序**。数据库迁移、插件版本、镜像版本、配置项之间有依赖；顺序错了会出现“服务起来了但功能不可用”。升级前读 release note，备份，先在副本环境演练，再按“迁移 → 插件 → 服务”的顺序切换。

- [ ] 四类存储都有备份，且做过恢复演练
- [ ] `worker_beat` 单实例，或有主备/锁保护
- [ ] 队列积压、任务失败率、单任务耗时有监控
- [ ] sandbox 网络与依赖受限，未与主应用共享文件系统
- [ ] ssrf_proxy 配置了允许列表，阻断元数据地址
- [ ] nginx 的请求体、超时与 SSE 缓冲已按场景调整
- [ ] 插件调试端口未暴露公网，插件来源受控
- [ ] 升级有副本演练与回滚方案

审计日志是另一个常被跳过的部分。至少应记录：谁改了应用配置、谁发布了版本、谁导出了知识库、谁安装了插件、Service API Key 何时创建与轮换。这些记录不一定每天看，但出事时是唯一能还原“发生了什么”的证据。日志本身要防篡改，并与业务数据分开存储。
