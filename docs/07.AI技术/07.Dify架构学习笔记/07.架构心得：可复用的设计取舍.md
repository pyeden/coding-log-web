# 07 架构心得：可复用的设计取舍

读完前六章，容易记住一堆目录名，却说不清“如果我自己设计一个 LLM 应用平台，该抄什么、不该抄什么”。这一章把 Dify 的做法抽成八条原则，每条都给出反例与适用条件。它们不是教条，而是“在什么约束下，这个选择才成立”。

## 本章目标

读完本章，你应该能：用八条原则解释 Dify 的大部分结构；判断每条原则在自己的系统里是否适用；识别盲目照搬会带来的成本；带着一份取舍清单去做自己的架构决策。

## 原则一：控制面与数据面分离

Dify 把构建端（`/console/api`）、对外 API（`/v1`）、终端用户（`/api`）拆成不同 blueprint，共用能力层但不共用鉴权边界。这就是控制面与数据面的分离：改配置的人、调接口的系统、用产品的用户，走不同的门。

反例是把工作台接口直接暴露给终端用户，靠前端隐藏按钮做权限。一旦有人抓包，就能改应用配置、读别人的会话。另一个反例是把 Service API Key 写进浏览器，等于把租户凭据公开。

适用条件：只要系统有“构建者”和“使用者”两类角色，就该分离。代价是要维护多套鉴权与限流；收益是故障与攻击面被切开，审计也能按入口做。

## 原则二：能力插件化，而不是编进内核

模型、工具、Agent 策略、数据源、触发器都以插件交付，主进程只负责编排与桥接。这样模型供应商更新不必等平台发版，企业内部工具也能独立迭代。

反例是把十几家模型的 SDK 全部 import 进主进程。短期开发快，长期会出现依赖冲突、镜像膨胀、升级互相牵制。更隐蔽的反例是“插件化但共享进程”：一个插件崩溃带崩整个 API，隔离等于没做。

适用条件：能力种类多、更新快、来源分散。代价是供应链治理：签名、版本、权限、依赖都要管。能力少于三种、更新很慢时，插件化可能是过度设计。

## 原则三：长任务异步化，并且有状态机

索引、异步工作流、清理、摘要都走 Celery，HTTP 请求只负责提交与查询状态。这不是为了“看起来架构先进”，而是因为 embedding 与模型调用天然慢，同步会超时、会重复提交。

反例是把文档索引放在上传接口里同步执行。用户看到转圈，超时后重试，同一文档被索引三遍，向量库里出现重复分段。另一个反例是异步了但没有状态：任务失败后文档永远显示“处理中”，没人知道该重试还是放弃。

适用条件：单任务耗时超过几秒、可能失败、需要重试。代价是要维护队列、worker、状态表与补偿逻辑。任务很短且强实时时，异步反而增加延迟与复杂度。

## 原则四：变量池作为契约

工作流节点不直接调用下游，而是从变量池取输入、把输出写回池里。节点之间通过命名约定解耦，引擎才能并行、暂停、恢复、复用子图。

反例是节点之间通过全局变量或数据库隐式传值。图上看起来没依赖，运行时却互相影响；一改顺序就出 bug。另一个反例是变量命名随意，`text`、`content`、`output` 混用，三个月后没人敢删字段。

适用条件：有图编排、需要并行或恢复。代价是契约治理：命名、类型、版本兼容都要约定。纯线性脚本不需要变量池，直接函数传参更清楚。

## 原则五：多租户边界前置

Dify 以 workspace/tenant 为隔离边界，应用、知识库、凭据、插件都挂在租户下。鉴权不是“登录后就能看”，而是每次数据访问都带租户条件。

反例是先查出数据再在前端过滤。列表接口返回了其他租户的记录，只是页面没显示；一旦有人改请求参数，数据就泄露。另一个反例是后台任务不带租户上下文，靠“文档 ID 全局唯一”来保证安全，代码一改就失效。

适用条件：SaaS、多团队、多客户。代价是每个查询、每个任务、每个缓存键都要带租户维度，容易漏。单租户内部系统可以简化，但要把“未来可能多租户”的扩展点留出来。

## 原则六：可观测性内建，而不是事后补

Dify 在 `app_factory` 的请求钩子里注入追踪信息，扩展层接入 OpenTelemetry 与 Sentry，任务与插件各有日志。排障时可以用 trace id 串起请求、任务与外部调用。

反例是只打“出错了”一行日志，没有请求 ID、没有模型、没有耗时。用户报障时，只能复现猜。另一个反例是指标只采集 CPU 和内存，不采集队列积压与模型错误率，系统“看起来健康”，业务已经不可用。

适用条件：所有需要长期运行的系统。代价是埋点与存储成本。早期可以只保留请求 ID、关键阶段耗时、错误分类三样，比一上来做全套 dashboard 更实际。

## 原则七：配置版本化，草稿与发布分离

应用有草稿与发布版本，调试不影响线上；发布时固化配置，出问题可以回滚。这把“改配置”变成了可审计的变更，而不是直接改生产。

反例是工作台保存即生效。构建者调 prompt 时，线上用户正在受影响；出了问题也无法判断是哪次修改导致。另一个反例是发布没有版本记录，只能靠数据库备份回滚，代价极大。

适用条件：配置会影响线上行为、多人协作。代价是发布流程与存储成本。个人项目可以简化，但至少要保留“当前版本”和“上一版本”。

## 原则八：执行沙箱化，出站流量收口

代码节点跑在独立 sandbox，外部请求默认经过 ssrf_proxy，插件跑在独立守护进程。三层隔离解决的是同一个问题：不要让不可信代码或外部输入直接接触内网与宿主。

反例是为了让代码节点“能装包”，把 sandbox 网络完全放开并挂载宿主目录。便利换来的是任意代码执行与数据泄露。另一个反例是允许模型直接请求任意 URL，攻击者可以通过提示词读取云元数据。

适用条件：允许用户写代码、访问外部 URL、安装插件。代价是性能与兼容性：沙箱有超时、依赖受限、代理可能拦截合法请求。纯内部、完全可信的脚本可以放宽，但要明确边界。

## 八条原则对照表

| 原则 | 解决的问题 | 主要代价 | 不建议照搬的场景 |
| --- | --- | --- | --- |
| 控制面/数据面分离 | 权限与攻击面 | 多套鉴权与限流 | 单角色内部工具 |
| 能力插件化 | 发布解耦 | 供应链治理 | 能力少且稳定 |
| 长任务异步化 | 超时与重复提交 | 队列与状态机 | 毫秒级同步任务 |
| 变量池契约 | 解耦与恢复 | 命名/类型治理 | 简单线性脚本 |
| 多租户前置 | 数据隔离 | 全链路带租户维度 | 单租户部署 |
| 可观测性内建 | 定位慢与错 | 埋点与存储 | 一次性脚本 |
| 配置版本化 | 变更可回滚 | 发布流程 | 个人试验项目 |
| 沙箱与出站收口 | 代码与 SSRF 风险 | 性能与兼容性 | 完全可信环境 |

这张表建议反过来用：先看“不建议照搬的场景”，确认自己不在其中，再决定要不要引入对应复杂度。架构原则的价值不在于“看起来专业”，而在于它解决的失败是否真的会发生。

如果按阶段引入，可以参考下面的顺序。先解决“会丢数据”和“会串数据”，再解决“改不动”和“查不到”，最后才追求“扩得快”。顺序反了，通常会在最贵的地方返工。

| 阶段 | 优先引入 | 原因 | 可以暂缓 |
| --- | --- | --- | --- |
| 最小可用 | 配置版本化、请求 ID | 先保证能回滚、能定位 | 插件化、多租户 |
| 多人协作 | 控制面/数据面分离、审计 | 权限与责任边界先立住 | 沙箱加固 |
| 对外服务 | 多租户前置、沙箱与出站收口 | 数据与代码风险最高 | 细粒度容量优化 |
| 规模增长 | 异步队列拆分、插件化 | 解耦发布与扩容 | 自建调度器 |

## 关键代码：契约与状态机

第一条可复用的代码不是某个框架，而是“契约”。把能力抽象成窄接口，插件与主进程才能独立演进：

```python
from typing import Protocol, Sequence

class ChatModel(Protocol):
    def chat(
        self,
        messages: Sequence[dict],
        *,
        temperature: float = 0.7,
        max_tokens: int | None = None,
    ) -> str: ...

    def stream_chat(
        self,
        messages: Sequence[dict],
        *,
        temperature: float = 0.7,
    ) -> "Iterator[str]": ...
```

接口越窄，越好替换；但太窄会丢失供应商特性。折中方式是“核心接口 + 可选能力声明”，让调用方按能力而不是按品牌选择。

第二条是状态机。异步任务如果没有明确状态，重试与补偿就无从谈起：

```json
{
  "document_status": ["queued", "indexing", "completed", "failed", "disabled"],
  "transitions": {
    "queued": ["indexing", "failed"],
    "indexing": ["completed", "failed"],
    "failed": ["queued"],
    "completed": ["disabled", "queued"],
    "disabled": ["queued"]
  },
  "retryable": ["failed"],
  "idempotency_key": "document_id + index_version"
}
```

状态机的关键不是状态名，而是“谁能迁移、迁移后做什么”。比如 `failed → queued` 必须清理残留向量，否则重试会写出重复数据；`completed → queued` 必须记录新版本，避免旧任务覆盖新结果。

## 如果我来设计同类系统：取舍清单

- [ ] 先明确用户角色：构建者、调用方、终端用户是否真的需要三套入口
- [ ] 列出所有长任务，定义状态、重试、幂等键与补偿动作
- [ ] 能力清单按“更新频率 × 来源数量”排序，决定哪些必须插件化
- [ ] 工作流变量建立命名规范与输出 schema，变更保留兼容期
- [ ] 所有数据表与缓存键带租户维度，后台任务显式传租户上下文
- [ ] 请求 ID 贯穿入口、队列、模型调用与插件，错误分类可聚合
- [ ] 配置变更走版本与发布，保留上一版本可回滚
- [ ] 允许执行代码或访问 URL 的地方，默认沙箱 + 出站允许列表
- [ ] 向量库、对象存储、元数据库都有备份与恢复演练
- [ ] 为每一处“降级”设计用户可见的提示，不做静默降级

最后一条经验：不要一次性把所有原则都实现。先找出当前系统最痛的失败，用一条原则去解；解决后再看下一条。架构不是原则的堆叠，而是“用可接受的复杂度，换掉不可接受的 failure mode”。
