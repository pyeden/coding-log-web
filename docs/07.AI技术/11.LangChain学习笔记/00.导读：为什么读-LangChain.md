# 00 导读：为什么读 LangChain

## 本章要解决的问题

第一次接触 LangChain 的人，通常会被两件事同时击中：一是它的文档目录长得像一座城市，包、集成、链、Agent、检索、观测各占一片；二是社区里对它的评价极其分裂，一边说「没有它根本写不动」，另一边说「一层没必要的包装，不如自己调 API」。这两种说法都不算错，因为它们评价的根本不是同一个东西。

这一章不铺开 API，而是先回答三个更靠前的问题：LangChain 到底在抽象什么？这些抽象替你省掉了哪些重复劳动，又新增了哪些成本？在 LangChain、LlamaIndex、LangGraph、Dify、n8n 之间，什么时候该用它、什么时候不该用？把这三点想清楚，后面八章读起来才不会变成背诵类名。

## LangChain 的定位

用一句话概括：LangChain 是一个面向大语言模型应用的开发框架，提供 Python 与 JavaScript/TypeScript 两套实现，核心目标是把「调用模型」升级为「编排一个可组合、可观测、可替换的应用」。

这句话里有四个关键词，值得逐一拆开。

**开发框架，不是模型。** LangChain 本身不训练、不托管模型。它通过一层统一的客户端接口去调用各家模型服务，所以你换模型时改的是配置而不是业务代码。模型能力的上限由服务商决定，LangChain 只负责把你和它之间的管道接好。

**双实现。** Python 版本与 JS/TS 版本共享同一套设计理念——Runnable 协议、消息类型、工具调用契约、LCEL 的管道式组合——但具体模块名与部分能力并不完全对齐。跨语言团队要特别注意：概念可以互通，代码不能照抄。

**可组合。** 这是 LangChain 真正的立身之本。提示词、模型、解析器、检索器、工具，都被收敛成同一种可调用对象，于是可以用一个管道符把它们串起来，并且免费获得流式、批量、异步、重试、回退这些横切能力。

**可观测。** 一条链跑通只是开始，线上更常见的问题是「这一步为什么慢了」「这次为什么答错」。框架把每次调用拆成可追踪的 run 树，配合追踪平台才能定位到具体的提示词和模型返回。

## 它解决的三个问题

### 抽象：让不同厂商的模型看起来像同一个

每家模型服务的请求体、消息格式、流式协议、工具调用字段都不一样。如果直接写 HTTP 请求，业务代码里会长满厂商特判。LangChain 用统一的消息类型（System / Human / AI / Tool）与统一的调用接口把差异吃掉，代价是你要接受它的抽象——某些厂商独有的参数只能通过额外的透传字段表达。

### 编排：把「一步调用」变成「一条流水线」

真实应用很少只有一次模型调用。检索要查库、模型要拿检索结果、输出要解析成结构化数据、失败要重试或降级。没有框架时，这些逻辑会以嵌套函数和 try/catch 的形式散落各处；用 Runnable 组合后，它们变成一条声明式的链，控制流与数据流同时可见，测试时也能逐段替换。

### 生态连接：不必为每个集成重写一遍

文档加载器、文本切分、向量库、嵌入模型、工具、追踪——这些部件的接口一旦统一，就能互相插拔。LangChain 生态里绝大多数集成都来自社区贡献，质量参差，但「先能跑通再替换」的路径确实比自己从零对接要快。

| 能力 | 没有框架时 | 用 LangChain 后 | 代价 |
| --- | --- | --- | --- |
| 模型调用 | 每家写一套 HTTP 封装 | 统一客户端 + 消息类型 | 厂商独有参数需透传 |
| 组合编排 | 函数嵌套、手写控制流 | 管道式组合，横切能力内置 | 抽象层增加调试难度 |
| 流式输出 | 自己解析 SSE / chunk | 同一接口返回增量 | 部分集成流式支持不全 |
| 批量与并发 | 手写线程池与限流 | `batch` + `max_concurrency` | 错误处理语义要自己确认 |
| 观测 | 自己打日志 | run 树 + 追踪平台 | 需要额外服务与成本 |
| 集成对接 | 逐个读厂商文档 | 现成 Loader / Store / Tool | 集成质量不齐，需自测 |

## 与相邻工具的边界

初学者最容易混淆的是「都能做 AI 应用，为什么有这么多名字」。它们的差别不在功能清单，而在**抽象层次**与**谁来承担控制流**。

| 工具 | 核心抽象 | 擅长的事 | 不擅长的事 |
| --- | --- | --- | --- |
| LangChain | Runnable / Chain | 通用编排、模型与集成的统一接入 | 复杂有状态流程、可视化运营 |
| LlamaIndex | Index / Query Engine | 数据接入与检索增强，文档密集场景 | 通用工具编排、非检索型流程 |
| LangGraph | State / Node / Edge | 有状态、可循环、可中断的 Agent 流程 | 简单线性链（杀鸡用牛刀） |
| Dify | 应用 / 工作流（可视化） | 低代码搭应用、运营与发布 | 深度定制、复杂代码逻辑 |
| n8n | 节点 / 工作流（自动化） | 系统间集成、定时与事件触发 | 模型语义层的抽象 |

一个实用的判断顺序是：**先问控制流有多复杂，再问谁来维护**。线性、少分支、以检索为主，LlamaIndex 更省事；需要循环、人工审批、断点续跑，LangGraph 更合适；业务方要自己改提示词和流程，Dify 这类平台更现实；只是把系统 A 的数据搬到系统 B 再顺手调一次模型，n8n 足够。LangChain 的位置在中间偏底层：它提供零件和胶水，复杂流程再往上叠 LangGraph。

需要说明的是，这些工具并非互斥。常见组合是「用 LangChain 的模型与检索部件打底，用 LangGraph 编排状态机，用 LangSmith 做追踪」。把 LangChain 理解成「零件库 + 胶水层」比理解成「一站式平台」更接近事实。

## 版本演进与破坏性变更

LangChain 的迭代速度是它最被诟病的地方，而大部分「教程跑不通」都源于版本错位。理解它为什么拆包，比记住具体版本号更有用。

| 阶段 | 主要变化 | 对使用者的影响 |
| --- | --- | --- |
| 0.1 前后 | 拆出 `langchain-core`，把契约与集成分离 | 导入路径大面积变化，旧教程开始失效 |
| 0.2 | 清理早期遗留链与旧式 Agent 写法 | `initialize_agent` 一类接口逐步退场 |
| 0.3 | 收敛依赖、只支持较新的 Python 与 Pydantic 2 | 老项目升级需要处理类型与序列化差异 |
| 1.0 方向 | 官方持续整合抽象、强化与 LangGraph 的协作 | 具体变更以官方迁移指南为准 |

拆包的逻辑值得理解：把「稳定契约」（Runnable、消息、工具）放进 `langchain-core`，把「易变的第三方集成」放进 `langchain-community` 或各家合作包，把「高层组装」留在 `langchain`。这样升级某个集成不会带着整个框架一起动。代价是你要清楚每个类到底住在哪个包里——这也是新手最常见的报错来源。

## 阅读顺序

这八章按「先建立地图，再深入部件，最后回到工程」组织，不建议跳读第一章。

1. **架构总览**：先看包分层与运行时数据流，知道每类能力住在哪一层。
2. **核心抽象**：Runnable 与 LCEL 是全书的地基，后面所有示例都建立在它上面。
3. **模型层**：消息、提示词模板、结构化输出、工具绑定，这是每天都在用的部分。
4. **检索与 RAG**：从文档到上下文的完整链路，以及检索质量的判断方法。
5. **工具与 Agent**：从 ReAct 循环到 LangGraph 的状态机，理解「自主」的边界。
6. **记忆与状态**：会话隔离、检查点、跨会话存储，多轮应用的分水岭。
7. **可观测与评测**：没有追踪和评测，优化只能靠感觉。
8. **工程化**：流式、并发、成本、版本锁定与上线检查。

时间有限时，按 00 → 02 → 03 → 08 阅读，可以覆盖「怎么写」与「怎么不出事」；要做 RAG 再加 04，要做 Agent 再加 05、06。

## 最小可用示例：先建立手感

在读架构之前，先跑通一条最小的链，能帮你把抽象落到具体代码上。安装时建议把「契约层」与「厂商客户端」分开装，而不是只装一个大包——这样依赖关系更清楚，升级时也更容易判断影响范围。

```bash
pip install langchain-core langchain-openai
# 需要高层组合函数时再装 langchain
pip install langchain
```

下面这条链只有三步：把变量填进模板、调用模型、把回复变成字符串。它的价值不在功能，而在于让你亲手验证「一次 `invoke` 会经历哪些环节」。跑通之后，再回头看本章的抽象与分层，理解会具体很多。

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

prompt = ChatPromptTemplate.from_template("用一句话解释：{topic}")
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
chain = prompt | model | StrOutputParser()

print(chain.invoke({"topic": "什么是 LangChain"}))
```

跑通之后可以做两个小实验：把 `invoke` 换成 `stream`，观察输出是否逐字返回；把 `StrOutputParser` 去掉，观察返回对象的类型变化。这两个动作会让你对第二章的 Runnable 协议有直觉，而不是停留在名词层面。

## 版本基线声明

这份笔记写于 2026 年 10 月，结构上对齐 0.3 系列的文档组织方式：`langchain-core` 提供契约、`langchain` 提供高层组装、合作包提供具体厂商客户端、`langgraph` 提供有状态编排。文中不承诺任何具体小版本号与默认参数值，因为这两者变化最快。

阅读时请遵守三条原则：第一，示例代码用于说明结构，复制前先对照官方文档确认导入路径；第二，任何「默认值」都以你锁定的版本为准，不要相信博客；第三，遇到类名不存在，优先怀疑版本与包拆分，而不是怀疑自己写错。

## 常见坑

- [ ] 把 LangChain 当成模型服务，误以为换框架就能提升回答质量
- [ ] 照着两三年前的教程写 `from langchain.xxx import ...`，忽略拆包后的路径
- [ ] 在 Python 与 JS 之间直接翻译代码，忽略两边能力差异
- [ ] 为了一个线性调用引入整条链，增加调试成本却没有收益
- [ ] 把 `langchain-community` 里的集成当成生产级组件，未做可用性验证
- [ ] 用 LangChain 承担本该由 LangGraph 处理的有状态流程
- [ ] 未锁定依赖版本，几天后重新安装就构建失败
