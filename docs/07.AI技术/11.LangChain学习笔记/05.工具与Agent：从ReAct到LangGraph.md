# 05 工具与 Agent：从 ReAct 到 LangGraph

## 本章要解决的问题

「让模型自己决定调用哪个工具」听上去像智能，实际上是一段被反复执行的循环：模型输出一个调用意图，程序执行工具，把结果回填给模型，模型再决定下一步。这段循环能解决检索解决不了的问题——查实时数据、改状态、触发外部动作；也能制造 RAG 时代没有的风险——无限循环、错误参数、越权操作、成本失控。

这一章把 Agent 拆成三层来看：工具怎么定义、循环怎么跑、状态怎么管。理解这三层，你就能判断一个场景到底需不需要 Agent，以及需要多复杂的 Agent。

## 核心概念与术语

| 术语 | 含义 | 关键影响 |
| --- | --- | --- |
| 工具（Tool） | 带名称、描述、参数 schema 的可调用函数 | 描述质量直接决定选择准确率 |
| `bind_tools` | 把工具清单绑定给模型 | 模型只产生调用意图，不执行 |
| ReAct 循环 | 思考 → 调用 → 观察，循环直到收敛 | 简单直接，但缺少显式状态 |
| `AgentExecutor` | 早期封装好的执行循环 | 可用，但定制与可观测性受限 |
| StateGraph | 以状态为核心的图运行时 | 显式节点、边、循环与中断 |
| 条件边 | 按状态决定下一节点 | 实现分支与退出条件 |
| `interrupt` | 在图中间暂停等待外部输入 | 人工审批的基础 |
| 人在回路 | 关键动作前由人确认 | 不可逆操作的最后一道闸 |

## 工具：描述比实现更重要

模型看不到你的函数体，它只能看到工具名、描述与参数 schema。所以「工具选错」的根因通常是描述写得像注释，而不是实现有 bug。

一个好的工具定义包含四件事：动宾结构的名称、说明「什么时候用、什么时候不要用」的描述、边界清晰的参数、明确的返回结构。描述里写清反面场景，能显著降低误调用——例如「仅在用户明确要求退款时使用；咨询政策请用知识库检索」。

```python
from langchain_core.tools import tool

@tool
def query_order(order_id: str) -> dict:
    """按订单号查询订单状态。

    仅在用户提供了订单号时调用。若用户只是询问配送政策，
    请改用知识库检索工具，不要调用本工具。
    """
    # 真实实现应做鉴权与超时控制
    return {"order_id": order_id, "status": "shipped", "eta_days": 2}
```

参数 schema 越窄越好。用枚举代替自由字符串、用必填标记减少缺参、用类型约束减少解析失败。工具返回也要克制：返回一大段原始 JSON 会挤占上下文，返回结构化摘要加必要标识更实用。

## ReAct 循环的本质

ReAct 的核心不是「让模型思考」，而是**把一次不可控的长推理，拆成若干次可控的小步骤**。每一步模型只做一件事：决定调用哪个工具、传什么参数，或者判断可以结束。程序负责执行与回填。

| 阶段 | 谁在做 | 产出 | 失败表现 |
| --- | --- | --- | --- |
| 思考 | 模型 | 下一步意图 | 反复犹豫、空转 |
| 调用 | 程序 | 工具执行结果 | 参数错误、超时、异常 |
| 观察 | 模型 | 是否需要继续 | 忽略结果、重复调用 |
| 收敛 | 模型/程序 | 最终答案或终止 | 不收敛、超步数 |

这条循环有三个必须由程序守住的边界：**最大步数**（防止无限循环）、**单次超时**（防止卡死）、**成本上限**（防止 token 爆炸）。模型没有「我该停了」的可靠直觉，停止条件必须写在代码里。

## 从 AgentExecutor 到 LangGraph

早期的 `AgentExecutor` 把循环封装好了，上手很快。但它的控制流是隐式的：你很难在中途插入人工审批、很难把中间状态持久化、很难在失败后从断点继续。这些恰好是生产环境最需要的。

LangGraph 的思路是把循环显式画出来：状态是一个可在节点间传递的对象，节点是函数，边决定走向，条件边实现分支，检查点负责持久化。这样「第几步、停在哪、下次从哪继续」都变成可查询的事实，而不是黑盒内部状态。

| 维度 | AgentExecutor 风格 | LangGraph 风格 |
| --- | --- | --- |
| 控制流 | 框架内置循环 | 显式图结构，自己定义 |
| 状态 | 隐含在循环内部 | 显式 State，可检查点 |
| 中断与审批 | 支持有限 | 原生 `interrupt` |
| 断点续跑 | 需自行设计 | 依赖 checkpointer |
| 适用场景 | 单轮工具调用、原型 | 多步流程、长任务、需审批 |

## 一个最小状态图

下面的例子展示结构：定义一个状态、两个节点、一条条件边。真实项目里节点内部通常还会调用模型决定下一步，这里用简化逻辑突出骨架。

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    question: str
    notes: list[str]
    answer: str

def retrieve(state: State) -> dict:
    return {"notes": [f"检索到的资料片段：{state['question']}"]}

def answer(state: State) -> dict:
    joined = "\n".join(state["notes"])
    return {"answer": f"基于资料作答：{joined}"}

graph = StateGraph(State)
graph.add_node("retrieve", retrieve)
graph.add_node("answer", answer)
graph.add_edge(START, "retrieve")
graph.add_edge("retrieve", "answer")
graph.add_edge("answer", END)

app = graph.compile()
print(app.invoke({"question": "如何申请退款", "notes": [], "answer": ""})["answer"])
```

加入循环与退出条件时，用条件边读取状态决定走向。下面用伪代码示意结构，具体 API 名称以官方文档为准。

```python
def should_continue(state: State) -> str:
    if state.get("answer"):
        return "done"
    if len(state.get("notes", [])) >= 3:
        return "give_up"
    return "retrieve"

graph.add_conditional_edges("retrieve", should_continue, {
    "retrieve": "retrieve",
    "done": "answer",
    "give_up": "answer",
})
```

## 人在回路与不可逆操作

凡是「发消息、下单、退款、删除数据」这类不可逆动作，都不应该让模型单方面决定。标准做法是在执行节点前插入中断：图跑到这里暂停，把待确认的动作与参数展示给人，人确认后再恢复执行。

这带来两个工程要求：一是状态必须可持久化，否则进程重启后人确认了也接不上；二是待确认内容必须包含足够上下文，让人能判断——只显示「是否继续」等于把责任推给人却没有给信息。

```python
from langgraph.types import interrupt

def confirm(state: State) -> dict:
    decision = interrupt({"action": "refund", "amount": state.get("amount")})
    return {"approved": bool(decision)}
```

## 工具调用失败与幻觉参数

Agent 的失败大多不是「模型不会用工具」，而是「模型编了参数」。处理清单如下：

- [ ] 执行前校验参数类型与枚举，不合法直接返回结构化错误
- [ ] 对不存在的资源（订单号、用户 ID）返回明确错误码，而非空结果
- [ ] 工具异常转换成模型可读的错误信息，避免整条链崩溃
- [ ] 同一工具连续失败两次后强制终止或转人工
- [ ] 对写操作做幂等（请求去重、幂等键），防止重试造成重复副作用
- [ ] 记录每次调用的入参出参，便于复盘幻觉参数
- [ ] 限制单会话工具调用总次数与总耗时

一个容易被忽略的细节：把错误信息回填给模型时，要写「为什么错、你能怎么修正」，而不是抛一段堆栈。模型看不懂堆栈，但能理解「order_id 必须是 12 位数字，你给的是 8 位」。

## 状态设计：只存该存的

图的状态是整个系统的“共享内存”，设计得好，节点之间不用互相知道对方；设计得差，它会变成一个新的全局变量。三条原则值得遵守。

第一，**状态只放可序列化的事实**，不放数据库连接、客户端实例、临时缓存。第二，**消息列表与业务字段分开**，消息用于模型上下文，业务字段用于分支判断，不要把关键状态藏在自然语言里。第三，**每增加一个字段就问一句：谁会读它**。没有人读的字段只是噪声，还会在检查点里反复落盘。

一个真实的反例是把“用户当前情绪”用一段描述存在消息里，然后在条件边里用子串匹配判断。这种写法在演示里能跑，上线后只要模型换个措辞就会失效。正确做法是用结构化字段加枚举值，由模型通过结构化输出写入。

## 什么时候不该用 Agent

如果流程是固定的三步，写死比让模型决定更可靠、更便宜、更好测。Agent 的价值出现在**步骤数量不确定、需要根据中间结果决定下一步**的场景。判断标准很简单：如果你能画出一张完整的流程图并且分支有限，就用链或图；如果画不出来，才交给模型决定。

另外，Agent 的可观测性要求比链高得多。没有追踪，你只能看到「最后答错了」，看不到它在第几步走偏。第七章的观测能力，是 Agent 上线的前置条件。

## 常见坑

- [ ] 工具描述只写功能不写边界，导致误调用
- [ ] 没有最大步数与超时，偶发无限循环耗尽额度
- [ ] 把写操作交给模型自由调用，缺少人工确认
- [ ] 工具返回原始大 JSON，挤爆上下文
- [ ] 错误信息不可读，模型无法自我修正
- [ ] 用 Agent 处理本可以写死的固定流程
- [ ] 没有持久化状态，中断后无法恢复
