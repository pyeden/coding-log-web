# 07 可观测与评测：Tracing 与数据集评估

## 本章要解决的问题

链跑通了，接着是永无止境的调优：改提示词、换模型、调切块、加重排。问题是每次改动之后，你怎么知道它变好了？如果答案是「拿几个问题试了试，感觉还行」，那你不具备迭代能力——你只有运气。

这一章讲两件事：**看见**（追踪每次调用发生了什么）与**衡量**（用固定数据集判断改动是否有效）。前者解决「线上为什么慢/错」，后者解决「改了到底有没有用」。两者合起来，才构成一个可以持续优化的系统。

## 核心概念与术语

| 术语 | 含义 | 作用 |
| --- | --- | --- |
| Trace | 一次请求的完整调用记录 | 端到端排查的入口 |
| Run | trace 中的一个节点 | 对应一次链/模型/工具调用 |
| Span 层次 | run 之间的父子关系 | 定位慢在哪一层 |
| Dataset | 固定的输入-期望输出集合 | 回归评测的基线 |
| Evaluator | 对输出打分的函数或模型 | 把主观判断变成可比较的数字 |
| 实验（Experiment） | 在数据集上跑一次配置 | 用于对比不同版本 |
| PII | 个人身份信息 | 追踪数据脱敏的重点 |

## 开启追踪

LangChain 的追踪通过环境变量开启：设置开关、API key 与项目名，之后所有 Runnable 调用会自动上报。LangSmith 是官方平台，其他观测后端通常也支持通过回调接入。

```bash
export LANGCHAIN_TRACING_V2=true
export LANGSMITH_API_KEY="<your-key>"
export LANGCHAIN_PROJECT="coding-log-prod"
```

三个变量里最容易出错的是项目名。它决定数据落到哪个面板，命名建议带上环境（dev / staging / prod），否则测试流量会淹没生产数据，排查时找不到重点。

```python
# 也可以只对特定调用开启，避免把本地调试混进生产项目
result = chain.invoke(
    {"question": "退款政策是什么"},
    config={"run_name": "rag-answer", "tags": ["prod", "faq"], "metadata": {"user_tier": "pro"}},
)
```

`run_name` 与 `tags` 不是装饰。追踪面板里最常见的操作是「筛出某一类请求」，没有标签就只能靠时间戳大海捞针。

追踪还有一项常被低估的价值：它让「延迟」变得可分。用户抱怨的“慢”可能是模型首字慢、可能是检索慢、也可能是工具调用链太长。只看总耗时无法区分，而 trace 的层级结构会直接告诉你是哪一段占了大头，优化才有方向。

## trace 的层次结构

一次 RAG 请求会展开成一棵树，理解这棵树才知道该看哪一层。

| 层次 | 典型内容 | 排查价值 |
| --- | --- | --- |
| Chain（根） | 整条链的输入输出、总耗时 | 判断整体是否异常 |
| Retriever | 查询、命中文档、耗时 | 召回是否准确、是否慢在检索 |
| Prompt | 模板变量与最终消息 | 上下文是否被正确组装 |
| LLM | 请求参数、token 数、首字延迟 | 成本与延迟的主要来源 |
| Parser | 原始输出与解析结果 | 结构化失败的直接证据 |
| Tool | 工具名、参数、返回 | Agent 走偏的定位点 |

一个实用的排查顺序是：先看根节点耗时分布，再看 LLM 的 token 与首字延迟，最后看 Retriever 的命中文档。绝大多数「答得不好」在这三步内能定位到具体环节。

## 用数据集做评测

评测的最小闭环是三步：准备数据集、定义评估器、跑实验对比。数据集不需要很大，二三十条覆盖典型场景的问题就足以发现明显退步；关键是**固定**——同一份数据、同一套评估器，才具备可比性。

```python
from langsmith import Client, evaluate

client = Client()

def answer_question(inputs: dict) -> dict:
    return {"answer": chain.invoke(inputs["question"])}

def correctness(run, example) -> dict:
    # 简化示意：实际可用规则匹配、模型打分或人工标注
    expected = example.outputs["answer"]
    got = run.outputs["answer"]
    return {"key": "correctness", "score": 1.0 if expected in got else 0.0}

results = evaluate(
    answer_question,
    data="rag-faq-baseline",
    evaluators=[correctness],
    experiment_prefix="prompt-v3",
)
```

评估器的选择取决于你关心什么：

| 指标 | 衡量什么 | 适用场景 | 注意 |
| --- | --- | --- | --- |
| 正确性 | 是否与标准答案一致 | 有明确答案的任务 | 表述多样时误判多 |
| 忠实度 | 是否只依据给定资料 | RAG | 需要资料作为输入 |
| 相关性 | 是否回答了问题 | 开放问答 | 判定标准较主观 |
| 格式合规 | 是否符合 schema | 结构化输出 | 规则可完全自动化 |
| 延迟与成本 | 耗时、token | 全场景 | 与质量指标一起看 |

不要只盯一个指标。常见的情况是准确率提升但平均 token 翻倍，或者延迟下降但忠实度变差，这些都需要同时观察才能发现。

## 评测集怎么建才有用

一份能用的评测集有三个特征：**来自真实流量**、**覆盖失败模式**、**有可判定的期望**。从日志里摘取真实问题，比凭空编造更接近分布；覆盖失败模式意味着要主动加入“资料里没有答案”“表述含糊”“多条件组合”这类难例；可判定的期望不一定是标准答案，也可以是一组必须命中的关键词或必须出现的引用。

规模上，二十到五十条足以支撑日常迭代，上千条未必更好——维护成本高，而且每次改动都要等很久。建议分两层：一个十到十五条的“快速集”，每次改提示词都跑；一个更大的“全量集”，发版前跑。

还有一条组织建议：把评测集按场景分组（问答、抽取、拒答、工具调用），报告里分场景看指标。只看总体平均分很容易掩盖局部退步，比如整体准确率涨了两个点，但拒答能力崩了。

## 模型作为评估器的取舍

用更强的模型给输出打分，可以覆盖开放式问题，但引入两个问题：评估本身有成本，且评估结果带有评估模型的偏好。工程上的折中是：规则能判的用规则（格式、关键词、引用是否存在），规则判不了的用模型，并且定期人工抽检校准。

另一个细节是**评估集要包含反例**：资料里没有答案的问题，正确行为是拒答而不是编造。只测「能答对的」，会让系统在真实场景里显得比实际更可靠。

## 日志脱敏与 PII

追踪会把提示词、模型输出、检索文档原样记录下来。如果用户输入里有手机号、身份证号、地址，这些都会进入第三方平台。这不是理论风险，而是合规问题。

处理方式有三层：入口处对敏感字段做掩码或哈希；追踪配置里过滤掉不需要记录的字段；选择支持数据驻留与保留策略的后端。如果业务不允许数据出域，就必须自建观测，而不是用 SaaS。

## 自建观测的取舍

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| LangSmith | 与框架深度集成，开箱可用 | 数据出境、按量计费 |
| 自建（OpenTelemetry 等） | 数据可控、可与现有监控打通 | 需要自己实现语义约定与面板 |
| 混合 | 生产自建、研发用 SaaS | 两套体系，口径需对齐 |

判断标准是数据敏感度与团队运维能力。内部工具用 SaaS 最省事；涉及用户隐私或强合规要求时，自建或私有化部署更现实。

无论选哪种，都应该把追踪当作产品功能的一部分而不是调试附件：出问题时它能把“用户说答错了”变成具体的提示词、命中文档与模型输出；没有它，排查只能靠重现，而 LLM 的输出本身就不保证可重现。

## 从追踪到回归

有了追踪与评测，迭代流程应该是：线上发现坏案例 → 加入数据集 → 改一版 → 跑实验 → 对比指标与成本 → 灰度上线 → 继续观察。缺少任何一环，优化就会退化成猜测。

这里有一个常被跳过的步骤：**把线上坏案例变成测试用例**。追踪面板里的每条失败请求都是免费的标注数据，不沉淀下来，下次还会犯同样的错。

此外，评测要与发布绑定。没有跑过评测集的版本不应该上生产，这条规则比任何工具都重要，因为它把“质量”从个人习惯变成了流程约束。

## 常见坑

- [ ] 未设置项目名，开发与生产数据混在一起
- [ ] 只看最终答案，不看检索命中与提示词组装
- [ ] 评测集只有正例，模型编造时无人发现
- [ ] 每次改动换一套评估器，结果无法横向比较
- [ ] 追踪里包含完整用户输入，未做脱敏
- [ ] 用单一指标决策，忽略成本与延迟
- [ ] 线上坏案例不回流，问题反复出现
