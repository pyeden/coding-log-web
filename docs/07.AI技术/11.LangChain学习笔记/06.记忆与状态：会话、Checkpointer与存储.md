# 06 记忆与状态：会话、Checkpointer 与存储

## 本章要解决的问题

多轮对话的第一个版本几乎都是「把所有历史拼进提示词」。它在前十轮工作得很好，然后在某个时刻同时暴露三个问题：token 成本随轮次线性上涨、模型开始忽略早期指令、超过上下文窗口直接报错。更麻烦的是并发场景——两个用户同时对话，历史互相串了。

这一章区分两类东西：**短期记忆**是「这次对话的上下文」，有窗口限制，必须裁剪；**长期记忆**是「跨会话的事实」，需要外部存储与检索。此外还要讲清一个更底层的概念：状态放在哪里，决定了你能不能中断、能不能恢复、能不能并发。

## 核心概念与术语

| 术语 | 含义 | 生命周期 |
| --- | --- | --- |
| 短期记忆 | 当前会话的消息历史 | 单次会话，受上下文窗口约束 |
| 长期记忆 | 跨会话保留的用户偏好与事实 | 持久，需检索与更新策略 |
| 裁剪（trim） | 按 token 数或轮次保留最近消息 | 每次调用前执行 |
| 摘要压缩 | 把旧历史概括成一段摘要 | 定期执行，替代原始消息 |
| Checkpointer | 保存图执行状态的机制 | 每步或每轮持久化 |
| `thread_id` | 会话标识，用于隔离状态 | 与用户/会话绑定 |
| Store | 跨线程的键值存储 | 长期记忆的载体 |

## 短期记忆：裁剪与摘要

历史不能无限增长，这一点没有争议；有争议的是怎么删。三种常见策略各有代价。

| 策略 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 保留最近 N 轮 | 只取尾部消息 | 简单、可预测 | 早期承诺与约束会丢失 |
| 按 token 预算裁剪 | 按 token 计数从尾部保留 | 更贴近真实成本 | 需要 tokenizer，计数有误差 |
| 摘要 + 最近若干轮 | 旧消息压缩成摘要 | 保留长期要点 | 摘要有损，且需额外调用 |

实践中常把「系统消息 + 摘要 + 最近若干轮」组合起来：系统消息始终保留（它承载约束），中间用摘要承接早期对话，尾部保留原始消息保证连贯性。裁剪时要注意消息配对——工具调用消息与工具结果消息不能被切开，否则会出现格式错误。

```python
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage, trim_messages

messages = [SystemMessage(content="你是严谨的技术助理。")] + history

trimmed = trim_messages(
    messages,
    max_tokens=2000,
    strategy="last",
    token_counter=model,          # 用模型自带的计数器更接近真实
    include_system=True,          # 系统消息必须保留
    start_on="human",             # 从一条用户消息开始，避免开头是孤立回复
)
```

`trim_messages` 的参数含义在各版本间基本稳定，但 token 计数方式与模型支持程度有差异，接入前建议用真实对话验证一次截断位置是否符合预期。

## 长期记忆：Store 与检索

短期记忆解决「这次说了什么」，长期记忆解决「这个人是谁、偏好什么、之前决定过什么」。它不该塞进历史，而应该被检索出来。

LangGraph 的 Store 提供了跨线程的键值存储：以命名空间与键组织数据，可以在节点里写入，也可以按语义检索（取决于具体实现的后端）。典型用法是在对话结束后抽取事实写入，在下一次对话开始时按用户 ID 检索相关条目。

```python
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
namespace = ("users", "u_1001")

store.put(namespace, "pref_language", {"value": "中文", "confidence": 0.9})
item = store.get(namespace, "pref_language")
print(item.value if item else "未记录")
```

长期记忆真正的难点不是存储，而是**更新与冲突**。用户先说「用中文」，后来说「以后都用英文」，如果两条都留着，检索时就会互相矛盾。工程上通常给每条记忆加时间戳与置信度，写入时按主题去重覆盖，读取时取最新且置信度最高的一条。

## Checkpointer：状态放在图里

一旦流程有多个步骤、可能中断、需要恢复，状态就不能只放在内存变量里。Checkpointer 的作用是：每执行一步，把当前状态存一份快照，并关联到 `thread_id`。这样同一个 `thread_id` 再次调用时，会从上次的快照继续。

| 实现 | 适用场景 | 特点 |
| --- | --- | --- |
| 内存 | 本地调试、单进程 | 重启即丢失，不能用于生产 |
| SQLite | 单机服务、中小规模 | 零运维，写入串行需注意 |
| Postgres | 多实例部署 | 支持并发与备份，需要连接池 |

```python
from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import StateGraph, START, END

checkpointer = MemorySaver()
app = graph.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "user-1001-session-7"}}
app.invoke({"messages": [("human", "我叫小林，做后端")]}, config)
app.invoke({"messages": [("human", "我刚才说我做什么？")]}, config)
```

第二段调用能记住第一段，靠的不是提示词里拼了历史，而是同一个 `thread_id` 恢复了状态。这就是「状态放在图里」与「历史放在字符串里」的本质差别：前者是可查询、可恢复、可并发隔离的结构化状态；后者是一段越来越长、越来越贵的文本。

生产环境要注意三件事：**thread_id 的生成规则**必须稳定且不可猜测；**检查点保留策略**要定，否则存储无限膨胀；**并发写入同一 thread** 要有锁或队列，否则后写覆盖先写。

## 一个常见的设计错误

很多人把「记忆」实现成全局变量或进程内字典，按用户 ID 索引。单机演示没问题，一旦多实例部署就会出现「同一个用户这次连到 A 实例、下次连到 B 实例，记忆消失」。正确做法是把状态放到共享存储（Postgres、Redis 或专门的 Store），进程只做无状态计算。

另一个错误是把长期记忆混进短期历史。结果是每次对话都把用户全部档案拼进提示词，成本高且噪声大。正确做法是按需检索：先判断这次任务需要哪些事实，再取对应条目。

与此相关的一个判断是：不要把“模型应该记住的事”和“系统应该知道的事”混在一起。偏好、称呼、已确认的决策适合写入长期记忆；权限、余额、订单状态属于业务数据，应该每次从数据库现查。把后者写成记忆，只会得到一份注定过期的快照。

## 把历史组织成提示词

裁剪只是手段，最终目的是让模型看到一份“既能理解上下文、又不超预算”的消息序列。一个稳定的组织顺序是：系统约束在最前，接着是长期记忆摘要（以事实陈述而非对话片段的形式），再是近期对话，最后是本次用户输入。

这个顺序不是审美选择。系统约束在最前是因为它定义行为边界；事实摘要用陈述句是因为它比一句句对白更省 token 且不易被误读为指令；近期对话靠后是因为它最影响当前回复的风格与指代。把长期记忆放在最后，模型容易把它当成新输入而过度响应。

另一个细节是关于“重置”。当用户切换话题或明确说“重新开始”，旧历史往往变成干扰。工程上可以提供一个显式的会话派生机制：新建 `thread_id`，需要时再把长期记忆带过去。比在旧历史里插入一句“忽略前面的话”可靠得多。

## 序列化与迁移

检查点要落盘就必须序列化。这里有两个坑：一是自定义对象可能无法序列化，导致写入失败；二是版本升级后旧检查点的结构不兼容，恢复时报错。

规避方式很朴素：状态里只放基本类型与消息对象，复杂对象存引用（ID）而不是实体；升级前先在测试环境验证旧检查点能否读取，必要时做一次性迁移或清理。

另一个常被忽略的运维问题是**清理**。检查点不是业务数据，不应该永久保留；按“天/小时”设定保留期，并确保删除不会影响正在进行的会话。如果使用关系型数据库，定期看一下表体积与索引大小，很多“突然变慢”都是检查点表膨胀导致的。

## 常见坑

- [ ] 历史无限追加，成本和延迟随轮次上涨
- [ ] 裁剪时切断工具调用与工具结果，导致格式错误
- [ ] 用进程内字典存会话，多实例部署后记忆丢失
- [ ] `thread_id` 用时间戳或随机数，无法恢复上一次会话
- [ ] 长期记忆只写不更新，新旧事实冲突
- [ ] 检查点不设保留期，数据库持续膨胀
- [ ] 状态里塞入不可序列化的对象，落盘失败
- [ ] 多用户共享同一 thread，出现串话
