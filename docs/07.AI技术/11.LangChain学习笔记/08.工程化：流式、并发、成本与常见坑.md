# 08 工程化：流式、并发、成本与常见坑

## 本章要解决的问题

前七章解决的是「能不能做出来」，这一章解决「能不能稳定跑下去」。上线之后，问题会变得非常具体：首字延迟三秒用户就关页面、晚高峰并发把接口打成 429、月底账单比预期高四倍、某个依赖升级后整条链报错、灰度发布时新旧版本行为不一致。

这些不是模型问题，是工程问题。本章按「用户体验 → 吞吐 → 成本 → 可维护性 → 上线」的顺序，给出一套可以直接落地的做法。

## 核心概念与术语

| 术语 | 含义 | 关注点 |
| --- | --- | --- |
| `stream` | 逐块返回最终输出 | 前端拼接、首字延迟 |
| `astream_events` | 按事件流返回中间过程 | 展示「正在检索/正在生成」 |
| 回调（Callback） | 在调用生命周期插入钩子 | 日志、进度、自定义指标 |
| 背压 | 下游消费慢导致上游阻塞 | 流式连接的稳定性 |
| 限流 | 主动控制单位时间请求数 | 避免触发服务商配额 |
| 缓存 | 命中相同输入直接返回 | 成本与延迟双降 |
| 模型路由 | 按难度选择不同模型 | 成本结构优化 |
| 依赖锁定 | 固定版本与哈希 | 构建可复现 |

## 流式的三种模式

| 模式 | 拿到什么 | 适合场景 | 代价 |
| --- | --- | --- | --- |
| `stream` | 最终输出的增量片段 | 纯文本聊天 | 看不到中间步骤 |
| `astream_events` | 各节点的事件（开始、增量、结束） | 需要展示「检索中」「生成中」 | 事件多，前端需过滤 |
| 回调 | 自定义钩子触发 | 埋点、审计、进度条 | 需自行处理线程与异常 |

`astream_events` 的关键是事件过滤。一条链会产出大量事件，前端只关心其中两三类，不过滤会把带宽和渲染都拖垮。

```python
async for event in chain.astream_events({"question": "退款政策"}, version="v2"):
    kind = event["event"]
    if kind == "on_chat_model_stream":
        chunk = event["data"]["chunk"]
        if chunk.content:
            print(chunk.content, end="", flush=True)
    elif kind == "on_retriever_end":
        print(f"\n[检索到 {len(event['data']['output'])} 条资料]")
```

对接前端时建议用 SSE 而不是 WebSocket：单向推送、断线重连语义清晰、经过代理更友好。后端在 `StreamingResponse` 里逐条写出，注意设置 `X-Accel-Buffering: no` 一类头部，避免反向代理缓冲把流变成一次性返回。

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import json

app = FastAPI()

@app.post("/chat")
async def chat(payload: dict):
    async def gen():
        async for event in chain.astream_events(payload, version="v2"):
            if event["event"] == "on_chat_model_stream":
                text = event["data"]["chunk"].content
                if text:
                    yield f"data: {json.dumps({'delta': text}, ensure_ascii=False)}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(gen(), media_type="text/event-stream")
```

流式带来的一个隐性成本是**错误处理变复杂**：响应头已经发出，中途出错无法再返回 500。常见做法是在流里发送一条结构化错误事件，由前端提示重试。

## 并发、限流与重试

并发控制有三层，缺一不可。

**应用层**：用信号量限制同时在飞的请求数，避免把服务商配额一次性打满。**协议层**：`batch` 的 `max_concurrency` 控制批量任务的并发。**重试层**：指数退避加随机抖动，并区分可重试错误（限流、超时、5xx）与不可重试错误（参数错误、内容审核）。

```python
import asyncio

sem = asyncio.Semaphore(8)

async def guarded(question: str) -> str:
    async with sem:
        return await chain.ainvoke({"question": question})

async def run_all(questions: list[str]):
    tasks = [guarded(q) for q in questions]
    return await asyncio.gather(*tasks, return_exceptions=True)
```

注意 `gather` 的 `return_exceptions=True`：没有它，一个失败会取消其余任务，批处理场景下非常浪费。拿到结果后要显式区分异常与正常值，不要假设都是字符串。

重试的另一个陷阱是**幂等**。读操作重试无害，写操作重试可能造成重复下单、重复扣款。写操作要么带幂等键，要么不自动重试。

限流还有一层容易被忽略：**入口**。即使内部并发控制得很好，外部用户或爬虫瞬时流量仍可能把整个服务拖住。在网关层做每用户速率限制、对超长输入设上限，比在模型调用层做补救便宜得多。

## 成本控制的四个杠杆

| 杠杆 | 做法 | 节省幅度 | 风险 |
| --- | --- | --- | --- |
| 缓存 | 相同输入命中缓存直接返回 | 高（重复请求多时） | 数据时效性、缓存键设计 |
| 模型路由 | 简单任务走小模型，复杂任务升级 | 中高 | 路由判断错误导致质量下降 |
| 提示词瘦身 | 删冗余示例、压缩检索上下文 | 中 | 可能损失准确率 |
| 输出约束 | 限制 `max_tokens`、要求简洁 | 中 | 截断风险 |

缓存要注意键的构成：提示词、模型名、温度、检索结果版本都应参与哈希。只按用户问题做键，会在知识库更新后返回过期答案。LangChain 提供全局缓存接口，可接内存或数据库后端，具体导入路径随版本变化，接入前以官方文档为准。

```python
from langchain_core.globals import set_llm_cache
from langchain_community.cache import SQLiteCache

set_llm_cache(SQLiteCache(database_path=".langchain_cache.db"))
```

模型路由的最小实现是按输入长度与任务类型分流：分类、抽取、格式化走小模型；需要推理与长文生成走大模型。上线前用评测集验证分流没有明显掉点。

四个杠杆里，**缓存与瘦身的收益最确定**，因为它们不改变模型能力；路由与输出约束则要配合评测，否则很容易用质量换成本。实际操作时建议先测一遍“哪些请求在重复”，再决定加不加缓存，而不是一开始就上全套。

## 版本锁定：LangChain 最大的痛点

依赖漂移是这套生态最常见的事故来源。同一份代码，今天装和一个月后装，可能因为间接依赖升级而行为不同。三条硬性做法：

- 用锁文件固定全部直接与间接依赖，CI 与生产使用同一份；
- 生产环境只装锁定版本，不使用范围升级；
- 升级时按「读迁移说明 → 跑评测集 → 灰度 → 观察一周」的流程走，不跳步。

| 检查项 | 目的 |
| --- | --- |
| 锁文件已提交 | 构建可复现 |
| 核心包与 provider 包版本兼容 | 避免接口错配 |
| Python / Node 版本固定 | 避免运行时差异 |
| 升级前后评测对比 | 量化影响 |
| 回滚方案可用 | 出问题时能退回 |

## 部署形态

两种常见形态：**自建服务**（FastAPI/Express 包一层，暴露 HTTP 或 SSE 接口）与**图服务**（用 LangGraph Server 一类运行时托管图与检查点）。前者灵活、可控，适合已有后端体系；后者省去状态与并发的基础设施，适合以图为核心的应用。

无论哪种，都要准备好：健康检查、超时与熔断、结构化日志、追踪开关、密钥从环境注入（不要写进镜像）、以及一个能一键回滚的发布流程。

部署形态的选择还应考虑状态存在哪里。把检查点放在服务本地磁盘上，看似简单，但一旦水平扩容就会出现“请求到了另一台实例、会话丢失”的问题。要么粘性会话加本地存储，要么直接用共享数据库，后者在运维上更可靠，代价是多一层网络往返。

## 提示词也是代码

上线之后，提示词往往比模型选型更容易引发事故：有人直接在后台改了模板，把输出格式的约束删了，下游解析全线失败。把提示词当配置随意热改，是把一个强类型接口降级成了运行时字符串。

合理的做法是：提示词存仓库、有版本号、变更走评审、与评测集绑定。热更新可以做，但必须限定在“措辞微调”层面，结构、输出格式、工具清单这类约束不允许绕过发布流程。同时保留回滚能力——出现异常时可以一键切回上一版提示词，而不是花半小时手动复原。

## 上线前检查清单

- [ ] 首字延迟与整体延迟在目标网络下实测过
- [ ] 流式中断、超时、错误事件都有前端兜底
- [ ] 并发上限与重试策略已配置，且有退避
- [ ] 写操作幂等，重试不会产生重复副作用
- [ ] 缓存键包含模型与知识版本，避免过期答案
- [ ] 依赖锁定，CI 与生产一致
- [ ] 追踪已开，敏感字段已脱敏
- [ ] 评测集可一键运行，基线指标有记录
- [ ] 成本有日/周监控与告警阈值
- [ ] 有明确回滚步骤与责任人

## 常见坑

- [ ] 反向代理缓冲导致「流式」实际一次性返回
- [ ] 流中出错无法返回状态码，前端一直转圈
- [ ] 批处理未限制并发，触发服务商限流
- [ ] 对所有错误一律重试，把配额耗尽
- [ ] 缓存键过粗，知识更新后仍返回旧答案
- [ ] 只用一个模型，成本与质量都没有优化空间
- [ ] 依赖用范围版本，构建结果不可复现
- [ ] 上线未做压测，高峰直接雪崩
