# 01 架构总览：包分层与运行时

## 本章要解决的问题

装完 LangChain 的第一天，你会遇到一个很具体的困惑：`ChatOpenAI` 到底从哪导入？为什么有的教程写 `langchain.chat_models`，有的写 `langchain_openai`，还有的写 `langchain_community`？同一个能力散落在三个包里，是混乱，还是有意为之？

这一章把包结构当成一张地图来读：每一层负责什么、依赖指向哪边、哪些层会频繁变化、哪些层值得你信任。读完你应该能回答两个问题——「这个模块该住在哪个包」以及「一次 `invoke` 内部到底发生了什么」。前者决定你查文档的效率，后者决定你排查问题的方向。

## 核心概念与术语

| 包 / 概念 | 职责 | 稳定性 | 典型内容 |
| --- | --- | --- | --- |
| `langchain-core` | 定义契约与基础类型 | 高，变更谨慎 | Runnable、消息、提示词模板、工具接口、输出解析器 |
| `langchain` | 高层组装与常用链 | 中 | `create_retrieval_chain` 一类组合函数、通用链 |
| `langchain-community` | 社区贡献的第三方集成 | 低，维护等级不齐 | 大量 Loader、VectorStore 适配、老式工具 |
| `langchain-<provider>` | 官方合作包，单一厂商精修 | 中高 | `langchain-openai`、`langchain-anthropic` 等 |
| `langgraph` | 有状态图运行时 | 中高，演进快 | StateGraph、检查点、中断、持久化 |
| `langsmith` | 观测与评测的客户端 | 中 | trace 上报、数据集与评估接口 |
| Runnable | 一切可调用对象的统一协议 | 高 | `invoke` / `batch` / `stream` 及其异步版本 |

## 分层不是洁癖，是依赖方向

把上面几张表放在一起看，会发现一条清晰的依赖方向：**上层依赖下层，下层绝不知道上层**。`langchain-core` 不导入任何厂商 SDK；`langchain-community` 依赖 `langchain-core`；应用代码依赖上面所有层，但只应该主动接触 `langchain-core` 与具体的 provider 包。

这条规则解释了三个常见现象。

第一，`langchain-community` 里为什么有那么多「能用但没人管」的集成。它本质是一个贡献池，收录门槛低、维护者分散，适合验证想法与内部工具，不适合作为生产依赖的核心路径。选型时优先找有没有独立的合作包，有就用合作包。

第二，为什么升级 `langchain` 有时不影响你的代码。因为你的代码真正依赖的是 `langchain-core` 里的 Runnable 与消息类型，只要这层契约不变，高层包的调整就伤不到你。反过来，如果你的代码到处 `from langchain.xxx import ...`，就相当于把自己绑在了变化最快的那一层。

第三，为什么 `langgraph` 是独立包而不是 `langchain` 的子模块。它解决的是另一类问题——有状态、可循环、可中断的流程编排——与「零件库」的定位不同。把两者解耦，才能让只想用零件的人不必背上图运行时的复杂度。

## 运行时的数据流

一条最朴素的链只有三个环节：提示词把输入组装成消息，模型把消息变成回复，解析器把回复变成你要的结构。这条数据流看起来简单，但每个环节都在做隐形的工作。

**提示词环节**负责两件事：变量填充与消息序列构造。它决定了模型「看到什么」，也决定了多轮对话里历史消息以什么顺序、什么角色出现。模板里的变量名与调用时传入的字典键必须严格对应，这类错误在编译期发现不了，只会在运行时抛 KeyError。

**模型环节**负责把消息序列序列化成厂商请求，再把响应反序列化成统一的消息对象。流式与非流式的差别在这里被吸收：非流式一次性返回完整消息，流式则把增量片段拼成同一个消息对象。

**解析器环节**负责把自然语言变成程序可用的数据。它可能是简单的字符串提取，也可能是 JSON 解析加 Pydantic 校验。这里是幻觉最容易暴露的地方——模型输出格式稍有偏差，解析就会失败，而失败信息往往比模型回答本身更有价值。

| 环节 | 输入 | 输出 | 失败时的典型表现 |
| --- | --- | --- | --- |
| Prompt | 业务字典 | 消息序列 | 变量缺失、角色顺序错误 |
| Model | 消息序列 | AI 消息 | 超时、限流、上下文超限 |
| Parser | AI 消息内容 | 结构化数据 | JSON 截断、字段缺失、类型不符 |

## 同步、异步与流式三条路径

同一个 Runnable 暴露多条执行路径，这是 LangChain 设计上最省事也最容易误用的地方。

- `invoke(input)`：同步阻塞，返回完整结果。适合脚本、批处理、离线任务。
- `ainvoke(input)`：异步，返回协程。适合 Web 服务，一个进程内并发处理多个请求。
- `stream(input)`：流式，逐块返回。适合聊天界面，让首字延迟从数秒降到数百毫秒。
- `astream(input)`：异步流式，Web 服务的默认选择。

关键点在于：**三条路径共享同一份组合逻辑**。你写一次 `prompt | model | parser`，它就自动具备以上全部能力，不需要为流式单独写一套代码。这是 Runnable 协议最大的价值，也是它值得先学的原因。

但要留意一个语义差异：`stream` 返回的是「增量片段」还是「累积快照」，取决于具体实现与版本。前端拼接时必须以官方文档为准，并且用真实模型验证一次，不要假设。

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个严谨的技术编辑，只回答被问到的问题。"),
    ("human", "用三句话解释：{topic}"),
])
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
chain = prompt | model | StrOutputParser()

# 同步：一次性拿结果
print(chain.invoke({"topic": "什么是向量检索"}))

# 流式：逐片输出
for chunk in chain.stream({"topic": "什么是向量检索"}):
    print(chunk, end="", flush=True)
```

```python
import asyncio

async def main():
    # 异步 + 并发：适合 Web 服务里同时处理多个请求
    results = await chain.abatch(
        [{"topic": "RAG"}, {"topic": "Agent"}, {"topic": "函数调用"}],
        config={"max_concurrency": 3},
    )
    for r in results:
        print(r[:60])

asyncio.run(main())
```

上面两段代码没有写任何重试、限流、并发控制，却已经具备这些能力的入口——`with_retry`、`with_fallbacks`、`batch` 的并发参数都是协议自带的。第二章会展开。

## 框架层与编排层的职责切分

初学者常把「LangChain 能做的事」和「应该由 LangChain 做的事」混为一谈。一个清晰的切分是：

**框架层管「一次调用的正确性」**：消息格式对不对、模型参数怎么传、流式怎么拼、解析失败怎么报错、这次调用的耗时与 token 是多少。这些是横切关注点，重复实现没有意义。

**编排层管「多次调用之间的关系」**：先检索还是先分类、失败后走哪条分支、要不要等人审批、循环几次退出、状态存在哪里。这些是业务语义，框架不该替你做决定。

把这条线画清楚，很多架构争议就消失了：简单的线性流程用 LCEL 组合即可；一旦出现循环、分支、人工介入、断点续跑，就该把控制流交给 LangGraph，而不是用 Python 的 if/while 把链包起来。后者短期能跑，长期会变成没人敢改的黑盒。

## 一个常见的导入对照

| 你要的东西 | 应该从哪导入 | 备注 |
| --- | --- | --- |
| 提示词模板 | `langchain_core.prompts` | 契约层，稳定 |
| 消息类型 | `langchain_core.messages` | System / Human / AI / Tool |
| 输出解析器 | `langchain_core.output_parsers` | 字符串、JSON、结构化 |
| Runnable 组合件 | `langchain_core.runnables` | Parallel / Passthrough / Lambda / Branch |
| 具体模型客户端 | `langchain_<provider>` | 如 `langchain_openai` |
| 向量库适配 | 独立合作包或 `langchain_community` | 优先选独立包 |
| 图编排 | `langgraph` | StateGraph 与检查点 |
| 追踪与评测 | `langsmith` | 也可用环境变量自动上报 |

这张表的用法是反向的：报 `ModuleNotFoundError` 时先查它住在哪一层，再决定是装包还是改导入路径，而不是盲目 `pip install langchain`。

还有一条经验值得记住：**合作包的版本通常跟随 core 的兼容范围，而不是与 `langchain` 同步**。所以「升级 langchain 但没升级 langchain-openai」很容易出现接口错配，报错信息往往指向一个看起来完全无关的方法。排查这类问题时，先把 core、langchain、provider 三个包的版本列出来，再对照官方兼容说明，比逐行读堆栈快得多。

## 一次调用的完整路径

把前面几节串起来，一次 `invoke` 在框架内部大致经历六个动作：解析输入并按 schema 校验、渲染提示词模板、把消息交给模型客户端、客户端序列化请求并处理响应、解析器转换输出、回调与追踪上报。其中任何一步失败，异常都会沿链向上冒泡，并附带当前节点的信息。

理解这条路径的实际收益是缩小排查范围。同样是「返回为空」，如果失败在提示词环节，通常是变量缺失；如果失败在模型环节，通常是内容审核拦截或 token 超限；如果失败在解析环节，通常是输出格式不符。三种情况的修法完全不同，先定位环节再动手，能省掉大量无效尝试。

## 常见坑

- [ ] 把所有导入都写成 `from langchain.xxx`，升级时全线崩
- [ ] 在生产环境依赖 `langchain-community` 中维护状态不明的集成
- [ ] 为流式输出单独写一套业务逻辑，导致两条路径行为不一致
- [ ] 假设 `stream` 一定返回增量片段，未在真实模型上验证
- [ ] 用 Python 循环包住整条链来实现重试与分支，绕过了协议能力
- [ ] 在同步框架里调用 `ainvoke`，或在异步框架里调用 `invoke` 阻塞事件循环
- [ ] 未固定 provider 包版本，模型参数默认值随升级悄悄变化
