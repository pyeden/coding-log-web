# 02 核心抽象：Runnable 与 LCEL

## 本章要解决的问题

如果把 LangChain 的所有类名忘掉，只留一个概念，那应该是 Runnable。它解释了为什么提示词、模型、解析器、检索器能用同一个竖线串起来，也解释了为什么一条链天然支持同步、异步、流式与批量。

但 Runnable 也是最容易被误用的地方：有人把十几个步骤塞进一条巨型链，出问题后连哪一步慢都定位不到；有人以为 `|` 只是语法糖，于是在链外用 Python 写了大量胶水代码，把协议能力全部浪费掉。这一章要讲清三件事：Runnable 的契约到底是什么、LCEL 的组合语义如何传递数据、以及什么时候应该把链拆开。

## 核心概念与术语

| 术语 | 含义 | 实际用途 |
| --- | --- | --- |
| Runnable | 统一的可调用协议，规定输入输出与四条执行路径 | 让不同部件可互换、可组合 |
| LCEL | LangChain Expression Language，用管道符声明式组合 | 一条表达式同时获得流式、批量、异步 |
| `input_schema` / `output_schema` | 部件声明的输入输出结构 | 组合前静态检查，减少运行时错误 |
| `RunnableParallel` | 让多个分支吃同一份输入，结果合并为字典 | 并行取数、多维分析 |
| `RunnablePassthrough` | 原样透传输入，可附带新增字段 | 在链中保留原始问题 |
| `RunnableLambda` | 把普通函数包装成 Runnable | 接入自定义逻辑 |
| `RunnableBranch` | 按条件选择不同子链 | 轻量路由 |
| `config` | 运行时配置，承载并发、回调、标签 | 控制批大小、追踪名称、超时 |

## Runnable 协议的四个面

一个合格的 Runnable 必须提供四组方法，同步与异步成对出现：

- `invoke(input, config)`：接收单个输入，返回单个输出。
- `batch(inputs, config)`：接收输入列表，返回输出列表，并发度可配。
- `stream(input, config)`：返回增量迭代器。
- `ainvoke` / `abatch` / `astream`：对应的异步版本。

这四组方法的组合不是随便定的。`batch` 默认就是 `invoke` 的并发封装，`stream` 的聚合结果必须与 `invoke` 一致——这两条隐含约定，是「同一份逻辑多形态执行」的基础。如果你自己实现一个部件，最好也遵守它，否则组合进链里会出现难以解释的行为差异。

另外两个属性值得记住：`input_schema` 与 `output_schema`。它们让你在写代码时就知道某个部件要什么、给什么。排查「为什么下游收到的是字符串不是字典」这类问题时，先看 schema 比打印日志快得多。

## LCEL 的组合语义

`a | b` 的含义非常朴素：把 `a` 的输出作为 `b` 的输入。没有魔法，也没有隐式类型转换。由此可以推出三条实用规则。

**规则一：链条的形状由数据结构决定。** 如果某个部件输出字典，下游要么接收整个字典，要么用 `RunnablePassthrough.assign` 或 lambda 取出单个键。很多「KeyError」不是模型的问题，而是忘了链上传递的是一个字典。

**规则二：并行不是自动的。** 只有显式使用 `RunnableParallel`（或它的字典简写），多个分支才会并发执行。顺序写的两行 `invoke` 永远是串行的。

**规则三：横切能力挂在链上，不挂在部件上。** `with_retry`、`with_fallbacks`、`with_config` 作用于整个 Runnable，写在链尾就等于给整条链加重试。如果只想保护模型调用，就把它们挂在模型对象上。

下面这段示例把三件常用工具放在一起：并行分支同时生成摘要与关键词，`RunnablePassthrough` 保留原始文本，最后合并成结构化结果。

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnableParallel, RunnablePassthrough
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

summary_prompt = ChatPromptTemplate.from_template("用两句话概括：\n{text}")
keyword_prompt = ChatPromptTemplate.from_template("提取 5 个关键词，逗号分隔：\n{text}")

chain = RunnableParallel(
    summary=summary_prompt | model | StrOutputParser(),
    keywords=keyword_prompt | model | StrOutputParser(),
    source=RunnablePassthrough(),
)

result = chain.invoke({"text": "LangChain 用统一协议把模型、提示词与解析器组合起来……"})
print(result["summary"])
print(result["keywords"])
print(result["source"]["text"][:30])
```

`RunnableBranch` 适合按输入特征走不同提示词，例如按语言分流。它的判断函数同步执行，因此只能做轻量判断，不要在里面调用模型。

```python
from langchain_core.runnables import RunnableBranch, RunnableLambda

route = RunnableBranch(
    (lambda x: x["lang"] == "en", english_chain),
    (lambda x: x["lang"] == "ja", japanese_chain),
    default_chain,
)
```

## 重试、回退与降级

生产环境里，模型调用失败不是异常，而是常态：限流、超时、偶发的 5xx、内容审核拦截。`with_retry` 与 `with_fallbacks` 是两件不同的工具，别混用。

| 能力 | 解决的问题 | 典型配置 | 注意事项 |
| --- | --- | --- | --- |
| `with_retry` | 同一模型的瞬时失败 | 最大尝试次数、指数退避 | 重试会重复计费，需设上限 |
| `with_fallbacks` | 主模型不可用或超限 | 备用模型列表、异常类型过滤 | 备用模型能力可能明显更弱 |
| `with_config` | 运行时标签与超时 | `run_name`、`tags`、`timeout` | 标签是追踪系统里的检索键 |

```python
fast = ChatOpenAI(model="gpt-4o-mini", temperature=0, timeout=20, max_retries=2)
backup = ChatOpenAI(model="gpt-4.1-mini", temperature=0, timeout=30)

robust_model = fast.with_fallbacks([backup]).with_config({"run_name": "chat-primary"})
```

注意两点：其一，`max_retries` 是客户端层重试，`with_retry` 是链层重试，叠加使用会放大调用次数；其二，回退链上的模型并不共享上下文之外的记忆，切换后行为可能明显不同，降级要有可观测的标记。

## 调试一条链

链式写法最大的代价是「看不见中间结果」。有三种低成本的补救方式：

1. **给每段命名**：`prompt.with_config({"run_name": "build_prompt"})`，追踪面板里一眼能看出是哪一段。
2. **临时插桩**：用 `RunnableLambda(lambda x: (print(x), x)[1])` 把中间值打出来，确认后删除。
3. **导出结构**：用一个最简输入跑一次，观察 `input_schema` 与实际传入是否一致，很多错误在这一步就暴露。

如果开了追踪，整条链会呈现为一棵 run 树，每个节点的输入输出、耗时、token 都能看到。这也是为什么第七章要单独讲观测——链式写法的可维护性，很大程度上依赖追踪质量。

## 自定义部件与函数包装的边界

`RunnableLambda` 让普通函数能参与组合，但它不是万能的。它适合做轻量的转换、拼接、条件判断；不适合在里面写网络请求、数据库查询、长时间的 CPU 计算。原因有两层：一是异步链里执行同步阻塞代码会卡住事件循环，并发能力瞬间归零；二是包在 lambda 里的逻辑不会自动获得流式与批量能力，链上看起来一致，实际行为却退化了。

需要复用、需要流式、需要被独立测试的逻辑，应该封装成正式的 Runnable 或独立节点，而不是塞进一个匿名函数。判断标准很简单：如果这段逻辑需要写注释才能看懂，或者它自己做 IO，就不该待在 lambda 里。

另一个容易被忽略的细节是异常语义。链上某个部件抛异常，默认会中断整条链；而 `with_fallbacks` 只对指定部件生效。如果希望「这一步失败就走默认值」，应该在这一步单独包一层，而不是指望整条链的兜底。

## 并行与流式的相互影响

并行分支能降低总延迟，但它与流式输出的体验并不总是兼容。当链尾是 `RunnableParallel` 时，流式输出需要等待多个分支的结果合并，前端看到的可能是长时间的静默后突然全部出现。这种感觉比「逐字输出」差很多。

常见的折中是：对话主路径保持单线流式，把分支任务（关键词提取、分类、敏感词检查）放到模型调用之前或之后异步执行，不要把用户可见的输出卡在并行汇合点上。如果确实需要并行生成，至少确保主线分支能先开始输出。

## 什么时候该把链拆开

LCEL 很顺手，但顺手会诱导你把所有逻辑塞进一条表达式。以下几种情况应该主动拆：

- 单个步骤需要独立的错误处理与降级策略；
- 需要在中间步骤做人工确认或外部系统写入；
- 步骤数量超过七八个，链的可读性开始下降；
- 出现循环或需要根据上一步结果决定下一步走几次。

前两条属于控制流复杂度，后两条属于可维护性。一旦触线，把子链封装成函数或直接迁移到 LangGraph，比继续加 `|` 更划算。拆开后还有一个附带好处：每一段都能单独写单元测试，用假模型替掉真实调用，测试速度与稳定性都会好很多。

## 常见坑

- [ ] 忘记链的输入是字典，下游直接用字符串取值导致 KeyError
- [ ] 以为顺序书写的两个调用会并发，实际串行拖慢整体
- [ ] 把 `with_retry` 挂在链尾，导致提示词构造失败也被重试
- [ ] 回退模型与主模型输出格式不一致，解析器直接崩
- [ ] 在 `RunnableLambda` 里写阻塞 IO，破坏异步链的并发能力
- [ ] 链太长且无命名，线上定位不到慢在哪一步
- [ ] 依赖 `stream` 的分片粒度做业务判断，未验证实现差异
