# 04 检索与 RAG：从文档到上下文

## 本章要解决的问题

RAG 的演示极其简单：读几个 PDF、切块、存进向量库、检索、拼进提示词。真正上线后，问题会集中在三个地方——**召回不到**（知识明明在库里，检索结果却是无关段落）、**答非所问**（召回到了，但模型没用上或者被干扰）、**越改越差**（调整切块参数后，部分问题变好、另一部分变坏，却没有办法量化）。

这一章沿着「文档如何变成上下文」这条链路，把每个环节的可调参数与失效模式讲清楚，最后给出一套能落地的评估方法。重点不是记住类名，而是知道每一刀切在哪里、代价是什么。

## 核心概念与术语

| 术语 | 含义 | 影响的指标 |
| --- | --- | --- |
| Document Loader | 把各类文件读成统一文档对象 | 覆盖度、元数据完整性 |
| Text Splitter | 把长文本切成可检索片段 | 召回精度与上下文完整性 |
| `chunk_size` | 单片段的目标长度 | 太大噪声多，太小语义断裂 |
| `chunk_overlap` | 相邻片段的重叠长度 | 缓解边界信息丢失，增加冗余 |
| Embeddings | 把文本映射为向量 | 语义检索的上限 |
| VectorStore | 存储向量并支持相似度查询 | 延迟、规模、过滤能力 |
| Retriever | 给定查询返回文档列表的接口 | 检索策略的抽象点 |
| 重排（Rerank） | 对初筛结果做二次排序 | 提升 top-k 的准确性 |

## 链路拆解：五个环节各自会坏在哪

### 加载：元数据比正文更重要

加载器把 PDF、网页、Markdown、数据库记录读成文档对象，正文之外还会带元数据。很多人只关心正文，结果上线后无法回答「这条制度是哪一年生效的」「这段话出自哪份文档第几页」。元数据是后置过滤与引用的基础，能保留就保留。

扫描版 PDF 需要 OCR，表格型文档直接切文本会丢结构。这两类问题在加载阶段就要识别，不要指望检索能补救。

### 切分：最常见的质量瓶颈

切分决定了「一个片段能否独立表达完整意思」。固定长度切分简单，但会把一句话、一张表切开；按语义或标题切分更合理，但依赖文档结构规整。工程上通常用递归字符切分——先按段落，再按句子，最后按字符——并针对中文补充中文标点分隔符。

| 参数 | 经验起点 | 调大后的影响 | 调小后的影响 |
| --- | --- | --- | --- |
| `chunk_size` | 500–1000 字符 | 上下文完整，噪声与成本上升 | 精度提高，语义易断裂 |
| `chunk_overlap` | 50–150 字符 | 边界信息保留更好，存储冗余 | 边界答案容易丢失 |
| 分隔符顺序 | 段落 → 句子 → 字符 | 结构保留好，依赖文档质量 | 切分均匀，语义受损 |

经验起点不是标准答案。正确做法是固定一组真实问题，对两三个配置做对比，看召回率与答案质量，而不是凭感觉调参。

### 嵌入与存储：选型决定下限

嵌入模型决定语义空间的质量，向量库决定规模与运维成本。选型时不要只看「支持多少亿向量」，先看你的规模量级与过滤需求。

| 方案 | 部署形态 | 适合场景 | 主要代价 |
| --- | --- | --- | --- |
| FAISS | 进程内库 | 原型、单机、离线批处理 | 无服务化、持久化需自己管 |
| Chroma | 轻量服务/嵌入式 | 中小规模、快速起步 | 大规模与高可用能力有限 |
| pgvector | PostgreSQL 扩展 | 已有 PG、需要事务与联合查询 | 索引调优需经验 |
| Milvus | 独立分布式 | 亿级向量、多租户 | 运维复杂度高 |

一个常被忽略的点是**过滤（filter）**。真实业务里，「只在这位用户的文档里检索」「只要 2024 年之后的版本」这类条件，比纯向量相似度更常用。选型时如果过滤能力弱，后面会付出很大代价。

### 检索：策略比参数更值钱

| 策略 | 做法 | 适合解决的问题 |
| --- | --- | --- |
| 相似度检索 | 取向量距离最近的 k 条 | 语义明确的单点问题 |
| MMR | 在相关性与多样性间折中 | 结果高度重复、需要覆盖面 |
| 多查询 | 让模型改写多个查询再合并 | 用户表述模糊、同义表达多 |
| 混合检索 | 向量 + 关键词（如 BM25） | 专有名词、编号、代码标识符 |
| 重排 | 初筛较多候选后用小模型精排 | top-k 精度不足 |

专有名词与编号是纯向量检索的天然弱点：「ERR_2041」这类字符串在语义空间里几乎没有区分度，必须靠关键词通道补。这也是混合检索在工程上比「换更大的嵌入模型」更有效的原因。

### 组装：上下文不是越多越好

把检索结果拼进提示词时，要解决三件事：顺序、去重、标注来源。顺序上，把最相关的放在开头或结尾（中间位置容易被忽略）；去重避免同一段落以不同片段重复出现；标注来源让模型可以引用，也让人能核对。

另一个实践是给上下文设硬预算。比如只允许检索内容占提示词总长度的一半，超了就减 k 或者先做摘要。不设预算的系统在长文档场景下会以两种方式坏掉：要么超出窗口直接报错，要么模型被冗长资料淹没，回答质量反而下降。

## 两种写法

第一种是 LCEL 手写，透明、可控，适合需要精细调整的场景。

```python
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_community.vectorstores import FAISS

vectorstore = FAISS.from_documents(docs, OpenAIEmbeddings())
retriever = vectorstore.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 4, "fetch_k": 20},
)

prompt = ChatPromptTemplate.from_messages([
    ("system", "只依据给定资料回答；资料不足时明确说无法回答，并说明缺什么。"),
    ("human", "资料：\n{context}\n\n问题：{question}"),
])

def format_docs(docs):
    return "\n\n".join(f"[{i+1}] {d.page_content}" for i, d in enumerate(docs))

chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | ChatOpenAI(model="gpt-4o-mini", temperature=0)
    | StrOutputParser()
)

print(chain.invoke("退款申请多久内有效？"))
```

第二种是用现成的组合函数，代码更短，约定更多。`create_stuff_documents_chain` 负责把文档塞进提示词，`create_retrieval_chain` 负责串起检索与回答，返回结构里通常包含回答与命中的文档。

```python
from langchain.chains import create_retrieval_chain
from langchain.chains.combine_documents import create_stuff_documents_chain

qa_chain = create_stuff_documents_chain(ChatOpenAI(model="gpt-4o-mini"), prompt)
rag_chain = create_retrieval_chain(retriever, qa_chain)
result = rag_chain.invoke({"input": "退款申请多久内有效？"})
print(result["answer"])
```

这两者的取舍：手写版便于插入重排、过滤、缓存、日志；组合版上手快，但定制点较少。团队里常见做法是先用组合版跑通，再把关键路径替换成手写版。

还有第三个容易被忽略的选择：把检索做成一个工具，交给 Agent 按需调用。它适合“不是每个问题都需要查库”的场景，代价是每次都要多一轮模型决策，延迟与成本上升。如果业务里八成的请求都需要检索，直接走固定链路更划算。

## 预处理：容易被跳过但收益最高的一步

把文档丢进切分器之前，先做三件事。**去重**：同一份制度以不同版本存在于三个目录，检索时会反复命中旧版，答案自然错。**清洗**：页眉页脚、导航文字、重复的免责声明会占用大量片段预算，却能提供零信息。**补结构**：给每个片段加上标题路径（如「第三章 › 退款 › 时限」），这行文字在嵌入时权重很高，能显著提升召回。

这三件事都不需要模型，纯规则即可，但收益往往大于把 `chunk_size` 从 800 调到 600。原因是它们减少的是噪声，而调参优化的是排序。

## 怎么判断 RAG 好不好

不要用「感觉答得不错」当标准。最小可行的评估集是二十到五十条真实问题，每条标注「应该命中的文档」与「理想答案要点」。然后分别看：

- **召回率**：正确文档是否出现在 top-k 中。这是上限，召回不到就别谈生成。
- **忠实度**：答案是否只使用了给定资料，有没有编造。
- **相关性**：答案是否真正回答了问题，而不是复述资料。

分环节看指标的好处是知道该改哪里：召回低就调切分与检索策略，召回高但忠实度低就改提示词与上下文组织。

## 常见坏味道

- [ ] 切块过大，一个片段塞进多个主题，检索命中却答偏
- [ ] 切块过小，答案被切断，模型只能猜
- [ ] 只做向量检索，遇到编号与专有名词就失效
- [ ] 检索结果不去重，同一段落重复占满上下文
- [ ] 提示词里不要求「资料不足时说不知道」，模型自由发挥
- [ ] 没有保留来源元数据，无法核对与引用
- [ ] 用调整参数的方式解决数据质量问题（文档本身过时或重复）
- [ ] 没有固定评估集，每次改动只能靠个别案例判断
