# 03 模型层：ChatModel、消息与结构化输出

## 本章要解决的问题

大部分「模型不听话」的问题，其实发生在调用模型之前或之后：调用前是提示词与消息结构没组织好，调用后是解析与校验没兜住。模型层这一章要回答四个具体问题——`ChatModel` 与老式 `LLM` 有什么区别、消息对象到底承载了什么、怎么做才能稳定拿到结构化数据、以及那些温度、超时、最大 token 参数分别在什么场景下重要。

## 核心概念与术语

| 术语 | 含义 | 使用要点 |
| --- | --- | --- |
| `ChatModel` | 以消息序列为输入输出的模型接口 | 当前主流，支持多轮与工具调用 |
| `LLM` | 以纯文本为输入输出的老式接口 | 仍存在，但新项目不建议作为主路径 |
| 消息（Message） | 带角色的内容单元 | System / Human / AI / Tool 四类 |
| `PromptTemplate` | 单字符串模板 | 适合简单补全式任务 |
| `ChatPromptTemplate` | 消息序列模板 | 多轮、角色控制的标准做法 |
| `MessagesPlaceholder` | 在模板中预留消息列表插入点 | 注入历史对话或工具结果 |
| 结构化输出 | 让模型返回可校验对象而非自由文本 | 依赖 schema 约束与解析器 |
| `bind_tools` | 把工具定义绑定到模型 | 模型据此决定是否发起调用 |

## 从 LLM 到 ChatModel

`LLM` 接口接收一段字符串、返回一段字符串，是早期补全模型的抽象。`ChatModel` 接收消息列表、返回一条 AI 消息，能表达角色、多轮、工具调用、多模态内容。今天几乎所有的商业模型都以聊天形式提供能力，因此 `ChatModel` 是默认选择。

这个转变带来的直接影响是：**提示词不再是「一段话」，而是「一组带角色的消息」**。系统提示约束行为边界，用户消息承载当次任务，AI 消息保存历史回复，工具消息回传外部执行结果。很多「模型忽略指令」的案例，本质是把该放系统消息的内容塞进了用户消息，或者在多轮里让系统消息被历史淹没。

## 消息类型与内容形态

| 消息类型 | 角色语义 | 典型内容 | 常见错误 |
| --- | --- | --- | --- |
| System | 全局约束与人格设定 | 规则、输出格式、边界 | 写太长导致关键约束被稀释 |
| Human | 用户输入 | 文本、图片引用、文件片段 | 把系统指令混进用户消息 |
| AI | 模型回复 | 文本、工具调用请求 | 手工伪造历史导致格式不符 |
| Tool | 工具执行结果 | 结构化结果、错误信息 | 结果过大撑爆上下文 |

消息的 `content` 字段在不同版本里既可能是字符串，也可能是内容块列表（文本块、图片块等）。多模态场景下必须按内容块组织，并且确认目标模型支持对应类型。跨版本迁移时，这是最容易被忽略的兼容点之一。

```python
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage

messages = [
    SystemMessage(content="你是一名后端工程师，回答必须给出可执行的命令。"),
    HumanMessage(content="怎么查看某个端口被谁占用？"),
    AIMessage(content="使用 lsof -i :8080 查看占用该端口的进程。"),
    HumanMessage(content="那 Windows 呢？"),
]
```

## 提示词模板：把变量与角色分开

`ChatPromptTemplate` 的价值在于把「结构」与「变量」解耦。结构在代码里固定，变量在运行时填充，模板本身可以被测试、被版本管理、被非工程角色审阅。

`MessagesPlaceholder` 解决的是多轮对话的插入问题：模板里留一个位置，运行时把历史消息列表塞进去。它比手工拼接字符串可靠得多，因为角色标签由消息对象保证，不会被文本拼接破坏。

```python
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是客服助手。只回答与订单相关的问题；无法确定时明确说不知道。"),
    MessagesPlaceholder("history"),
    ("human", "{question}"),
])

filled = prompt.invoke({
    "history": messages,
    "question": "我的订单什么时候发货？",
})
```

## 结构化输出：从「希望它返回 JSON」到「保证能解析」

自由文本解析是脆弱的：模型可能加一段解释、可能用中文引号、可能截断。稳定拿到结构化数据的路径有三条，按可靠性与可移植性排序如下。

| 方式 | 做法 | 优点 | 限制 |
| --- | --- | --- | --- |
| `with_structured_output` | 传入 Pydantic 模型或 schema | 框架负责提示与解析，代码最干净 | 依赖模型对结构化能力的支持程度 |
| 工具调用 | `bind_tools` 后取 `tool_calls` | 与函数调用生态一致 | 需要自行处理未调用的情况 |
| 提示词 + 解析器 | 要求输出 JSON，用解析器校验 | 兼容性最好 | 最脆弱，需要重试与兜底 |

推荐默认走第一条，并把失败当作正常分支处理：解析失败时记录原始输出、触发一次更严格的重新生成，仍失败则降级为人工处理或默认值。

```python
from pydantic import BaseModel, Field
from typing import Literal

class Triage(BaseModel):
    """工单分类结果"""
    category: Literal["billing", "bug", "feature", "other"] = Field(description="工单类别")
    urgency: int = Field(ge=1, le=5, description="紧急程度，1 最低 5 最高")
    summary: str = Field(description="不超过 40 字的中文摘要")

structured_model = model.with_structured_output(Triage)
result = structured_model.invoke("用户说：付款成功但会员没到账，已经等了两小时。")
print(result.category, result.urgency, result.summary)
```

注意 `Field(description=...)` 不是装饰，它是模型理解字段含义的主要依据。字段名含糊、描述缺失，输出质量会明显下降。schema 越窄越好：能用枚举就不要用自由字符串，能用范围约束就不要只在描述里写。

## 工具绑定与参数传递

`bind_tools` 把工具签名变成模型可见的「可调用清单」。模型不会执行工具，它只会返回一个调用意图（工具名 + 参数），执行由你的代码负责。这一点必须记牢：**模型发起调用不等于调用成功**，参数可能缺、可能类型错、可能引用了不存在的枚举值。

另外，`bind_tools` 之后同一份配置通常仍可复用，但部分参数（如强制工具选择、并行调用开关）由具体厂商支持，写法不同。跨厂商时把这类参数集中在配置层，不要散落在业务代码里。

## 采样参数与运行限制

| 参数 | 作用 | 调优建议 |
| --- | --- | --- |
| `temperature` | 输出随机性 | 抽取、分类、结构化用低值；创意文案适当提高 |
| `max_tokens` | 单次输出上限 | 按场景设硬上限，防止成本失控 |
| `timeout` | 单次请求超时 | 交互场景短、离线批处理长 |
| `max_retries` | 客户端重试次数 | 与链层重试叠加时注意总次数 |
| 工具选择策略 | 是否强制调用工具 | 结构化抽取可强制，对话场景放开 |

这些参数里最容易被忽视的是 `max_tokens`。它不仅控制成本，也影响截断：结构化输出被截断后解析必然失败，而错误信息通常只显示「JSON 不完整」，很难联想到是上限设小了。

## 选模型时真正该看的维度

社区讨论常把模型比较简化成「谁更聪明」，但在工程里，决定能不能用的是另外几个维度：**结构化输出稳不稳定**（同样的 schema 跑一百次成功率多少）、**首字延迟**（交互场景比总分更重要）、**上下文窗口与计费方式**（长文档场景差异很大）、**是否支持工具并行调用**（影响 Agent 步数）、**内容审核策略**（会不会把正常业务句式拦下来）。

一个实用做法是给候选模型建一张小表，用同一套二十条真实请求跑一遍，记录成功率、中位延迟与单次成本。这张表比任何榜单都可靠，因为它测的是你的任务、你的提示词、你的网络环境。

## 成本与上下文窗口的估算

成本估算的粗略方法是：输入 token ≈ 提示词 + 历史 + 检索上下文，输出 token ≈ 回复长度。真正让账单失控的往往不是单次价格，而是三件事：历史无限增长、检索塞入过多文档、失败重试翻倍。

上下文窗口则决定「能塞多少」。工程上的做法不是精确计算，而是设预算：为系统提示、历史、检索、输出各留一份配额，超了就裁剪或摘要。第六章会讲具体裁剪手段，这里只需建立一个意识——**窗口是预算，不是容量**。

## 常见坑

- [ ] 把系统指令写进用户消息，多轮后约束被稀释
- [ ] `MessagesPlaceholder` 的变量名与调用时字典键不一致
- [ ] 用自由文本解析代替结构化输出，线上频繁解析失败
- [ ] Pydantic 字段无描述、无枚举约束，模型自由发挥
- [ ] 把工具调用意图当成执行结果，未校验参数就落库
- [ ] 提高 `temperature` 做数据抽取，导致同一输入结果不稳定
- [ ] 未设 `max_tokens`，个别长回复把成本拉高一个量级
- [ ] 更换模型后未回归结构化输出成功率
