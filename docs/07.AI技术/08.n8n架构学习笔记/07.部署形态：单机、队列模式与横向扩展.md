# 07 部署形态：单机、队列模式与横向扩展

单机跑 n8n 的体验非常好：一个容器、一个卷、一个端口，十分钟上线。问题出现在「开始有人依赖它」之后：早高峰几十个 Webhook 同时到达，编辑器点保存要转三秒，一个解析 Excel 的 Code 节点让整台实例失去响应。这些症状指向同一件事——控制面与数据面挤在同一个进程里。这一章讲三种部署形态的取舍，队列模式的数据流，以及横向扩展时那些「必须共享」的东西。

## 要解决的问题

**第一，什么时候必须上队列模式？** 判断信号不是 QPS，而是「执行时长与请求量相乘」。一个每天一万次、每次两百毫秒的流程，单机轻松；一个每小时十次、每次五分钟的流程，单机也还行；但一个每天两千次、每次三十秒的流程，就会把执行槽位排满，Webhook 开始超时。这时需要的是把执行从接收请求的进程里拆出去。

**第二，为什么扩容后 Webhook 时好时坏？** 因为 Webhook 需要「注册」到某个进程上。多副本时，如果请求被负载均衡打到没有注册该路径的实例，就是 404。队列模式用专门的 webhook 进程解决这个问题；普通的 multiple main 部署则需要额外的粘性策略或统一入口。

**第三，扩展时到底要共享什么？** 数据库、加密密钥、二进制存储是硬约束；Redis 是队列模式的必需组件；配置版本、时区、外部访问地址属于「不一致就会出怪事」的软约束。漏掉任何一个，症状都很像「随机故障」。

## 核心概念与术语

| 术语 | 说明 | 何时出现 |
| --- | --- | --- |
| main 进程 | 承载编辑器接口与（默认）执行的进程 | 所有形态 |
| worker | 只消费队列、执行工作流的进程 | 队列模式 |
| webhook 进程 | 只接收并处理 Webhook 的进程 | 队列模式、大流量入口 |
| Redis | 队列与状态协调的中间件 | 队列模式 |
| 执行模式 | 单机或队列 | 部署配置 |
| 并发上限 | 单实例同时执行的 production 数量 | 需要限流时 |
| 任务执行器 | 隔离运行用户代码的进程/服务 | 1.x 的代码隔离机制 |
| 粘性会话 | 同一客户端固定打到同一实例 | 多副本编辑器 |
| 迁移 | 启动时对数据库结构升级 | 升级与回滚 |
| 发布目录 | 版本化产物 + current 软链 | 部署与回滚 |

## 机制拆解：三种形态与一条队列

```text
【A. 单机】
浏览器 ──► main（API + 执行 + 调度）──► DB / 本地二进制

【B. 队列模式】
浏览器 ──► main（API + 调度 + 可选执行）
                │ 投递任务
                ▼
              Redis ──► worker × N ──► DB / 共享二进制存储
外部请求 ──► webhook 进程 × M ──► Redis / 直接执行

【C. 多副本 main（非官方推荐路径）】
LB ──► main × N（共享 DB + 密钥 + 存储）
        编辑器需粘性；Webhook 注册需额外处理
```

三种形态的取舍可以列成表：

| 维度 | 单机 | 队列模式 | 多副本 main |
| --- | --- | --- | --- |
| 部署复杂度 | 低 | 中高 | 中 |
| 执行隔离 | 无 | 有（worker 独立扩展） | 无 |
| 抗长任务 | 差 | 好 | 差 |
| 编辑器体验 | 好 | 好（主进程不跑重活） | 需要粘性 |
| 官方支持 | 是 | 是（推荐的扩展方式） | 有限 |
| 适合规模 | 个人/小团队 | 生产、有明显峰值 | 只读展示等特殊场景 |

队列模式的核心是一条「任务投递」链路：main 收到触发后不自己执行，而是把执行任务写进 Redis；worker 从队列取出任务，加载工作流定义与凭据，执行并写回数据库。这个设计带来两个直接收益：**执行可以独立扩容**（加 worker 即可），**长任务不再阻塞入口**（Webhook 进程可以快速 ACK）。代价是引入 Redis 与更多进程，排障时要跨多个日志源。

并发控制是队列模式最实用的旋钮。每个 worker 默认会同时执行多个任务，数量由配置决定；生产环境通常还有一个单独的 production 并发上限。设置依据是「单任务的资源占用 × 并发数 ≤ 容器限额」，而不是凭感觉调大。并发过高会出现内存暴涨、外部 API 限流、数据库连接耗尽；并发过低则任务排队，Webhook 超时。稳妥做法是先设一个保守值，用监控观察队列深度与单任务耗时，再逐步调整。

共享约束是横向扩展的第二块内容，列成清单更清楚：

| 必须共享 | 不共享的后果 | 检查方式 |
| --- | --- | --- |
| 数据库 | 工作流/执行记录各存一份，编辑器看不到别人的修改 | 各实例连同一个库，`select count(*) from workflow_entity` 一致 |
| 加密密钥 | 凭据随机解密失败 | 各实例环境变量一致，且纳入密钥管理 |
| 二进制存储 | 附件 404、执行详情打不开 | 统一挂同一卷或同一对象存储 |
| 时区与调度 | 定时任务重复或偏移 | 配置一致，调度只在一个角色上生效 |
| 外部访问地址 | 回调 URL 错误、分享链接失效 | 各实例 `WEBHOOK_URL` 一致 |
| 版本 | 参数语义不一致，节点加载失败 | 所有角色使用同一镜像 tag |

任务执行器（task runner）是 1.x 里与部署强相关的一块：它的目标是让用户代码在受控的独立进程里运行，从而限制资源占用与崩溃影响面。是否默认启用、如何配置随版本演进，具体以官方文档为准。对部署者的实际意义是：**如果你的流程大量使用 Code 节点，就要为「代码执行环境」单独规划资源与监控**，而不是把它当成主进程的一部分。

最后是升级与回滚。n8n 启动时会检查数据库结构并执行迁移，这意味着「新版本启动过一次」之后，旧版本未必能直接回退——迁移可能是单向的。稳妥的升级流程是：备份数据库与二进制存储 → 在预发环境跑新版本并验证关键工作流 → 生产滚动升级 → 观察执行成功率 → 需要回滚时同时回滚数据库快照，而不是只换镜像。发布目录用「版本化目录 + current 软链」的方式切换，好处是回滚只是改一次软链，且新旧产物并存便于对比。

## 可操作示例：一套最小可用的队列模式编排

下面只表达结构，具体变量名与默认值以官方环境变量文档为准（1.x 期间部分变量改过名，照抄旧文章容易踩空）：

```yaml
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: n8n
      POSTGRES_USER: n8n
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - pg:/var/lib/postgresql/data

  redis:
    image: redis:7
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis:/data

  n8n-main:
    image: docker.n8n.io/n8nio/n8n
    environment: &n8n-env
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_DATABASE: n8n
      DB_POSTGRESDB_USER: n8n
      DB_POSTGRESDB_PASSWORD: ${POSTGRES_PASSWORD}
      QUEUE_BULL_REDIS_HOST: redis
      EXECUTIONS_MODE: queue
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
      WEBHOOK_URL: https://n8n.example.com/
    ports:
      - "5678:5678"
    volumes:
      - n8n_data:/home/node/.n8n

  n8n-worker:
    image: docker.n8n.io/n8nio/n8n
    command: ["worker"]
    environment: *n8n-env
    deploy:
      replicas: 2
    volumes:
      - n8n_data:/home/node/.n8n

volumes:
  pg:
  redis:
  n8n_data:
```

这份编排里几个刻意的选择值得说明。`&n8n-env` 锚点保证 main 与 worker 的数据库、Redis、密钥完全一致——手动复制环境变量是「只在 worker 上失败」类问题的头号来源。worker 用 `replicas` 横向扩展，而 main 保持单实例，避免编辑器会话与调度重复。`n8n_data` 被两个服务共享，是为了让二进制文件在小规模部署下可用；规模再大就该换成对象存储，让容器彻底无状态。

生产入口还建议加一层反向代理，把编辑器与 Webhook 分开限流：

```nginx
upstream n8n_main { server 127.0.0.1:5678; }

server {
  listen 443 ssl;
  server_name n8n.example.com;

  location / {
    proxy_pass http://n8n_main;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 300s;   # 同步响应的工作流需要更长的读超时
  }
}
```

`proxy_read_timeout` 常被忽略：默认值通常比工作流执行时间短，于是出现「调用方 504、n8n 里执行成功」。如果使用「等最后节点」的响应模式，读超时必须与最长执行时间匹配；更好的做法是改成「收到即返回」，把等待从 HTTP 层移到业务层。

关于粘性会话，需要区分两类流量。编辑器是长连接加重度前端状态，多副本时必须让同一个浏览器固定落到同一实例，否则会出现「刚保存就从画布消失」「执行进度串线」这类看起来像 bug 的现象；Webhook 则相反，它没有会话概念，应该让任意实例都能处理，靠共享队列而不是靠粘性来分发。把这两类流量放进同一个 upstream 并用同一种策略，是很多「扩容后更不稳定」的根源。分开配置虽然多花十分钟，但能省掉后续无数次的「偶发」解释与事后复盘。

容量估算可以按一个简单公式做初稿：需要的 worker 数 ≈ 峰值每秒任务数 × 平均任务时长 ÷ 单 worker 并发数。算出来的数字通常偏乐观，因为任务时长分布是长尾的；留一倍余量，再用队列深度做扩容信号，比一次性算准更实际，也更容易向团队解释清楚为什么要加机器。

## 常见坑

- [ ] 多副本只共享数据库：凭据随机失效、附件随机 404。
- [ ] main 与 worker 环境变量不一致：只有 worker 上报错，且错误信息指向凭据。
- [ ] 队列模式仍让 main 跑重活：入口照样被拖慢，白拆了架构。
- [ ] 并发调到很高：数据库连接耗尽，表现为大面积超时而非报错。
- [ ] 升级只换镜像不备份数据库：迁移单向，回滚无路。
- [ ] 反向代理超时短于工作流耗时：调用方看到失败，实际执行成功，产生重复补偿。
- [ ] 多实例都跑调度器：定时任务触发多次，数据重复。
- [ ] 二进制用容器内临时路径：重启即丢，且无从恢复。
- [ ] 把 Redis 当持久存储：没开持久化，重启后队列中的任务消失。
- [ ] 编辑器和 Webhook 共用同一个 upstream 与同一种负载策略：前者要粘性，后者要无状态，混在一起必然出问题。
