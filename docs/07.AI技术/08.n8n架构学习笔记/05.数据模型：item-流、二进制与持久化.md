# 05 数据模型：item 流、二进制与持久化

n8n 里所有流动的东西都由同一种容器装着：item。它有两个字段，一个放 JSON，一个放二进制引用。节点之间传递的是「item 的数组」，而节点内部处理这批数组的方式可以完全不同。数据模型看起来简单，但它决定了很多实际问题的答案——为什么 Code 节点里 `$json` 只指一条、为什么附件在几天后打不开、为什么数据库半年涨到几十 GB。这一章把 item、二进制存储、执行记录保留三件事放在一起讲，因为它们共同构成了「数据会占用多少资源」的完整答案。

## 要解决的问题

**第一，为什么有的节点一次处理全部数据，有的一次只处理一条？** 因为 item 数组是一个批处理单位，但节点的实现可以选择「一次拿全量」或「逐条处理」。集成类节点通常逐条调用外部 API；Code 节点让你显式选择模式；聚合类节点则把多条合并成一条。理解这一点，才知道该在哪里写循环、在哪里不该写。

**第二，为什么执行记录里的附件过一段时间打不开？** 因为二进制数据默认不只存在数据库里：JSON 里保存的是引用，真实字节放在文件系统或对象存储。清理策略、容器重建、卷没挂载，任何一种都会让引用变成悬空指针。

**第三，磁盘到底被什么吃掉了？** 通常是执行记录。每个节点每次运行的数据都会被保存，一个每天跑 1440 次的定时工作流，即使每次只有几 KB，一年也是可观的数字；如果有二进制或大 JSON，增长会快一个数量级。裁剪策略不是可选项。

## 核心概念与术语

| 术语 | 说明 | 注意点 |
| --- | --- | --- |
| item | 最小数据单元 `{ json, binary }` | 一个节点处理一批 item |
| item 数组 | 节点间传递的单位 | 输出按「输出槽」分组为二维数组 |
| pairedItem | 输出来源映射 | 影响溯源、合并与错误定位 |
| Code 节点模式 | 全量 / 逐条 | 决定你拿到的是数组还是单条 |
| 二进制数据 | 文件类内容，按引用存储 | 存储位置由实例配置决定 |
| 执行记录 | 每次运行的数据与状态快照 | 增长最快，必须裁剪 |
| 静态数据 | 工作流级小型持久状态 | 存游标可以，存文件不行 |
| 数据库 | SQLite 或 Postgres | 队列模式必须共享数据库 |
| 保留策略 | 按时间/数量清理执行 | 影响审计能力与磁盘 |

## 机制拆解：二维数组与三条存储线

先看节点之间的数据形状。一个节点接收的是「输入槽 → item 列表」，返回的是「输出槽 → item 列表」：

```text
上游节点
  outputs[0] = [ item0, item1, item2 ]     ← 输出槽 0 的三条数据
  outputs[1] = [ item3 ]                   ← 输出槽 1（如 IF 的 false）

下游节点接收
  inputs[0]  = [ item0, item1, item2 ]     ← 目标节点的输入槽 0
```

大多数节点只有一个输入槽和一个输出槽，所以日常感知不到这层结构。一旦用到 Merge（多输入）、IF/Switch（多输出）、错误输出（额外输出槽），二维就变成必须理解的东西：连错槽位不会报错，只会「数据没过来」。

Code 节点的两种模式是数据模型最直观的体现：

| 模式 | 你拿到的 | 适用 | 陷阱 |
| --- | --- | --- | --- |
| 所有 item 一次处理 | `$input.all()` 返回数组 | 聚合、排序、跨条计算、批量请求 | 数据量大时内存压力大 |
| 每条 item 单独处理 | `$input.item` / `$json` 是单条 | 逐条转换、逐条调用 | 无法看到其它 item，跨条统计会错 |

一段对照代码可以说明差别。全量模式下你写的是数组处理：

```javascript
// 模式：Run Once for All Items
const rows = $input.all().map(i => i.json);
const total = rows.reduce((s, r) => s + Number(r.amount || 0), 0);
return rows.map(r => ({
  json: { ...r, share: total ? Number(r.amount) / total : 0 }
}));
```

逐条模式下同样的需求会算错，因为每条都以为自己看到的是全部：

```javascript
// 模式：Run Once for Each Item
// 这里 $json 只有当前一条，无法求全局 total
const amount = Number($json.amount || 0);
return { json: { ...$json, amount, note: 'processed' } };
```

逐条模式并非没有价值：它更省内存，也更贴近集成节点逐条调用的语义。选择标准很简单——**需要跨条信息就用全量，只需要单条转换就用逐条**。

还有一个常被低估的细节：一个 item 的 `binary` 不是单个文件，而是「字段名 → 文件元信息」的映射，同一条 item 可以挂多个二进制。遍历时要按字段名取值，不能假设只有 `data` 一个键；用 Set 节点重命名或重组 item 时若没有显式保留 `binary`，引用会在这一步被丢掉，而执行记录里看不出来，只表现为下游读不到文件。

第二条线是二进制。JSON 里放的是元信息（文件名、MIME、大小）与引用，真实字节按实例配置存放：

| 存储模式 | 位置 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 默认/本地文件系统 | 实例数据目录 | 零配置、快 | 容器重建易丢、多实例不共享 |
| 外部对象存储（S3 兼容） | 外部桶 | 可共享、可扩展 | 需配置凭据与网络 |
| 数据库内 | 数据库 | 备份简单 | 数据库体积膨胀、性能差 |

具体用哪一种由实例配置决定（官方文档里对应 binary data 相关设置），本文不逐一列举变量名，因为命名随版本调整过。判断标准是部署形态：单机小流量可以本地；队列模式或多副本必须外部共享存储，否则 A 实例写入的附件，B 实例读不到。

第三条线是执行记录的持久化。每条执行会保存节点级的输入输出数据、状态与耗时。这带来两个后果：一是它天然是「数据快照」，包含业务数据，涉及隐私时要考虑访问控制与保留时长；二是它增长最快，必须配置裁剪。常见的策略组合是「按时间保留 + 按数量上限 + 定期清理」，三个开关配合使用：

```bash
# 示例：开启裁剪，限制保留时长与总量（变量名以官方文档为准）
EXECUTIONS_DATA_PRUNE=true
EXECUTIONS_DATA_MAX_AGE=168          # 小时，约七天
EXECUTIONS_DATA_PRUNE_MAX_COUNT=10000
```

生产环境还有一个隐形选项：只保存失败执行的完整数据，成功执行只留摘要。这样既保留排障能力，又把体积压下来。代价是无法回放成功执行的中间数据，需要权衡。

数据库选型则是这一切的地基：

| 选型 | 适用 | 不适用 |
| --- | --- | --- |
| SQLite | 单机、个人、低并发 | 队列模式、多副本、高写入 |
| Postgres | 生产、队列模式、多副本 | 极端轻量场景（成本略高） |

切库不是改个连接串就完事：历史数据要迁移，加密密钥要一致，二进制存储要一并规划。这三件事在计划阶段想清楚，比事后补救便宜得多。

## 可操作示例：把一条带附件的流程拆开看

一个典型的「下载发票 → 解析 → 归档」流程，数据形状会经历三次变化：

```text
HTTP Request（Response Format = File）
  outputs[0] = [ { json: {...}, binary: { data: { fileName, mimeType, ... } } } ]

Code 节点（逐条）
  $json  = 上面的 json
  $binary = 上面的 binary（字段名可能是 data，取决于节点）

Write Binary File / 上传节点
  读取 binary 引用 → 写入目标位置
```

对应的 Code 节点只处理元信息，不碰字节：

```javascript
// 逐条模式：只整理元信息，二进制原样透传
const meta = {
  fileName: $binary?.data?.fileName || 'unknown.pdf',
  mimeType: $binary?.data?.mimeType || 'application/octet-stream',
  receivedAt: $now.toISO()
};
return { json: meta, binary: $binary };
```

注意 `return` 的形状：逐条模式返回单个对象，全量模式返回数组。混用会导致「节点执行成功但下游没数据」，因为返回值形状不被识别。

清理与核对可以在数据库侧做，先量化再决策：

```sql
-- Postgres：按状态与时间看执行记录的规模分布
SELECT status, count(*) AS n,
       pg_size_pretty(sum(pg_column_size(execution_data))::bigint) AS data_size
FROM execution_entity
WHERE "startedAt" > now() - interval '30 days'
GROUP BY status
ORDER BY n DESC;
```

这张表能直接回答「该保留多久」：如果 30 天内失败执行只有几百条，而成功执行有几十万条，那策略就很清楚——成功执行留短、失败执行留长。反过来，如果失败率高，先修流程再谈裁剪，否则会把排障证据一起删掉。

还有一个实操层面的取舍：**批大小**。同一个节点处理 10 条还是 10000 条，行为差异很大。全量模式会把所有 item 读进内存，遇到大字段时很容易触发容器内存上限；逐条模式内存平稳，但每条都要走一次节点调度的开销。稳妥的做法是在入口处就分批，例如按 100 条一组推进，而不是等到内存告警再回头改结构。分批的代价是要处理「跨批的状态」，这也是为什么游标与去重键应该存在数据库里，而不是内存变量里。

最后提醒一句关于数据的合规性：执行记录里保存的是真实业务数据，包括手机号、订单、邮件正文。它既能帮你排障，也可能成为泄露面。至少要做到三点：按角色限制查看执行的权限、对敏感字段在写入数据库前做脱敏、把保留时长压到业务真正需要的长度。这三件事都属于架构决策，等到出事再补，成本会高得多。

## 常见坑

- [ ] 在逐条模式里做跨条统计：结果永远只反映当前一条。
- [ ] 混用返回形状：全量模式返回单对象、逐条模式返回数组，都会静默丢数据。
- [ ] 把二进制当 JSON 处理：`JSON.stringify(binary)` 只会得到引用元信息。
- [ ] 容器没挂数据卷：重启后二进制与 SQLite 一起消失。
- [ ] 多副本用本地二进制存储：附件随机 404。
- [ ] 不配裁剪：数据库半年后膨胀到无法备份。
- [ ] 裁剪过狠：出问题时没有历史执行可查，只能靠复现。
- [ ] 把大文件塞进静态数据或节点参数：工作流本身变成数据仓库，编辑器加载变慢。
- [ ] 迁移数据库时忘了带加密密钥：凭据全部解不开，表现为大面积鉴权失败。
- [ ] 一次性把十万条数据灌进全量模式：不是算错，而是直接把容器内存打满，连容器日志都来不及留下完整的现场。
