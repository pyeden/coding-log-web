# 06 扩展机制：自定义节点、代码节点与凭据

内置节点覆盖了绝大多数常见系统，但真实项目里总有一块「只有你公司才有」的逻辑：一个内部 RPC、一套自定义签名、一种私有协议。这时候有四种选择：用 HTTP 节点硬拼、写 Code 节点、开发自定义节点、把逻辑放到外部服务。选错不会立刻出问题，但会在半年后变成维护负担。这一章给出四者的边界，并解释凭据体系里最容易被忽视的一件事——为什么换一次加密密钥，所有凭据就全废了。

## 要解决的问题

**第一，什么时候值得写自定义节点？** 判断标准不是「能不能写」，而是「复用频率与治理需求」。一次性的逻辑放 Code 节点最快；被五个工作流复用的逻辑值得封装；需要版本管理、参数校验、凭据类型、可视化配置的，才值得做成节点包。自定义节点是产品化投资，不是解决一次性问题的工具。

**第二，Code 节点能做多少事？** 它能做纯计算、字段整形、签名、解析，但它运行在一个受限环境里：没有任意 npm 包、网络访问受配置约束、执行可能被隔离到独立进程。把它当通用运行时，会撞上「为什么 require 失败」「为什么超时」这类问题。

**第三，凭据为什么不能随便迁移？** 凭据以密文形式存在数据库，解密依赖实例的加密密钥。密钥不同，密文就是一堆无法还原的字节。这不是设计缺陷，而是把「数据库泄露」与「凭据泄露」解耦的必要代价。

## 核心概念与术语

| 术语 | 说明 | 何时会碰到 |
| --- | --- | --- |
| `INodeType` | 节点实现的核心接口 | 写自定义节点 |
| `description` | 节点的元信息与参数定义 | 决定界面上出现哪些字段 |
| `execute()` | 节点执行入口 | 返回按输出槽分组的 item 数组 |
| `typeVersion` | 节点版本号 | 改参数结构时递增，老工作流保持旧语义 |
| `INodeExecutionData[][]` | 执行返回类型 | 二维：输出槽 → item 列表 |
| `ICredentialType` | 凭据类型定义 | 自定义鉴权方式时实现 |
| 加密密钥 | 用于加解密凭据的实例级密钥 | 迁移、扩容、恢复都会涉及 |
| 社区节点 | 第三方发布的节点包 | 引入供应链风险 |
| `$vars` | 实例级变量 | 存环境相关配置 |
| `$env` | 环境变量访问 | 可能被配置禁用 |
| task runner | 独立进程执行用户代码 | 代码隔离与资源限制 |

## 机制拆解：四种扩展方式的边界

先给一张决策表，按「复用频率 × 治理需求」四象限来选：

| 方式 | 开发成本 | 复用性 | 可治理性 | 适合 |
| --- | --- | --- | --- | --- |
| HTTP 节点 + 表达式 | 极低 | 中 | 低 | 调一个 REST 接口、字段映射 |
| Code 节点 | 低 | 中 | 中 | 复杂转换、签名、解析、批处理 |
| 自定义节点 | 高 | 高 | 高 | 内部平台的标准接入、需要参数校验与凭据类型 |
| 外部服务 | 中高 | 高 | 高 | 重计算、强事务、需要独立扩缩容 |

自定义节点的最小结构并不复杂。核心是一个类，实现 `description` 与 `execute()`：

```typescript
import {
  IExecuteFunctions,
  INodeExecutionData,
  INodeType,
  INodeTypeDescription,
} from 'n8n-workflow';

export class InternalQuote implements INodeType {
  description: INodeTypeDescription = {
    displayName: 'Internal Quote',
    name: 'internalQuote',
    group: ['transform'],
    version: 1,
    description: '查询内部报价服务',
    defaults: { name: 'Internal Quote' },
    inputs: ['main'],
    outputs: ['main'],
    properties: [
      {
        displayName: 'SKU',
        name: 'sku',
        type: 'string',
        default: '',
        required: true,
      },
    ],
  };

  async execute(this: IExecuteFunctions): Promise<INodeExecutionData[][]> {
    const items = this.getInputData();
    const results: INodeExecutionData[] = [];

    for (let i = 0; i < items.length; i++) {
      const sku = this.getNodeParameter('sku', i) as string;
      const resp = await this.helpers.request({
        method: 'GET',
        url: `https://quote.internal/api/price?sku=${encodeURIComponent(sku)}`,
        json: true,
      });
      results.push({ json: resp, pairedItem: { item: i } });
    }

    return [results];
  }
}
```

这段代码里有三个值得注意的设计点。**`getNodeParameter` 按 item 下标取值**：参数可以是表达式，逐条求值，所以必须传 `i`。**返回值是二维数组**：外层是输出槽，内层是 item 列表；返回 `[results]` 表示所有数据从槽 0 输出。**`pairedItem` 要手动补**：新构造的 item 如果不带来源信息，后续的合并与错误定位就会断链。

节点包还需要一个入口声明，让 n8n 知道去哪里加载编译产物：

```json
{
  "name": "n8n-nodes-internal-quote",
  "version": "0.1.0",
  "main": "index.js",
  "n8n": {
    "nodes": ["dist/nodes/InternalQuote/InternalQuote.node.js"]
  }
}
```

`typeVersion` 的演进规则要提前想清楚：参数结构一旦改变，就递增版本号，并在实现里按版本分支处理旧参数。这样老工作流继续按旧语义运行，新工作流享受新结构。反过来，直接改参数名而不升版本，会让所有已存在的工作流在升级后静默失效——这是自定义节点最常见的破坏性变更。

Code 节点则是另一条路。它的优势是「改一行就生效」，劣势是治理成本：没有参数校验、没有类型提示、逻辑藏在 JSON 里难以 review。一个实用的分工是：**参数面板负责「配什么」，Code 节点负责「怎么算」**；一旦某段代码超过五十行、或者开始需要单元测试，就该考虑搬到自定义节点或外部服务。

关于 `$helpers`，需要提醒一句：早期 Function 节点里提供过一组便捷方法（例如发起 HTTP 请求），很多教程仍在沿用那些写法。1.x 的 Code 节点暴露的辅助能力与运行环境随版本变化，官方文档是唯一可靠依据；写之前先确认当前版本可用的对象，不要照抄旧示例。同样地，`require` 能否使用取决于部署配置与代码隔离方式，把「能 require」当成默认前提，迁移到启用隔离的环境时就会全线报错。

凭据体系是第三块。自定义凭据类型的样子大致如下：

```typescript
import { ICredentialType, INodeProperties } from 'n8n-workflow';

export class InternalApi implements ICredentialType {
  name = 'internalApi';
  displayName = 'Internal API';
  properties: INodeProperties[] = [
    {
      displayName: 'Base URL',
      name: 'baseUrl',
      type: 'string',
      default: '',
    },
    {
      displayName: 'API Key',
      name: 'apiKey',
      type: 'string',
      typeOptions: { password: true },
      default: '',
    },
  ];

  authenticate = {
    type: 'generic' as const,
    properties: {
      headers: {
        'X-Api-Key': '={{$credentials.apiKey}}',
      },
    },
  };
}
```

`typeOptions.password` 让输入框变掩码，`authenticate` 声明如何把凭据注入请求。凭据在数据库里是密文，密文由实例的加密密钥派生出的密钥加密。于是有了那条铁律：**换密钥 = 旧凭据全部无法解密**。扩容时多个实例必须共享同一个密钥，否则会出现「在 A 上配好的凭据，在 B 上解密失败」；迁移时如果只搬数据库不搬密钥，凭据表还在，但全是废数据。

`$vars` 与 `$env` 常被混用，差异在于治理粒度：

| 维度 | `$vars` | `$env` |
| --- | --- | --- |
| 存放位置 | 实例的变量配置 | 进程环境变量 |
| 谁能改 | 管理员在界面/配置中维护 | 部署与运维 |
| 是否随工作流导出 | 否 | 否 |
| 是否可被关闭 | 视版本与权限 | 可被配置禁用 |
| 适合放什么 | 区域、品牌名、开关 | 密钥、连接串（谨慎） |
| 不适合放什么 | 密钥 | 频繁变更的业务配置 |

趋势建议：业务开关用 `$vars`，真正的密钥尽量放凭据类型里，而不是 `$env`。因为凭据有加密、有权限、有审计，而环境变量会通过日志、崩溃转储、`docker inspect` 等多个渠道泄露。

自定义节点的成本不只在写代码那几天。它要跟着 n8n 主版本升级，要维护 peer 依赖，要在每个部署环境里安装，还要为参数变更写迁移说明。一个只有两条工作流在用、半年没人改的节点，往往在第二次升级时被直接删掉，改回 Code 节点。所以在动手前先问一句：这段逻辑是「公司资产」还是「一次性胶水」？前者值得工程化，后者越轻越好。

从运行安全角度看，用户代码（Code 节点与部分自定义逻辑）与主进程的关系也在演进。1.x 引入了把代码放到独立进程执行的机制，目的就是避免一段死循环或内存泄漏拖垮整个实例。是否启用、如何配置随版本与部署方式变化，具体以官方文档为准；但结论稳定：**不要假设代码一定与主进程隔离，也不要假设它一定不隔离**，把重计算放到外部服务永远是最稳的选择。

## 可操作示例：从 Code 节点迁移到自定义节点

假设有一段「生成内部签名」的代码在五个工作流里重复。第一步先把它收敛成一个 Code 节点函数：

```javascript
// 公共逻辑：按内部规范生成签名
const crypto = require('crypto');
const secret = $env.INTERNAL_SIGN_SECRET;
const payload = `${$json.method}\n${$json.path}\n${$json.timestamp}`;
const sign = crypto.createHmac('sha256', secret).update(payload).digest('base64');
return [{ json: { ...$json, signature: sign } }];
```

第二步评估是否值得封装：如果调用方还会增加、参数需要校验、密钥需要统一管理，就做成节点包；否则保持 Code 节点，并在工作流命名上标注「公共逻辑，改动需通知」。判断依据可以量化成三条：复用次数大于三、变更频率高于每月一次、出错影响面跨团队——满足两条就封装。

第三步是发布与信任。社区节点是第三方代码，安装即等于在生产环境执行陌生人的代码，且能访问同进程的资源。治理上至少要做三件事：只从可信来源安装、锁定版本并纳入变更记录、在隔离环境（独立实例或 task runner）里先验证。企业环境更稳妥的做法是自建私有 registry，把节点包当成内部依赖管理。

## 常见坑

- [ ] 为一次性需求写自定义节点：开发两天，使用一次，之后无人维护。
- [ ] 改参数结构不升 `typeVersion`：老工作流升级后静默失效。
- [ ] `execute()` 返回一维数组：类型不对，运行时报错或数据丢失。
- [ ] 忘记 `pairedItem`：合并节点行为异常、错误无法定位到源数据。
- [ ] 在 Code 节点里 `require` 任意包：隔离环境或受限配置下直接失败。
- [ ] 照抄旧教程里的 `$helpers` 用法：当前版本可能不存在或不兼容。
- [ ] 把密钥写进 `$vars` 或节点参数：随导出、日志、截图一起泄露。
- [ ] 扩容时各实例用不同加密密钥：凭据随机失效，极难排查。
- [ ] 直接安装来源不明的社区节点：等于给生产环境开了一个后门。
- [ ] 用 Code 节点承载长耗时计算：占住执行槽位，拖慢同实例的其它工作流。
