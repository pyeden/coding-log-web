# 04 触发器与入口：Webhook、定时与轮询

工作流不会自己开始。它需要一个入口：一个 HTTP 请求、一个到点的时间、一次外部系统的轮询命中、一次人工点击。入口决定了三件后续无法更改的事——数据以什么形状进入、失败由谁感知、重复调用会不会造成重复副作用。这一章把 n8n 的几类入口放在一起对比，重点讲 Webhook 的两套地址、三种响应模式，以及定时与轮询在语义上的差别。

## 要解决的问题

**第一，为什么测试地址能用、上线后 404？** 因为 n8n 对 Webhook 有两套注册机制。测试地址只在编辑器「监听测试事件」期间临时生效；生产地址要求工作流处于激活状态，并由运行时在启动时注册。两者路径不同，行为也不同。把测试地址配到第三方回调里，是新手最常见的上线事故。

**第二，为什么同一个表单提交了两次？** 外部系统在超时后重发，或者用户双击，都会造成重复请求。n8n 不会自动去重：它对每个到达的请求都创建一次执行。幂等必须由工作流自己实现，通常靠业务主键加唯一约束或去重表。

**第三，定时任务和轮询触发器有什么区别？** 定时是「到点就跑」，不管有没有数据；轮询是「按间隔去问外部系统有没有新数据」，需要维护游标或时间去重。前者适合报表、清理、对账；后者适合没有 Webhook 能力的第三方系统。选错了会出现「空跑一堆执行」或「漏掉数据」。

## 核心概念与术语

| 术语 | 说明 | 关键细节 |
| --- | --- | --- |
| 测试地址 | `/webhook-test/<path>` | 仅在编辑器监听期间有效，用于调试 |
| 生产地址 | `/webhook/<path>` | 工作流激活后生效，第三方应配这个 |
| 激活 | 让工作流进入运行态 | 定时与 Webhook 类触发器依赖它 |
| 响应模式 | 决定 HTTP 响应何时返回 | 立即返回、等最后节点、用专门节点返回 |
| Respond to Webhook | 显式构造响应的节点 | 可设状态码、响应体、响应头 |
| 定时触发器 | 按间隔或 cron 执行 | 与上次执行是否成功无关 |
| 轮询触发器 | 按间隔拉取外部数据 | 需要游标或时间去重 |
| 手动触发器 | 编辑器内点击执行 | 不产生生产触发语义 |
| 表单触发器 | 由内置表单页提交触发 | 适合内部轻量收集 |
| 聊天入口 | 由聊天界面消息触发 | 适合对话式交互原型 |

再看一眼数据形状。Webhook 节点把一次请求拆成几个固定字段放进 item 的 `json`：请求体在 `body`、请求头在 `headers`、查询串在 `query`，此外还有与请求本身相关的元信息。所以正确写法是 <code v-pre>{{ $json.body.orderId }}</code>，而不是 <code v-pre>{{ $json.orderId }}</code>——除非你在节点里显式开启了「只取 body」之类的简化选项（不同版本行为不同，以当前版本参数为准）。

## 机制拆解：两套地址、三种响应

先用一张图区分测试与生产的注册路径：

```text
【测试】
编辑器点「监听测试事件」
   → 前端通知后端：为这个工作流临时挂载 /webhook-test/<path>
   → 你发一次请求 → 数据回显到画布
   → 停止监听 → 挂载撤销（第三方再调就是 404）

【生产】
工作流激活（active=true）
   → 后端在启动/激活时注册 /webhook/<path> 路由
   → 外部请求到达 → 创建 execution → 引擎执行
   → 进程重启后由激活状态重新注册
   → 取消激活 → 路由撤销
```

这段差异解释了两个常见现象：本地调试一切正常，部署到另一台实例后回调失败（因为新实例上工作流没激活）；以及「刚刚还能用，改完保存就不行了」（保存后短暂的重注册窗口，或激活状态被改动）。

响应模式是第二个关键点。三种模式决定了调用方的体验：

| 响应模式 | 行为 | 适合场景 | 风险 |
| --- | --- | --- | --- |
| 收到即返回 | 请求一到达就回 200，执行异步继续 | 第三方要求快速 ACK、后续处理很慢 | 调用方拿不到处理结果，失败只能靠告警 |
| 等最后节点 | 执行完成后用最后节点的输出作为响应 | 同步查询、需要返回结果 | 执行慢会触发调用方超时 |
| 用 Respond to Webhook 节点 | 在流程中间显式返回 | 需要自定义状态码/响应体、先回后继续 | 流程里必须真的走到该节点 |

第三种最灵活，但有一个硬约束：**每个请求路径上都必须能到达一个响应节点**，包括错误分支。否则调用方会一直等到超时。实践中常见的做法是：入口后先判断参数是否合法，不合法直接走 Respond to Webhook 返回 400；正常路径处理完再返回 200。

触发器类型的横向对比：

| 入口类型 | 触发源 | 是否需激活 | 幂等难点 | 典型用途 |
| --- | --- | --- | --- | --- |
| Webhook | 外部 HTTP 请求 | 是（生产地址） | 重发、双击、至少一次投递 | 表单、支付回调、系统事件 |
| 定时 | 时间 | 是 | 多实例重复调度、时区 | 报表、对账、清理 |
| 轮询 | 固定间隔拉取 | 是 | 游标丢失导致重复或漏读 | 无 Webhook 的第三方系统 |
| 手动 | 人工点击 | 否 | 无 | 一次性任务、调试 |
| 表单 | 内置表单提交 | 是 | 重复提交 | 内部收集、审批发起 |
| 聊天 | 聊天消息 | 视配置 | 会话状态 | 对话式原型 |

多实例部署时，定时触发需要特别注意：如果多个实例都处于激活状态并且都运行调度器，同一个 cron 可能被触发多次。官方的队列模式对调度有专门处理，具体行为与开关以 Scaling 文档为准；自建多实例时不要假设「只有一台会跑」。

## 可操作示例：一个带鉴权与自定义响应的 Webhook

先用测试地址验证链路。注意测试地址的路径前缀与生产不同：

```bash
# 测试：先在编辑器点「监听测试事件」，再执行
curl -sS -X POST 'https://n8n.example.com/webhook-test/order' \
  -H 'Content-Type: application/json' \
  -H 'X-Signature: <hmac>' \
  -d '{"orderId":"A1001","amount":19.9}'

# 生产：工作流激活后使用
curl -sS -X POST 'https://n8n.example.com/webhook/order' \
  -H 'Content-Type: application/json' \
  -d '{"orderId":"A1001","amount":19.9}'
```

Webhook 节点的配置大致如下。`authentication` 建议至少用 Header Auth，密钥存在凭据里而不是节点参数里：

```json
{
  "name": "订单回调",
  "type": "n8n-nodes-base.webhook",
  "typeVersion": 2,
  "position": [0, 0],
  "parameters": {
    "path": "order",
    "httpMethod": "POST",
    "responseMode": "responseNode",
    "options": {
      "rawBody": true
    }
  },
  "webhookId": "<stable-id>"
}
```

`rawBody` 是为签名校验准备的：HMAC 必须对原始字节计算，JSON 重新序列化后空格与键序都会变，签名就对不上。拿到原始体后，用一个 Code 节点做校验：

```javascript
// Code 节点：校验 HMAC-SHA256，失败则抛出，交给错误分支处理
const crypto = require('crypto');
const secret = $env.WEBHOOK_SECRET;           // 建议从环境变量或凭据注入
const raw = $json.body;                        // 开启 rawBody 后为原始字符串
const expected = crypto
  .createHmac('sha256', secret)
  .update(raw, 'utf8')
  .digest('hex');
const received = ($json.headers['x-signature'] || '').toLowerCase();

if (!crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(received))) {
  throw new Error('invalid signature');
}

return [{ json: { ok: true, payload: JSON.parse(raw) } }];
```

最后用 Respond to Webhook 节点显式返回，避免调用方等到超时：

```json
{
  "name": "返回受理",
  "type": "n8n-nodes-base.respondToWebhook",
  "typeVersion": 1,
  "position": [520, 0],
  "parameters": {
    "respondWith": "json",
    "responseBody": "={{ { \"accepted\": true, \"orderId\": $json.payload.orderId } }}",
    "options": {
      "responseCode": 202
    }
  }
}
```

去重则可以在入口后立刻做：用订单号作为键，先查库或查去重表，已存在就走「重复请求」分支直接返回 200。比起在下游补救，入口去重的成本最低，也最容易解释。

对于定时任务，配置层面要注意时区：cron 表达式默认按工作流或实例时区解释，跨时区团队必须显式指定，否则「每天九点」在另一台机器上是另一个时刻。对于轮询任务，则要确认游标存在哪里：存在静态数据里，多实例会互相覆盖；存在数据库里，才具备跨实例一致性。

表单与聊天入口看起来更「产品化」，但它们的定位仍是原型工具：表单触发器适合内部收集与轻量审批，聊天入口适合对话式验证。它们的共同特点是入口与展示强绑定，做品牌化、复杂权限、多语言时很快会碰到天花板。把它们当作验证业务闭环的手段，而不是长期面向客户的界面。

还有两个容易被忽略的入口约束。其一是路径冲突：同一路径在同一实例上只能对应一个激活的工作流，重复注册会导致其中一个失效，表现是「请求打到了别的工作流」。另外，HTTP 方法本身就是语义承诺：GET 应当可安全重放，POST 才承载副作用。很多外部系统在失败后会自动重发 GET，如果入口用 GET 触发了写操作，重复执行几乎是必然结果。其二是请求体大小与超时：多数部署在前面还有一层反向代理，代理的默认限制往往比 n8n 本身更紧，大文件或慢处理最先失败在代理层。排查 413、504 这类错误时，先看代理配置，再看应用日志。

## 常见坑

- [ ] 把测试地址配进第三方后台：监听一停就 404。
- [ ] 工作流未激活就期待生产地址可用：激活状态与保存是两件事。
- [ ] 用「等最后节点」响应慢流程：调用方先超时，n8n 侧仍在执行，形成「对方以为失败、实际成功」。
- [ ] 忘记错误分支也要返回响应：异常路径上调用方一直挂着。
- [ ] 签名校验用解析后的 JSON 重新序列化：字节变了，签名永远不匹配。
- [ ] 密钥写死在节点参数或表达式里：会随工作流导出泄露。
- [ ] 定时任务不设时区：跨时区部署后执行时间漂移。
- [ ] 轮询不存游标：每次全量拉取，重复处理并拖慢外部系统。
- [ ] 多实例同时激活定时工作流：同一时刻触发多次，产生重复数据。
