# 00 导读：为什么读 n8n 的架构

大多数人接触 n8n，是从一个「把表单提交转发到飞书群」的工作流开始的：拖两个节点、连一条线、点一下测试，三十秒跑通。于是很容易得出一个结论——这不过是个可视化脚本工具。真正把它放进生产环境之后，问题才依次冒出来：Webhook 在重启后为什么不再响应？同一个表单被提交两次，为什么下游收到了两条消息？工作流跑到第 7 个节点失败，重试是从头跑还是从断点跑？几十个定时任务同时触发，进程为什么被压垮？

这些问题都不是「节点用得熟不熟」的问题，而是架构问题。这份笔记不打算做节点百科，而是把 n8n 当成一个可拆解的系统：请求从哪里进来、定义存在哪里、执行由谁负责、状态如何持久化、边界靠什么守住。

## 要解决的问题

**第一，脚本会腐烂，平台不会自动腐烂。** 用 Python 写一个同步脚本，一周能上线；三个月后要加鉴权、加重试、加人工审批、加失败告警，脚本就变成一堆 `try/except` 和手写状态机。n8n 把「触发、编排、重试、记录、凭据」这些横切关注点收进了运行时，业务只写在节点参数和少量代码里。代价是你必须理解它的运行时约定，否则会在错误的地方排查问题。

**第二，AI 工作流让「编排层」重新变得重要。** 一个 LLM 调用本身不难，难的是把检索、工具调用、人工复核、结构化落库串成一条可重跑、可回放的链路。n8n 在 1.x 里把 AI 相关节点做成了 LangChain 风格的一组节点（Agent、Chain、Memory、Tool 等），这让它同时具备「集成平台」和「轻量 Agent 编排器」两种身份。理解它的数据模型，才知道什么时候该用节点、什么时候该写代码、什么时候该换一个专门的框架。

**第三，读懂架构才能判断边界。** n8n 不是消息队列，不是通用计算平台，也不是多租户 SaaS 基座。把它用在这些地方，早期很爽，后期很痛。这份笔记会反复指出这些边界在哪里。

还有一层更现实的原因：**维护成本通常被低估**。可视化编排降低了「写出来」的门槛，却把复杂度转移到了「看得懂、改得动、查得清」上。一个两百节点的工作流，如果没有命名规范、没有分支注释、没有错误工作流兜底，接手的人面对的就是一张无法推理的图。架构视角的价值在于，它让你知道哪些复杂度是平台本该吸收的（重试、凭据、日志），哪些必须由你自己设计（幂等、去重、状态机、人工审批），从而避免把后者伪装成前者。读完之后，你至少应该能对三个问题给出明确回答：这个工作流失败后由谁发现、重跑会不会产生重复副作用、扩到十倍流量时第一个撑不住的是什么。

## 核心概念与术语

先把后面八章会反复出现的词固定下来。术语的英文写法保留，因为官方文档、日志和社区讨论里用的都是英文。

| 术语 | 英文/标识 | 含义 | 为什么重要 |
| --- | --- | --- | --- |
| 工作流 | workflow | 一份由节点和连接组成的 JSON 定义，包含名称、节点数组、连接表、设置 | 它是「定义」，不是「进程」；改它不影响已开始的执行 |
| 节点 | node | 工作流中的一个步骤，带类型、版本、参数、位置 | 节点类型决定了它能做什么，`typeVersion` 决定参数语义 |
| 连接 | connections | 源节点名 → 输出序号 → 目标节点列表的映射 | 分支、并行、错误分支全靠它表达 |
| 数据项 | item | 节点间传递的最小数据单元，形如 `{ json, binary }` | 一个节点处理的是「一批 item」，不是一个对象 |
| 执行 | execution | 一次工作流运行实例，有独立 id、状态和日志 | 排障的第一入口；保留策略直接决定数据库体积 |
| 触发器 | trigger | 让工作流自动开始的节点（Webhook、定时、轮询等） | 只有激活（active）的工作流才会响应生产触发 |
| 激活 | activation | 把工作流登记到运行时的动作 | 未激活的工作流，生产 URL 不生效 |
| 凭据 | credential | 加密存储的第三方认证信息，按类型复用 | 与工作流解耦；加密密钥丢失等于全部失效 |
| 队列模式 | queue mode | 用 Redis 把执行分发给多个 worker 的部署形态 | 横向扩展的唯一官方路径 |
| 任务执行器 | task runner | 在独立进程中运行用户代码（Code 节点等）的机制 | 代码隔离与资源限制的关键 |

只记住一句话也可以：**n8n 的核心抽象是「工作流定义 + item 流 + 执行记录」**，其余都是围绕这三样东西的服务。

## 机制拆解：它和相邻产品到底差在哪

先看一张定位对比表。很多选型争论，本质是把不同层次的东西放在一起比。

| 维度 | n8n | Zapier / Make | Dify / Coze 一类 | 自己写服务 |
| --- | --- | --- | --- | --- |
| 主要形态 | 可视化工作流 + 自托管运行时 | SaaS 集成自动化 | LLM 应用/Agent 平台 | 任意 |
| 编排抽象 | 节点 + 连接 + item 流 | Trigger/Action 场景 | Prompt + 知识库 + Agent 编排 | 代码 |
| 部署 | 自托管为主，也有云版 | 纯 SaaS | SaaS 或私有部署 | 自建 |
| 扩展方式 | 自定义节点、Code 节点、社区节点 | 有限的自定义 | 插件/工具，边界较窄 | 无限制 |
| 长尾集成 | 官方节点 + 社区节点 + HTTP 兜底 | 集成数量多但偏 SaaS | 偏 LLM 生态 | 自己写 |
| 适合场景 | 内部系统胶水、定时任务、AI 流水线、需要数据不出内网 | 市场/销售团队轻量自动化 | 面向终端用户的 AI 应用 | 高并发、强一致、核心交易 |

一句话概括边界：**Zapier 卖的是「集成目录」，Dify/Coze 卖的是「面向用户的 AI 应用」，n8n 卖的是「可自托管的编排运行时」**。所以 n8n 的强项是内网系统之间的胶水、定时批处理、需要人工介入的 AI 流水线；弱项是高吞吐、强事务、复杂状态机。

再看它的内部分层。文字版示意：

```text
┌──────────────────────────────────────────────┐
│ 编辑器 UI（浏览器里的 Vue 应用）              │
│ 画布 / 参数面板 / 执行预览 / 凭据管理          │
└───────────────┬──────────────────────────────┘
                │ REST（CRUD、手动执行）+ WebSocket（推送）
┌───────────────▼──────────────────────────────┐
│ 后端控制面（Node.js 进程）                    │
│ 路由 / 鉴权 / 工作流与凭据存取 / 激活管理      │
└───────────────┬──────────────────────────────┘
                │ 交给执行引擎
┌───────────────▼──────────────────────────────┐
│ 执行引擎（n8n-core）                          │
│ 拓扑遍历 / 节点执行 / item 传递 / 错误处理     │
└───────────────┬──────────────────────────────┘
                │ 读定义、写执行记录、读凭据
┌───────────────▼──────────────────────────────┐
│ 持久化：数据库（SQLite/Postgres）+ 二进制存储  │
│ 可选：Redis（队列模式）+ 文件系统/S3           │
└──────────────────────────────────────────────┘
```

关键结论有三条。**其一，编辑器只是客户端**：它不承载执行，关掉浏览器不影响正在跑的工作流，反过来后端挂了画布也救不了你。**其二，定义与运行分离**：工作流 JSON 存在数据库里，执行记录是另一张表里的快照与日志；改定义不会改写历史执行。**其三，单机模式下控制面与数据面在同一个进程里**，这就是为什么一个死循环的 Code 节点能把整个实例拖垮——第 07 章会讲队列模式和 task runner 如何把这两者拆开。

## 可操作示例：十分钟把实例跑起来

最小验证不需要写代码，用官方镜像即可。具体镜像 tag 与参数以官方文档为准，下面只演示结构：

```bash
# 单机试跑：数据落在命名卷里，端口映射到本机
docker volume create n8n_data
docker run -d --name n8n \
  -p 5678:5678 \
  -v n8n_data:/home/node/.n8n \
  docker.n8n.io/n8nio/n8n
```

生产环境更常见的是 compose，把数据库、加密密钥、对外域名一次定好：

```yaml
services:
  n8n:
    image: docker.n8n.io/n8nio/n8n
    restart: unless-stopped
    ports:
      - "5678:5678"
    environment:
      - N8N_HOST=n8n.example.com
      - N8N_PROTOCOL=https
      - WEBHOOK_URL=https://n8n.example.com/
      - GENERIC_TIMEZONE=Asia/Shanghai
      - N8N_ENCRYPTION_KEY=${N8N_ENCRYPTION_KEY}
    volumes:
      - n8n_data:/home/node/.n8n
volumes:
  n8n_data:
```

启动后先确认进程活着，再看健康检查端点是否返回正常：

```bash
curl -sS https://n8n.example.com/healthz
# {"status":"ok"}
```

`N8N_ENCRYPTION_KEY` 建议在首次启动前显式设定并纳入密钥管理，原因在第 06、07 章会展开：它决定凭据能否被解密，也决定多个实例能否共享同一套凭据。

## 常见坑

- [ ] 把编辑器地址当成 API 地址：编辑器走的是内部 REST 路径，对外集成应该用公开 API 或 Webhook。
- [ ] 在生产用默认 SQLite：单机玩具可以，队列模式与并发写入会很快暴露问题。
- [ ] 以为「保存」等于「生效」：定时与 Webhook 类触发器需要工作流处于激活状态。
- [ ] 把 n8n 当消息队列用：它没有消费组、没有分区、没有至少一次投递保证，重试语义是自己实现的。
- [ ] 凭记忆写环境变量：n8n 的变量名在 1.x 里改过几轮，写之前查官方环境变量页。
- [ ] 忽略版本差异：本文统一按 1.x 叙述，不锁定小版本；具体行为以官方文档和你部署的版本为准。
