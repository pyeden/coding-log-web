# 01 架构总览：编辑器、后端与执行引擎

第一次打开 n8n，最容易产生的误解是「这个画布就是系统」。于是排障时习惯性地刷新页面、点重试、看画布上的红框，却不去看服务端日志和执行记录。事实上，画布只是一个 HTTP 客户端；真正决定工作流能不能跑、跑成什么样子的，是另外三层：控制面后端、执行引擎、以及它们背后的数据库与二进制存储。这一章把这四层拆开，给出一个可以拿来做容量估算和故障定位的模型。

## 要解决的问题

**为什么点一下「执行」就能看到节点一个个变绿？** 因为手动执行是由后端发起、通过长连接把进度推回浏览器的，执行本身并不在浏览器里发生。理解这一点，你就不会在「关闭浏览器」时担心任务中断，也不会在「页面卡住」时误判任务失败。

**为什么同一份工作流导入另一台实例后行为不同？** 工作流 JSON 只描述「做什么」，不描述「在哪跑、用什么凭据、什么时区、什么版本」。这些都在实例级配置里。环境不一致时，定义相同、运行时不同，结果自然不同。

**为什么小版本升级会突然报参数错误？** 因为节点有 `typeVersion`。节点类型的参数定义会随版本演进，工作流记录的是它被创建时的版本号。升级运行时但保留旧 `typeVersion` 通常兼容，但把节点「升级版本」是一次语义迁移，需要重新核对参数。第 06 章会细讲。

## 核心概念与术语

| 术语 | 标识/位置 | 说明 | 排障时的意义 |
| --- | --- | --- | --- |
| 编辑器 | editor UI | 浏览器端应用，负责画布、参数面板、执行预览 | 它挂了通常只是前端问题，执行可能仍在继续 |
| 控制面 | REST 后端 | 提供工作流、凭据、执行记录、用户的读写接口 | 4xx/5xx 多半在这里，先看服务端日志 |
| 推送通道 | WebSocket | 把执行进度、协作状态推给前端 | 断线会导致「看不到进度」而非「执行停止」 |
| 工作流定义 | workflow | 节点、连接、设置组成的 JSON | 存在数据库，可导出导入，是版本管理对象 |
| 执行记录 | execution | 一次运行的状态、数据、错误 | 存在数据库，增长最快，需要保留策略 |
| 凭据 | credential | 按类型加密存储的认证信息 | 与工作流解耦，换加密密钥即全部失效 |
| 节点类型 | node type | 形如 `n8n-nodes-base.httpRequest` 的标识 | 决定加载哪个包里的哪个类 |
| 运行时入口 | main / worker / webhook | 不同角色启动的进程 | 队列模式下三者职责分离 |
| 静态数据 | static data | 工作流级的小型持久状态 | 适合存游标、去重键，不适合存大对象 |

一句话记忆：**workflow 是「图纸」，execution 是「施工记录」，credential 是「钥匙」，node type 是「工具箱」**。

## 机制拆解：四层与四个包

文字版分层图，从上到下依次是对外接口、控制面、数据面、存储：

```text
浏览器（编辑器）
   │  HTTPS：REST 读写 + WebSocket 推送
   ▼
n8n 主进程（控制面）
   ├─ 路由与鉴权（登录、API Key、Webhook 路由注册）
   ├─ 工作流/凭据/执行的 CRUD
   └─ 调度器（定时触发器）
        │ 手动执行 / 生产触发
        ▼
执行引擎（数据面）
   ├─ 解析 workflow JSON，构建节点图
   ├─ 按连接拓扑逐节点执行
   ├─ 在节点间传递 item 数组
   └─ 写执行记录、处理错误与重试
        │
        ▼
存储
   ├─ 数据库：工作流、凭据（密文）、执行、用户、标签
   ├─ 二进制存储：文件系统 / 外部对象存储
   └─ 可选 Redis：队列模式下的任务分发
```

代码层面，n8n 的仓库按职责拆成几个包，这个分层对读源码和写自定义节点都很关键：

| 包 | 职责 | 你会在什么时候碰它 |
| --- | --- | --- |
| `n8n-workflow` | 类型定义、表达式求值、工作流数据结构、节点接口 | 写自定义节点时 `import` 接口类型 |
| `n8n-core` | 执行引擎、节点加载、凭据解密、二进制数据 | 排查「执行到一半停住」「凭据解不开」 |
| `n8n-nodes-base` | 内置节点实现（HTTP、Webhook、Code、各类集成） | 想知道某个内置节点到底发了什么请求 |
| `n8n-editor-ui` | 前端编辑器（Vue） | 改界面、排查前端行为 |
| `n8n`（CLI） | 启动入口、命令、配置装载 | 部署、导出导入、跑迁移 |

控制面与数据面合在同一个进程里，是单机模式最容易被忽视的约束。一个 Code 节点里的死循环、一次超大文件的解析、一个没有超时的 HTTP 请求，都会占住事件循环，让同进程里的登录、保存、Webhook 响应一起变慢。这不是 bug，而是部署形态的必然结果；解决办法不在代码里，而在第 07 章的进程拆分。

**定义与运行时分离**是整套架构的第一原则，它带来四个推论：

1. **改定义不影响已开始的执行**。执行开始时会把工作流数据装载进内存，之后你对画布的修改只影响下一次运行。这既是保护也是陷阱：线上出问题时改参数并不会「救回」正在跑的那一次。
2. **执行记录是独立实体**。它有自己的状态机（新建、运行中、成功、失败、等待、取消等）和数据快照，因此可以被单独查询、裁剪、重跑。
3. **节点是纯逻辑单元，状态在外部**。除了静态数据与凭据，节点不持有跨执行的记忆；重试与幂等必须自己设计。
4. **多实例不能共享内存状态**。横向扩展时，所有实例必须共享数据库与加密密钥，且不能依赖本进程内的缓存做一致性判断。

还有一类常被混淆的东西是「静态数据」。它挂在单个工作流上、跨执行保留，看起来像内存，实际上写在数据库里。理解它属于存储层而不是执行层，就能解释两个现象：多实例部署时它需要共享数据库才能一致；它也不适合存放大对象，否则会拖慢每次读写的整体表现。

再看一次运行在四层之间的路径，分三种入口：

```text
手动执行（编辑器点按钮）
  编辑器 → REST → 主进程直接调用执行引擎 → 结果推回前端
生产 Webhook
  外部请求 → 主进程（或 webhook 进程）→ 创建 execution → 执行引擎
定时触发
  调度器到点 → 创建 execution → 执行引擎（队列模式下投递到 Redis）
```

三条入口的差别不止是「谁来调用」，还包括失败由谁感知：手动执行把错误直接显示在画布上，生产触发只能靠执行记录、错误工作流或外部监控发现。这意味着同一份工作流在测试时「很好用」，上线后却可能安静地失败几周——因为它缺少一条把失败送出去的回路。架构上，这条回路属于你必须在 `settings` 里显式配置的部分，而不是平台默认赠送的。

这条路径解释了第 04 章会反复强调的现象：**测试地址只在「监听」期间有效，生产地址要求工作流已激活**。两者走的不是同一条注册路径。

## 可操作示例：确认你的实例处于哪种形态

先看进程与端口。单机模式下只有一个主进程，队列模式下会看到 worker 与 webhook 角色：

```bash
# 容器内查看进程与启动命令
docker exec -it n8n ps -ef | head -20

# 宿主机查看监听端口（默认 5678）
lsof -nP -iTCP:5678 -sTCP:LISTEN
```

再看实例的关键配置是否成组出现。下表是「同一套系统」的最小一致性要求，缺一项就会出现「某些执行能跑、某些不能」的怪现象：

| 配置 | 单机 | 队列模式 | 不一致的后果 |
| --- | --- | --- | --- |
| 数据库 | SQLite 可接受 | 必须共享 Postgres | 工作流在 A 实例可见、B 实例不存在 |
| 加密密钥 | 单实例自定义 | 所有实例必须相同 | 凭据在别的实例解密失败 |
| 外部访问地址 | 建议显式配置 | 必须显式配置 | Webhook 回调地址错误 |
| 二进制存储 | 本地卷 | 必须共享（卷或对象存储） | 执行记录能打开但附件丢失 |
| 时区 | 显式设置 | 所有实例一致 | 定时任务偏移、表达式日期错位 |

导出一份工作流，可以直接看到「定义」长什么样，也能确认哪些东西不在定义里：

```bash
# 导出全部工作流为单个 JSON，用于备份与比对
n8n export:workflow --all --output=/tmp/workflows.json
# 只导出某个工作流
n8n export:workflow --id=<workflow-id> --output=/tmp/one.json
```

```json
{
  "name": "demo",
  "nodes": [
    {
      "id": "a1b2c3",
      "name": "Webhook",
      "type": "n8n-nodes-base.webhook",
      "typeVersion": 2,
      "position": [0, 0],
      "parameters": { "path": "demo", "httpMethod": "POST" }
    }
  ],
  "connections": {},
  "settings": { "executionOrder": "v1" }
}
```

注意 `settings.executionOrder`：它影响分支与节点的执行顺序语义，属于「定义里但容易被忽略」的字段，第 03 章会展开。凭据只以「类型 + id + 名称」的形式出现在节点上，密文永远不在导出文件里，这也是为什么迁移必须连同密钥一起考虑。

## 常见坑

- [ ] 把前端卡顿当成执行失败：先看执行记录状态，再看浏览器控制台。
- [ ] 只看主进程日志：队列模式下执行失败的信息在 worker 里。
- [ ] 认为导出的 JSON 就是完整备份：凭据密文、二进制文件、数据库里的历史执行都不在里面。
- [ ] 在容器里改了 `~/.n8n` 却没挂卷：重启即回到初始状态。
- [ ] 多实例部署时只共享数据库、不共享加密密钥：表现为「部分节点随机报凭据错误」。
- [ ] 用内部 REST 路径做外部集成：编辑器接口不是公开契约，升级可能变。
- [ ] 忽略 `typeVersion`：手动「升级节点版本」后没重新核对参数，是小版本升级后最常见的故障源。
