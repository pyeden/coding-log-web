# 01 Web自动化教程

## 本章目标

用 Playwright 稳定地把「用户在浏览器里做了一件什么事、应该看到什么结果」写成可重复执行的用例，并让它进入 CI。读完本章你应能独立完成：搭好工程、写出可靠的定位器、跳过登录、处理等待、在失败时拿到可复盘的证据、用分片把回归时间压下来。Selenium 4 作为存量方案的对照一并说明。

## 核心概念与术语

**浏览器（browser）与上下文（context）**。Playwright 里 `browser` 是进程级的浏览器实例，`context` 相当于一个独立的无痕会话，拥有独立的 cookie、localStorage 与缓存。**每条用例一个 context** 是最重要的隔离原则：它让用例之间不共享登录态、不互相污染，也让并行变得安全。`page` 是 context 里的一个标签页。

**定位器（locator）**。Playwright 的 `locator` 是惰性的——它描述「怎么找」，不缓存元素引用，每次操作时重新查找。这解决了一类经典问题：页面重新渲染后，之前抓到的元素句柄失效。Selenium 的 `WebElement` 是即时查找，拿到的是快照，页面更新后需要重新查找。

**自动等待（auto-waiting）**。Playwright 在执行点击、填充、断言前会自动等待元素「可操作」：可见、稳定（不再移动）、可接收事件、未被禁用。绝大多数场景不需要手写等待。Selenium 没有这个机制，必须用显式等待（`WebDriverWait`）包住每一个可能不同步的操作。

**严格模式（strict mode）**。定位器默认要求唯一匹配，匹配到多个元素会直接报错。这是好事：它把「你以为是第一个按钮，其实是第三个」这类静默错误变成显式失败。

**storageState**。把 context 的 cookie 与 localStorage 序列化到文件，下次用它启动新 context 即可跳过登录。它比「每条用例都走一遍登录」快得多，也避开了验证码、短信、风控。

**trace**。Playwright 的执行轨迹，包含每一步的 DOM 快照、网络请求、控制台日志与截图。失败时打开 trace，可以像看录像一样逐帧回放，是排查 flaky 用例的第一工具。

**worker 与 shard**。worker 是同一台机器上的并行进程数；shard 是把用例集合切分到多台机器的分片。前者提速度，后者才是缩短 CI 墙钟时间的关键。

## 工具/方案对比

| 维度 | Playwright（推荐主线） | Selenium 4 |
| --- | --- | --- |
| 官方站点 | playwright.dev | selenium.dev |
| 浏览器支持 | Chromium、Firefox、WebKit 统一 API | 各浏览器各自的驱动，通过 W3C WebDriver 协议统一 |
| 等待模型 | 内置自动等待 + 断言重试 | 需自行编写显式等待 |
| 定位能力 | role、label、placeholder、testid 等语义定位器 | ID、Name、CSS、XPath、链接文本等 |
| 隔离模型 | context 原生支持，隔离彻底 | 新建 driver 实例或清理 cookie |
| 登录态复用 | `storageState` 一行搞定 | 需自行保存 cookie 并注入 |
| 调试能力 | trace 回放、Inspector、代码生成 | 日志、截图，依赖第三方 |
| 并行 | 内置 worker 与 shard | 需 Selenium Grid 或自建调度 |
| 生态成熟度 | 较新但迭代快 | 十几年积累，企业存量资产多 |
| 适合场景 | 新项目、需要稳定与速度 | 已有 Selenium 资产、需覆盖冷门浏览器 |

结论很实际：**新项目直接上 Playwright**；已有大量 Selenium 用例的团队，除非迁移收益明确，否则优先把 Selenium 4 的显式等待与 Grid 用好，再逐模块迁移。

## 定位器优先级

定位器的稳定性直接决定用例寿命。按下面的顺序选，越靠前越抗改版：

| 优先级 | 定位方式 | Playwright 写法 | 说明 |
| --- | --- | --- | --- |
| 1 | 无障碍角色 + 名称 | `get_by_role("button", name="提交")` | 与真实用户和读屏软件一致，改样式不影响 |
| 2 | 表单标签 | `get_by_label("用户名")` | 依赖 label 与输入框的关联，语义强 |
| 3 | 专供测试的 id | `get_by_test_id("order-submit")` | 需要研发配合加 `data-testid`，最稳定 |
| 4 | 占位符/文本 | `get_by_placeholder("请输入手机号")` | 文案改动会失效，可接受 |
| 5 | CSS 选择器 | `locator(".order-list > li:nth-child(2)")` | 结构一变就碎 |
| 6 | XPath | `locator("//div[@class='x']/span")` | 最后手段，可读性与稳定性都差 |

实践建议：把 1–3 作为默认选项；遇到确实没有语义锚点的元素（图表、画布、第三方组件），先推动研发补 `data-testid`，再考虑 CSS。**永远不要用 `nth-child` 这类位置选择器做主定位**，列表一排序就全错。

## 上手路径：第一条可运行用例

### Python 版本

```python
import os
from playwright.sync_api import sync_playwright, expect

BASE_URL = os.getenv("BASE_URL", "http://localhost:3000")

def test_create_order():
    with sync_playwright() as p:
        browser = p.chromium.launch(headless=True)
        context = browser.new_context(viewport={"width": 1280, "height": 800})
        page = context.new_page()

        page.goto(f"{BASE_URL}/login")
        page.get_by_label("用户名").fill("demo")
        page.get_by_label("密码").fill("demo123")
        page.get_by_role("button", name="登录").click()

        # 断言会自动重试，直到超时（默认 5 秒）
        expect(page.get_by_role("heading", name="工作台")).to_be_visible()

        page.get_by_test_id("new-order").click()
        page.get_by_label("商品名称").fill("测试商品")
        page.get_by_label("数量").fill("2")
        page.get_by_role("button", name="提交").click()

        expect(page.get_by_test_id("order-status")).to_have_text("已创建")
        context.storage_state(path="auth.json")  # 复用登录态
        browser.close()
```

对应的 `pytest` 运行方式是 `pytest test_order.py --headed --tracing retain-on-failure`，`pytest-playwright` 插件会自动注入 `page` fixture 并在失败时保留 trace。

### TypeScript 版本

```ts
import { test, expect } from '@playwright/test';

// 复用 Python 步骤产出的登录态；也可用 globalSetup 统一生成
test.use({ storageState: 'auth.json' });

test('创建订单', async ({ page }) => {
  await page.goto('/orders');
  await page.getByTestId('new-order').click();
  await page.getByLabel('商品名称').fill('测试商品');
  await page.getByLabel('数量').fill('2');
  await page.getByRole('button', { name: '提交' }).click();

  await expect(page.getByTestId('order-status')).toHaveText('已创建');
});
```

注意两段代码的差异只是语法，思路完全一致：**语义定位 → 操作 → 可重试断言 → 复用登录态**。

### Selenium 4 对照

```python
from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

driver = webdriver.Chrome()  # Selenium 4.6+ 由 Selenium Manager 自动准备驱动
driver.get("http://localhost:3000/login")

wait = WebDriverWait(driver, 10)
wait.until(EC.visibility_of_element_located((By.NAME, "username"))).send_keys("demo")
driver.find_element(By.NAME, "password").send_keys("demo123")
driver.find_element(By.CSS_SELECTOR, "button[type=submit]").click()

wait.until(EC.visibility_of_element_located((By.CSS_SELECTOR, "[data-testid=order-status]")))
assert driver.find_element(By.CSS_SELECTOR, "[data-testid=order-status]").text == "已创建"
driver.quit()
```

关键差别在于：Selenium 每一处需要同步的地方都得自己写 `wait`，写漏一处就是 flaky 的种子。

## 页面对象：让用例读起来像业务

用例一多，最痛的不是写，是改。前端把「提交订单」按钮从一个 `div` 换成 `button`、给输入框加了一层包裹、把列表改成虚拟滚动——这些改动都不该让二十条用例同时变红。解决办法是把「元素在哪、怎么点」收进页面对象，用例只表达业务动作。

一个页面对象至少承担三件事：**暴露业务方法**（`login_as`、`create_order`）、**封装定位器**（外部拿不到选择器字符串）、**收敛等待**（等什么状态算「页面就绪」由页面对象决定）。下面是一个最小示例：

```python
from playwright.sync_api import Page, expect

class OrderPage:
    def __init__(self, page: Page):
        self.page = page
        self.new_order = page.get_by_test_id("new-order")
        self.status = page.get_by_test_id("order-status")

    def open(self):
        self.page.goto("/orders")
        expect(self.new_order).to_be_enabled()
        return self

    def create(self, name: str, qty: int):
        self.new_order.click()
        self.page.get_by_label("商品名称").fill(name)
        self.page.get_by_label("数量").fill(str(qty))
        self.page.get_by_role("button", name="提交").click()
        expect(self.status).to_have_text("已创建")
```

用例随之变成两行：

```python
def test_create_order(page):
    OrderPage(page).open().create("测试商品", 2)
```

判断页面对象写得好不好，有一个简单标准：**前端改版时，你需要改的文件应该只有一个**。如果一次改版要动五个测试文件，说明选择器泄漏到用例里了。页面对象也有反面：不要把它写成「页面上每个元素一个属性」的机械映射，那只是把定位器搬了个家。只暴露用例真正用到的动作与状态，其余留白，页面对象才不会随页面膨胀而失控。

## 工程化

### 等待：只用三种手段

1. **自动等待**：点击、填充、`expect` 断言，默认已经处理，不要额外加。
2. **显式等待状态**：需要等网络或渲染完成时，用 `page.wait_for_load_state("networkidle")`、`expect(locator).to_be_visible()`、`page.wait_for_url(...)`。
3. **业务信号**：等某个接口返回时，用 `page.wait_for_response("**/api/orders")`，而不是等固定秒数。

禁止 `time.sleep` 与 `page.wait_for_timeout` 作为常规手段。它们只适合临时排查，留在代码里就是将来某天的随机失败。

### 环境与数据：把不确定性挡在用例之外

**固定视口与设备。** 默认视口不同会导致响应式布局切换，某些元素在窄屏下被折叠进汉堡菜单，点击自然失败。在配置里显式声明 `viewport`，移动端场景用设备预设，而不是靠默认值碰运气。

**固定时区与语言。** 断言里出现日期、货币、千分位时，时区与 locale 差异会直接让断言错位。Playwright 支持在 context 级别设置 `timezone_id` 与 `locale`，测试环境统一成业务所在时区。

**禁用动画。** 元素在过渡动画中位置不稳定，点击可能落在旧坐标上。最简单的做法是注入一段样式把 `animation` 与 `transition` 关掉，或者给测试环境加一个 URL 参数由前端识别。这比在每处点击前加等待可靠得多。

**数据自造自清。** 用例需要订单就自己创建，需要用户就自己注册，创建时把标识记下来，结束时删掉。共享一套「测试账号 + 固定数据」看似省事，实际会让用例互相踩踏，且一旦有人手工改过数据，整批用例同时失效。

### 登录态复用

登录态用 `storageState`；业务数据用 API 造。典型做法是在 `globalSetup` 里调登录接口拿 token 写入 `auth.json`，用例内需要订单、商品等数据时直接调接口创建，并把 id 注册到清理列表，`afterEach` 统一删除。这样用例既不依赖共享测试库，也不会互相踩踏。

### 用接口造数据，而不是点界面造数据

一条 UI 用例如果需要五条订单才能验证分页，正确做法不是「点五次新建」，而是直接调接口批量创建。界面操作慢、易碎，且一旦中间某步失败，整条链路都不可用；接口造数快、失败信息明确，还能精确控制字段。

```python
def seed_orders(request, base_url, token, count=5):
    headers = {"Authorization": f"Bearer {token}"}
    return [request.post(f"{base_url}/api/orders", headers=headers,
                         data={"sku": "SKU-1", "qty": 1}).json()
            for _ in range(count)]
```

原则是：**用最快的通道准备前提，用最真实的通道验证结论**。前提数据走接口，结论断言走界面，两者不要混。

### 用例组织与命名

按「业务域 + 场景」分目录，而不是按页面分。用户从登录到下单会经过三个页面，如果按页面组织，这条用例放哪都别扭；按业务域组织，它就是「订单域」下的一条主流程用例。命名用中文或英文都行，但要能一眼看出「验证什么」：`test_create_order_with_insufficient_stock_fails` 比 `test_order_2` 有用得多，失败列表本身就是一份可读的测试报告。

### 报告与调试

```bash
# 失败时保留 trace，事后回放
npx playwright test --trace retain-on-failure
npx playwright show-trace test-results/xxx/trace.zip

# 交互式调试：逐步执行，实时看定位器匹配到谁
npx playwright test --debug
```

报告用内置 HTML reporter 即可：`npx playwright test --reporter=html`。CI 上把 `playwright-report/` 作为 artifact 上传，失败时点开就能看到每步截图与 trace 入口。

### 并行与分片

```bash
npx playwright test --workers=4
npx playwright test --shard=1/4   # 四台机器各跑四分之一
```

分片的前提是用例互相独立。如果多条用例共享同一个账号的购物车，分片后必然互相干扰——这又回到「数据要自己造」的原则。

### CI 示例

```yaml
name: e2e
on:
  pull_request:
  schedule:
    - cron: '0 18 * * *'   # 每天 UTC 18 点跑全量

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test --shard=${{ matrix.shard }}/4
        env:
          BASE_URL: ${{ secrets.STAGING_URL }}
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report-${{ matrix.shard }}
          path: playwright-report/
          retention-days: 7
```

合并报告可用 `npx playwright merge-reports --reporter=html ./all-reports`，把各分片的 blob 报告合成一份。

## 失败分析与 flaky 治理

用例变红时，先分类再动手，否则很容易陷入「重跑一次就绿了」的自我欺骗。四类原因对应四种处理方式：

| 现象 | 常见原因 | 处理方式 |
| --- | --- | --- |
| 每次都红，报错稳定 | 产品缺陷或断言写错 | 提缺陷或修断言，最省事的一类 |
| 偶发红，trace 里元素未出现 | 等待不足或接口慢 | 换成等待业务信号，不用固定延时 |
| 偶发红，点击落空或点错元素 | 动画、遮挡、多匹配 | 禁用动画、加 `scroll_into_view_if_needed`、收紧定位器 |
| 只在 CI 红，本地绿 | 环境差异、并发争抢、资源不足 | 对齐环境变量、隔离数据、提高超时上限 |

治理 flaky 的关键是**统计**而不是**感觉**。给每条用例记录最近若干次的通过率，低于阈值的自动打上标记并隔离到一个单独的「观察集」，不阻塞主流水线，但每周必须有人处理：要么修好，要么删掉。放任不管的代价是团队逐渐无视红色告警，那时自动化就只剩下心理安慰的作用。

还有一条经验：**失败信息要自解释**。断言时写清楚期望与实际，例如「订单状态应为已创建，实际为待支付」，比一句 `assert failed` 省下十分钟排查。Playwright 的 `expect` 失败信息已经包含期望值与实际值，自定义断言时也请保持这个习惯。

## 稳定性与常见坑

- [ ] 用 `nth-child`、绝对 XPath 做主定位，改版即碎
- [ ] 用 `time.sleep` 等接口返回，网络慢就红
- [ ] 所有用例共用一个 context，登录态互相污染
- [ ] 每条用例都真实走登录，被验证码或风控拦下
- [ ] 断言只检查元素存在，不检查文本与业务状态
- [ ] 忽略 `strict mode` 报错，用 `.first` 掩盖多匹配问题
- [ ] 上传文件、下载文件、新窗口没有单独处理
- [ ] 时区与语言未固定，日期断言跨环境失败
- [ ] 动画未禁用导致点击落空
- [ ] CI 里没装浏览器依赖，报可执行文件缺失
- [ ] 失败不保留 trace，排查只能靠猜
