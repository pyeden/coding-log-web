# 02 API自动化教程

## 本章目标

把「接口能返回 200」升级为「接口符合契约、业务规则正确、异常路径可控」。读完本章你能独立搭起一套接口测试工程：用 pytest + requests 写用例，用 pydantic 或 JSON Schema 校验结构，用数据工厂造数据并清理，用 OpenAPI 做契约回归，最后把冒烟集挂到 CI 门禁上。

## 核心概念与术语

**接口契约**。接口不是「能通就行」，而是一份约定：路径、方法、请求字段、响应字段、错误码、分页方式、幂等语义。契约一旦漂移，前端、App、第三方都会在中途炸掉。**契约测试**就是把这个约定写成可执行的断言。

**状态码的语义分层**。2xx 表示成功，4xx 表示调用方的问题（参数错、无权限、资源不存在），5xx 表示服务端的问题。测试断言里区分这三类非常重要：一个本该 400 的请求返回了 500，说明服务端缺少参数校验，这是真实缺陷，不是「反正都失败了」。

**幂等（idempotency）**。同一个请求执行一次和执行多次，对资源状态的最终影响相同。GET、PUT、DELETE 按 HTTP 语义应当是幂等的，POST 通常不是。支付、下单这类场景需要业务层幂等键（idempotency key），测试必须覆盖「重复提交只生效一次」。

**鉴权方式**。常见三种：**Bearer Token**（登录换 token，放在 `Authorization` 头）、**OAuth2 客户端模式**（服务间调用，用 client_id/secret 换 access_token）、**签名**（把参数按规则排序后加盐做 HMAC，防篡改）。测试代码要把鉴权收敛成一个 fixture，而不是每条用例手写请求头。

**数据工厂**。接口测试最大的隐形债是数据。共享一套测试库的后果是：A 用例改了订单状态，B 用例就红了。数据工厂的思路是「谁需要谁创建，创建即登记，结束即清理」。

**测试替身（stub/mock）**。当被测服务依赖不可控的第三方（短信、支付网关），用挡板替代真实依赖。注意：mock 只能验证「我们的逻辑对不对」，不能验证「集成是否真的通」，两者要分开建用例。

## 工具/方案对比

| 维度 | pytest + requests | Playwright APIRequestContext | REST Assured | Postman + Newman |
| --- | --- | --- | --- | --- |
| 语言 | Python | Python / TypeScript | Java / Kotlin | 图形化 + JSON |
| 上手成本 | 低 | 低（已有 Playwright 工程时几乎零成本） | 中（需 Java 工程） | 最低 |
| 断言能力 | 任意 Python 断言 + pydantic | 内置 expect + 任意 JS 断言 | Hamcrest/AssertJ，表达力强 | pm.* 脚本，较弱 |
| 与 UI 用例共享登录态 | 需自行处理 | 天然共享（同一 context 的 cookie/token） | 需自行处理 | 需自行处理 |
| 数据驱动 | pytest parametrize | test.describe + 循环 | DataProvider | CSV/JSON |
| 报告 | pytest-html / allure | 内置 HTML + trace | 需集成 | Newman 内置 |
| CI 友好度 | 高 | 高 | 高 | 中（依赖导出的 collection） |
| 适合场景 | 后端为主的接口回归 | 前后端一体的端到端工程 | Java 技术栈团队 | 手工联调、快速验证、给非技术同学用 |

选型建议：**Python 团队用 pytest + requests**，工程结构最清晰、生态最全；**已经有 Playwright 工程**的团队直接用 `APIRequestContext`，好处是登录态、报告、CI 配置全部复用；**Java 团队**用 REST Assured；**Postman** 留给探索期和联调，不适合做长期回归主力——collection 的版本管理与断言表达力都会拖后腿。

## 状态码与断言基线

| 场景 | 期望状态码 | 还应断言什么 |
| --- | --- | --- |
| 正常查询 | 200 | 响应结构、关键字段值、分页字段 |
| 创建成功 | 201（或 200，按团队约定） | 返回的资源 id 可被后续查询到 |
| 参数缺失/格式错误 | 400 | 错误码与错误字段定位 |
| 未登录 | 401 | 不泄漏内部信息 |
| 已登录但无权限 | 403 | 与 401 明确区分 |
| 资源不存在 | 404 | 不要退化成 500 |
| 冲突（重复创建） | 409 | 幂等键生效 |
| 服务端异常 | 500 | 不应在正常用例中出现 |

落成规范：每条用例至少断言「状态码 + 业务码 + 一个关键字段」，只断言状态码的用例价值极低。

### 第一个可运行用例

```python
# conftest.py
import os
import pytest
import requests

BASE_URL = os.getenv("BASE_URL", "http://localhost:8000")

@pytest.fixture(scope="session")
def token() -> str:
    resp = requests.post(
        f"{BASE_URL}/api/auth/login",
        json={"username": os.environ["TEST_USER"], "password": os.environ["TEST_PASS"]},
        timeout=10,
    )
    resp.raise_for_status()
    return resp.json()["access_token"]

@pytest.fixture(scope="session")
def api(token: str) -> requests.Session:
    s = requests.Session()
    s.headers.update({"Authorization": f"Bearer {token}"})
    s.base_url = BASE_URL  # 自定义属性，便于用例内拼接
    yield s
    s.close()
```

```python
# tests/test_orders.py
import pytest
from pydantic import BaseModel, Field

class Order(BaseModel):
    id: int = Field(gt=0)
    status: str
    amount: float = Field(ge=0)

def test_create_order(api):
    resp = api.post(f"{api.base_url}/api/orders", json={"sku": "SKU-1", "qty": 2}, timeout=10)
    assert resp.status_code == 201, resp.text

    order = Order.model_validate(resp.json())
    assert order.status == "created"

    # 创建的资源必须能被查回来，验证的是「真的落库了」
    got = api.get(f"{api.base_url}/api/orders/{order.id}", timeout=10)
    assert got.status_code == 200
    assert got.json()["id"] == order.id
```

运行：`pytest -q --html=report.html`。注意 `pydantic` 的 `model_validate` 是 v2 的写法，v1 用 `parse_obj`，升级时不要混用。

### Playwright 版本（TypeScript）

```ts
import { test, expect } from '@playwright/test';

test('创建订单并回查', async ({ request }) => {
  const created = await request.post('/api/orders', {
    data: { sku: 'SKU-1', qty: 2 },
  });
  expect(created.status()).toBe(201);

  const body = await created.json();
  expect(body.status).toBe('created');

  const got = await request.get(`/api/orders/${body.id}`);
  expect(got.ok()).toBeTruthy();
  expect((await got.json()).id).toBe(body.id);
});
```

`request` fixture 会继承 `baseURL` 与 `storageState`，所以浏览器里登录后的 token 可以直接复用，这是它最大的便利。

### REST Assured 版本（Java）

```java
import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.equalTo;

@Test
void createOrder() {
    given()
        .header("Authorization", "Bearer " + token)
        .contentType("application/json")
        .body("{\"sku\":\"SKU-1\",\"qty\":2}")
    .when()
        .post("/api/orders")
    .then()
        .statusCode(201)
        .body("status", equalTo("created"));
}
```

## 鉴权：三种模式怎么写

**Bearer Token**：登录接口拿 token，放进 session 头。token 过期时间短时，在 fixture 里判断 401 后自动刷新一次，避免整轮用例因为 token 到期集体挂掉。

**OAuth2 客户端模式**：服务间调用先用 client_id/secret 换 access_token，注意 `grant_type=client_credentials`，并且**不要把 secret 写进代码**，从环境变量或 CI secret 注入。

```python
def get_service_token(base_url: str, client_id: str, client_secret: str) -> str:
    resp = requests.post(
        f"{base_url}/oauth/token",
        data={"grant_type": "client_credentials", "client_id": client_id, "client_secret": client_secret},
        timeout=10,
    )
    resp.raise_for_status()
    return resp.json()["access_token"]
```

**签名**：常见规则是把所有业务参数按 key 字典序拼接，末尾追加密钥，做 HMAC-SHA256 后转十六进制。测试端要独立实现一遍签名算法——这本身就是对文档的一次校验，签名算错往往说明文档和实现不一致。

```python
import hashlib, hmac

def sign(params: dict, secret: str) -> str:
    raw = "&".join(f"{k}={params[k]}" for k in sorted(params))
    return hmac.new(secret.encode(), raw.encode(), hashlib.sha256).hexdigest()
```

## 数据工厂与清理

```python
# factories/order_factory.py
import pytest

@pytest.fixture
def order(api):
    resp = api.post(f"{api.base_url}/api/orders", json={"sku": "SKU-1", "qty": 1}, timeout=10)
    resp.raise_for_status()
    data = resp.json()
    yield data
    # 清理：即使用例失败也要执行
    api.delete(f"{api.base_url}/api/orders/{data['id']}", timeout=10)
```

三条原则：**自造**（不依赖别人留下的数据）、**登记**（创建后立刻记下 id）、**必清**（放在 fixture 的 teardown 里，用例抛异常也会执行）。清理失败不应该让用例变红——记录日志即可，避免「清理失败掩盖真实断言失败」。对于无法删除的审计类数据，改用「标记 + 定时归档」，或者在独立租户下跑测试。

## 结构校验与契约测试

**JSON Schema**：适合跨语言、跨团队共享的契约文件。

```python
import json
from jsonschema import validate

schema = json.load(open("schemas/order.json"))
validate(instance=resp.json(), schema=schema)
```

**pydantic**：适合 Python 工程内部，类型提示即文档，错误信息更贴近业务字段名。

**OpenAPI 契约测试**：从 `openapi.json` 里取出每个路径的响应 schema，对真实响应做校验。这样接口文档一改，测试就会提醒你「实现与文档不一致」——注意方向：契约测试发现的是**不一致**，至于哪边对，需要人来判断。

```python
import json, requests
from jsonschema import validate

spec = requests.get(f"{BASE_URL}/openapi.json", timeout=10).json()

def test_order_response_matches_spec(api):
    schema = spec["paths"]["/api/orders/{order_id}"]["get"]["responses"]["200"]["content"]["application/json"]["schema"]
    resp = api.get(f"{api.base_url}/api/orders/1", timeout=10)
    validate(instance=resp.json(), schema=schema)
```

实际项目中 schema 常带 `$ref`，需要先用 `jsonref` 之类工具解析引用再校验，否则会报无法解析。

## 负向用例与幂等

负向用例才是接口测试的价值所在。至少覆盖：

- **缺字段**：删掉必填字段，期望 400 且错误信息指向该字段。
- **类型错**：数字传字符串、数组传对象，期望 400 而不是 500。
- **越权**：用 A 用户的 token 访问 B 用户的资源，期望 403 或 404（按团队约定，但不能是 200）。
- **边界值**：金额 0、负数、超大值；分页 size 超上限。
- **重复提交**：同一幂等键提交两次，第二次应返回同一资源或明确的冲突码，不能创建两条订单。
- **并发**：两个请求同时扣减库存，验证不会超卖（这类用例要用线程或协程并发发起）。

幂等用例的写法要点是**同一次测试内复用同一个幂等键**，并断言资源总数只增加了一条：

```python
def test_idempotent_create(api):
    key = "test-idem-0001"
    headers = {"Idempotency-Key": key}
    first = api.post(f"{api.base_url}/api/orders", json={"sku": "SKU-1", "qty": 1}, headers=headers, timeout=10)
    second = api.post(f"{api.base_url}/api/orders", json={"sku": "SKU-1", "qty": 1}, headers=headers, timeout=10)
    assert first.status_code == 201
    assert second.status_code in (200, 201, 409)
    assert first.json()["id"] == second.json().get("id", first.json()["id"])
```

## 工程化：报告与 CI 门禁

报告用 `pytest-html` 就够，需要更细的失败归因再上 allure。关键是把**请求与响应**打进失败日志，否则排查只能靠复现。

```yaml
name: api-smoke
on:
  pull_request:
  push:
    branches: [master]
jobs:
  smoke:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -r api-tests/requirements.txt
      - name: Smoke gate
        env:
          BASE_URL: ${{ secrets.STAGING_URL }}
          TEST_USER: ${{ secrets.TEST_USER }}
          TEST_PASS: ${{ secrets.TEST_PASS }}
        run: pytest api-tests -q -m smoke --maxfail=1 --html=report.html
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: api-report
          path: report.html
```

门禁设计要点：**PR 只跑 smoke 标记的用例**（几十条，两分钟内），全量放在每日定时任务或发布前。用 `-m smoke` 这种标记而不是目录划分，便于同一条用例既属于冒烟又属于回归。

## 接口层不该验证什么

接口测试很有用，但不是万能的。明确它的边界，可以避免写出大量看似覆盖、实则无效的用例。

**不要验证纯前端渲染逻辑。** 接口返回了正确的字段，页面把它显示成什么样，是前端的事。除非接口本身承担了格式化职责（例如返回富文本或预渲染片段），否则这类断言应该在 Web 层做。

**不要验证第三方服务的行为。** 「支付网关会返回成功」不是你的系统要保证的事。接口测试应该验证「网关返回成功时我们怎么处理」「网关超时我们怎么处理」，而这两种情况用挡板模拟即可，不需要真实调用。

**不要用接口测试替代性能测试。** 单条用例响应 200 毫秒，不代表并发 500 时还能 200 毫秒。性能需要独立的压测方案与指标，混在一起只会让两者都不准。

**不要指望接口测试发现交互缺陷。** 按钮点不动、弹窗被遮挡、表单校验提示错位，这些只有 UI 层能发现。接口层全绿而线上不可用，是分层失衡的典型症状。

## 环境与数据的治理

接口测试最容易在「环境」上翻车，三个约定能省掉大量沟通成本。

**环境用变量表达，不用分支判断。** 常见反模式是 `if env == "prod": base = ...`，散落在几十个文件里。正确做法是只在一个地方读取 `BASE_URL`，其余代码一律用相对路径拼接，切换环境只改一个变量。

**测试账号按用途分组。** 至少需要：普通用户、管理员、无权限用户、已注销用户。每组账号的权限边界写成文档，用例按需取用。不要用「一个万能管理员账号」测所有场景，越权用例根本写不出来。

**数据清理要有兜底。** fixture 清理在用例异常时通常能执行，但进程被杀、CI 超时就不会。因此还需要一个「按前缀清理」的兜底任务：所有测试数据带统一前缀（如 `auto_`），每天定时扫描删除超过 24 小时的残留。这比事后手工清库可靠得多。

**敏感数据不进仓库。** 账号、密钥、真实用户手机号一律走环境变量或 CI secret。日志里也要脱敏，否则报告一上传，凭据就泄了。

## 失败归因：三种红色要分清

接口用例变红时，先判断属于哪一类，处理方式完全不同。

**第一类：产品缺陷。** 表现为状态码与业务码不符合预期，且可稳定复现。直接提缺陷，附上请求体、响应体与预期。这类用例在缺陷修复前应保持红色——不要为了让流水线变绿而放宽断言。

**第二类：用例问题。** 表现为断言写错、字段名过时、依赖了已变更的接口。修用例即可，但要顺带检查：是不是接口文档没同步？如果是，契约测试应该先红，说明契约覆盖有缺口。

**第三类：环境问题。** 表现为连接超时、502、数据库连接池耗尽。这类失败最危险，因为它会训练团队「红了就重跑」。正确做法是给环境问题打上独立标记并从结果统计中剔除，同时推动环境负责人修复，而不是让它长期占据失败列表。

一个实用做法是在报告里把三类失败分列统计。当「用例问题」占比超过两成，说明维护流程有问题；当「环境问题」持续出现，说明测试环境该升级了。

## 轻度并发验证

接口测试不必做完整压测，但有两类并发问题值得用简单脚本兜住：**超卖**与**重复创建**。用线程池同时发 10 个请求，断言最终库存只减了 10 或明确拒绝超额，就能抓住大部分乐观锁缺失的问题。

```python
from concurrent.futures import ThreadPoolExecutor

def test_no_oversell(api):
    with ThreadPoolExecutor(max_workers=10) as pool:
        results = list(pool.map(
            lambda _: api.post(f"{api.base_url}/api/orders", json={"sku": "SKU-LIMITED", "qty": 1}, timeout=10).status_code,
            range(10),
        ))
    assert results.count(201) <= 5  # 假设库存只有 5
```

这类用例不适合放进每次 PR 的门禁（资源争抢会让它不稳定），放在每日任务里跑更合适。

## 稳定性与常见坑

- [ ] 只断言状态码，不断言业务字段
- [ ] 依赖共享测试库的数据，用例顺序一变就红
- [ ] token 硬编码在代码里，过期后整批失败
- [ ] 用例之间没有清理，数据越跑越多
- [ ] 把 5xx 当成「预期失败」写进断言，掩盖真实缺陷
- [ ] 没有超时设置，某个接口挂起拖死整轮
- [ ] 时区/浮点精度导致金额断言偶发失败（用 Decimal 或允许误差）
- [ ] 分页用例只测第一页，漏掉边界
- [ ] 契约测试没解析 `$ref`，报错后直接跳过
- [ ] 并发用例共享同一份库存数据，互相踩踏
