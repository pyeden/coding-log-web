# 04 iOS自动化教程

## 本章目标

以 XCUITest 为主线，把 iOS App 的关键路径写成可回归的用例；同时说明当团队需要「一套脚本同时覆盖 Android 与 iOS」时，如何用 Appium + XCUITest driver 达成。读完本章你能：区分模拟器与真机的差异、处理签名与 WebDriverAgent、按约定使用 accessibility identifier、应对系统弹窗与动画、用 `xcodebuild test-without-building` 做并行回归。

## 核心概念与术语

**XCUITest**。Apple 官方的 UI 测试框架，属于 XCTest 体系。测试代码编译成一个独立的 runner App 安装到设备上，通过无障碍接口驱动被测 App。它运行在真实设备或模拟器上，能访问系统级 UI，因此可以做「跳转设置、处理权限弹窗」这类跨应用操作。

**accessibility identifier**。iOS 上最稳的定位锚点。它不影响界面显示，只供自动化与无障碍使用，由开发在代码里设置：

```swift
addButton.accessibilityIdentifier = "detail_add_to_cart"
```

与 `accessibilityLabel` 的区别要分清：**label 是给用户（和读屏）看的文案，会随产品文案改动；identifier 是给测试看的标识，应当稳定不变**。混用 label 做定位，等于把用例绑在文案上。

**WebDriverAgent（WDA）**。Appium 在 iOS 上的执行代理：一个用 XCUITest 写的 App，接收 WebDriver 协议请求并转成 XCUITest 调用。它必须被签名并安装到设备上，这是 iOS 自动化门槛高于 Android 的根本原因。

**capability**。与 Android 类似，但多了签名相关项：`xcodeOrgId`、`xcodeSigningId`、`updatedWDABundleId`。真机上这几项配错，表现为「WDA 启动超时」或「无法安装 WebDriverAgentRunner」。

**模拟器与真机**。模拟器跑在 Mac 上，启动快、可并行、不需要签名，但**不支持相机、蓝牙、蜂窝网络、部分传感器**，且性能特征与真机差异很大。真机才能验证真实交互与性能，代价是签名、设备管理、连接稳定性。

**测试计划（Test Plan）与 xctestrun**。Xcode 支持把一组测试配置导出成 `.xctestrun` 文件，配合 `test-without-building` 在已编译产物上重复执行，跳过每次编译的时间。这是 iOS 回归提速的关键手段。

## 工具/方案对比

| 维度 | XCUITest（推荐主线） | Appium + XCUITest driver | XCTest 单元测试 |
| --- | --- | --- | --- |
| 语言 | Swift / Objective-C | 任意（Python/Java/JS…） | Swift / Objective-C |
| 执行位置 | 设备上的 runner App | 设备上的 WDA，PC 端调度 | 与被测代码同进程 |
| 跨平台复用 | 无（仅 iOS） | 与 Android 共用页面对象思路与用例结构 | 无 |
| 系统弹窗处理 | 原生 `addUIInterruptionMonitor` | 需切到 SpringBoard 或使用 alert 接口 | 不涉及 |
| 速度 | 快 | 慢（每步一次协议往返 + WDA 开销） | 最快 |
| 环境门槛 | 中（只需 Xcode） | 高（WDA 签名、驱动版本匹配） | 低 |
| 稳定性 | 高 | 中 | 高 |
| 适合场景 | iOS 专属回归、性能与系统交互 | 跨端统一脚本、非 Swift 团队 | 逻辑与视图单元验证 |

选型结论：**团队以 iOS 为主、研发用 Swift，直接写 XCUITest**，它最快最稳，且失败信息最贴近代码；**需要一套脚本覆盖双端、或测试团队不写 Swift，用 Appium**，代价是要养 WDA 与签名。两条路的页面对象设计思路完全一致，可以对照 Android 篇的示例阅读：同一个「商品详情页」在两端只是定位语法不同，业务动作的抽象是一样的。

## 模拟器与真机

| 维度 | 模拟器 | 真机 |
| --- | --- | --- |
| 启动速度 | 快（秒级） | 慢（安装 + 签名） |
| 并行能力 | 强（可同时开多个） | 受设备数量限制 |
| 签名要求 | 无 | 必须有开发者证书与描述文件 |
| 硬件能力 | 无相机、蓝牙、蜂窝 | 完整 |
| 性能表现 | 与真机差异大 | 真实 |
| 适用 | 日常回归、CI 主干 | 发布前验证、硬件相关功能 |

务实的分工：**日常回归全部跑模拟器**，把反馈速度做上来；**每周或发布前在真机上跑一遍核心路径**。不要试图用模拟器验证「耗电」「流畅度」「推送到达」这类只有真机才成立的东西。

## 环境与签名

```bash
# 1. 查看可用模拟器
xcrun simctl list devices available

# 2. 启动指定模拟器
xcrun simctl boot "iPhone 15"

# 3. 直接跑 XCUITest（最简路径，无需 Appium）
xcodebuild test \
  -project Shop.xcodeproj \
  -scheme ShopUITests \
  -destination 'platform=iOS Simulator,name=iPhone 15,OS=17.5' \
  -resultBundlePath results.xcresult
```

真机 + Appium 的 WDA 首次构建：

```bash
# WDA 工程随 Appium 的 XCUITest driver 一起提供，先找到它的路径
appium driver install xcuitest

# 用 Xcode 打开 WDA 工程，配置签名 Team 后执行（也可用命令行）
xcodebuild -project WebDriverAgent.xcodeproj \
  -scheme WebDriverAgentRunner \
  -destination 'platform=iOS,name=我的 iPhone' \
  test
```

签名三件事必须对齐：**Team ID**（`xcodeOrgId`）、**签名身份**（`xcodeSigningId`，通常是 `iPhone Developer`）、**WDA 的 Bundle ID**（`updatedWDABundleId`，需与描述文件匹配）。三者任一不匹配，WDA 就装不上。

## capabilities 关键项

| 键 | 示例值 | 说明 |
| --- | --- | --- |
| `platformName` | `iOS` | 平台，必填 |
| `appium:automationName` | `XCUITest` | 自动化引擎 |
| `appium:deviceName` | `iPhone 15` | 设备名，需与 `simctl`/Xcode 中一致 |
| `appium:platformVersion` | `17.5` | 系统版本 |
| `appium:udid` | 设备 UDID | 真机必填，多设备时用于指定 |
| `appium:bundleId` | `com.example.shop` | 已安装 App 的包标识 |
| `appium:app` | `/abs/path/Shop.app` 或 `.ipa` | 未安装时提供 |
| `appium:xcodeOrgId` | `ABCDE12345` | 真机签名必需 |
| `appium:xcodeSigningId` | `iPhone Developer` | 真机签名必需 |
| `appium:updatedWDABundleId` | `com.example.wda` | 与描述文件匹配的 WDA 标识 |
| `appium:noReset` | `true` | 保留应用状态 |
| `appium:wdaLaunchTimeout` | `90000` | 真机首次启动 WDA 较慢，需放大 |

一个常见误区是以为「模拟器不需要签名，所以 capability 随便写」。实际上 `deviceName` 与 `platformVersion` 必须与已安装的模拟器精确匹配，否则会话创建会失败并提示找不到设备。

## 上手路径

### XCUITest 版本

```swift
import XCTest

final class CheckoutUITests: XCTestCase {
    private var app: XCUIApplication!

    override func setUpWithError() throws {
        continueAfterFailure = false
        app = XCUIApplication()
        app.launchArguments += ["-uitest"]   // 让 App 走测试配置：关闭动画、指向测试环境
        app.launch()
    }

    func testAddToCartUpdatesBadge() {
        app.buttons["detail_add_to_cart"].tap()

        let badge = app.staticTexts["cart_badge"]
        XCTAssertTrue(badge.waitForExistence(timeout: 5))
        XCTAssertEqual(badge.label, "1")
    }
}
```

`waitForExistence(timeout:)` 是 XCUITest 里最常用的等待手段——它比 `sleep` 精确，也比轮询优雅。断言失败时 Xcode 会附上界面层级快照，排查成本很低。

### Appium 版本

```python
from appium import webdriver
from appium.options.ios import XCUITestOptions
from appium.webdriver.common.appiumby import AppiumBy
from selenium.webdriver.support.ui import WebDriverWait

options = XCUITestOptions()
options.platform_name = "iOS"
options.automation_name = "XCUITest"
options.device_name = "iPhone 15"
options.platform_version = "17.5"
options.bundle_id = "com.example.shop"
options.no_reset = True
options.wda_launch_timeout = 90000

driver = webdriver.Remote("http://127.0.0.1:4723", options=options)
wait = WebDriverWait(driver, 15)

try:
    wait.until(lambda d: d.find_element(AppiumBy.ACCESSIBILITY_ID, "detail_add_to_cart")).click()
    badge = wait.until(lambda d: d.find_element(AppiumBy.ACCESSIBILITY_ID, "cart_badge"))
    assert badge.text == "1"
finally:
    driver.quit()
```

### 双端共用的页面对象

```python
class ProductDetailPage:
    ADD = "detail_add_to_cart"
    BADGE = "cart_badge"

    def __init__(self, driver):
        self.driver = driver

    def add_to_cart(self):
        self.driver.find_element(AppiumBy.ACCESSIBILITY_ID, self.ADD).click()
        return self

    def badge_text(self) -> str:
        return self.driver.find_element(AppiumBy.ACCESSIBILITY_ID, self.BADGE).text
```

这段代码在 Android 与 iOS 上都能跑——前提是两端研发都把 `accessibilityIdentifier`（Android 侧是 `contentDescription`）设成同一套字符串。这就是「同一套页面对象思路」的具体落地方式，也是跨端自动化真正的成本所在：**不是写脚本，是推动两端统一标识**。

## 定位策略

| 优先级 | 方式 | XCUITest 写法 | Appium 写法 |
| --- | --- | --- | --- |
| 1 | accessibility identifier | `app.buttons["detail_add_to_cart"]` | `AppiumBy.ACCESSIBILITY_ID` |
| 2 | 元素类型 + 谓词 | `app.buttons.matching(NSPredicate(format: "label == %@", "提交"))` | `-ios predicate string` |
| 3 | 类链（class chain） | 不适用 | `-ios class chain` |
| 4 | XPath | 支持但慢 | `AppiumBy.XPATH` |

优先用 identifier 的原因很实际：iOS 的元素层级会随系统版本变化（同一控件在不同版本里可能多包一层 `Other`），按类型路径定位的脚本升级系统就崩。而 identifier 由业务代码设置，不受层级变动影响。

## 系统弹窗与动画

**权限弹窗**。相机、定位、通知、相册的授权弹窗属于系统进程，不属于你的 App。XCUITest 用中断监视器处理：

```swift
addUIInterruptionMonitor(withDescription: "系统权限") { alert in
    for label in ["允许", "Allow", "好", "OK"] {
        let button = alert.buttons[label]
        if button.exists {
            button.tap()
            return true
        }
    }
    return false
}
app.tap()   // 触发一次交互，监视器才会被调用
```

注意 `app.tap()` 这一行不能省——中断监视器只在「你的测试与界面交互」时才被回调，光注册不交互是等不到弹窗的。Appium 侧的做法是切到 SpringBoard 上下文直接点按钮，或者用 `autoAcceptAlerts` 类 capability（不同驱动版本行为略有差异，以官方文档为准）。

**动画**。iOS 的转场动画（尤其是导航栈推入）会让元素在短时间内位置不稳定。推荐两种做法：一是在测试构建里通过启动参数关闭动画；二是等待「目标页面特征元素存在」而不是等待固定时长。前者更快，后者更通用。

**键盘**。iOS 键盘出现会遮挡底部按钮，且不同输入法高度不同。稳妥做法是输入后收起键盘（`app.keyboards.buttons["Return"].tap()` 或点击空白区域），再操作目标元素。

## 工程化：并行与 CI

`test-without-building` 是提速的核心：先编译一次，之后反复执行，跳过编译开销。

```bash
# 1. 只编译测试产物
xcodebuild build-for-testing \
  -project Shop.xcodeproj \
  -scheme ShopUITests \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath build

# 2. 在已编译产物上并行执行
xcodebuild test-without-building \
  -xctestrun "$(ls build/Build/Products/*.xctestrun | head -1)" \
  -destination 'platform=iOS Simulator,name=iPhone 15' \
  -parallel-testing-enabled YES \
  -maximum-parallel-testing-workers 4
```

并行执行的前提同样是**用例之间互不干扰**：并行 worker 会启动多个模拟器实例，共享同一份后端数据。因此数据必须带用例前缀，或每个 worker 使用独立的测试账号。

CI 示例（GitHub Actions 的 macOS runner）：

```yaml
name: ios-ui
on:
  pull_request:
    paths: ['ios/**']
jobs:
  uitest:
    runs-on: macos-14
    steps:
      - uses: actions/checkout@v4
      - name: Select Xcode
        run: sudo xcode-select -s /Applications/Xcode_15.4.app
      - name: Build for testing
        run: |
          xcodebuild build-for-testing \
            -project ios/Shop.xcodeproj \
            -scheme ShopUITests \
            -destination 'generic/platform=iOS Simulator' \
            -derivedDataPath build
      - name: Run tests
        run: |
          xcodebuild test-without-building \
            -xctestrun "$(ls build/Build/Products/*.xctestrun | head -1)" \
            -destination 'platform=iOS Simulator,name=iPhone 15' \
            -resultBundlePath results.xcresult
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: xcresult
          path: results.xcresult
```

`xcresult` 里有每一步的截图与界面层级，失败时用 Xcode 打开即可回放，比日志直观得多。

## 真机设备管理

真机带来的额外复杂度主要在「设备」本身，几条经验能省下大量时间。

**设备必须信任开发者证书。** 首次安装后要在「设置 → 通用 → VPN与设备管理」里手动信任，否则 App 装上了也打不开。CI 上的设备需要预先完成这一步，并且不能被系统重置。

**保持设备唤醒与解锁。** 屏幕锁定后 WDA 会话会断开，表现为「元素全部找不到」。测试机应关闭自动锁屏，必要时用 `simctl` 或设备管理工具保持常亮。

**固定系统版本。** 系统升级会改变控件层级与弹窗文案，跨版本的用例需要分别验证。测试机不要开启自动更新，升级前先在模拟器上跑一遍全量回归。

**设备命名要稳定。** `deviceName` 是会话创建的关键参数，重命名设备会让所有脚本失效。给测试机起固定名字并记录在文档里，比依赖 UDID 更直观（UDID 仍然要用，但作为并行分配的依据）。

## 用例设计与断言粒度

iOS 用例的常见问题是「太细」。因为 XCUITest 能访问到每一个控件，很容易写出「检查这个 label 的字体颜色」这类断言，结果每次 UI 微调都要改脚本。

建议把断言分成三层：

1. **存在性**：目标页面出现了预期的关键控件。用于验证「跳转成功」。
2. **业务值**：金额、数量、状态文案正确。用于验证「逻辑正确」。
3. **交互结果**：点击后产生了正确的新状态（角标加一、列表多一行）。用于验证「操作生效」。

样式、颜色、间距一律不测——那是设计走查与截图对比的职责，不是功能自动化的职责。

另一个原则是**一条用例只验证一个业务结论**。把「登录 + 搜索 + 加购 + 下单 + 支付」写成一条超长用例，失败时你只知道「中间某处不对」，排查成本极高；拆成五条短用例，失败点一目了然，而且可以并行。

**时间与本地化也会咬人。** 断言里出现日期、金额、星期时，设备语言与地区设置决定格式：同一串「2026/10/28」在英文环境下会变成「Oct 28, 2026」，`HH:mm` 还可能因十二小时制变成「上午 9:05」。测试机应统一语言、地区与二十四小时制，并在启动参数里通过 `-AppleLanguages`、`-AppleLocale` 显式覆盖，而不是依赖人工设置。**深色模式**同理：跟随系统切换会让截图整体偏色，跑视觉回归前先固定外观模式，功能断言则尽量不依赖颜色。还有一点常被忽略：测试账号与应用初始数据应在用例开始前通过深链或启动参数直接注入，而不是靠 UI 一层层点进去准备；注入失败就让用例立刻失败，别让它半路以「找不到元素」的形式暴露，那样排查方向会被带偏。

## 与持续交付的配合

iOS 的发布节奏受审核约束，自动化能发挥最大价值的位置是**提测与回归**，而不是线上监控。

推荐的三道门：

- **提交门**：只跑与改动模块相关的用例（用 Xcode 的 test plan 分组，或按类名过滤），控制在五分钟内。
- **每日回归**：全量在模拟器上跑，结果附 `xcresult` 与失败截图，发到团队频道。
- **发布前**：核心路径在真机上跑一遍，覆盖升级安装（从旧版本覆盖安装）与首次安装两种场景。

升级安装这条特别容易被忽略：很多问题只在「用户从旧版本升级上来」时出现——数据库迁移失败、缓存格式不兼容、权限状态残留。新装永远是干净的，测不出这些。

## 失败排查的固定动作

iOS 的失败信息通常比 Android 更明确，但仍建议按固定顺序看：

1. **看 `xcresult`**：Xcode 打开后能逐步骤回放，包含截图与层级快照，这是最高效的入口。
2. **看失败截图**：确认界面停在哪一页，是弹窗挡住、还是根本没跳转。
3. **看元素层级**：在 Xcode 的 Debug View Hierarchy 里对照 identifier 是否正确设置。
4. **看 WDA 日志**（Appium 场景）：会话建立失败、元素查找超时都会打印具体原因。
5. **手动复现**：手工正常而脚本失败，多半是等待或标识问题；手工也失败，才是产品缺陷。

把「先看 xcresult」变成团队肌肉记忆，比反复讨论「是不是又 flaky 了」有用得多。

## 稳定性与常见坑

- [ ] 用 `accessibilityLabel` 文案做定位，产品改文案就全红
- [ ] WDA 签名配置不一致，真机永远启动超时
- [ ] 只注册了中断监视器却从不交互，弹窗无人处理
- [ ] 用 `sleep` 等转场动画，慢设备必挂
- [ ] 并行执行时多个 worker 共用同一账号，数据互相覆盖
- [ ] 模拟器上验证相机、推送，结论无效
- [ ] `deviceName` 与实际模拟器不一致，会话创建失败
- [ ] 每次 CI 都全量编译，回归时间被编译吃掉
- [ ] 键盘遮挡底部按钮，点击落空
- [ ] 元素层级随系统版本变化，类型路径定位失效
- [ ] 失败不留 `xcresult`，只能靠日志猜
