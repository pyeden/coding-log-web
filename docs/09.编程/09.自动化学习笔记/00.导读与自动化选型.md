# 00 导读与自动化选型

## 本章目标

读完本章，你要能回答三个问题：**这个场景到底该不该自动化**、**该落在哪一层**、**选哪套工具链**。后面四篇分别讲 Web、API、Android、iOS 的具体写法，但它们都建立在本章的判断之上。一句话概括：**先把测试分层摆对，再谈工具；工具选错只是返工，分层选错是长期负债。**

## 自动化的边界：什么时候不该自动化

自动化不是「把手工用例翻译成脚本」。它的本质是**用可重复执行的代码替代重复的人工判断**，所以只有同时满足下面三条才值得投入：

1. **可重复**：同一份输入，期望结果稳定。涉及主观判断（界面好不好看、文案语气是否得体）的部分不适合。
2. **高频或高价值**：回归频率高，或者失败代价高（支付、权限、数据一致性）。
3. **有维护预算**：脚本是要养的。没有人力跟着产品迭代修脚本，三个月后它就是一堆红色告警。

明确不该自动化的典型场景：

- **一次性验证**：上线前的临时检查，写完脚本的时间比手工点一遍还长。
- **需求剧烈变动中的模块**：前端大改版期间写 UI 用例，等于给一个正在移动的靶子画准星。
- **探索性测试**：新功能的缺陷往往藏在「脚本没想到的路径」里，探索性测试的价值恰恰在于不按剧本走。
- **强依赖不可控外部系统的链路**：第三方沙箱不稳定、短信验证码无法自动获取，这类环节应做**挡板/桩**，而不是硬等。
- **只跑一次的迁移校验**：数据迁移用一次性 SQL 校验脚本即可，不必纳入回归体系。

反过来，**最该优先自动化的**是：核心业务主流程的冒烟（下单、登录、支付）、接口契约与字段校验、跨端一致的业务规则、每次发版必测的回归集合。

## 四类目标对比

下表是选型的第一张地图。注意「投入」指首次建成成本，「维护成本」指每轮迭代的持续成本。

| 维度 | Web 自动化 | API 自动化 | Android 自动化 | iOS 自动化 |
| --- | --- | --- | --- | --- |
| 被测对象 | 浏览器中的页面与交互 | HTTP 接口、业务规则、契约 | Android 原生/混合 App | iOS 原生/混合 App |
| 主流工具 | Playwright、Selenium 4 | Playwright APIRequestContext、pytest + requests、REST Assured、Postman + Newman | Appium 2 + UiAutomator2、Espresso | XCUITest、Appium + XCUITest driver |
| 单条用例耗时 | 秒级到十几秒 | 毫秒级到百毫秒级 | 十秒级到分钟级 | 十秒级到分钟级 |
| 首次投入 | 中 | 低 | 高（环境、设备、驱动） | 很高（签名、WDA、设备） |
| 收益 | 覆盖端到端用户路径 | 覆盖业务规则与契约，最快定位 | 覆盖 App 关键路径与兼容性 | 覆盖 App 关键路径与系统交互 |
| 维护成本 | 中高（选择器、等待） | 低（接口稳定即可） | 高（版本、机型、弹窗） | 很高（系统版本、签名、动画） |
| 脆弱度 | 中 | 低 | 高 | 高 |
| 建议占比 | 10%–20% | 60%–70% | 10% | 5%–10% |

这张表最重要的读法是**最后一行的占比**。绝大多数团队的自动化投入应该压在 API 层：快、稳、定位准。UI 自动化只保留「用户真的会这么走」的关键路径。

## 选型决策树

按顺序问自己，命中即停：

1. **被测逻辑能否通过接口直接触达？**
   - 能 → 走 **API 自动化**。除非这条路径的价值就在于「用户点击后确实能走通」，否则不要下沉到 UI。
   - 不能 → 进入 2。
2. **问题只出现在某个端上吗？**
   - 只在浏览器 → **Web 自动化**（Playwright 优先；团队已有 Selenium 资产且迁移成本高则留 Selenium 4）。
   - 只在 Android → **Android 自动化**（Appium 2 + UiAutomator2；纯原生且团队是 Kotlin/Java，可评估 Espresso）。
   - 只在 iOS → **iOS 自动化**（XCUITest 主线；需要与 Android 共用一套脚本时用 Appium + XCUITest driver）。
   - 多端都要 → 先做 API 层，再对每端只保留 1–3 条主流程。
3. **团队没有专职测试开发，只有业务测试同学？**
   - 优先 Playwright（自带报告、trace、代码生成）与 Postman/Newman（可视化编写、命令行执行）。
4. **需要在 CI 里跑、且要求并发？**
   - Web：Playwright 的分片与多 worker 最省事。
   - 移动端：先解决设备农场或本地模拟器并发，再谈框架。

## 测试分层：API 为主，UI 为辅

传统「测试金字塔」从上到下是 UI → 集成 → 单元，越往下越多越快。实践中更贴合自动化落地的是「**测试奖杯**」：单元测试打底，**集成/API 测试占最大头**，UI 测试只留薄薄一层。

理由很直接：一条 UI 用例平均要经历启动浏览器或安装 App、渲染、等待网络、断言界面，任何一环抖动都会失败；而同样的业务规则，一条 API 用例几百毫秒就能验完，失败时还能直接指出是哪个字段错了。所以正确的顺序是：

- 业务规则、边界值、权限矩阵 → **API 层**。
- 跨服务的编排与数据一致性 → **API 层 + 少量集成**。
- 「用户能不能走通这条路」→ **UI 层，只保留主流程**。

一个可执行的配额：新项目第一年，API 用例数与 UI 用例数之比控制在 **5:1 以上**；如果反过来，说明分层出了问题，先别加 UI 用例，先把 API 覆盖补上。

需要强调的是，分层不是教条。有些系统天生没有可用的接口（例如第三方提供的黑盒页面），这时 UI 自动化就是唯一选择；有些系统的风险集中在渲染与交互本身（例如可视化编辑器、拖拽布局），也只能在 UI 层验证。判断标准始终是「这一层能不能更早、更准地发现缺陷」，而不是「标准答案怎么写」。

## 核心术语表

| 术语 | 含义 | 为什么重要 |
| --- | --- | --- |
| flaky（不稳定用例） | 同一代码、同一环境下结果时红时绿 | 它会摧毁团队对自动化的信任，比没有自动化更糟 |
| page object（页面对象） | 把页面元素定位与操作封装成类，用例只调用业务方法 | 降低选择器变更带来的扩散成本，四端通用 |
| capability | 启动会话时传给驱动的键值对配置（设备、应用、自动化引擎） | 移动端 80% 的启动失败源于 capability 写错 |
| accessibility id | 元素的无障碍标识，Android 对应 contentDescription，iOS 对应 accessibilityIdentifier | 最稳的跨端定位方式，需要研发配合埋点 |
| storageState | Playwright 保存的浏览器登录态（cookie + localStorage） | 跳过登录步骤，省时间也减少验证码干扰 |
| trace | Playwright 记录的执行轨迹（含快照、网络、日志） | 失败回放的第一手证据，比截图信息量大得多 |
| fixture | 测试前置/后置的复用单元（pytest、Playwright Test） | 数据准备与清理的标准做法，避免用例互相污染 |
| 契约测试 | 校验实现是否符合 OpenAPI/JSON Schema 约定 | 在联调前发现字段缺失、类型漂移 |
| WDA | WebDriverAgent，iOS 上承载 XCUITest 的代理程序 | Appium 跑 iOS 的前提，签名问题多半出在这里 |
| 数据工厂 | 用代码按需造数据并登记清理的模块 | 让用例自带数据，摆脱共享测试库的相互踩踏 |

## 上手路径：先跑通一条最小链路

在动手写业务用例前，先确认工具链能跑通。以 Web 为例，最小验证只需要三步：

```bash
# 1. 建一个独立目录，避免和业务工程耦合
mkdir -p automation-lab && cd automation-lab
npm init -y
npm i -D @playwright/test
npx playwright install chromium

# 2. 跑官方示例，确认浏览器能起来
npx playwright test --headed
```

```python
# 3. 或者用 Python 版本验证（pip install playwright pytest-playwright）
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("https://playwright.dev/")
    print(page.title())
    browser.close()
```

能打印出标题，说明浏览器、驱动、网络都通了。移动端同理：先确认 `adb devices` 能看到设备、`appium driver list --installed` 能看到 UiAutomator2，再写第一条用例。

## 工程化：一个测试仓库长什么样

四类自动化建议放在同一个仓库的不同目录下，共享配置、工具函数与 CI 流水线：

```text
automation/
├── api/                 # 接口用例：pytest 或 Playwright request
│   ├── fixtures/        # 登录态、数据工厂
│   └── schemas/         # JSON Schema 文件
├── web/                 # 浏览器用例
│   ├── pages/           # page object
│   └── tests/
├── android/             # Appium + UiAutomator2 用例
├── ios/                 # XCUITest 工程或 Appium 用例
├── reports/             # 本地输出，不入库
└── .github/workflows/   # 分层的 CI 流水线
```

三条工程约定值得从第一天就立起来：

1. **失败必须可诊断**：报告里要有请求/响应、截图、trace 或设备日志，否则排查成本会吃掉自动化的全部收益。
2. **用例必须能独立跑**：任何一条用例单独执行都应通过，不依赖执行顺序。
3. **环境必须参数化**：地址、账号、设备名从环境变量读，绝不硬编码。

## 从零到一的落地节奏

自动化最容易死在「一次想做完」。合理的节奏是按季度推进，每一阶段都要有可交付物：

**第一个月：打通链路。** 目标不是覆盖多少用例，而是让 CI 能稳定跑起来。选一条最关键的主流程，把环境准备、执行、报告、通知这条链路走通。此时用例数量少得可怜是正常的，重要的是团队能看到一条绿色的流水线。

**第二至三个月：铺接口。** 把核心业务的接口用例补齐，优先覆盖权限矩阵、金额计算、状态机流转这三类最容易出错的地方。每补一条用例，同步补齐它的数据准备与清理逻辑，不要留「以后再补」的尾巴。

**第四至六个月：收口 UI。** 等接口层稳定后，再补端到端主流程。这时你会发现 UI 用例写得很快，因为大部分业务断言已经在接口层做完了，UI 层只需要确认「页面能打开、关键元素在、提交后状态正确」。

**之后：治理。** 建立 flaky 用例的统计与隔离机制，每周看一次失败分布。失败率超过 5% 的用例必须修或者删，不允许长期挂着。

## 三种常见反模式

**反模式一：把所有手工用例翻译成脚本。** 手工用例里有大量「顺便看一眼」的检查，这些在脚本里会变成脆弱的断言。自动化用例应该重新设计，只保留有明确预期结果的部分，而不是逐条搬运。

**反模式二：追求覆盖率数字。** 覆盖率是结果不是目标。为了数字去写一堆只断言状态码 200 的接口用例，除了拖慢流水线没有任何价值。真正有价值的用例是「如果这个逻辑错了，它会红」。

**反模式三：把自动化当质量保险。** 自动化只能证明「已知的路径仍然正常」，不能发现「没想到的问题」。它替代的是重复劳动，不是思考。探索性测试、代码评审、线上监控这三件事，一件都不能少。

## 团队协作与角色分工

自动化不是测试同学一个人的事，三个角色必须配合：

- **研发**：为关键元素补 accessibility id 或 test id，保证接口字段语义稳定，避免无通知的破坏性变更。这是 UI 自动化能否长期活下去的前提。
- **测试**：设计用例、维护脚本、分析失败原因，判断是产品缺陷还是脚本问题。
- **运维/平台**：提供 CI  runner、设备农场、测试环境与数据快照，保证流水线不被环境问题拖垮。

最容易被忽略的是研发这一环。如果前端同学每次改版都换一遍 class 名，测试同学就只能不停改选择器，最终双方都失去耐心。把「新增交互元素必须带 test id」写进团队规范，比任何框架选型都管用。

## 稳定性与常见坑

- [ ] 没有设置全局超时，某条用例卡死拖垮整轮
- [ ] 用固定 `sleep` 代替显式等待
- [ ] 用例之间共享账号或数据，导致顺序依赖
- [ ] 断言只看「元素存在」，不看业务结果
- [ ] 失败只留一张截图，没有日志与网络记录
- [ ] 测试环境数据被人工改动，用例假设失效
- [ ] 所有用例都跑在 UI 层，回归时间超过半小时
- [ ] 没有 flaky 用例的隔离与统计机制，红色告警被习惯性忽略
- [ ] 移动端用例没处理系统弹窗与软键盘遮挡
