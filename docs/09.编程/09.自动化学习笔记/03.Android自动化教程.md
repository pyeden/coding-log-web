# 03 Android自动化教程

## 本章目标

用 Appium 2 + UiAutomator2 驱动真实 Android 设备或模拟器，把 App 的关键用户路径写成可回归的用例。读完本章你能：配好 SDK 与 adb、写出正确的 capabilities、用稳定的定位策略找元素、处理 WebView 与系统弹窗、在 CI 里用无头模拟器跑起来。纯原生团队另有一条路是 Espresso，本章也会说明它适合与不适合的地方。

## 核心概念与术语

**Appium 2 的架构**。Appium 2 把驱动拆成可插拔的插件，服务端本身只负责协议转换。跑 Android 需要先安装 **UiAutomator2 driver**，它是基于 Google UiAutomator 框架实现的自动化引擎，通过设备上的 instrumentation 与 App 交互。这一点和 Appium 1 内置驱动的时代不同，第一次上手必须先 `appium driver install uiautomator2`。

**adb（Android Debug Bridge）**。连接设备、安装应用、查看日志、截图、模拟按键都靠它。自动化脚本报错时，第一个动作往往是 `adb logcat` 看崩溃栈，而不是盯着 Python 异常。

**capability**。启动会话时传给 Appium 的配置项，决定「用哪台设备、哪个引擎、打开哪个 App、要不要重置」。它是移动端最常出错的地方：包名写错、Activity 写错、`appium:` 前缀漏了，都会得到一句语焉不详的会话创建失败。

**accessibility id 与 resource-id**。两者都是元素的稳定标识：`resource-id` 来自布局里的 `android:id`，通常形如 `com.example.shop:id/btn_add`；`accessibility id` 对应 `contentDescription`，是给无障碍服务读的语义标签。前者依赖开发的 id 命名，后者依赖无障碍标注，**两者都比 XPath 稳定**。

**WebView 与混合应用**。原生壳里嵌 H5 页面时，元素不在原生层级树中，必须切换到 WebView 上下文才能用 CSS/XPath 定位。切换的前提是 App 开启了 WebView 调试（`setWebContentsDebuggingEnabled(true)`）。

**UiAutomator 选择器**。一种在设备端执行的原生查找语法，支持滚动查找（`UiScrollable`），适合「元素在列表深处需要滑动才可见」的场景——这是 XPath 做不到也不该做的事。

## 工具/方案对比

| 维度 | Appium 2 + UiAutomator2 | Espresso | UiAutomator（原生） |
| --- | --- | --- | --- |
| 运行位置 | 设备上运行 instrumentation，PC 端用 WebDriver 协议调度 | 与被测 App 同一进程 | 设备上独立进程 |
| 语言 | 任意（Python/Java/JS…） | Kotlin / Java | Kotlin / Java |
| 是否需要改 App 代码 | 不需要 | 需要 `androidTest` 源集与依赖 | 不需要 |
| 跨 App 操作 | 支持（可操作系统设置、其他应用） | 不支持（限本应用内） | 支持 |
| 稳定性 | 中（受弹窗、动画、设备影响） | 高（与应用同进程，同步机制强） | 中高 |
| 速度 | 慢（每步一次协议往返） | 快 | 中 |
| 适合场景 | 端到端回归、跨端统一脚本 | 开发自测、单 App 内的 UI 逻辑 | 系统级交互、跨应用流程 |

实践建议：**端到端回归用 Appium**，因为它能覆盖「打开 App → 登录 → 下单 → 收到推送」这种跨应用路径，且能和 iOS 共用一套页面对象思路；**开发同学的单模块 UI 验证用 Espresso**，跑得快、失败信息准，适合放进单元测试流水线。两者不是替代关系，而是分工。

## 环境准备

```bash
# 1. 安装命令行工具与平台工具（Android Studio 亦可，或用 sdkmanager）
sdkmanager "platform-tools" "platforms;android-34" "system-images;android-34;google_apis;arm64-v8a"

# 2. 创建并启动模拟器
avdmanager create avd -n test_api34 -k "system-images;android-34;google_apis;arm64-v8a"
emulator -avd test_api34 -no-window -no-audio -gpu swiftshader_indirect &

# 3. 确认设备可见
adb wait-for-device
adb devices

# 4. 安装 Appium 2 与 UiAutomator2 driver
npm i -g appium
appium driver install uiautomator2
appium driver list --installed

# 5. 启动服务（默认 4723 端口）
appium --address 127.0.0.1 --port 4723
```

注意 `adb devices` 里设备状态必须是 `device` 而不是 `unauthorized` 或 `offline`，否则后面的会话一定创建失败。

## capabilities 关键项

| 键 | 示例值 | 说明 |
| --- | --- | --- |
| `platformName` | `Android` | 平台，必填 |
| `appium:automationName` | `UiAutomator2` | 自动化引擎，Appium 2 必填 |
| `appium:deviceName` | `emulator-5554` | 设备名，用 `adb devices` 里的标识 |
| `appium:platformVersion` | `14` | 系统版本；多设备时可省略 |
| `appium:app` | `/abs/path/app.apk` | 安装包绝对路径（首次安装用） |
| `appium:appPackage` | `com.example.shop` | 包名，已安装时用它启动 |
| `appium:appActivity` | `.ui.MainActivity` | 启动 Activity |
| `appium:noReset` | `true` | 不重置应用状态，保留登录态 |
| `appium:fullReset` | `false` | 与 `noReset` 互斥，谨慎使用 |
| `appium:newCommandTimeout` | `120` | 无指令超时（秒），CI 上适当放大 |
| `appium:udid` | 设备序列号 | 多设备并行时用于指定目标 |
| `appium:chromeOptions` | `{ "w3c": true }` | WebView 场景下配置 Chromedriver |

两个最容易踩的坑：一是 `appium:` 前缀，Appium 2 对非标准前缀的 capability 会直接拒绝；二是 `noReset` 与 `fullReset` 同时为 `true`，行为未定义且必然出问题。

## 上手路径：第一条可运行用例

```python
from appium import webdriver
from appium.options.android import UiAutomator2Options
from appium.webdriver.common.appiumby import AppiumBy
from selenium.webdriver.support.ui import WebDriverWait

options = UiAutomator2Options()
options.platform_name = "Android"
options.automation_name = "UiAutomator2"
options.device_name = "emulator-5554"
options.app_package = "com.example.shop"
options.app_activity = ".ui.MainActivity"
options.no_reset = True
options.new_command_timeout = 120

driver = webdriver.Remote("http://127.0.0.1:4723", options=options)
wait = WebDriverWait(driver, 15)

try:
    # 用 accessibility id 定位搜索入口
    wait.until(lambda d: d.find_element(AppiumBy.ACCESSIBILITY_ID, "搜索")).click()

    # resource-id 定位输入框
    box = wait.until(lambda d: d.find_element(AppiumBy.ID, "com.example.shop:id/search_input"))
    box.send_keys("耳机")

    driver.find_element(AppiumBy.ID, "com.example.shop:id/btn_search").click()

    # 断言结果列表出现
    first = wait.until(lambda d: d.find_element(AppiumBy.ID, "com.example.shop:id/item_title"))
    assert "耳机" in first.text
finally:
    driver.quit()
```

会话创建后建议先 `driver.implicitly_wait(0)`，移动端隐式等待与显式等待混用会放大不确定性；需要等待就写显式等待。

## 定位策略

| 优先级 | 方式 | 写法 | 说明 |
| --- | --- | --- | --- |
| 1 | accessibility id | `AppiumBy.ACCESSIBILITY_ID, "结算"` | 语义稳定，需开发标注 contentDescription |
| 2 | resource-id | `AppiumBy.ID, "com.example.shop:id/btn_pay"` | 依赖 id 命名，通常最准 |
| 3 | UiAutomator 文本 | `AppiumBy.ANDROID_UIAUTOMATOR, 'new UiSelector().text("结算")'` | 文案会变，但可读性好 |
| 4 | UiAutomator 滚动 | `new UiScrollable(...).scrollIntoView(...)` | 列表深处元素的唯一正解 |
| 5 | XPath | `//android.widget.TextView[@text="结算"]` | 慢且脆，最后手段 |

一个典型误区是用 XPath 处理长列表。XPath 只能匹配当前已渲染的节点，虚拟列表里没滑到的元素根本不存在于层级树中，这时必须用 `UiScrollable`。另一个误区是把 `index` 写进选择器，列表排序一变就全错。

页面对象的封装思路与 iOS 篇完全一致：把定位器与等待收进类里，用例只表达业务动作。读者可以对照 [iOS 自动化教程](/note/automation/ios/) 的示例，看同一个「商品详情页」在两端如何实现。

## WebView 与混合应用

```python
# 查看当前可用的上下文
print(driver.contexts)   # ['NATIVE_APP', 'WEBVIEW_com.example.shop']

# 切到 WebView 后用标准 Web 定位
driver.switch_to.context("WEBVIEW_com.example.shop")
driver.find_element("css selector", "button.submit").click()

# 切回原生继续操作
driver.switch_to.context("NATIVE_APP")
```

三个前提缺一不可：App 打开 WebView 调试开关、测试机上装了与 WebView 版本匹配的 Chromedriver、capability 里配置了 `chromeOptions`。如果 `contexts` 只有一项，99% 是调试开关没开。

混合应用还有一类坑：H5 与原生之间的跳转需要等待上下文切换完成，直接 `switch_to.context` 可能抛 `NoSuchContextException`。稳妥做法是轮询 `driver.contexts` 直到目标上下文出现，再切换。

## 稳定性工程

**等待**。移动端的「慢」是常态：冷启动、页面转场、网络加载、动画。三条原则：会话建立后关掉隐式等待；所有交互前用显式等待确认元素 `displayed` 且 `enabled`；对页面转场用「等待目标页面某个特征元素出现」，而不是睡两秒。

**系统弹窗**。权限申请、通知授权、版本更新提示、电量优化提示，会在任意时刻弹出并抢走焦点。处理方式有两种：一是在 capability 里预置权限（`autoGrantPermissions`），从源头减少弹窗；二是封装一个「弹窗巡检」方法，在关键操作前尝试关闭已知弹窗，匹配不到就继续。后者是兜底，不能替代前者。

**软键盘遮挡**。输入后键盘可能挡住按钮，导致点击坐标落在键盘上。处理办法是输入完成后 `driver.hide_keyboard()`，或者在点击前对目标元素执行 `scrollIntoView`。

**动画与 Toast**。Toast 出现时间短，用 `WebDriverWait` 配合 `presence_of_element_located` 可能错过。更可靠的是在测试构建里延长 Toast 时长，或者直接断言「操作后的页面状态」而不是 Toast 文案。

**数据与账号**。移动端登录往往绑定设备与短信，建议测试环境提供「固定验证码」或「白名单手机号」，避免自动化卡在验证码。登录态用 `noReset=true` 保留，但要注意不同用例之间的状态污染——必要时在 teardown 里清理应用数据（`adb shell pm clear <package>`）。

**取证**。移动端复现成本高，失败现场必须留证据：截图、`page_source`、logcat 三件套是底线。Appium 支持在会话开始时录制视频（依赖 ffmpeg），对排查「操作顺序正确但界面状态不对」的问题特别有效。录制会拖慢执行速度，建议只在失败重跑或夜间回归时开启。

**设备差异**。同一份脚本在不同厂商 ROM 上的表现可能不同：状态栏高度、权限弹窗样式、后台限制策略都不一样。跨机型回归至少覆盖一台原生 ROM 与一台深度定制 ROM，并把差异点写进页面对象，而不是散落在用例里。

## 真机与 CI

本地调试用模拟器足够，回归建议真机 + 模拟器混合：模拟器跑主流程（快、可并行），真机跑关键路径与兼容性（准、能发现厂商问题）。

CI 上的两种形态：

1. **自建设备**：一台 Linux/macOS runner 接多台真机（USB 或无线 adb），用 `appium:udid` 分配任务。适合设备固定的团队。
2. **云设备农场**：把 apk 上传，由平台提供设备矩阵。优点是省维护，缺点是成本与网络延迟。

本地 CI 跑模拟器的关键命令：

```bash
# 启动无头模拟器并等待就绪
emulator -avd test_api34 -no-window -no-audio -no-snapshot &
adb wait-for-device
until [ "$(adb shell getprop sys.boot_completed | tr -d '\r')" = "1" ]; do sleep 2; done

# 安装被测包并跑用例
adb install -r app-debug.apk
pytest android/tests -q --junitxml=report.xml
```

`sys.boot_completed` 这个轮询不能省。模拟器进程启动不等于系统可用，直接跑用例会得到一堆「设备未就绪」的诡异错误。

## Espresso 对照：什么时候值得写

Espresso 运行在被测应用同一进程内，直接访问视图树，天然规避了「跨进程查找元素」的同步问题，因此更快更稳。代价是它只能测本应用，且需要在工程里新增 `androidTest` 源集：

```kotlin
// app/src/androidTest/java/com/example/shop/CartTest.kt
@RunWith(AndroidJUnit4::class)
class CartTest {
    @get:Rule
    val rule = ActivityScenarioRule(MainActivity::class.java)

    @Test
    fun addToCart_updatesBadge() {
        onView(withId(R.id.btn_add)).perform(click())
        onView(withId(R.id.cart_badge)).check(matches(withText("1")))
    }
}
```

运行 `./gradlew connectedAndroidTest` 即可在已连接设备上执行。它适合两类场景：开发提交前的快速自检，以及单个页面内复杂的交互逻辑（表单校验、列表联动）。不适合的场景是跨应用流程（拉起支付、跳转系统设置）与多端统一脚本——这两类交给 Appium。

一个务实的分工是：**Espresso 进代码仓库，随 PR 跑；Appium 用例独立仓库，随发布跑**。两者共享同一套业务场景清单，但断言粒度不同，前者细、后者粗。

## 设备矩阵与用例筛选

移动端自动化最大的成本不在写脚本，而在「跑多少设备」。全矩阵跑一遍既慢又贵，合理做法是按风险分层：

| 层级 | 设备范围 | 用例范围 | 触发时机 |
| --- | --- | --- | --- |
| 冒烟 | 一台主流机型 + 一台低端机 | 登录、核心下单、支付 | 每次提测 |
| 回归 | 三种屏幕尺寸 + 两种系统版本 | 全部 P1 用例 | 每周或发布前 |
| 兼容 | 厂商 ROM 抽样（含深度定制） | 关键路径 + 已知差异点 | 大版本发布前 |

低端机这一层不能省。很多问题只在内存紧张、CPU 较慢的设备上暴露：动画掉帧导致点击落空、列表复用导致元素错位、后台被系统杀死导致登录态丢失。这些在旗舰机上永远复现不了。

用例筛选上，建议给每条用例打上「设备敏感」标签：涉及相机、定位、推送、生物识别的用例必须在真机上跑，模拟器上的结果不可信；纯 UI 流程的用例用模拟器即可。

## 失败排查的固定动作

移动端失败的现象往往很模糊——「元素找不到」「会话断开」。固定按下面顺序排查，能覆盖八成情况：

1. **看截图**：Appium 会在失败时自动截图（`get_screenshot_as_file`），先确认界面停在哪一页。
2. **看页面层级**：`driver.page_source` 打印当前 XML，确认元素是否真的存在、id 是什么。很多「找不到」其实是 id 写错或元素在另一个上下文里。
3. **看 logcat**：`adb logcat -d | grep -i "AndroidRuntime\|FATAL"`，确认 App 是否崩溃。
4. **看 Appium 服务日志**：会话创建失败会明确写出哪个 capability 不合法。
5. **手动复现一次**：如果手工也失败，那是产品缺陷；手工正常而脚本失败，才是脚本问题。

把这几步写成一份排查清单贴在团队文档里，比每次靠经验摸索快得多。

## 稳定性与常见坑

- [ ] capability 漏了 `appium:` 前缀，会话直接创建失败
- [ ] `appPackage` / `appActivity` 写错，App 启动后立即崩溃
- [ ] 用 XPath 找长列表元素，滑不到就找不到
- [ ] 隐式等待与显式等待混用，超时时间互相叠加
- [ ] 没处理权限弹窗，第一条用例就卡住
- [ ] 软键盘遮挡目标元素，点击落空
- [ ] 用例之间共用登录态，状态互相污染
- [ ] 设备未就绪就开跑，报大量无意义失败
- [ ] WebView 未开调试，`contexts` 只有 `NATIVE_APP`
- [ ] 只在一种 ROM 上验证，忽略厂商定制差异
- [ ] 失败不保留截图与 logcat，排查靠猜
