# 08 并发编程

## 本章目标

理解 goroutine 与 channel 的协作模型，能用 `select`、`sync`、`context` 组织可控的并发流程，并知道如何发现与避免竞态。

## Goroutine

在函数调用前加 `go` 就启动一个 goroutine，由运行时调度到操作系统线程上。goroutine 初始栈很小，可以轻松创建成千上万个；但「轻量」不等于「免费」，无界创建仍会耗尽内存与下游资源。

`main` 返回时程序立即退出，不会等待其他 goroutine；因此需要 `sync.WaitGroup`、channel 或 context 来协调生命周期。

```go
package main

import (
	"fmt"
	"sync"
)

func worker(id int, jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
	defer wg.Done()
	for job := range jobs {
		results <- job * job
	}
}

func main() {
	jobs := make(chan int, 3)
	results := make(chan int, 3)

	var wg sync.WaitGroup
	for i := 1; i <= 2; i++ {
		wg.Add(1)
		go worker(i, jobs, results, &wg)
	}

	for i := 1; i <= 3; i++ {
		jobs <- i
	}
	close(jobs)
	wg.Wait()
	close(results)

	sum := 0
	for r := range results {
		sum += r
	}
	fmt.Println("sum:", sum)
}
```

channel 的方向类型（`<-chan`、`chan<-`）能在编译期约束读写，推荐在函数签名中使用。**只有发送方关闭 channel**，接收方关闭会 panic；向已关闭的 channel 发送也会 panic。

## 缓冲与非缓冲

非缓冲 channel 的发送与接收必须同时就绪，天然形成同步点；缓冲 channel 在缓冲未满时发送不阻塞，适合解耦生产与消费。缓冲大小应来自实际背压需求，而不是随意写一个大数。

常见模式是 worker pool：固定数量 goroutine 消费同一个 jobs channel，结果写入 results，主协程负责关闭与收集。需要「任一任务失败就取消全部」时，用 `context.WithCancel` 配合 `errgroup`（官方扩展库 `golang.org/x/sync/errgroup`），比手写 channel 更不容易泄漏。

## select 与超时

`select` 同时等待多个 channel 操作，哪个就绪执行哪个；多个同时就绪时随机选择。`default` 分支让 select 非阻塞，常用于「尝试发送，失败就丢弃」。

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

	done := make(chan string, 1)
	go func() {
		time.Sleep(100 * time.Millisecond)
		done <- "完成"
	}()

	select {
	case msg := <-done:
		fmt.Println(msg)
	case <-ctx.Done():
		fmt.Println("超时:", ctx.Err())
	}
}
```

`context` 用于传递取消信号与截止时间，应作为函数的第一个参数，且不要存进结构体。收到取消后要尽快清理并返回，长时间忽略 `ctx.Done()` 会让上游一直等待。关闭 channel 后仍可接收剩余缓冲值，接收完毕后得到零值，`v, ok := <-ch` 的 `ok` 为 false 可用来判断是否已关闭。

## 共享内存与锁

多个 goroutine 访问同一变量时，读改写不是原子操作。用 `sync.Mutex` 保护临界区，或用 channel 传递所有权。`sync.RWMutex` 适合读多写少；`atomic` 适合简单计数，但不要用它替代对复杂不变量的加锁。

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	var wg sync.WaitGroup
	counter := 0

	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			mu.Lock()
			counter++
			mu.Unlock()
		}()
	}
	wg.Wait()
	fmt.Println(counter)
}
```

Go 的口号是「不要通过共享内存来通信，而要通过通信来共享内存」，但锁并非禁忌；关键是明确哪一小段状态需要保护，避免锁粒度过大。

## 竞态与循环变量

`go test -race` 或 `go run -race` 会在运行时检测数据竞争，CI 应至少跑一次。竞态可能偶发，不能靠「本地没复现」判断不存在。

单次初始化用 `sync.Once`，它保证函数在多协程下只执行一次，常见于懒加载配置或单例。简单的计数场景可用 `sync/atomic`，但原子操作只保证单个变量，无法维护多个字段之间的不变量。

Go 1.22 起，`for` 循环的迭代变量每轮独立，闭包捕获的是当前轮的值；1.21 及更早版本所有迭代共享同一个变量，需要在循环体内 `v := v` 固定。这个变更只影响新语义编译的模块，升级时要留意 `go.mod` 的 go 版本。

## 常见坑

- **goroutine 泄漏**：向无人接收的 channel 发送，永久阻塞。
- **忘记 `wg.Add(1)` 或 `Done()`**：Wait 永久挂起或 panic。
- **在 goroutine 里 panic**：没有 recover 会导致整个进程退出。
- **关闭 channel 后又发送**：直接 panic。
- **用 `time.Sleep` 等待结果**：不稳定，应使用同步原语。
