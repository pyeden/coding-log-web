# 10 测试、性能与工程化

## 本章目标

用 `testing` 写出表驱动测试与子测试，掌握基准测试、覆盖率与 pprof 的基本用法，并把 `-race`、`vet`、CI 串成可执行的工程流程。

## 测试文件与表驱动

测试文件以 `_test.go` 结尾，与被测包同目录、同包名，`go test` 会自动发现。测试函数签名固定为 `func TestXxx(t *testing.T)`。

表驱动（table-driven）是 Go 的主流写法：把输入与期望放进切片，循环执行并用 `t.Run` 创建子测试。新增用例只需加一行数据，失败时子测试名能直接定位。

```go
package calc

// Add 返回两个整数之和。
func Add(a, b int) int {
	return a + b
}
```

```go
package calc

import "testing"

func TestAdd(t *testing.T) {
	cases := []struct {
		name string
		a, b int
		want int
	}{
		{"正数", 2, 3, 5},
		{"负数", -2, 3, 1},
		{"零", 0, 0, 0},
	}

	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			if got := Add(tc.a, tc.b); got != tc.want {
				t.Fatalf("Add(%d, %d) = %d, want %d", tc.a, tc.b, got, tc.want)
			}
		})
	}
}

func BenchmarkAdd(b *testing.B) {
	for i := 0; i < b.N; i++ {
		Add(i, i)
	}
}
```

`t.Fatalf` 会立即终止当前测试；需要继续收集多个失败时用 `t.Errorf`。子测试可用于并行：在子测试内调用 `t.Parallel()`，但要确保用例之间没有共享可变状态。

## 运行与覆盖率

```bash
go test ./...                       # 运行所有测试
go test -run TestAdd -v ./calc      # 只跑匹配的测试
go test -bench . -benchmem ./calc   # 基准测试与内存分配
go test -cover ./...                # 覆盖率
go test -coverprofile=cover.out ./... && go tool cover -html=cover.out
go test -race ./...                 # 竞态检测
```

覆盖率反映「被执行到的语句比例」，不保证断言有效。优先覆盖分支与错误路径，而不是追求数字。

## 基准测试

基准函数以 `BenchmarkXxx(b *testing.B)` 命名，`b.N` 由框架动态调整，测试代码必须执行 `b.N` 次。准备数据放在循环外，必要时 `b.ResetTimer()`。用 `-benchmem` 观察每次操作的分配次数与字节数，分配往往比 CPU 时间更值得优化。

Go 1.18+ 支持模糊测试（fuzzing）：函数以 `FuzzXxx` 命名，用 `f.Fuzz` 接收输入，`go test -fuzz=FuzzXxx` 运行。它适合解析器、编解码这类输入空间很大的函数；导致崩溃的输入会被写入 `testdata/fuzz`，成为回归用例。执行时间长的集成测试可以用 `testing.Short()` 配合 `-short` 跳过。

## pprof 与性能定位

标准库 `runtime/pprof` 或 `net/http/pprof` 可采集 CPU、内存、goroutine 等剖面。命令行程序常用：

```bash
go test -bench . -cpuprofile cpu.out ./calc
go tool pprof -top cpu.out
```

先测量再优化。常见收益点依次是：减少分配、避免不必要的序列化、缩小锁粒度、复用缓冲（`sync.Pool`）、批量 IO。微优化前先确认热点，否则容易把复杂度花在 1% 的路径上。

## 工程化检查

- `gofmt -l .`：格式必须统一。
- `go vet ./...`：可疑构造与格式字符串。
- `staticcheck ./...`：更严格的静态分析（第三方工具）。
- `go test -race ./...`：并发代码必跑。
- `go build ./...`：确保所有包可编译。

CI 中固定 Go 版本，缓存模块目录，先跑格式与 vet（快），再跑测试与竞态（慢）。发布二进制用 `-trimpath` 并在构建信息中保留提交号，便于回溯。

测试辅助函数应调用 `t.Helper()`，这样失败时报告的是调用方行号而不是辅助函数内部。多组基准结果对比可用 `benchstat`（`golang.org/x/perf/cmd/benchstat`），它给出统计意义上的差异，比肉眼比较纳秒数可靠。CI 中加 `-count=1` 可以禁用测试结果缓存，避免「没跑却显示通过」。

## 常见坑

- **测试依赖执行顺序**：每个测试应独立，共享状态用 `t.Cleanup` 释放。
- **基准测试里把准备代码算进耗时**：记得 `b.ResetTimer()`。
- **只测正常路径**：错误分支与边界值才是缺陷高发区。
- **用 `time.Sleep` 等待异步结果**：应使用 channel 或轮询加超时。
- **覆盖率 100% 就放心**：断言写错时覆盖率毫无意义。
