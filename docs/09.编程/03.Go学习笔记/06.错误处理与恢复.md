# 06 错误处理与恢复

## 本章目标

理解 `error` 是普通接口而非异常机制，掌握包装、判定与自定义错误，知道 `panic`/`recover` 的正确边界。

## error 接口

Go 把错误当作值：函数把错误作为最后一个返回值交给调用方，调用方显式判断。`error` 接口只有一个方法 `Error() string`，任何实现它的类型都能作为错误。

这种设计让错误处理显式、可测试，也意味着没有「自动向上抛」——每一层要么处理，要么包装后返回。忽略错误（`_ = f()`）是明确的决定，不应是默认习惯。

## 包装与判定

`fmt.Errorf` 配合 `%w` 可以包装错误，保留原始错误链；`errors.Is` 判断链上是否存在目标错误，`errors.As` 把链上某个错误提取为具体类型。二者都比直接比较 `==` 更可靠。

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("not found")

type QueryError struct {
	Table string
	Err   error
}

func (e *QueryError) Error() string {
	return fmt.Sprintf("query %s: %v", e.Table, e.Err)
}

func (e *QueryError) Unwrap() error { return e.Err }

func find(id int) error {
	if id == 0 {
		return fmt.Errorf("find(%d): %w", id, ErrNotFound)
	}
	return &QueryError{Table: "users", Err: ErrNotFound}
}

func main() {
	fmt.Println(errors.Is(find(0), ErrNotFound))

	var qerr *QueryError
	if err := find(1); errors.As(err, &qerr) {
		fmt.Println("表:", qerr.Table)
	}
}
```

`errors.As` 的第二个参数必须是指向错误类型的指针，否则会 panic。自定义错误实现 `Unwrap()` 后即可参与错误链；`Is` 与 `As` 会逐层解包。

## 哨兵错误与自定义类型

- **哨兵错误**（sentinel error）：包级 `var ErrX = errors.New(...)`，调用方用 `errors.Is` 判断。适合「调用方需要区分这一种情况」的少量错误。
- **自定义类型**：携带上下文字段，调用方用 `errors.As` 提取。适合需要结构化信息的场景。

错误信息应包含「做什么失败」与「关键参数」，用 `fmt.Errorf("open %s: %w", path, err)` 这种形式，避免只返回 `"failed"`。不要把敏感信息写进错误文本。错误字符串通常小写开头、结尾不加标点，因为上层往往会把它嵌入更长的句子。

## panic 与 recover

`panic` 用于程序无法继续的状态，例如不可恢复的配置错误、违反不变量。`recover` 只能在 `defer` 中生效，用于在边界处把 panic 转成错误或记录日志。库代码通常不应 recover 调用方的 panic，除非明确要隔离边界。

```go
package main

import "fmt"

func safeDiv(a, b int) (result int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered: %v", r)
		}
	}()
	return a / b, nil
}

func main() {
	fmt.Println(safeDiv(10, 2))
	fmt.Println(safeDiv(1, 0))
}
```

除零、越界、空指针解引用会触发运行时 panic。生产服务常在 HTTP 中间件里 recover，避免单个请求打崩整个进程，但这是兜底，不是日常错误处理手段。

Go 1.20 新增 `errors.Join`，可把多个错误合并成一个仍支持 `Is`/`As` 的错误，适合批量操作后统一返回。另一个实践原则是「只处理一次」：要么在当前层恢复并记录，要么包装后返回，不要既打印日志又向上返回，否则同一个错误会被多层重复记录。

goroutine 内的 panic 不会被外层的 `recover` 捕获，必须在 goroutine 内部自己 defer recover，否则整个进程会退出。包装层数也不宜过深，调用方需要判断的哨兵错误应尽量靠近顶层，链太长会增加理解成本；`errors.Unwrap` 可以手动解开一层，适合诊断而非业务判断。

## 常见坑

- **用 `==` 比较包装后的错误**：包装后指针不同，应使用 `errors.Is`。
- **`%v` 代替 `%w`**：错误链断裂，上层无法判定。
- **`recover` 写在普通函数里**：不在 `defer` 中不会生效。
- **panic 当异常用**：跨包传播的 panic 难以推理，优先返回 error。
- **错误信息缺少上下文**：排查时只能看到 `EOF`，不知道是哪个文件。
