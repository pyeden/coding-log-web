# 01 环境与工具链

## 本章目标

把一段 C++ 源码变成可执行文件，并能解释每一步发生了什么。学完本章，你应该能独立写出最小的 CMake 工程、用 `-std=c++17` 固定语言标准、打开常用警告，并在程序崩溃时用调试器定位到具体行号。本章所有结论以 C++17 为基准，涉及更高标准的地方会明确标注。

## 核心概念

翻译单元（translation unit）是预处理后的源文件，是编译的基本单位；声明（declaration）引入名字与类型，定义（definition）分配存储或给出函数体；ODR（One Definition Rule）规定同一实体在全程序只能有一份定义；未定义行为（UB）是标准不作要求的程序状态，必须从设计上避免。

## 从源码到可执行文件

C++ 采用分离编译模型（separate compilation）。一次构建通常包含四个阶段：

1. **预处理（preprocessing）**：展开 `#include`、处理宏与条件编译，产出翻译单元（translation unit）。
2. **编译（compilation）**：把翻译单元翻译成汇编或目标文件，此阶段做语法与类型检查。
3. **汇编（assembly）**：把汇编翻译成机器码，形成 `.o` 目标文件。
4. **链接（linking）**：合并多个目标文件与库，解析外部符号，产出可执行文件。

因此「编译通过」不等于「链接通过」：声明了却没定义的函数，语法检查没问题，链接时才会报 `undefined symbol`。反过来，头文件里写了非 `inline` 的函数定义，被多个源文件包含时又会触发重复定义（ODR 违规）。

## 编译命令与常用选项

Apple clang 与 GCC 的常用参数基本一致：

```bash
clang++ -std=c++17 -Wall -Wextra -O2 -g hello.cpp -o hello
```

- `-std=c++17`：固定语言标准。不写则使用编译器默认值，跨机器构建时行为可能不同。
- `-Wall -Wextra`：打开绝大多数常用警告。警告不是噪音，未初始化变量、隐式窄化往往正是缺陷来源。
- `-O2` / `-g`：优化与调试信息。两者可以同时使用，Release 构建保留符号更利于线上定位。
- `-I路径`：追加头文件搜索目录；`-L路径` 与 `-l库名`：追加库搜索目录与链接库。

最小可运行程序如下。它同时演示了标准库头文件、`const` 局部对象与 `std::string` 的基本用法：

```cpp
#include <iostream>
#include <string>

int main() {
    const std::string name = "C++17";
    std::cout << "Hello, " << name << "!\n";
    return 0;
}
```

## 头文件、声明与定义

头文件（header）负责放声明，源文件负责放定义。声明告诉编译器「这个名字存在、类型是什么」，定义则真正分配存储或给出函数体。下面的例子把声明与 `inline` 定义放在同一个翻译单元里，`inline` 允许函数在多个翻译单元中出现相同定义而不违反 ODR：

```cpp
#include <iostream>

int square(int x);              // 声明：只需要签名

inline int square(int x) {      // 定义：inline 允许头文件复用
    return x * x;
}

int main() {
    std::cout << square(7) << '\n';
}
```

头文件保护（include guard）用于防止同一翻译单元重复包含。现代编译器普遍支持 `#pragma once`，它更简洁但属于扩展；可移植写法仍是宏保护：

```cpp
#ifndef PROJECT_MATH_UTILS_H_
#define PROJECT_MATH_UTILS_H_

int add(int a, int b);

#endif  // PROJECT_MATH_UTILS_H_
```

## 最小 CMake 工程

手写编译命令适合单文件实验，多文件项目建议直接使用 CMake。下面这份 `CMakeLists.txt` 指定 C++17、开启警告并声明可执行目标：

```cmake
cmake_minimum_required(VERSION 3.16)
project(hello LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_executable(hello main.cpp)
target_compile_options(hello PRIVATE -Wall -Wextra)
```

`CMAKE_CXX_EXTENSIONS OFF` 表示使用纯标准模式（`-std=c++17` 而非 `-std=gnu++17`），可避免依赖编译器扩展。构建流程是 `cmake -S . -B build` 然后 `cmake --build build`。

## 调试与未定义行为

调试器（debugger）方面，GDB 与 LLDB 的命令高度相似：`break` 下断点、`run` 启动、`next` 单步跳过、`step` 单步进入、`print` 查看变量、`bt` 打印调用栈。macOS 上通常使用 LLDB。

必须尽早建立 **未定义行为（undefined behavior, UB）** 的意识：越界访问、解引用空指针、有符号整数溢出、读取未初始化变量，标准都不规定结果。编译器可以假设 UB 不会发生，从而做出让代码「看起来正常」的优化。开启 `-fsanitize=address,undefined` 能在开发期捕获大量此类问题，代价是运行变慢，不要用于发布构建。

## 常见坑 / 最佳实践

- 不要依赖编译器默认标准，工程里显式写 `-std=c++17` 或 `CMAKE_CXX_STANDARD`。
- 头文件只放声明、模板与 `inline` 函数；普通函数定义放源文件。
- 每个头文件都加保护，宏名带项目前缀，避免与第三方库冲突。
- 打开 `-Wall -Wextra`，并把警告当作待修缺陷；CI 中可加 `-Werror`。
- 出现崩溃先看调用栈，再用 sanitizer 复现，不要靠打印猜测。
- 永远不要用「在我机器上是好的」解释 UB。
