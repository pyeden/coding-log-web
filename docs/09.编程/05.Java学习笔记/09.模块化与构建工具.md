# 09 模块化与构建工具

## 本章目标

理解 JPMS（Java Platform Module System，Java 9）要解决的「类路径地狱」，会写 `module-info.java`，并能用 Maven 或 Gradle 描述一个可复现的构建。目标是让「在我机器上能跑」不再成为理由。

## 核心概念

类路径（classpath）的问题是**没有边界**：所有 jar 平铺在一个命名空间里，缺依赖到运行时才报 `NoClassDefFoundError`，两个 jar 含同名包会静默覆盖。

模块系统引入三个声明：`requires`（依赖哪些模块）、`exports`（哪些包对外可见）、`opens`（哪些包允许反射访问）。模块路径上的代码必须显式声明依赖，编译器在**编译期**就能发现缺失模块；未 `exports` 的包对其他模块不可见，实现真正的封装。

模块分三类：**具名模块**（有 `module-info.class`）、**自动模块**（普通 jar 放在模块路径上，模块名由 `Automatic-Module-Name` 或文件名推导）、**未命名模块**（类路径上的所有代码）。未命名模块可以读所有模块，但不能被具名模块 `requires`——这是迁移期的过渡态。

`jlink` 可以基于模块图裁剪出只含所需模块的运行时镜像；`jdeps` 分析依赖并给出模块化建议；`--add-opens` 是给反射框架的临时后门，应尽量避免长期使用。

构建工具方面，Maven 用**约定优于配置**的目录结构与生命周期（`validate` → `compile` → `test` → `package` → `verify` → `install` → `deploy`），依赖坐标是 `groupId:artifactId:version`。Gradle 用 Kotlin/Groovy DSL 描述任务图，增量构建更快。

可复现构建（reproducible build）的关键是：锁定依赖版本（Maven 用 `dependencyManagement` 或 BOM，Gradle 用 version catalog / lockfile）、固定插件版本、统一 `maven.compiler.release`。

迁移到模块系统不要一步到位。可行路径是：先给 jar 补上 `Automatic-Module-Name`，让依赖方能用稳定名字 `requires`；再收敛内部包、只 `exports` 必要的 API；最后才拆出真正的 `module-info.java`。类路径与模块路径可以共存，但具名模块不能依赖未命名模块。

Maven 多模块项目用父 POM 统一版本（`dependencyManagement`）与插件配置，子模块只声明「用什么」。排查依赖冲突用 `mvn dependency:tree -Dincludes=groupId:artifactId`，比逐个排除靠猜高效。

Gradle 的优势在增量与缓存：开启配置缓存与构建缓存后，未变化的模块不会重复编译。代价是构建脚本必须避免在配置阶段做 IO 与读取环境变量，否则缓存会失效。

JDK 自带工具已能覆盖大部分诊断：`jdeps` 看依赖、`jlink` 裁剪运行时、`jar --describe-module` 查看模块描述符。依赖治理上把版本集中写在一处（BOM 或 version catalog），升级时只改一个地方，比散落在各模块可靠得多。构建脚本本身也是代码，应纳入评审与格式化；`mvn -o` 离线构建则可用于验证本地仓库是否完整。

## 代码示例

一个导出服务包的模块声明：

```java
// src/main/java/module-info.java
module com.example.app {
    requires java.net.http;      // 使用 JDK 的 HTTP 客户端模块
    requires java.logging;

    exports com.example.app;                          // 只有这个包对外可见
    // exports com.example.app.spi to com.example.cli; // 定向导出：包必须真实存在
}
```

模块内的实现类，`internal` 包不导出即对外不可见：

```java
package com.example.app;

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;

public class Greeting {
    public String fetchTitle() throws Exception {
        HttpClient client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(3))
                .build();
        HttpRequest request = HttpRequest.newBuilder(URI.create("https://dev.java/"))
                .timeout(Duration.ofSeconds(5))
                .GET()
                .build();
        HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());
        return "status=" + response.statusCode();
    }

    public static void main(String[] args) throws Exception {
        System.out.println(new Greeting().fetchTitle());
    }
}
```

消费方模块必须显式 `requires`，否则编译失败——这正是模块化带来的早期反馈：

```java
// src/main/java/module-info.java（消费方）
module com.example.cli {
    requires com.example.app;
}
```

Maven 最小可用的 `pom.xml`，编译目标用 `release` 而不是 `source`/`target`：

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example</groupId>
  <artifactId>app</artifactId>
  <version>0.1.0</version>

  <properties>
    <maven.compiler.release>21</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.10.2</version>
      <scope>test</scope>
    </dependency>
  </dependencies>
</project>
```

对应的 Gradle Kotlin DSL：

```kotlin
plugins {
    application
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

application {
    mainModule = "com.example.app"
    mainClass = "com.example.app.Greeting"
}

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.2")
}

tasks.test {
    useJUnitPlatform()
}
```

常用命令：`mvn -q clean verify`、`gradle build`、`jdeps --module-path mods --print-module-deps`，需要裁剪运行时用 `jlink --add-modules com.example.app --output runtime`。

## 常见坑

- **在模块项目里混用类路径**：类路径代码进入未命名模块，具名模块无法 `requires` 它。
- **忘了 `exports`**：包内类对其他模块不可见，报「package is not visible」。
- **反射框架报 `InaccessibleObjectException`**：需要 `opens`，而不是无脑 `--add-opens` 全局放开。
- **`source`/`target` 代替 `release`**：可能编译出引用了高版本 API 的代码，运行时才炸。
- **依赖版本靠传递**：不使用 BOM 时，不同路径引入不同版本，行为随依赖树变化。
- **把 `target/` 或 `build/` 提交进仓库**：构建产物不应入库，用 `.gitignore` 排除。
