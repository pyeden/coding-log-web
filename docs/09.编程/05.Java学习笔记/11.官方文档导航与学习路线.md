# 11 官方文档导航与学习路线

## 本章目标

建立一套不依赖二手教程的查证路径：遇到「这个类怎么用」「这个语法从哪个版本开始」时，十分钟内从官方文档拿到确定答案。同时给出一条可执行的学习顺序。

## 核心概念

官方文档分工明确，各有各的读法。

**dev.java** 是 Oracle 维护的官方教程站，按主题组织（Language Basics、Classes、Generics、Streams、Concurrency 等），适合系统学习与快速回顾语法。

**API 文档**（Javadoc，`docs.oracle.com/en/java/javase/21/docs/api/`）是查询入口。每个类的页面结构固定：模块归属 → 包声明 → 类签名（`implements`/`extends`）→ 说明 → 字段/构造器/方法摘要 → 方法详情。注意方法详情里的 **Since:** 标注，它直接告诉你版本起点，`@since 21` 即 Java 21 新增。

**Java 语言规范**（JLS，`docs.oracle.com/javase/specs/`）定义语法的精确语义，遇到「整数提升规则」「重载解析顺序」这类问题只有它能给出权威答案。JVM 规范（JVMS）则描述字节码与类文件格式。

**OpenJDK 的 JEP 索引**（`openjdk.org/jeps/`）记录每个特性的提案与版本，是判断「某特性是否正式」的唯一可靠来源：标题里带 *Preview* 说明是预览特性，需要 `--enable-preview` 且可能在后续版本变化。

版本策略要记牢：Java 8 → 11 → 17 → 21 是 LTS，其余为半年一个的功能版本。学习与生产以 LTS 为锚点，读到新特性先查它落在哪个 LTS。

读文档的三种典型场景：查 API 用法看方法详情与 `@throws`；判断版本兼容看 `Since:` 与 `@Deprecated`；理解边界行为看 JLS 对应章节。博客适合建立直觉，不适合当依据。

读 JEP 有个技巧：先看 Summary 与 Goals，再看 `Status` 与 `Release`，最后看 Alternatives 了解为什么没选别的方案。这比通读全文更快抓住「它解决什么问题、代价是什么」。

升级策略上，LTS 之间通常有三年跨度，跨版本升级要关注三类变化：被移除的 API（`forRemoval`）、默认行为变化（如 Java 18 的 UTF-8 默认编码）、以及被弃用的 JVM 参数。先在 CI 用新 JDK 跑全量测试，再评估运行时参数与第三方库兼容性。

学习路线上最常见的误区是「收集资料代替动手」。每读一章至少写一个能跑的程序，把示例改成自己的场景，遇到不确定的行为就去查 JLS 或开一段 `jshell` 验证——这个习惯比记住任何 API 都值钱。

## 代码示例

把学习路线写成可执行的数据结构，比列在纸上更容易维护：

```java
import java.util.List;

public record LearningPlan(String week, List<String> topics, String deliverable) {
    public static void main(String[] args) {
        List<LearningPlan> plan = List.of(
                new LearningPlan("第 1 周", List.of("环境与工具链", "语言基础"),
                        "能独立编译运行多文件项目"),
                new LearningPlan("第 2-3 周", List.of("面向对象", "集合与泛型"),
                        "用 record/sealed 建模一个订单模型"),
                new LearningPlan("第 4-5 周", List.of("异常与日志", "Stream"),
                        "把一段循环重构为流式管道"),
                new LearningPlan("第 6-7 周", List.of("并发", "虚拟线程"),
                        "用虚拟线程改写一个阻塞式抓取任务"),
                new LearningPlan("第 8 周", List.of("模块化与构建", "测试"),
                        "搭一个 Maven 多模块项目并接入 CI"));

        plan.forEach(p -> System.out.printf("%-8s %-28s -> %s%n",
                p.week(), String.join("、", p.topics()), p.deliverable()));
    }
}
```

用枚举固化 LTS 版本与关键特性，避免记错版本号：

```java
import java.util.List;

public class VersionMap {
    enum Release {
        JAVA_8(List.of("Lambda", "Stream", "java.time")),
        JAVA_11(List.of("HttpClient", "var 局部变量类型推断", "单文件源码直接运行")),
        JAVA_17(List.of("record", "sealed", "switch 模式匹配（预览）")),
        JAVA_21(List.of("虚拟线程", "switch 模式匹配（正式）", "顺序集合"));

        private final List<String> highlights;

        Release(List<String> highlights) {
            this.highlights = highlights;
        }

        String describe() {
            return name() + " -> " + String.join(", ", highlights);
        }
    }

    public static void main(String[] args) {
        for (Release release : Release.values()) {
            System.out.println(release.describe());
        }
    }
}
```

注意 `record` 在 Java 16 正式、`sealed` 在 Java 17 正式；`switch` 模式匹配在 Java 17 是预览、Java 21 才正式。查证时以 JEP 的 `Status` 字段为准，不要凭印象。

## 常见坑

- **把预览特性写进生产**：需要 `--enable-preview`，且下个版本可能不兼容，升级时编译直接失败。
- **只看博客的版本号**：二手资料常把预览当正式，务必回查 JEP 或 API 文档的 `Since:`。
- **API 文档只看方法签名**：`@throws`、线程安全性说明、`@implSpec` 往往才是踩坑点。
- **用 `@Deprecated` 的替代品却不看 `forRemoval`**：标记为待移除的 API 会在未来版本消失。
- **跳过 JLS 直接猜语义**：整数提升、重载解析、字符串拼接行为都有明确规范，猜必错。
