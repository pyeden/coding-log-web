# 10 测试与工程质量

## 本章目标

建立「单元测试 → 集成测试 → 端到端测试」的分层意识，会写 JUnit 5 的断言与参数化测试，理解 `assert` 与断言的差别，并知道静态检查、覆盖率、CI 各自能兜住什么。

## 核心概念

测试的价值在于**快速反馈**与**可重构的底气**。测试金字塔（test pyramid）的实践含义是：大量单元测试（毫秒级、无 IO）、适量集成测试（真实数据库或 HTTP 桩）、极少端到端测试（跨进程、慢且脆）。反过来头的「冰淇淋筒」结构会让 CI 从分钟级退化到小时级。

**单元测试**（unit test）检验一个行为单元，好的测试按 Arrange-Act-Assert 三段式组织。命名应描述行为而不是方法名，如 `divide_byZero_throws`。测试之间必须相互独立，不依赖执行顺序与共享可变状态。

JUnit 5 由三部分组成：JUnit Platform（运行引擎）、JUnit Jupiter（新编程模型）、JUnit Vintage（兼容 JUnit 4）。`@Test` 标记测试方法，`@BeforeEach`/`@AfterEach` 做隔离，`@ParameterizedTest` 配 `@ValueSource`/`@CsvSource` 覆盖多组输入，避免复制粘贴。

断言要**具体**：`assertEquals(expected, actual, "上下文")` 比 `assertTrue(a == b)` 提供的诊断信息多得多。异常断言用 `assertThrows`，并检查异常类型与消息，不要只 `try/catch` 后 `fail()`。

JDK 自带的 `assert` 关键字**默认关闭**，只在 `-ea` 时生效，适用于内部不变量（invariant）检查，不能替代测试，也不能用于校验外部输入——参数校验应用 `Objects.requireNonNull` 与显式抛 `IllegalArgumentException`。

质量门禁还包括：`javac -Xlint:all` 打开编译警告、静态分析（SpotBugs、Error Prone）、依赖漏洞扫描、格式化与 CI 强制检查。**覆盖率**（coverage）是发现「没测到」的工具而不是目标；把覆盖率当 KPI 只会催生无断言的空测试。

测试替身分三类：**stub** 提供固定返回值，**fake** 是轻量实现（如内存版仓储），**mock** 校验交互。优先用 stub 与 fake；mock 只在必须验证「是否调用了外部副作用」时使用，因为它把测试和实现细节绑在一起。

测试数据建议用 builder 或工厂方法构造，只写与当前用例相关的字段，其余给默认值；否则新增一个字段会让几十个测试同时编译失败。

工程质量还包括可读性：命名一致、方法短小、注释解释「为什么」而不是「做什么」。CI 至少应包含编译、单元测试、静态检查三步，并且失败必须阻断合并——没有阻断能力的检查等于没有。

## 代码示例

被测类与不变量校验，外部输入一律显式检查：

```java
import java.util.Objects;

public class Calculator {
    public int divide(int dividend, int divisor) {
        if (divisor == 0) {
            throw new ArithmeticException("除数不能为 0");
        }
        return dividend / divisor;
    }

    public String normalize(String raw) {
        Objects.requireNonNull(raw, "raw 不能为 null");
        String trimmed = raw.strip();
        if (trimmed.isEmpty()) {
            throw new IllegalArgumentException("不能为空白字符串");
        }
        return trimmed.toLowerCase();
    }

    public static void main(String[] args) {
        Calculator c = new Calculator();
        System.out.println(c.normalize("  Java21 "));
    }
}
```

JUnit 5 测试类（需要 `junit-jupiter` 依赖，不在 JDK 内）：

```java
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;

class CalculatorTest {
    private Calculator calculator;

    @BeforeEach
    void setUp() {
        calculator = new Calculator();
    }

    @Test
    void divide_byZero_throws() {
        ArithmeticException e = assertThrows(ArithmeticException.class,
                () -> calculator.divide(1, 0));
        assertEquals("除数不能为 0", e.getMessage());
    }

    @ParameterizedTest
    @CsvSource({"10,2,5", "9,3,3", "-8,4,-2"})
    void divide_returnsQuotient(int dividend, int divisor, int expected) {
        assertEquals(expected, calculator.divide(dividend, divisor));
    }
}
```

`@CsvSource` 一行一组参数，比写三个几乎相同的 `@Test` 更易维护，失败时也会明确指出是哪一行数据。

`assert` 只用于内部不变量，需 `java -ea` 启动：

```java
public class InvariantDemo {
    static int applyDiscount(int priceCents, int percent) {
        assert priceCents >= 0 : "价格不能为负: " + priceCents;
        assert percent >= 0 && percent <= 100 : "折扣越界: " + percent;
        return priceCents * (100 - percent) / 100;
    }

    public static void main(String[] args) {
        System.out.println(applyDiscount(1000, 20));
        try {
            System.out.println(applyDiscount(1000, 120));
        } catch (AssertionError e) {
            System.out.println("断言触发: " + e.getMessage());
        }
    }
}
```

不加 `-ea` 时上面的断言全部失效，这正是它不能当输入校验用的原因。

## 常见坑

- **测试依赖执行顺序**：共享静态状态会让单跑通过、全跑失败。
- **只测正常路径**：边界值（0、负数、最大长度、空集合）才是缺陷高发区。
- **断言信息缺失**：CI 里只看到 `expected true but was false`，无从定位。
- **把 `System.out` 当断言**：需要人眼确认，等于没有测试。
- **mock 过多**：测试变成对实现的复述，重构即失败，应尽量测行为。
- **覆盖率 100% 的幻觉**：getter/setter 撑起数字，关键分支仍未覆盖。
