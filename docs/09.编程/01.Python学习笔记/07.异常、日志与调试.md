# 07 异常、日志与调试

## 本章目标

写出能区分「可恢复错误」与「程序缺陷」的异常处理，用 `logging` 取代 `print` 调试，并在出错时快速定位到根因。

## try 的完整形态

`try/except/else/finally` 四段各有职责：`except` 捕获并处理，`else` 在**没有异常**时执行，`finally` 无论如何都执行（清理资源）。只捕获你真正知道如何处理的异常；裸 `except:` 会吞掉 `KeyboardInterrupt` 与 `SystemExit`，应写 `except Exception:` 并记录。多个 `except` 从上到下匹配，第一个命中的生效，因此子类必须写在父类之前；同构处理可以写成 `except (ValueError, TypeError):`。

```python
def parse_age(raw: str) -> int:
    try:
        age = int(raw)
    except ValueError as exc:
        raise ValueError(f"年龄必须是整数，收到 {raw!r}") from exc
    else:
        if not 0 <= age <= 150:
            raise ValueError("年龄超出合理范围")
        return age
    finally:
        print("parse_age 结束")

print(parse_age(" 30 "))
```

`raise ... from exc` 建立**异常链**，`__cause__` 指向原始异常，回溯里显示「The above exception was the direct cause」。`from None` 则主动切断上下文，适合把底层实现细节对调用方隐藏。捕获异常后要么处理、要么重抛，不要既记录又静默返回一个看似正常的默认值。

## 自定义异常

业务错误应定义自己的异常类型，并建立层级，让调用方能按粒度捕获：

```python
class AppError(Exception):
    """应用异常基类。"""

class ConfigError(AppError):
    pass

class NetworkError(AppError):
    def __init__(self, message: str, status: int | None = None) -> None:
        super().__init__(message)
        self.status = status

try:
    raise NetworkError("连接超时", status=504)
except ConfigError:
    print("配置问题")
except AppError as exc:
    print(f"业务失败: {exc}")
```

自定义异常不要继承 `BaseException`，也不要只为了「看起来专业」而造异常；标准库已有的 `ValueError`、`TypeError`、`KeyError` 语义清晰，优先复用。

## 异常组（3.11+）

Python 3.11 引入 `ExceptionGroup` 与 `except*`，用于一次抛出多个互不相关的错误，典型场景是并发任务汇总失败：

```python
def run_all() -> None:
    errors = []
    for name in ["a", "b"]:
        try:
            if name == "a":
                raise ValueError("a 失败")
        except ValueError as exc:
            errors.append(exc)
    if errors:
        raise ExceptionGroup("批量任务失败", errors)

try:
    run_all()
except* ValueError as group:
    for exc in group.exceptions:
        print("捕获:", exc)
```

`except*` 会把异常组按类型拆分，未被任何分支匹配的异常会在最后重新抛出。低于 3.11 的版本没有这个语法。

## logging 而不是 print

`print` 没有级别、时间、来源，也无法在部署时关闭。`logging` 提供 DEBUG/INFO/WARNING/ERROR/CRITICAL 五级，库代码只声明 logger，应用入口统一配置：

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)
logger = logging.getLogger(__name__)

logger.debug("这条不会显示")
logger.info("服务启动，端口 %s", 8000)
try:
    1 / 0
except ZeroDivisionError:
    logger.exception("计算失败")     # 自动附带 traceback
```

要点：使用 `%s` 惰性格式化，避免无谓的字符串拼接；`logger.exception` 只能在 `except` 块内使用；库模块不要调用 `basicConfig`，把配置权交给应用。生产环境通常把日志同时写到 stderr 与轮转文件，用 `logging.handlers.RotatingFileHandler` 控制体积；结构化日志则输出 JSON，便于采集与检索。

## 调试手段

1. **读 traceback**：从最后一行往上看，最后一行是异常类型与消息，其上是调用栈；`During handling of the above exception` 说明有二次异常。
2. **`breakpoint()`**：3.7+ 内置，进入 `pdb`。常用命令 `l` 看代码、`p expr` 打印、`n` 单步、`s` 进入函数、`c` 继续、`q` 退出。
3. **`python3 -m pdb script.py`**：从第一行开始调试。
4. **`python3 -X dev script.py`**：开发模式，开启额外警告，暴露资源未关闭等问题。
5. **最小复现**：把问题剥离成十几行脚本，多数 bug 在这一步就现形。

另外，`assert` 是调试工具而不是输入校验：`python3 -O` 会移除所有 assert，依赖它做安全检查会在生产环境失效。需要始终执行的校验请显式写 `if ...: raise`。

## 常见坑

- **吞异常**：`except Exception: pass` 让故障静默扩散，至少记录日志。
- **在 except 里 `raise` 丢失上下文**：需要保留原始栈就 `raise`，需要改写就 `raise NewError(...) from exc`。
- **捕获顺序写反**：父类在前会截获子类，`except Exception` 必须放在最后。
- **finally 中 return**：会覆盖 try 中的返回值与异常，禁止这样写。
- **日志重复输出**：多次 `basicConfig` 无效，handler 重复添加则会重复打印，配置一次即可。
- **用异常做流程控制**：能预判的分支用条件判断，异常留给「异常情况」。
