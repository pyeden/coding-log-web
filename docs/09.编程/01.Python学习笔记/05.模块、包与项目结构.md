# 05 模块、包与项目结构

## 本章目标

理解 `import` 到底做了什么，能设计出可安装、可测试、依赖可复现的项目结构，并避开循环导入与路径错乱。

## 模块与导入机制

一个 `.py` 文件就是一个**模块**（module），含有 `__init__.py` 的目录是**包**（package）。`import` 的执行过程是：查找模块 → 若未加载则执行模块顶层代码 → 把模块对象绑定到名字。模块只会被执行一次，结果缓存在 `sys.modules`。

```python
import json
from pathlib import Path
from collections import OrderedDict as OD

print(json.dumps({"ok": True}, ensure_ascii=False))
print(Path("docs") / "index.md")
print(OD(a=1))
```

`import a.b.c` 绑定的是顶层 `a`；`from a.b import c` 绑定 `c`。避免 `from module import *`，它污染命名空间且让依赖关系不可见。

模块级代码在首次导入时执行，因此导入应该是「定义」而不是「做事」：连接数据库、读配置文件、启动线程都属于副作用，会让测试和工具链意外触发。需要延迟加载时，把导入放进函数内部，或使用 `importlib.import_module`。

## 搜索路径

模块查找顺序：内置模块 → `sys.path` 中的目录（脚本所在目录、`PYTHONPATH`、标准库、site-packages）。这意味着**当前工作目录可能影响导入结果**。排查时打印：

```python
import sys

for entry in sys.path:
    print(entry or "<当前目录>")
```

`python3 -m package.module` 与 `python3 path/to/module.py` 的 `sys.path[0]` 不同，前者是当前目录，后者是脚本目录，这也是「-m 能跑、直接跑报 ImportError」的常见原因。

命名空间包（PEP 420）允许没有 `__init__.py` 的目录被导入，适合把一个大包拆成多个分发包；普通项目不需要刻意使用它，因为缺少 `__init__.py` 会让工具与读者都难以判断这是包还是普通目录。

## __name__ 与入口

模块的 `__name__` 在被导入时是模块名，被直接执行时是 `"__main__"`。因此把「只在命令行运行」的逻辑放进守卫：

```python
def main() -> int:
    print("执行主流程")
    return 0

if __name__ == "__main__":
    raise SystemExit(main())
```

`raise SystemExit(code)` 让退出码可控，便于 CI 判断成功与否。

## 包的写法与相对导入

`__init__.py` 会被执行，可用于暴露公共 API。下面这段是包内 `__init__.py` 的内容，属于包的一部分，单独执行会因相对导入失败，请在真实包中验证：

```python
# mypkg/__init__.py
from .core import Engine
from .errors import ConfigError

__all__ = ["Engine", "ConfigError"]
```

包内部互相引用用相对导入（`.core`、`..utils`），顶层入口用绝对导入。相对导入只在包内有效，直接运行包内文件会失败；正确做法是用 `python3 -m mypkg.cli`。

## pyproject 概览

现代项目用 `pyproject.toml` 统一描述构建后端、元数据与工具配置，它取代了 `setup.py` 的多数用途，也是 pip、ruff、pytest、mypy 共同读取的配置入口：

```toml
[project]
name = "mypkg"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["httpx>=0.27"]

[project.optional-dependencies]
dev = ["pytest>=8", "ruff>=0.6"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

安装时 `pip install -e ".[dev]"` 以可编辑模式装入当前项目并带上开发依赖。读取 `pyproject.toml` 不需要第三方库：标准库 `tomllib`（3.11+，只读）可以直接解析，写入 TOML 仍需第三方库。

## 项目布局

推荐 **src layout**，把源码放进 `src/`，避免「当前目录恰好能导入」掩盖打包问题：

```text
project/
  pyproject.toml
  README.md
  src/
    mypkg/
      __init__.py
      core.py
      cli.py
  tests/
    test_core.py
```

测试与源码分离，`tests/` 不随包发布。可编辑安装 `pip install -e .` 后，`import mypkg` 指向 `src/mypkg`，路径问题一次性解决。扁平布局（包直接放根目录）在小脚本里够用，但项目变大后容易与同名目录冲突。`__init__.py` 中的 `__all__` 只影响 `from mypkg import *` 与文档工具，不限制显式导入。

## 依赖与可复现环境

声明依赖与实际锁定要分开：

- `pyproject.toml` 的 `dependencies` 写**范围**，表达兼容性。
- 锁文件写**精确版本 + 哈希**，保证任何机器装出同一套包。pip 生态常用 `pip-tools` 生成 `requirements.txt`，`uv`、`poetry`、`pdm` 各有自己的锁文件格式。
- 开发依赖放 `optional-dependencies.dev`，不进入运行时。

```bash
python3 -m venv .venv && source .venv/bin/activate
python -m pip install -U pip
python -m pip install -e ".[dev]"
python -m pip freeze > requirements.lock
```

CI 中使用锁文件安装，并固定 Python 次版本（如 3.12.x），否则「本地能跑」无法复现。

## 常见坑

- **循环导入**：A 导入 B、B 又导入 A。把共享部分下沉到第三个模块，或把导入移进函数内。
- **文件名与标准库同名**：项目里出现 `json.py`、`random.py` 会遮蔽标准库，报错信息极具迷惑性。
- **依赖 `sys.path` 手工拼接**：一旦可安装，就不需要 `sys.path.append`。
- **把 `__init__.py` 写成业务逻辑**：导入即产生副作用，测试和工具会意外触发。
- **提交 `.venv` 或 `__pycache__`**：写入 `.gitignore`。
