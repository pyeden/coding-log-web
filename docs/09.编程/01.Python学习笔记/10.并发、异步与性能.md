# 10 并发、异步与性能

## 本章目标

分清 CPU 密集与 IO 密集两类问题，选对线程、进程或协程；能用 `concurrent.futures` 与 `asyncio` 写出可控的并发代码，并用性能工具定位瓶颈。

## GIL 意味着什么

CPython 有**全局解释器锁**（GIL），同一时刻只有一个线程执行 Python 字节码。因此：

- 多线程**不能**加速纯 Python 计算；
- 多线程**可以**加速 IO 等待（网络、磁盘），因为等待时会释放 GIL；
- 科学计算库（NumPy）在 C 层释放 GIL，仍能并行。

3.13 提供实验性的 free-threaded 构建（`python3.13t`），可关闭 GIL，但生态兼容性与性能仍在演进，生产环境应谨慎评估。判断任务类型比记结论更重要：**等待多 → 并发；计算多 → 并行进程**。

## threading 与线程池

`threading.Thread` 适合少量长生命周期任务；批量任务用 `concurrent.futures.ThreadPoolExecutor`，它统一了提交、等待、异常传播与结果收集。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import time

def fetch(url: str) -> str:
    time.sleep(0.2)                 # 模拟网络等待
    return f"{url} -> 200"

urls = [f"https://example.com/{i}" for i in range(4)]
with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(fetch, url) for url in urls]
    for future in as_completed(futures):
        print(future.result())
```

线程共享内存，必须用 `Lock` 保护复合操作；`queue.Queue` 是更安全的线程间通信方式。守护线程不会阻止解释器退出，但也不保证清理逻辑执行。

## multiprocessing 与进程池

`ProcessPoolExecutor` 为每个任务开独立解释器，绕开 GIL，代价是进程启动开销与数据序列化（pickle）。传给子进程的函数必须可导入，交互数据必须可 pickle；`if __name__ == "__main__":` 守卫在 Windows 与 macOS 上必需。

```python
from concurrent.futures import ProcessPoolExecutor

def cpu_bound(n: int) -> int:
    return sum(i * i for i in range(n))

if __name__ == "__main__":
    with ProcessPoolExecutor() as pool:
        print(list(pool.map(cpu_bound, [100_000, 200_000])))
```

数据量大时优先返回摘要而非整块对象，序列化成本常比计算更贵。

## asyncio

协程是**单线程内协作式并发**：`async def` 定义协程，`await` 让出控制权，事件循环负责调度。它适合大量网络连接，不适合 CPU 计算。`asyncio.run()` 是程序入口，不要在已运行的事件循环里再次调用。

```python
import asyncio

async def fetch(name: str, delay: float) -> str:
    try:
        async with asyncio.timeout(delay + 0.1):    # 3.11+
            await asyncio.sleep(delay)
        return f"{name} 完成"
    except TimeoutError:
        return f"{name} 超时"

async def main() -> None:
    async with asyncio.TaskGroup() as tg:           # 3.11+
        t1 = tg.create_task(fetch("A", 0.5))
        t2 = tg.create_task(fetch("B", 0.2))
    print(t1.result(), t2.result())

asyncio.run(main())
```

要点：`TaskGroup` 会在任一任务失败时取消同组其余任务并抛出 `ExceptionGroup`；`asyncio.timeout` 是 3.11+ 的上下文管理器，替代 `wait_for` 更易组合。不要用 `time.sleep` 阻塞事件循环，改用 `await asyncio.sleep`；同步库调用放进 `asyncio.to_thread()`。旧代码常见的 `asyncio.gather` 仍然可用，但它不会在失败时自动取消其余任务，需要 `return_exceptions` 或外层超时兼顾。

## 超时、取消与背压

任务取消通过 `CancelledError` 传播，捕获后应重新抛出（除非确实要吞掉）。生产代码要给外部调用设超时，并限制并发数（`asyncio.Semaphore` 或线程池 `max_workers`），否则对端会被打垮。队列满时阻塞生产者，就是最简单的背压。超时值应来自配置而不是散落在每个调用点，方便按环境调整。

## 性能分析

先用 `timeit` 测微基准，再用 `cProfile` 找热点，最后才优化。

```python
import cProfile
import pstats
from timeit import timeit

print(timeit("'-'.join(str(i) for i in range(1000))", number=1000))

def work() -> int:
    return sum(len(str(i)) for i in range(200_000))

profiler = cProfile.Profile()
profiler.enable()
work()
profiler.disable()
pstats.Stats(profiler).sort_stats("cumtime").print_stats(5)
```

`timeit` 会自动多次运行以减少噪声；`cProfile` 有开销，但足以判断「时间花在哪个函数」。内存问题用 `tracemalloc` 或 `sys.getsizeof` 排查，注意 `getsizeof` 不含引用对象。

## 常见坑

- **多线程做 CPU 计算**：受 GIL 限制，可能比单线程更慢。
- **协程里调用阻塞函数**：整个事件循环被卡住，所有任务停摆。
- **忘记 await**：协程对象被创建却未执行，通常伴随 `RuntimeWarning`。
- **无界并发**：一次创建上万任务导致内存与文件描述符耗尽。
- **共享可变状态无锁**：竞态条件难以复现，优先用消息传递或不可变数据。
