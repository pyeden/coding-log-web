# 10. 搜索、归档与点赞

## 本章目标

到这一章，文章已经能写、能读、能评论了。但如果一个读者只想找“讲 Markdown 的那篇”，或者只想看“技术”栏目下的内容，他还得自己一页页翻。这一章要补上三条“发现文章”的路：搜索、归档和点赞热度。

做完以后，你应该能：

- 在页面右上角输入关键词，得到标题或正文匹配的文章。
- 点侧栏的栏目或标签，看到这一类文章，而不是全站文章。
- 打开一篇文章，看到浏览量增加；登录后点一次赞，数字加一，再点一次，数字减一。
- 说得清“查询参数”“原子自增”“幂等”这几个词是什么意思。

## 先补概念

**查询参数**：网址里问号后面的那一段，比如 `?search=Django`。它不影响打开哪个页面，只是把额外条件交给服务器。`search` 是参数名，`Django` 是参数值。多个参数用 `&` 连接，例如 `?column=tech&page=2`。前端不需要为每种筛选新建一个页面，只要换参数，同一个列表组件就能显示不同结果。

**搜索**：服务器拿到关键词后，去文章的标题和正文里找包含它的记录。这里用的是“包含匹配”，不是智能语义搜索。搜 `Markdown` 会找到正文里出现这个词的文章；搜一句很长的话，可能什么都找不到。

**归档**：把文章按某个维度分组存放。这个项目有两个维度：栏目是一篇文只能属于一个的大分类，标签是一篇文可以挂多个的小标记。归档页本质上还是文章列表，只是多加了一个筛选条件。

**浏览量**：每打开一次文章详情，计数加一。它不区分是谁看的，同一个人刷新五次就算五次。这个数字不精确，但能反映“哪篇被翻得多”。

**原子自增**：让数据库自己执行“把这一列加一”，而不是先读到程序里、加一、再存回去。后者在两个人同时访问时会互相覆盖，丢掉一次计数。原子自增是一条数据库语句完成，不会丢。

**幂等**：同一个操作重复执行，最终结果保持一致。点赞在这里不是“每点一次加一”，而是“点过就取消，没点过就点上”的开关。点两次回到原点，点三次又点上，所以计数不会被刷上去。

**唯一约束**：数据库层面的一条硬规则，规定“同一篇文章 + 同一个用户”只能有一条点赞记录。应用代码可能写错，但数据库会兜底拒绝重复插入。

**最热**：按浏览量排序取前五篇。它不替代首页，只是给读者一个“大家在看什么”的入口。

### 第二步：先用命令行试搜索

不开浏览器也能验证后端。另开一个终端执行：

```bash
curl -s 'http://127.0.0.1:8000/api/articles/?search=Markdown' | python3 -m json.tool
```

返回的是一个分页对象，里面有 `count`（总条数）和 `results`（当前页的文章）。如果 `count` 大于零，说明搜索生效。再试一个不存在的词：

```bash
curl -s 'http://127.0.0.1:8000/api/articles/?search=不存在的词' | python3 -m json.tool
```

这时 `count` 应该是 0，`results` 是空数组。注意：搜不到不是错误，HTTP 状态码仍然是 200。前端要显示“没有找到”，而不是“加载失败”。

### 第三步：试栏目和标签

```bash
curl -s 'http://127.0.0.1:8000/api/articles/?column=tech' | python3 -m json.tool
curl -s 'http://127.0.0.1:8000/api/articles/?tag=django' | python3 -m json.tool
```

栏目参数既接受 slug，也接受数字 id；标签参数同时接受名字和 slug，并且不区分大小写。所以 `?tag=Django` 和 `?tag=django` 应该返回同一批文章。这个细节很重要，因为侧栏拿到的是标签名，而路由里经常用 slug。

### 第四步：看浏览量

先查一篇文章的当前浏览量：

```bash
curl -s 'http://127.0.0.1:8000/api/articles/' | python3 -m json.tool | head -40
```

从结果里挑一个 `slug`，连续请求两次详情：

```bash
curl -s 'http://127.0.0.1:8000/api/articles/你的slug/' | python3 -c "import json,sys; print(json.load(sys.stdin)['total_views'])"
curl -s 'http://127.0.0.1:8000/api/articles/你的slug/' | python3 -c "import json,sys; print(json.load(sys.stdin)['total_views'])"
```

第二个数字应该比第一个大一。如果 slug 含中文，命令行里要先做 URL 编码，浏览器里则由前端自动处理。

## 代码与文件

### 1. 搜索和筛选的入口

`ArticleViewSet` 声明了可搜索字段：

```python
search_fields = ["title", "body"]
ordering_fields = ["created", "updated", "total_views", "likes", "title"]
```

DRF 的 `SearchFilter` 会读取 `?search=`，对这两个字段做不区分大小写的包含匹配。注意参数名必须是 `search`。前端如果传成 `q`，后端不会报错，只会把它当成普通参数忽略，于是返回全部文章——这是很常见的一种“搜索失灵”。

栏目和标签在 `get_queryset` 里处理：

```python
column = self.request.query_params.get("column")
if column:
    column_query = Q(column__slug=column)
    if str(column).isdigit():
        column_query |= Q(column__id=int(column))
    queryset = queryset.filter(column_query)

tag = self.request.query_params.get("tag")
if tag:
    queryset = queryset.filter(
        Q(tags__name__iexact=tag) | Q(tags__slug__iexact=tag)
    ).distinct()
```

`query_params` 就是查询参数字典。`Q(...) | Q(...)` 表示“满足任意一个条件”。标签查询加了 `.distinct()`，因为一篇文章可能通过多个标签匹配，不去重会出现重复行。

### 2. 浏览量为什么这么写

```python
def retrieve(self, request, *args, **kwargs):
    instance = self.get_object()
    Article.objects.filter(pk=instance.pk).update(total_views=F("total_views") + 1)
    instance.total_views += 1
    serializer = self.get_serializer(instance)
    return Response(serializer.data)
```

第一句 `update(... F(...) + 1)` 让数据库自己做加法，是原子操作。第二句只是把内存里的对象也加一，好让本次响应返回新数字；它不会再次写数据库。不要写成 `instance.total_views += 1; instance.save()`，那样两个并发请求可能都读到旧值，最后只加了一次。

### 3. 点赞的开关逻辑

```python
like, created = ArticleLike.objects.get_or_create(
    article=article, user=request.user
)
if created:
    Article.objects.filter(pk=article.pk).update(likes=F("likes") + 1)
    liked = True
else:
    like.delete()
    Article.objects.filter(pk=article.pk, likes__gt=0).update(likes=F("likes") - 1)
    liked = False
```

`get_or_create` 先找记录，找不到才创建，并告诉你这次是不是新建的。新建说明“之前没点过”，于是加一；已经存在说明“点过了”，于是删掉记录并减一。减一的条件里带 `likes__gt=0`，避免出现负数。

模型里还有一条约束：

```python
constraints = [
    models.UniqueConstraint(
        fields=["article", "user"], name="unique_article_like"
    )
]
```

即使两个请求几乎同时到达，数据库也只允许一条 `(article, user)` 记录，计数不会凭空多出来。

### 4. 前端为什么只写一个列表组件

`ArticleFeed.vue` 接收一个 `filters` 对象，把它和分页参数一起发给 `listArticles`：

```js
const data = await listArticles({ page: page.value, page_size: 6, ...props.filters })
```

`SearchView` 只负责把网址里的 `q` 变成 `{ search: q }`；`ColumnView` 把路由参数变成 `{ column: slug }`；`TagView` 变成 `{ tag: slug }`。三个页面共用同一套卡片、空状态、分页和侧栏。这样加一种筛选，不用复制一整套页面逻辑。

点赞按钮则做了一件小事：请求失败时给提示，请求成功时直接用后端返回的 `liked` 和 `likes` 更新界面，不在前端自己猜数字。

## 检查点

- `?search=Markdown` 的 `count` 大于 0，`?search=乱写` 的 `count` 等于 0，状态码都是 200。
- `?column=tech` 和 `?tag=django` 只返回对应分类的文章。
- `?tag=Django` 与 `?tag=django` 结果一致。
- 连续打开同一篇详情两次，`total_views` 每次加一。
- 同一账号连续点两次赞，`likes` 回到原值；点三次，等于点一次。
- `/api/articles/hot/` 返回最多 5 篇，且浏览量从高到低。
- 搜索无结果时页面显示空状态，不显示红色报错。

## 常见错误

**报错：搜索框输入了词，结果还是全部文章。**

原因通常是参数名不对。前端传了 `q`，后端只认 `search`；或者请求根本没带上参数。打开浏览器开发者工具的 Network 面板，看请求网址里有没有 `?search=...`。修复：在 `SearchView` 里把 `q` 映射成 `{ search: q }`，不要直接把 `q` 塞进 filters。

**报错：点标签进入 `/tag/Django`，页面一篇都没有。**

原因是标签匹配虽然不区分大小写，但前端拿到的 `slug` 可能为空，或者把带空格的标签名直接拼进了路径。先看 `/api/tags/` 返回的 `slug` 是什么，再用它跳转；路径参数用 `encodeURIComponent`。如果是中文标签，浏览器地址栏会自动编码，但手写链接时容易漏。

**报错：点赞请求返回 403，提示 CSRF 校验失败。**

原因是写请求没有带 `X-CSRFToken`，或者登录后 CSRF token 已经轮换，前端还在用旧值。浏览器的 axios 拦截器会从 `csrftoken` cookie 读取并加头，所以正常页面操作不该出现；如果你用 curl 测试，要先 `GET /api/auth/csrf/`，登录后再取一次，然后带上 cookie 和请求头。修复方式见冒烟脚本里的写法。

**报错：刷新页面，浏览量没有变化。**

先确认你打开的是详情接口 `/api/articles/<slug>/`，而不是列表接口。列表不会增加浏览量。其次确认请求真的到了后端：看 `logs/app.log` 有没有对应记录。还有一种情况是你用了浏览器的后退缓存，页面没有重新发请求，手动刷新一次即可。

**报错：点赞数越点越大，或者出现负数。**

说明计数没有走开关逻辑，可能把“点赞”写成了每次 `likes + 1`，也没有唯一约束。检查 `ArticleLike` 是否真的建了唯一约束，并确认重复请求走的是 `get_or_create` 的 `else` 分支。数据库迁移没执行时，约束不会生效，先跑 `python manage.py migrate`。

## 小结

搜索、归档、最热和点赞，本质上都在回答同一个问题：读者怎么找到下一篇想看的文章。实现上尽量复用同一套列表接口和同一个列表组件，只在查询参数上做区分。浏览量用数据库原子自增，点赞用唯一约束加开关逻辑，这两处是本章最值得记住的工程细节。下一章讲怎么用测试把这些行为固定下来，以及出问题时去哪里看日志。
