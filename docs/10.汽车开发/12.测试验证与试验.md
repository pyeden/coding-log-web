# 测试验证与试验

测试验证最容易被误解成"证明东西没问题"。真实的工程含义恰好相反：它是在有限的时间、样车与预算下，用尽可能少的样本，量化"还有多少问题没被发现、发现后有多严重"。一个试验报告的价值，不在于结论写了"合格"，而在于它说清了在什么条件下、用什么判据、覆盖了哪些风险。

## 1. 领域定位与边界：用证据换确定性

整车的验证体系可以想成三层漏斗。最上层是仿真与台架，成本低、迭代快、覆盖广，但保真度有限；中间是零部件与系统级试验，能复现边界条件，但离整车体验还有距离；最下层是整车道路与场地试验，最真实，也最贵、最慢、样本最少。验证工作的核心能力，是判断"哪个问题应该在哪一层被发现"，而不是把所有问题都堆到实车上。

边界要划清。测试不负责改设计，但要用数据推动设计改；不负责量产一致性，那是质量体系的事，但要为它提供判据；不负责法规申报的行政流程，但要产出能被认证机构接受的证据。测试负责的是：把"我们认为它行"变成"有可复现的证据表明它在规定条件下行"。

三个目标互相拉扯。覆盖要全，就要多方案、多样车、多工况；周期要短，就要并行、要抽样；成本要低，就要少做破坏性试验。现实的做法是风险导向：对安全件、法规件、长周期件做全项验证，对成熟平台件做差异验证，对软件功能做持续回归。

最容易被忽略的是"验证的独立性"。如果试验判据由设计者自己定，那么"通过"很容易变成"把判据调到能通过"。成熟的体系会把判据前置到需求阶段，并让测试团队对判据的解释权独立于设计团队。

## 2. 流程中的位置

上游是需求与设计：性能目标、法规条款、DFMEA 识别的失效模式。下游是工装试生产、认证与量产。验证是把设计意图翻译成证据的中间环节，它的计划必须与设计冻结同步，而不是等样车出来才开始想"测什么"。

| 阶段 | 验证侧主要输入 | 关键输出 | 门禁关注点 |
| --- | --- | --- | --- |
| 概念设计 | 目标市场法规、平台沿用件清单 | 验证策略、认证路径、资源预算 | 法规项是否遗漏、周期是否可行 |
| 方案设计 | 性能目标、DFMEA 初稿 | DVP&R 初版、台架与样车需求 | 判据是否可测量、覆盖是否闭环 |
| 详细设计 | 冻结数模、供应商试验报告 | 零部件 DV 计划、台架方案 | 边界条件、加速因子是否合理 |
| 样车验证 | A/B/C 样车、场地与道路资源 | 系统与整车试验报告、问题清单 | 失效是否复现、根因是否闭环 |
| 工装试生产 | 工装件、产线节拍 | PV 报告、EOL 规范验证、一致性数据 | 工装件与手工件差异是否解释 |
| 认证与量产 | 申报资料、抽检计划 | 公告与 CCC 报告、年度确认试验 | 样本代表性、判据与法规一致 |

两个时点必须提前锁：验证策略与样车数量。前者决定"哪些风险靠仿真、哪些靠实车"，后者决定整个项目的时间与预算。样车数量一旦定少，后期发现覆盖缺口就只能靠加钱加急，或者带着已知风险放行。

## 3. 核心概念与术语表

| 术语 | 英文全称 | 一句话解释 |
| --- | --- | --- |
| 设计验证 | Design Verification (DV) | 证明设计输出满足设计输入 |
| 生产验证 | Production Validation (PV) | 证明工装件与量产过程能稳定满足要求 |
| 验证计划与报告 | Design Verification Plan and Report (DVP&R) | 把每条要求映射到试验、判据、责任人与结论 |
| 模型在环 | Model-in-the-Loop (MIL) | 控制算法与被控对象模型在仿真中闭环 |
| 软件在环 | Software-in-the-Loop (SIL) | 真实代码跑在仿真环境中 |
| 硬件在环 | Hardware-in-the-Loop (HIL) | 真实控制器接仿真被控对象与总线 |
| 整车在环 | Vehicle-in-the-Loop (VIL) | 实车或半实车接入虚拟交通环境 |
| 环境适应性试验 | Environmental Test | 温度、湿度、振动、盐雾、防水防尘等应力验证 |
| 耐久试验 | Durability Test | 用加速载荷模拟全生命周期损伤 |
| 标定 | Calibration | 在真实工况下整定控制参数，使性能与排放达标 |
| 问题闭环 | Issue Closure | 从发现、复现、根因、措施到验证的完整链条 |
| 样车 | Prototype | 用于验证的整车，按阶段分为骡子车、手工样车、工装样车 |
| 加速因子 | Acceleration Factor | 加速试验相对真实使用的损伤倍率 |
| 测量系统分析 | Measurement System Analysis (MSA) | 证明测量系统本身的误差可接受 |

## 4. 主流方案与取舍

验证手段的选择，本质是"保真度、速度、成本"三角。

| 方案 | 主要优势 | 代价与限制 |
| --- | --- | --- |
| 纯仿真 | 快、便宜、可覆盖极端与危险场景 | 模型误差难量化，传感器与执行器非理想特性缺失 |
| MIL/SIL | 早期验证控制逻辑，回归成本低 | 与真实硬件时序差异大，接口假设易失真 |
| HIL | 真实控制器加虚拟对象，可复现故障注入 | 建模工作量大，台架与被控对象保真度决定价值 |
| 台架试验 | 边界条件可控、可破坏、可加速 | 装车边界（振动、电磁、热）难以完全复现 |
| 封闭场地 | 场景可设计、可重复、风险可控 | 场景数量有限，驾驶员与交通流不真实 |
| 公开道路 | 最真实的使用条件与交通流 | 不可重复、样本少、极端场景难以遇到 |
| 全项验证 | 覆盖完整，认证友好 | 周期长、成本高，样车与台架资源紧张 |
| 差异验证 | 快、省，适合平台沿用件 | 假设沿用件无变化，一旦有隐性改动就漏检 |

一个常见的误区是把 HIL 当成"便宜的实车"。HIL 的价值在于可重复与可注入故障，而不是替代实车；如果模型本身不准，HIL 只会更快地给出错误结论。反过来，实车的价值在于暴露模型没想到的耦合，比如线束走向引起的电磁干扰、支架共振、装配应力。

另一个取舍是"加速试验的加速因子怎么定"。定得太激进，失效机理可能从真实模式变成实验室伪模式；定得太保守，试验周期无法接受。正确做法是用真实用户载荷谱做损伤等效计算，并用至少一组实际使用数据反向校核。

## 5. 关键交付物与评审要点

交付物分四类。**计划类**：验证策略、DVP&R、样车与台架资源计划、认证项清单。**执行类**：试验大纲与作业指导书、原始数据与照片、标定记录、问题清单。**结论类**：试验报告（含判据、偏差、异常说明）、失效分析报告、覆盖度评估。**体系类**：EOL 检测规范、抽检计划、量产后持续验证方案。

评审最该盯三件事。其一，判据是否可测量、可复现：写"无异响"这种判据，等于没写。其二，偏差是否被解释：实测比仿真差 15%，是模型保守、样件个体差异，还是设计真的不足，必须给出证据。其三，失效是否闭环到根因：换了件就好了，不等于问题解决，可能只是把失效转移到了别处。

还有一个评审常被跳过的问题：试验样本的代表性。手工样车与工装件在材料、公差、装配顺序上都可能不同，用手工样车的数据去证明量产能力，是最常见的逻辑跳跃。

## 6. 标准法规与工具链

环境与可靠性：ISO 16750 系列定义道路车辆电气电子设备的环境条件与试验，GB/T 28046 系列为国内对应标准；ISO 20653 定义防护等级；ISO 19453 系列针对电驱动系统的环境试验。电磁兼容：UN R10 与 GB 34660 约束整车与零部件的发射和抗扰。功能安全：GB/T 34590 系列与 ISO 26262 要求验证与确认活动覆盖安全目标。过程能力：ASPICE 评估研发过程成熟度，ISO/IEC 17025 约束实验室能力与数据可信度。道路试验方法类标准较多，具体版本与适用范围以最新官方发布为准。

工具链分四层。仿真：MATLAB/Simulink、CarSim、CarMaker、AMESim；HIL：dSPACE、Vector、NI 的实时平台，配 CANoe 做总线与诊断；测量与标定：INCA、CANape、Vector 记录仪、功率分析仪；数据：试验管理系统、时序数据库、自动化报告生成。工具的关键不是功能多，而是数据能否回链到需求 ID 与问题单，否则报告写完就变成死文档。

## 7. 与其他领域的接口冲突

**与设计的接口**：测试发现的失效，设计可能认为是"试验条件过严"，测试可能认为是"设计余量不足"（见[整车开发流程与项目管理](/note/vehicle-dev/)）。冲突的根源是判据没有前置约定。解决办法是在 DVP&R 评审时就把工况、公差、判定规则写死，并约定偏差的处理流程，而不是等报告出来再吵。

**与质量的接口**：DV 证明设计可行，PV 证明过程稳定，两者常被混用（见[制造工艺与质量体系](/note/manufacturing/)）。典型冲突是"用手工样车的数据支持 PPAP"，或者"用 PV 的一次通过率反推设计能力"。正确边界是：DV 对设计负责，PV 对过程负责，量产后的一致性由 SPC 与 EOL 持续监控。

**与热管理的接口**：环境舱试验需要整车热管理配合，电池、电驱、座舱的温控策略会改变试验结果（见[热管理](/note/thermal/)）。冲突是"试验工况与用户工况不一致"：在环境舱里恒温恒湿跑循环，和真实道路上反复冷启动、暴晒、爬坡，热负荷分布完全不同。试验大纲必须说明工况的代表性，以及它偏向保守还是激进。

**与 EEA 的接口**：HIL 台架要模拟整车的总线、电源与故障，网络拓扑与信号时序必须与实车一致（见 [EEA 学习笔记](/note/eea/)）。冲突是"台架简化"：为了省事只模拟关键报文，结果实车上出现的偶发通信超时在台架上永远复现不了。建议至少保留完整的网关转发路径与电源跌落特性。

**与智驾的接口**：智驾的验证依赖海量场景与里程，传统"抽几个工况跑一遍"的方法不适用（见[智能驾驶](/note/adas/)）。冲突是证据形式：法规与审核习惯看报告与签字，数据驱动团队习惯看统计分布。解决办法是建立场景库与覆盖率指标，把统计结论翻译成可审计的证据链。

**与整车安全的接口**：碰撞、气囊、主动安全的试验往往具有破坏性，样本一次性消耗（见[整车安全与法规](/note/vehicle-safety/)）。冲突是"试验数量与统计置信度"：撞一台车只能证明这一台，要证明一个配置族，需要按法规抽样并说明结构共性。这类论证必须在试验前完成，事后补逻辑很难成立。

## 8. 常见坑与检查清单

- [ ] 每条需求是否都能在 DVP&R 里找到对应的验证方法、判据与责任人
- [ ] 试验判据是否可量化、可复现，是否在试验前而非试验后确定
- [ ] 环境与耐久试验的加速因子是否有载荷谱依据，是否做过失效机理校核
- [ ] HIL 台架的模型是否与实车标定版本一致，故障注入是否覆盖传感器与总线异常
- [ ] 样车状态（手工件、工装件、软件版本）是否在报告中明确记录并可追溯
- [ ] 失效问题是否闭环到根因，措施是否在其他车型或工况上做过横向排查
- [ ] 标定数据是否与软件版本绑定，是否存在"报告用旧版、量产用新版"的情况
- [ ] 认证样本与量产状态是否一致，变更后是否评估过重新申报的必要性

## 9. 学习路径与资料

建议按"测量、建模、体系"三段学习。先学测量与数据处理：传感器原理、采样定理、滤波、不确定度分析，理解为什么"数据好看"不等于"结论可靠"；再学建模与仿真：被控对象建模、实时仿真、模型校核与确认；最后学体系：DVP&R 怎么写、ASPICE 怎么评估、认证流程怎么走。

资料优先级：标准原文与法规条款高于主机厂试验规范，高于供应商应用手册，高于论坛经验帖。标准告诉你"至少要做哪些"，试验规范告诉你"我们怎么做"，两者结合才是完整的方法论。

实践上最值得做的三件事：完整跟一次环境舱试验，看温变速率与布置方式如何影响结果；自己写一份 DVP&R，你会发现很多需求根本无法测量；参加一次失效分析，从现象反推到根因，比读十篇方法论更有用。

最后提醒：验证的产出不是"合格"两个字，而是"我们知道风险在哪里、有多大、由谁承担"。一份只写合格的报告，和一个说清边界的报告，价值差一个数量级。
