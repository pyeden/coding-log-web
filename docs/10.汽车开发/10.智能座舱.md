# 智能座舱

座舱是整车唯一一个用户每天主动直视、触摸、说话的界面。它的评价标准不是"功能多"，而是"在正确的时刻给出正确的信息，并且不让人分心"。这两句话听起来简单，落到工程上却要把计算平台、操作系统、交互设计、声学、显示、连接与软件生态拧成一股绳。

## 1. 这个领域解决什么问题

座舱可以拆成三层：最上面是交互层（屏幕、HUD、语音、方向盘按键、触觉反馈），中间是计算与系统层（座舱域控制器、SoC、Hypervisor、QNX/Android、中间件），最下面是与整车耦合的接口层（CAN/LIN/以太网、电源管理、诊断、OTA）。三层里任何一层出问题，用户感知到的都是"车机卡了"。

边界要划清。座舱不负责驾驶决策，那是智驾域的事；不负责车身电子的执行逻辑，那是车身域与 EEA 的事；不负责整车热管理的全局调度，虽然它要为域控争取散热。座舱负责的是：把人、车、云之间的信息流组织成可理解、可操作、可恢复的交互，并对这块屏幕在行车中的安全性负最终责任。

三个目标常年互相拉扯。体验要求响应快、动画顺、生态全；安全要求关键信息不被遮挡、驾驶中不做长交互、失效后有降级路径；成本要求少用一颗 SoC、少开一套模具、少养一个团队。真正的架构决策，都是在这三者之间选一个"可接受的坏结果"，而不是找到一个全都好的方案。

还有一个容易被忽略的约束：生命周期错配。整车寿命十年以上，消费电子芯片与 Android 大版本的节奏是两三年。座舱架构必须回答"三年后 SoC 停产了怎么办、五年后应用不兼容了怎么办"，这个问题的答案往往比选哪颗芯片更重要。

## 2. 在整车开发流程中的位置

上游是产品定义与造型：目标用户、价格带、屏幕形态、内饰主题。下游是 EEA、车身、热管理、智驾与法规认证。座舱的独特之处是"软硬解耦"——硬件在方案阶段锁死，软件要一直迭代到量产之后。

| 阶段 | 座舱侧主要输入 | 关键输出 | 门禁关注点 |
| --- | --- | --- | --- |
| 产品定义 | 用户画像、竞品体验、价格带 | 座舱功能清单、屏幕形态假设 | 功能与成本是否自洽 |
| 概念设计 | 内饰造型、仪表台布置、视野要求 | 屏幕数量与位置、HUD 方案、域控布置 | 法规视野、碰撞安全、可维修性 |
| 方案设计 | SoC 选型、操作系统策略 | 域控硬件方案、Hypervisor 架构、网络接口 | 算力余量、启动时间、供应链 |
| 详细设计 | 冻结数模、HMI 规范 | 硬件原理图、软件架构、交互原型 | 功能安全概念、信息安全分析 |
| 样车验证 | A/B 样车、台架资源 | 性能实测、语音与多模测试、稳定性 | 冷启动、卡顿、发热、回声 |
| 工装试生产 | 产线节拍、下线检测规范 | 检测项、老化筛选、版本冻结 | 一次通过率、版本一致性 |
| 量产与运营 | OTA 通道、用户反馈 | 版本迭代、灰度发布、回滚预案 | 回滚可用性、法规合规 |

两个时点必须提前锁：屏幕形态与布置（牵动仪表板结构、空调出风口、气囊、线束），以及 SoC 与操作系统路线（牵动团队能力、供应商合同、五年维护成本）。其余功能都可以在样车阶段加减，这两个改一次等于半个座舱重做。

## 3. 核心概念与术语表

| 术语 | 英文全称 | 一句话解释 |
| --- | --- | --- |
| 座舱域控制器 | Cockpit Domain Controller (CDC) | 把仪表、中控、HUD、语音等计算任务收拢到一台控制器 |
| 系统级芯片 | System on Chip (SoC) | 把 CPU、GPU、NPU、ISP 集成在一颗芯片上，座舱算力的核心 |
| 虚拟机监视器 | Hypervisor | 在硬件与操作系统之间做资源分区与隔离的一层 |
| 域隔离 | Domain Isolation | 让安全关键系统与娱乐系统共享硬件但互不影响 |
| 车载信息娱乐系统 | In-Vehicle Infotainment (IVI) | 中控屏上的娱乐与导航功能集合 |
| 车载安卓 | Android Automotive OS (AAOS) | 面向车机的 Android 版本，与手机投屏方案不是一回事 |
| 人机交互 | Human-Machine Interface (HMI) | 屏幕、语音、按键、手势、触觉的总和 |
| 抬头显示 | Head-Up Display (HUD) | 把信息投影到驾驶员前方视野，增强现实版本叠加车道级引导 |
| 驾驶员监控 | Driver Monitoring System (DMS) | 用摄像头判断疲劳、分心与接管能力 |
| 座舱监控 | Occupant Monitoring System (OMS) | 识别乘客、儿童遗留、安全带状态与手势 |
| 空中升级 | Over-the-Air Update (OTA) | 通过无线网络分发软件，需要分区备份与回滚机制 |
| 功能安全 | Functional Safety | 避免由电子电气故障导致的不合理风险 |
| 预期功能安全 | Safety of the Intended Functionality (SOTIF) | 在无故障情况下，因性能局限或误用导致的风险 |
| 信息安全 | Cybersecurity | 防未授权访问、篡改与数据泄露 |

## 4. 主流技术方案与取舍

座舱架构的第一个分岔是"几颗芯片、几套系统"。

| 方案 | 主要优势 | 代价与限制 |
| --- | --- | --- |
| 单 SoC + 单系统 | 成本最低、通信简单、开发快 | 娱乐应用崩溃可能拖垮仪表，安全隔离弱 |
| 单 SoC + Hypervisor 双系统 | 一套硬件跑 QNX 与 Android，隔离好、成本可控 | 资源划分与调度复杂，GPU 共享易争抢，调试门槛高 |
| 双 SoC 独立 | 仪表与娱乐彻底隔离，故障不互相传染 | 成本、功耗、体积上升，跨屏协同需额外通道 |
| QNX 做仪表与安全显示 | 实时性、启动快、认证成熟 | 生态与开发效率不如 Android，人力成本高 |
| Android 做信息娱乐 | 生态丰富、迭代快、应用迁移容易 | 启动慢，长期稳定性与安全加固压力大 |
| Linux 自研中间件 | 可控性高、授权成本低 | 团队门槛高，长期维护与认证工作量大 |
| 竖屏或旋转屏 | 视觉冲击强，导航信息纵向展示 | 布置与碰撞法规压力大，反光与盲操作问题突出 |
| 横屏联屏 | 信息分区清晰、成本可控 | 造型同质化，副驾屏使用率常被高估 |
| 全触控 | 成本低、内饰整洁 | 驾驶中盲操作差，安全与可用性争议大 |
| 保留实体按键 | 盲操作可靠、法规友好 | 成本与内饰设计约束增加 |

第二个分岔是"自研还是买"。自研能做出差异化，也把团队、周期与长期维护背在身上；买成熟方案上市快，但差异化只剩皮肤。折中做法是"硬件平台化、交互自研、生态开放"：底层用供应商的稳定底座，交互与场景自己做，应用层接第三方。

第三个分岔是"生态开放到什么程度"。完全封闭体验一致但应用少；完全开放像手机一样丰富，却把审核、安全与兼容性成本全部接过来。多数主机厂选择"白名单、应用商店审核、行车限制"的三层控制。

## 5. 关键交付物与评审要点

座舱交付物分四类。**架构类**：域控硬件规格、Hypervisor 资源分区表、软件分层架构、网络与诊断矩阵。**交互类**：HMI 设计规范（信息层级、颜色、字号、动效时长）、场景脚本、语音语料与唤醒策略、盲操作与降级方案。**验证类**：性能测试报告（冷启动、触控响应、帧率、长时间运行的内存与温度）、稳定性与压力测试、语音识别率与误唤醒统计、整车路噪下的语音可用性。**合规类**：功能安全概念与安全分析、信息安全威胁分析、渗透测试报告、OTA 合规文档、个人信息收集清单。

评审最该盯三件事。其一，关键信息的优先级是否在"最坏情况"下仍然成立：导航、报警、倒车影像、故障提示同时出现时，谁覆盖谁，有没有定义。其二，失效后的降级路径是否可感知：Android 崩溃时仪表还能不能显示车速与报警，黑屏时是否有物理备份。其三，性能指标是否在整车条件下测的：台架上流畅，装车后因为散热与电源管理降频而卡顿，是常见陷阱。

体验评价不能只靠工程师。建议建立"任务完成率、操作步数、首次成功率、主观负荷"的组合指标，让真实用户在真实路况下完成任务，而不是在会议室里看演示。

## 6. 标准、法规与工具链

与座舱直接相关的标准分三类。**人机与视野**：GB 4094《汽车操纵件、指示器及信号装置的标志》对标识与颜色有明确要求；GB 15084《机动车辆 间接视野装置 性能和安装要求》约束用摄像头与显示屏替代后视镜的条件；ISO 9241 系列提供人机交互的可用性框架。**功能与信息安全**：GB/T 34590 系列（对应 ISO 26262）定义功能安全流程与汽车安全完整性等级；ISO/SAE 21434 定义汽车网络安全工程；GB 44495-2024《汽车整车信息安全技术要求》与 GB 44496-2024《汽车软件升级通用技术要求》对信息安全与 OTA 提出强制要求，实施日期与适用条款以最新官方发布为准。**电磁兼容**：GB 34660 与 UN R10 约束整车与零部件的电磁发射和抗扰度。

工具链方面，操作系统与界面：QNX Momentics、Android Studio、Qt、Unity 或 Unreal、Kanzi 一类 HMI 工具；总线与诊断：CANoe、CANalyzer、Vehicle Spy；测试：座舱 HIL 台架、语音暗室与噪声回放系统、屏幕光学测量设备；数据：埋点与用户行为分析平台、OTA 灰度发布系统。工具选择的现实约束是团队熟悉度——一个用不顺手的工具，比一个功能少一点的工具更拖进度。

## 7. 与其他领域的接口与常见冲突

**与 EEA 的接口**：座舱域控通常挂在以太网上，仪表与车身信号还在 CAN 上，网关要做协议转换与优先级调度（见 [EEA 学习笔记](/note/eea/)）。典型冲突是带宽与实时性：中控屏的视频流、OTA 下载、诊断数据与智驾感知数据共享同一条骨干网，谁都不能被饿死。解决办法是在架构阶段就定义流量分级与限速策略，而不是等装车后靠"少开一个应用"糊过去。

**与智驾的接口**：仪表与 HUD 是智驾系统向驾驶员表达意图的最后一道窗口（见[智能驾驶](/note/adas/)）。冲突在于报警优先级与接管时序：自动紧急制动、车道偏离、驾驶员监控告警、导航提示可能同时发生，谁先显示、显示多久、用什么音效，必须在两侧共同定义，并做联合 HIL 测试。另一个冲突是地图与定位数据归属：导航用消费级地图，智驾用高精地图，两套坐标与更新节奏不同，融合不好会出现"屏幕说变道、车却不变"。

**与热管理的接口**：座舱域控与屏幕是持续发热源，夏季暴晒后舱内温度很高，SoC 会主动降频保护（见[热管理](/note/thermal/)）。冲突是性能与散热预算：用户最需要流畅的时刻，恰恰是硬件最热的时候。设计上要么给域控独立风道或导热路径，要么在软件里做"高温降级但保关键功能"的策略，并把这条策略写进验收标准。

**与整车安全的接口**：碰撞后座舱要负责解锁车门、点亮危险报警灯、触发紧急呼叫，这些动作在 12V 断电或气囊点爆后仍要可靠执行（见[整车安全与法规](/note/vehicle-safety/)）。冲突是电源与冗余：娱乐系统可以立刻断电，安全相关显示与通信必须撑住。这要求座舱内部按功能划分电源域，而不是整机一个开关。

**与汽车软件的接口**：座舱是否采用自适应 AUTOSAR、诊断是否走统一诊断服务、刷写是否走统一 OTA 通道，都要与整车软件架构对齐（见[汽车软件与 AUTOSAR](/note/autosar/)）。冲突常见于"两套升级体系"：座舱自己一套 OTA，整车另一套，版本组合爆炸后没人能复现问题。正确做法是统一版本清单与回滚策略。

**与整车开发的接口**：屏幕位置受造型与视野法规双重约束，改动往往在造型冻结之后才被发现不可行（见[整车开发流程与项目管理](/note/vehicle-dev/)）。冲突是"好看"与"可用"：低置屏幕反光、夜间亮度刺眼、副驾屏分散驾驶员注意力，这些都要在油泥模型阶段用真人视野验证，而不是等样车。

## 8. 常见坑与检查清单

- [ ] 关键信息（车速、挡位、报警、倒车影像）的显示优先级与覆盖规则是否书面定义并测试过
- [ ] Hypervisor 的 CPU、GPU、内存、存储分区是否留有余量，并做过一侧系统满负载的压力测试
- [ ] 冷启动到可用的时间是否在低温与高温两种条件下都测过，而不是只测常温
- [ ] 语音在高速路噪与开窗工况下的识别率是否达标，误唤醒是否有统计
- [ ] OTA 是否有分区备份、断点续传、失败回滚，以及刷写失败后的线下恢复路径
- [ ] 行车中是否禁止了长文本输入、视频播放等高风险交互，限制策略是否可审计
- [ ] 屏幕与 HUD 的夜间亮度、反光、色偏是否在实车与不同光照下评价过
- [ ] 人脸、语音、位置等个人信息的采集是否有告知、开关与本地化存储方案

## 9. 学习路径与资料

建议从"交互"入手，再往"系统"下沉。先读人机交互与可用性基础：信息层级、费茨定律、注意力分配、驾驶分心研究；再读操作系统与虚拟化：进程调度、GPU 共享、实时性与启动流程；最后读整车约束：EEA 拓扑、功能安全、信息安全与法规。

资料优先级：国家标准与强制法规原文高于主机厂公开白皮书，高于 ISO 与 SAE 标准的解读文章，高于行业拆解报告。标准只定义下限，但它是跨公司沟通时唯一不需要翻译的语言。

实践上最有效的三件事：跟一次完整的 HMI 可用性测试，看真实用户在哪里卡住；参加一次座舱 HIL 联调，理解"屏幕上的一个动画"背后有多少个模块在跑；亲手做一次 OTA 回滚演练，你会明白为什么版本管理比功能开发更值得投入。

最后提醒：座舱的评测最容易被"演示效果"欺骗。演示是精心设计的路径，量产是几万用户在各种极端条件下乱点。把评审从"看演示"改成"看任务完成率与故障恢复"，很多争论会自动消失。
