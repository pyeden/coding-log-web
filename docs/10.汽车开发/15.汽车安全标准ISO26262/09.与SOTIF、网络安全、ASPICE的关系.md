# 09. 与 SOTIF、网络安全、ASPICE 的关系

## 这一章解决什么

分清功能安全、预期功能安全、网络安全和过程成熟度的边界，避免用一个标准覆盖所有问题。

## 四类问题

| 标准/框架 | 主要问题 | 典型例子 |
| --- | --- | --- |
| ISO 26262 | E/E 故障导致的不合理风险 | 扭矩计算错误、传感器失效、看门狗失效 |
| ISO 21448（SOTIF） | 预期功能在已知/未知场景下性能不足 | 逆光摄像头识别失败、雷达误判 |
| ISO/SAE 21434 | 网络安全威胁 | 远程攻击、信号篡改、密钥泄露 |
| ASPICE | 开发过程能力与成熟度 | 需求管理、变更管理、测试过程不规范 |

它们互相补充，但不能互相替代。

## 功能安全 vs SOTIF

功能安全问：“系统坏了会不会危险？”
SOTIF 问：“系统没坏，但在某些场景下能力不够，会不会危险？”

例子：AEB 的制动执行器故障是功能安全问题；AEB 在暴雨/逆光下没识别出行人是 SOTIF 问题。

SOTIF 的核心工作包括：

- 场景识别与分类。
- 已知危险场景的验证。
- 未知场景的探索与字段监控。
- 性能边界和驾驶员提示。
- 安全论证与残余风险。

功能安全的安全机制不能解决“感知本来就不可靠”的问题；SOTIF 的验证也不能证明“执行器不会随机失效”。

## 功能安全 vs 网络安全

网络安全问：“有人故意攻击会不会导致危险？”
功能安全假设随机/系统性失效，不假设攻击者。

攻击可能破坏功能安全假设：

- 篡改传感器信号，让安全机制误判。
- 刷写恶意固件，绕过安全监控。
- 拒绝服务，让 FTTI 内无法进入安全状态。

因此要做联合分析：攻击树、TARA、功能安全影响分析、安全机制的抗攻击能力。

## 功能安全 vs ASPICE

ASPICE 评的是过程能力：需求管理、变更管理、测试过程是否规范。ISO 26262 评的是功能安全活动的充分性。

ASPICE 做得好，不代表 HARA 做得对；ISO 26262 做得好，也不代表过程成熟。两者可以共用需求、变更、测试证据，但目标不同。

## 与 AUTOSAR 的关系

AUTOSAR 提供软件架构、通信、诊断、OS、E2E 保护等机制。它是实现手段，不是安全标准。

用 AUTOSAR 不等于满足 ISO 26262；还要证明：

- E2E 保护覆盖了哪些信号。
- OS 分区是否满足免于干扰。
- 诊断事件和安全状态如何映射。
- 配置和工具链是否经过鉴定。

## 联合安全论证

复杂项目通常需要一张“联合安全论证”：

```text
功能安全：故障 → 安全机制 → 安全状态
SOTIF：场景 → 性能边界 → 残余风险
网络安全：威胁 → 攻击路径 → 缓解措施
ASPICE：过程 → 证据质量 → 可追溯
```

四类证据要能互相引用，而不是四套文档各说各话。

## 常见坑

- 把 SOTIF 问题当功能安全 bug 修。
- 把网络安全测试当功能安全验证。
- 用 ASPICE 评级代替安全评估。
- AUTOSAR 配置改了，不更新安全分析。
- 四套标准各做一套需求，追溯断裂。

## 小结

功能安全是“故障安全”，SOTIF 是“能力安全”，网络安全是“攻击安全”，ASPICE 是“过程可信”。下一章给出落地路线。
