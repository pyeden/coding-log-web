# 10. 工程落地路线与检查清单

## 这一章解决什么

把标准变成项目可执行的路线：先做什么、谁参与、每个阶段交什么证据。

## 阶段路线

### 1. 启动与边界

- 定义 item、系统边界、变型、操作模式。
- 确定适用版本、法规和客户要求。
- 任命安全经理，写安全计划。
- 识别供应商和 DIA 需求。

交付物：item 定义、安全计划、DIA 草案。

### 2. 概念阶段

- HARA，识别 hazardous event 和 ASIL。
- 定义 safety goal、安全状态、FTTI。
- 写功能安全概念（FSC）。
- 做初步安全分析（FTA/DFA）。

交付物：HARA、安全目标、FSC、初步安全分析。

### 3. 系统层

- 技术安全需求（TSR）。
- 系统架构与安全机制分配。
- 系统集成与验证计划。
- 更新 DFA、FTA。

交付物：TSR、系统架构、集成测试计划。

### 4. 硬件层

- 硬件安全需求（HSR）。
- 原理图、BOM、诊断设计。
- FMEDA、SPFM/LFM/PMHF。
- 故障注入、硬件测试。

交付物：HSR、FMEDA、硬件测试报告、DFA。

### 5. 软件层

- 软件安全需求（SSR）。
- 软件架构、免于干扰分析。
- 单元设计、编码规范、单元/集成测试。
- 工具置信度与组件鉴定。
- 目标板测试。

交付物：SSR、软件架构、测试报告、工具鉴定、追溯矩阵。

### 6. 验证、确认与评估

- 系统/整车验证。
- 安全案例。
- 确认评审、审核、功能安全评估。
- 问题整改与复核。

交付物：安全案例、确认措施记录、评估结论。

### 7. 生产与运行

- EOL 测试、生产一致性。
- 售后诊断、维修培训。
- 字段监控、故障统计、OTA 变更控制。
- 召回/报废流程。

交付物：生产控制计划、字段监控方案、变更记录。

## 检查清单

### 管理

- [ ] 安全计划有范围、角色、交付物、时间点。
- [ ] 安全经理有独立权限。
- [ ] 确认措施独立性与 ASIL 匹配。
- [ ] DIA 写清责任和证据。

### 概念

- [ ] item 边界和操作模式完整。
- [ ] HARA 覆盖正常/故障/维修/极限工况。
- [ ] S/E/C 有理由和评审记录。
- [ ] 安全目标可验证、可分配。
- [ ] FTTI/FHTI 有预算。

### 需求与架构

- [ ] 需求有唯一 ID、时间约束、安全状态。
- [ ] 需求追溯到安全目标。
- [ ] 安全机制分配到系统/硬件/软件。
- [ ] ASIL 分解有独立性证据。
- [ ] 免于干扰分析完成。

### 硬件

- [ ] FMEDA 与 BOM/原理图版本一致。
- [ ] SPFM/LFM/PMHF 达到目标或有偏差说明。
- [ ] 潜伏故障有自检/诊断策略。
- [ ] DFA 覆盖共因/级联失效。
- [ ] HSI 文档与软件实现一致。

### 软件

- [ ] SSR 覆盖故障检测、反应、时间。
- [ ] 单元/集成/目标板测试覆盖安全需求。
- [ ] 故障注入验证安全机制。
- [ ] 工具置信度评估完成。
- [ ] 复用组件有鉴定证据。
- [ ] 追溯矩阵闭合。

### 验证与运行

- [ ] 安全案例有主张、论据、证据。
- [ ] 确认评审/审核/评估完成。
- [ ] 生产 EOL 测试覆盖安全相关特性。
- [ ] 字段监控和售后流程到位。
- [ ] 变更/OTA 有安全影响分析。

## 常见失败模式

1. 把安全当文档工程，需求、设计、测试三张皮。
2. HARA 评低 ASIL，后面证据补不回来。
3. 冗余架构没有 DFA，独立性是假设。
4. FMEDA 覆盖率没有测试支撑。
5. 软件只测正常路径，故障注入缺失。
6. 供应商证据没有纳入整车安全案例。
7. 量产后变更绕过安全流程。

## 90 天启动建议

- 第 1–2 周：item 定义、边界、安全计划、角色。
- 第 3–4 周：HARA 工作坊、S/E/C 评审、安全目标。
- 第 5–6 周：FSC、TSR、架构安全机制分配。
- 第 7–8 周：硬件 FMEDA/DFA 启动，软件 SSR/架构。
- 第 9–10 周：测试计划、追溯矩阵、工具评估。
- 第 11–12 周：首次确认评审，整改，形成基线。

## 小结

ISO 26262 不是一张表，而是一条证据链。先把边界、HARA、需求、追溯做扎实，再谈工具和模板。证据链闭合，安全论证才站得住。
