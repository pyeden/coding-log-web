# 00. 为什么汽车软件需要功能安全

## 这一章解决什么

先建立问题意识：汽车上的电子电气系统一旦失效，后果可能不是“功能不好用”，而是人身伤害。ISO 26262 要解决的，就是这类由电子电气故障引起的“不合理风险”。

## 汽车已经变成软件产品

一辆现代汽车里有几十到上百个 ECU，刹车、转向、动力、电池、座舱、辅助驾驶都依赖软件。软件带来三个变化：

- 功能越来越依赖电子控制，机械备份越来越少。
- 同一个控制器上可能同时跑安全相关和非安全相关功能。
- 供应链变长，OEM、Tier1、软件供应商共同开发，责任边界容易模糊。

于是“软件写错”不再只是迭代问题：一个扭矩计算错误、一个信号超时、一个状态机卡死，都可能变成整车层面的危险。

## 功能安全管什么

功能安全（Functional Safety）关注的是：**电子电气系统的 malfunction 是否会导致不可接受的风险**。它不负责：

- 网络安全攻击（ISO/SAE 21434 管）。
- 预期功能不足，比如摄像头在逆光下识别不了（ISO 21448/SOTIF 管）。
- 普通质量问题和交付进度。

三者会互相影响，但不能互相替代。一个功能“设计上就不够好用”和“实现坏了”是两类问题。

## 核心链条

ISO 26262 的主线可以压缩成：

```text
item 定义
  → HARA 危害分析与风险评估
  → ASIL 等级
  → safety goal 安全目标
  → 功能安全需求 / 技术安全需求
  → 系统、硬件、软件设计与验证
  → 安全论证与评估
```

这条链的每一环都要有工作产物和追溯关系。标准不是“写一份文档”，而是要求你用证据证明：风险被识别、需求被分配、实现被验证、剩余风险可接受。

## 一个直观例子

假设“车辆在驾驶员没有踩加速踏板时意外加速”：

- 危害：非预期加速。
- 可能原因：扭矩请求错误、信号被篡改、控制逻辑卡死、传感器漂移。
- 安全目标：避免非预期加速导致不可接受的风险。
- 安全状态：切断驱动扭矩、进入降级模式、点亮故障灯。
- 关键时间：从故障发生到危险发生之间的容错时间窗（FTTI）。

后面的 HARA、ASIL、硬件度量、软件验证，都是围绕这类场景展开。

## 标准适用范围

ISO 26262:2018 主要面向道路车辆（以乘用车为主），摩托车、卡车/客车有单独的应用指南。它覆盖电子电气系统的功能安全，不覆盖机械、化学、火灾等非电子电气危害。
