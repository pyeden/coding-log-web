# 05. 硬件安全与度量

## 这一章解决什么

理解硬件层功能安全的核心：随机硬件失效、安全机制、FMEDA，以及 SPFM/LFM/PMHF 三个度量。

## 两类硬件失效

- **系统性失效**：设计或工艺缺陷，比如电容选型错误、PCB 布线错误。靠设计评审、验证、过程控制降低，不能只用概率描述。
- **随机硬件失效**：器件在使用中随机损坏，比如 MOS 短路、电阻开路。靠安全机制和定量分析控制。

功能安全同时管两类，但硬件度量的重点是随机失效。

## 安全机制

常见硬件安全机制：

- 双通道/冗余传感器，交叉比较。
- 看门狗、独立监控芯片。
- 锁步核、ECC 内存、CRC 总线。
- 电源监控、时钟监控。
- 安全继电器/切断路径。
- 诊断电路、故障注入。

每个机制要写清：检测什么故障、检测覆盖率、故障反应时间、进入什么安全状态。

## FMEDA

FMEDA（Failure Mode Effects and Diagnostic Analysis）是硬件定量分析的核心工作：

1. 列出器件和失效模式。
2. 估算失效率（来自数据库、厂商数据或现场数据）。
3. 判断失效是否安全、是否被安全机制覆盖。
4. 计算残余失效率和度量指标。

FMEDA 不是“填一张 Excel”，而是要能解释每个失效模式的分类和覆盖率假设。

## 三个度量

- **SPFM**（Single-Point Fault Metric）：单点故障度量，衡量单点失效被安全机制覆盖的程度。
- **LFM**（Latent Fault Metric）：潜伏故障度量，衡量未被发现的潜伏故障被覆盖的程度。
- **PMHF**（Probabilistic Metric for Random Hardware Failures）：随机硬件失效概率度量，通常按每小时失效概率表示。

常见目标值（仅作工程理解，具体以标准原文和项目安全计划为准）：

| ASIL | SPFM | LFM | PMHF |
| --- | --- | --- | --- |
| D | ≥ 99% | ≥ 90% | < 10⁻⁸ /h |
| C | ≥ 97% | ≥ 80% | < 10⁻⁷ /h |
| B | ≥ 90% | ≥ 60% | < 10⁻⁷ /h |
| A | 通常不要求 SPFM/LFM 目标 | — | < 10⁻⁶ /h |

不同版本/应用场景可能调整，项目必须锁定引用版本。

## 潜伏故障

潜伏故障是“已经坏了，但系统还没发现”的故障。比如冗余通道的一路已经失效，但另一路正常，驾驶员毫无感知；等第二路也失效，系统就直接失去冗余。

降低潜伏故障靠：

- 周期性自检。
- 上电自检。
- 故障注入。
- 诊断覆盖率分析。
- 维修策略和字段监控。

## 依赖失效分析（DFA）

冗余不是天然独立。DFA 要检查：

- 共因失效：同一电源、时钟、温度、振动、软件 bug。
- 级联失效：一个通道故障拖垮另一个通道。
- 共享资源：总线、内存、DMA、看门狗。
- 开发过程独立性：同一团队、同一工具、同一需求误解。

ASIL 分解和冗余架构没有 DFA，基本站不住。

## 硬件-软件接口（HSI）

硬件安全机制需要软件配合。HSI 文档要写：

- 软件能读哪些诊断寄存器。
- 故障如何上报、多久上报。
- 安全状态由谁执行。
- 启动/关闭顺序。
- 诊断测试的周期和条件。

HSI 不清，硬件设计了安全机制，软件却不知道何时读取，等于没有。

## 常见坑

- 只算 PMHF，不看 SPFM/LFM。
- 诊断覆盖率假设过高，没有测试证据。
- 冗余通道共享电源/时钟，DFA 没做。
- FMEDA 与原理图、BOM 版本不一致。
- 安全机制检测到了，但故障反应时间超过 FTTI。

## 小结

硬件安全的核心不是“选高可靠器件”，而是“用机制覆盖失效，并用数据证明覆盖足够”。下一章进入软件层。
