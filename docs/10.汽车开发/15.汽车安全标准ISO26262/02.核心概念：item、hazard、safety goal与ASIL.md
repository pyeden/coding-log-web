# 02. 核心概念：item、hazard、safety goal 与 ASIL

## 这一章解决什么

把最容易被混用的几个词分清：item、hazard、hazardous event、safety goal、ASIL、safety state、FTTI。

## item

item 是被分析的对象，可以是一个功能、一个系统或一个 ECU 集群。比如：

- “电子驻车制动功能”
- “车道保持辅助系统”
- “电池管理系统”

item 定义要写边界：包含哪些 ECU、传感器、执行器，和哪些外部系统交互，哪些不在范围内。

## hazard 与 hazardous event

- hazard：潜在的伤害来源，比如“非预期制动”。
- hazardous event：hazard 在特定工况下发生，比如“高速行驶时单侧非预期制动”。

HARA 分析的是 hazardous event，不是抽象 hazard。工况、车速、路面、驾驶员状态都会影响风险。

## safety goal

安全目标是针对 hazardous event 的顶层安全要求，描述“要避免什么”，不描述“怎么实现”。

例子：

- 避免非预期加速导致不可接受的风险。
- 避免在驾驶员未请求时施加制动。
- 避免转向助力突然丢失导致失去控制。

安全目标要可验证、可分配，不能写成“系统要安全”这种空话。

## ASIL

ASIL（Automotive Safety Integrity Level）是风险等级，分 A、B、C、D，D 最高；另有 QM（质量管理）表示不需要功能安全活动。

ASIL 由 HARA 的三个维度决定：

- Severity（S）：伤害严重度。
- Exposure（E）：工况暴露概率。
- Controllability（C）：驾驶员或其他系统能否控制。

ASIL 不是“代码质量等级”，也不是“产品重要程度”。它是特定 hazardous event 的风险等级，所以同一个 item 的不同安全目标可能有不同 ASIL。

## ASIL 分解

高 ASIL 可以通过分解降低单个元素的开发 rigor，但前提是：

- 需求被独立分配到冗余元素。
- 元素之间没有共因失效。
- 有依赖失效分析（DFA）证据。
- 分解后的 ASIL 组合满足原等级。

分解不是“把 D 拆成两个 A 就完事”，独立性不成立时不能简单降级。

## safety state 与 FTTI

- safety state：系统检测到故障后进入的安全状态，比如切断扭矩、降级助力、点亮故障灯。
- FTTI（Fault Tolerant Time Interval）：从故障发生到危险发生之间的时间窗。
- FHTI（Fault Handling Time Interval）：系统检测并处理故障所需时间。

设计安全机制时，FHTI 必须小于 FTTI，否则“检测到了也来不及”。

## 一个例子

场景：高速行驶中，电子助力转向突然输出反向扭矩。

- hazardous event：高速反向转向扭矩。
- S：可能致命，S3。
- E：高速行驶常见，E4。
- C：驾驶员很难抵抗，C3。
- ASIL：D。
- safety goal：避免非预期转向扭矩导致失去控制。
- safety state：逐步降低助力、报警、保留机械转向。
- FTTI：从故障到车辆失控的时间，可能只有几百毫秒。

这时软件的任务不是“算得更准”，而是“在时间窗内检测并进入安全状态”。

## 小结

概念不清，后面所有需求都会歪。记住一句话：HARA 定风险，安全目标定要避免什么，ASIL 定开发 rigor，FTTI 定时间预算。下一章讲 HARA 怎么做。
