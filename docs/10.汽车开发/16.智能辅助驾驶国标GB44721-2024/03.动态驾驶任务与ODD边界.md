# 03. 动态驾驶任务与 ODD 边界

## 这一章解决什么

把“系统能开”变成可定义的 ODD 和可验证的 DDT 能力，而不是一句“支持高速领航”。

## DDT 包含什么

动态驾驶任务至少包括：

- 横向控制：转向。
- 纵向控制：加速、制动。
- 目标与事件检测：车辆、行人、障碍物、交通信号。
- 决策与规划：车道选择、跟车、变道、避让。
- 车辆照明与信号装置控制。
- 必要时对驾驶环境作出响应。

L3/L4 的系统要在 ODD 内执行全部 DDT，而不是只做纵向或横向辅助。

## ODD 要写什么

一个可落地的 ODD 至少包含：

- 道路类型：高速、城市快速路、城市道路、匝道。
- 车道条件：车道线清晰度、宽度、曲率。
- 交通条件：拥堵、混合交通、施工区。
- 天气与光照：雨、雾、雪、夜间、逆光。
- 车速范围。
- 地理范围：城市、路段、国家/地区。
- 车辆状态：传感器清洁度、轮胎、载荷。
- 驾乘人员状态：L3 驾驶人是否在座位、是否可接管。

ODD 不是市场文案，要能被测试场景和运行监控验证。

## ODD 边界识别

系统必须能判断“我还在不在 ODD 内”：

- 地图/定位是否可信。
- 感知是否足够。
- 天气/光照是否超出设计。
- 道路结构是否变化。
- 传感器是否被遮挡/污染。
- 通信/云端依赖是否可用。

边界识别失败，系统就会在能力不足时仍然激活，这是典型 SOTIF 风险。

## 退出 ODD 的策略

接近 ODD 边界时，系统应提前规划：

- 提前发出接管请求。
- 降级到更保守的驾驶策略。
- 在安全位置执行 MRM。
- 记录退出原因。

不要等到“已经出 ODD”才反应，那时可能已经没有安全接管窗口。

## 场景库

ODD 要配场景库：

- 正常场景：跟车、变道、匝道、隧道。
- 边界场景：施工、事故、异形车辆、静止障碍物。
- 故障场景：传感器失效、制动降级、通信丢失。
- 人机场景：接管请求、驾驶员分心、驾驶员未接管。

场景库要能映射到仿真、场地和道路试验。

## 常见坑

- ODD 写得太宽，测试覆盖不了。
- 只写“高速公路”，不写天气、光照、交通、施工。
- 没有 ODD 边界识别，靠驾驶员自己判断。
- 退出 ODD 没有接管预算。
- 场景库只覆盖正常路况。
