# 13 开发流程、工具链与学习路线

架构能力的最后一公里是流程：一个人能画出漂亮的拓扑，和一个团队能按节点交付、按证据验收，是完全不同的两件事。整车项目的复杂度不在于单项技术，而在于几十个供应商、上千条需求、数年的生命周期必须对齐。流程与工具链就是把这种对齐变成可重复动作。

## 本章目标

理解 V 模型在 EEA 开发中的具体落点与交付物，掌握从需求到验证的工具链构成，并给出一条从"会写代码"到"能做架构判断"的学习路径。

## 核心概念

**V 模型** 的左侧是分解：整车需求 → 系统架构 → 子系统需求 → 软件/硬件设计；右侧是验证：单元测试 → 集成测试 → 系统测试 → 整车验证。EEA 的特殊之处在于"通信矩阵"和"诊断规范"同时出现在左右两侧——它们既是设计输入，也是验收依据。

**交付物** 是架构工作的可见成果。常见基线包括：整车拓扑图、通信矩阵（DBC/ARXML）、诊断规范（含 DID 与例程定义）、配电与搭铁方案、网络管理策略、时间同步方案、以及安全概念文档。缺任何一项，集成阶段都会以"需求不明"的形式返工。

**工具链** 的选型原则是"单一事实来源"。需求、模型、配置、代码、测试用例之间的追溯关系必须可机读，否则改一条需求要人工翻五个文档。常见组合是需求管理工具 + 架构建模工具 + AUTOSAR 配置工具 + HIL（Hardware-in-the-Loop，硬件在环）测试平台。

**验证层次** 不能跳。台架验证通信与时序，HIL 验证逻辑与故障注入，实车验证电磁兼容与真实工况。跳过台架直接上实车，问题会以"偶发"的形式出现，定位成本翻十倍。

## 关键设计与示例：交付物与验收

| 交付物 | 主要读者 | 验收方式 |
| --- | --- | --- |
| 拓扑图 | 系统、线束、采购 | 评审 + 与 BOM 一致性检查 |
| 通信矩阵 | 软件、测试 | 加载到工具无冲突，负载仿真通过 |
| 诊断规范 | 售后、产线、OTA | 用例覆盖关键服务与 NRC |
| 配电方案 | 电气、工艺 | 压降与温升核算复核 |
| 安全概念 | 安全经理、审核 | 危害分析与目标追溯完整 |

验收的关键是"可执行"。一份只能人读的矩阵，在集成时等于没有；能直接加载进仿真工具的矩阵，才具备约束力。

## 关键设计与示例：一条可落地的学习路线

```text
第 1 阶段（1-2 月）：读懂一张整车拓扑 + 一份 DBC
  目标：能解释每个网关存在的原因
第 2 阶段（2-3 月）：动手做一条 CAN 链路
  目标：算负载、配终端、抓报文、定位错误帧
第 3 阶段（3-6 月）：以太网与 SOME/IP
  目标：跑通服务发现，理解时延与丢包
第 4 阶段（6 月+）：平台与安全
  目标：读 AUTOSAR 规范，做一次 ASIL 论证与 TARA
```

每个阶段都要有可验证的产出：一份负载计算表、一次抓包分析、一个能跑的服务、一份安全分析。只看不练，术语会记住，判断力不会形成。

## 常见坑

把流程当负担。流程的价值在于让"谁在什么时候交付什么"无需重复沟通，跳过它省下的时间会在集成阶段成倍付出。

工具链割裂。需求在 A 工具、模型在 B 工具、测试在 C 工具，追溯靠人工维护，最终没人敢改需求。

只做正向验证。故障注入、边界工况、降级路径的验证往往被压缩，而这些恰恰是量产问题的高发区。

## 小结与参考

流程保证对齐，工具链保证追溯，验证层次保证问题早发现。架构师的核心能力不是记住所有标准，而是知道在什么约束下该问什么问题。参考 ISO 26262 对安全生命周期的要求、AUTOSAR 方法论分册，以及项目自身的开发流程规范；具体裁剪方式以组织与项目要求为准。

至此，这套笔记从术语、演进、网络、中间件、控制器、供电与物理、软件平台、诊断与安全，走到流程与路线。真正的架构能力来自项目里的一次次取舍，而不是读完一份文档。
