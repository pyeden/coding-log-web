# 09 AUTOSAR 经典平台与自适应平台

AUTOSAR（AUTomotive Open System ARchitecture，汽车开放系统架构）经常被当成一个"标准软件包"，实际上它是两份面向不同世界的规范：经典平台（Classic Platform，CP）服务硬实时与深嵌入式，自适应平台（Adaptive Platform，AP）服务高算力与动态部署。把两者混用，是平台选型阶段最常见的错误。

## 本章目标

理解 CP 的分层结构与运行机制，掌握 AP 的服务模型与执行管理，能够根据功能特性（实时性、算力、更新频率）选择平台，并看懂 ARXML 中描述软件组件的基本结构。

## 核心概念

**CP 的核心是分层与静态配置**。最底层是 MCAL（Microcontroller Abstraction Layer，微控制器抽象层），向上是 ECU 抽象层与服务层，再上是 RTE（Runtime Environment，运行时环境），最顶是 SWC（Software Component，软件组件）。RTE 把 SWC 之间的通信抽象成端口连接，运行时几乎不解释配置——绝大多数决策在编译期由配置工具生成。这让 CP 具备极强的确定性，也让变更成本很高：改一条信号往往要重跑生成链。

**AP 的核心是服务与动态性**。它基于 POSIX（PSE51 子集）提供 C++ 运行环境，包含 ARA（AUTOSAR Runtime for Adaptive Applications，自适应应用运行时）API，由执行管理（Execution Management）负责进程生命周期，通信管理负责面向服务的通信。AP 支持在运行时启动、停止、更新应用，天然适配 OTA 与多供应商共部署。

**平台选择** 的判据不是"新旧"，而是三个问题：是否有毫秒级硬实时闭环？是否需要频繁更新与动态部署？算力与内存是否宽裕？前两个答案指向 CP，后两个指向 AP，两者兼有则采用异构组合（AP 做上层，CP 做实时执行）。

## 关键设计与示例：一份 ARXML 片段

ARXML 是 AUTOSAR 的机读描述格式。下面是一段说明性片段，表达一个提供车速端口的软件组件：

```xml
<SW-COMPONENT-TYPE>
  <SHORT-NAME>SpeedProvider</SHORT-NAME>
  <PORTS>
    <P-PORT-PROTOTYPE>
      <SHORT-NAME>SpeedOut</SHORT-NAME>
      <REQUIRED-INTERFACE-TREF DEST="SENDER-RECEIVER-INTERFACE">
        /Interfaces/ISpeed
      </REQUIRED-INTERFACE-TREF>
    </P-PORT-PROTOTYPE>
  </PORTS>
</SW-COMPONENT-TYPE>
```

注意端口是"提供"还是"需要"由类型决定，接口引用必须解析到具体接口定义。集成阶段报出的"未解析引用"，多半是接口路径与版本不匹配，而不是语法错误。

## 关键设计与示例：两平台对照

| 维度 | CP | AP 
| --- | --- | --- |
| 语言与运行时 | C，静态配置 | C++，POSIX 子集 |
| 通信模型 | 信号/端口，RTE 生成 | 面向服务，SOME/IP 等 |
| 实时性 | 硬实时，可预测 | 软实时，依赖调度与资源 |
| 更新能力 | 整体刷写，变更需重生成 | 支持应用级更新与动态部署 |
| 典型落点 | 动力、底盘、车身执行器 | 座舱、智驾、中央计算 |

AUTOSAR 以年度发布（如 R21-11 等）组织规范版本，不同版本间的 API 与配置模型存在差异，跨版本迁移必须做兼容性评估。具体版本能力以官方发布说明与规范文档为准。

## 常见坑

在 CP 上做"动态功能"。CP 的确定性来自静态配置，运行时动态加载会破坏可预测性，也通不过安全论证。

在 AP 上照搬 CP 的周期任务模型。AP 的调度是操作系统级的，按固定周期堆任务会导致优先级反转与抖动。

忽略工具链锁定。CP 的配置工具与生成器往往与供应商绑定，换工具等于重做集成，这一点必须在项目早期评估。

## 小结与参考

CP 买的是确定性，AP 买的是灵活性，两者不是替代关系而是分工关系。架构师要做的，是把功能按实时性与更新频率切开，再分别落到合适平台。参考 AUTOSAR 官方规范（CP 与 AP 分册）与发布说明，具体版本以官方最新文档为准。
