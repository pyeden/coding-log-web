# 10 面向服务架构与软件平台

SOA（Service-Oriented Architecture，面向服务架构）在整车里常被简化成"用 SOME/IP 通信"，这是把手段当成了目的。SOA 真正改变的是依赖方向：功能不再依赖某个具体 ECU 的存在，而依赖一份稳定的服务契约。契约稳定，硬件才能替换，软件才能复用，组织才能并行。

## 本章目标

理解服务契约的构成与版本策略，掌握服务生命周期与部署边界，能够设计一个可演进的车载软件平台分层，并识别 SOA 落地时最常见的组织性障碍。

## 核心概念

**服务契约** 包含接口（方法、事件、字段）、语义（单位、取值范围、错误码）、服务质量（周期、时延、可靠性）与版本。只写接口不写语义，是"能编译但不能集成"的根源：两个团队对同一个字段的单位理解不同，联调时会花几天时间才发现问题。

**服务生命周期** 包括注册、发现、订阅、失效。车上的服务不是永远在线的：区域控制器可能因为配电策略休眠，服务必须先声明可用性语义，客户端才能做出正确的降级，而不是盲目等待超时。

**部署边界** 决定一个服务能否独立升级。若服务实现与其依赖的库、配置、数据强耦合，所谓"独立部署"只是形式。平台要提供的是运行环境、通信抽象与配置管理，而不是把所有东西打进一个镜像。

**平台分层** 通常分为：硬件与 BSP、Hypervisor/OS、通信中间件、平台服务（诊断、日志、时间、电源管理）、应用框架、应用。分层的价值在于每层只向下依赖，替换一层不影响上层语义。

## 关键设计与示例：一份服务契约的描述

```yaml
service: VehicleSpeed
version: 1.2.0
methods:
  - name: get
    request: {}
    response:
      speed_kph: { type: uint16, unit: km/h, range: [0, 300] }
      valid: { type: boolean }
events:
  - name: changed
    period_ms: 20
    qos: { deadline_ms: 60, reliability: best_effort }
errors:
  - code: NOT_READY
    meaning: 传感器未完成初始化
```

`valid` 字段比 `speed_kph` 更重要：它让"没有数据"与"速度为零"区分开。缺了这个字段，上层只能靠超时猜，降级逻辑必然写得含糊。

## 关键设计与示例：平台分层与职责

| 层 | 主要职责 | 常见误区 |
| --- | --- | --- |
| 应用 | 功能逻辑与体验 | 直接访问硬件寄存器 |
| 应用框架 | 生命周期、配置注入 | 把业务逻辑塞进框架 |
| 平台服务 | 诊断、日志、时间同步 | 各应用各自实现一套 |
| 中间件 | 服务发现与序列化 | 在应用里硬编码 IP |
| OS/Hypervisor | 隔离与调度 | 用容器替代硬实时隔离 |
| 硬件/BSP | 驱动与电气适配 | 驱动里写业务策略 |

时间同步值得单独强调：跨域融合功能依赖同一时间基准，若各应用各自读本地时钟，融合结果会出现系统性偏差，且很难在测试中复现。

## 常见坑

版本策略缺失。接口只加字段不升版本，客户端按旧结构解析新报文，错误表现为"偶发数据异常"。

服务粒度过细。把每个信号都做成服务，会发现发现机制与订阅开销超过传输本身；粒度过粗则复用性丧失。按"业务能力"划分，而不是按信号划分。

组织没有跟着改。SOA 要求接口负责人与实现团队分离，如果仍是"谁写 ECU 谁定接口"，契约会被实现细节不断侵蚀。

## 小结与参考

SOA 的产出是一组稳定契约与一套可替换的实现，而不是某个协议。平台的价值在于让替换变得便宜。参考 AUTOSAR AP 的服务模型、SOME/IP 规范与整车厂 SOA 设计规范；具体接口定义以项目基线为准。
