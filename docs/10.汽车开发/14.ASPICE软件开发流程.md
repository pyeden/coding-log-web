# ASPICE软件开发流程学习笔记

第一次接触 ASPICE，多半不是在教材里，而是在主机厂的供应商问卷里：请提供最近一次 Automotive SPICE 评估报告、目标能力等级 CL2、评估范围覆盖 VDA scope。对刚进入汽车软件的人来说，这套东西看起来像一堆编号和文档模板；对做过两三个量产项目的人来说，它其实是一张“过程体检表”，告诉你哪些环节靠人扛、哪些环节靠机制。

这篇笔记想讲清楚流程本身：ASPICE 解决什么问题、过程是怎么组织的、六个软件过程各自要交出什么、能力等级怎么评、一次评估怎么跑，以及它和功能安全、网络安全这些标准是什么关系。术语会尽量给出英文全称，标准号和过程号保持可核实；凡是版本相关的细节，都以 VDA QMC 发布的最新 PAM 为准。

## 1. 为什么汽车软件要讲 ASPICE

汽车软件的开发周期和消费电子完全不同。一个车型的生命周期常常是十到十五年，软件在交付后还要经历多次 OTA、法规升级和召回；同一套软件往往由主机厂、一级供应商、二级供应商分层完成，接口和责任边界天然模糊。在这种结构下，“代码能跑”远远不够，还要回答三个问题：需求有没有被完整实现、改动会不会影响别处、出了问题能不能追到根因。

ASPICE（Automotive Software Process Improvement and Capability dEtermination）就是为这三个问题准备的一套共同语言。它不规定你用哪种架构、哪个 AUTOSAR 版本、哪种编程语言，也不判断你的算法好不好；它只问：这个过程有没有被定义、有没有被真正执行、有没有被监控和调整、有没有留下可核查的证据。换句话说，它评的是“过程的成熟度”，不是“产品的先进程度”。

最常见的两个误解是：把它当功能安全标准，以为 CL2 等于满足 ISO 26262；把它当文档竞赛，评估前突击补模板。前者混淆过程能力与安全完整性，后者混淆证据与纸张。ASPICE 的价值在于让研发过程可预测：需求变更能做影响分析，测试覆盖能对上需求，缺陷能闭环，项目延期能提前看到信号。代价是真实的：要有工作产品、要有评审、要有配置管理和度量，这些都花时间。

对个人来说，理解 ASPICE 的收益是知道自己在链条中的位置：写需求时知道它会被哪条用例验证，改接口时知道要通知哪些下游，评审时知道要留下什么记录。这些习惯与“大公司流程”无关，是工程能力的一部分。

## 2. ASPICE 是什么：模型、标准与版本

### 2.1 PRM、PAM 与评估标准

ASPICE 的文档体系里有两个核心概念。PRM（Process Reference Model，过程参考模型）定义每个过程的目的（purpose）和预期结果（outcome），只讲“这个过程中应该达成什么”，不讲怎么做。PAM（Process Assessment Model，过程评估模型）把 PRM 的 outcome 落到可观察的指标上：每个过程属性（Process Attribute，PA）对应哪些客观证据、工作产品应该包含什么、评级规则是什么。

这套结构来自 ISO/IEC 33000 系列。ISO/IEC 33001 是术语，33002 规定评估怎么执行，33003 规定测量框架的要求，33004 规定过程参考模型、评估模型和成熟度模型的要求，33020 给出过程能力测量的框架，也就是 CL0 到 CL5 与 PA 的定义。ASPICE 本身由 VDA QMC（Verband der Automobilindustrie — Quality Management Center，德国汽车工业协会质量管理中心）维护，是行业模型，不是 ISO 标准；它引用 ISO/IEC 33020 的能力等级，所以评估报告里的 CL 和 PA 编号在各行各业是通用的。

### 2.2 版本演进

| 版本 | 发布时间 | 主要变化 |
| --- | --- | --- |
| Automotive SPICE 2.5 | 2010 | 基于 ISO/IEC 15504，确立 CL0–CL5 与过程属性的结构，很多老项目仍按此签约 |
| Automotive SPICE 3.0 | 2015 | 转向 ISO/IEC 33000 系列，重写过程参考模型与评估模型，过程编号大改 |
| Automotive SPICE 3.1 | 2017 | 3.0 的修订版，修正工作产品和评级细节，是目前存量评估最常用的版本 |
| Automotive SPICE 4.0 | 2023 | 再次重构过程模型与工作产品，调整部分过程编号并增加新的过程领域，具体以 VDA QMC 最新 PAM 为准 |

选版本的原则很简单：跟着合同走。合同写 3.1 就用 3.1 的 PAM 和指南；新项目按 4.0 建过程时，先确认评估员与客户是否已切换。跨版本对照一定查对应版本的 PAM，不要凭记忆改编号。

| SWE 软件（Software） | SWE.1 软件需求分析、SWE.2 软件架构设计、SWE.3 详细设计与单元构建、SWE.4 软件单元验证、SWE.5 软件集成与集成测试、SWE.6 软件合格性测试 | 从软件需求到软件验证 |
| SUP 支持（Supporting） | SUP.1 质量保证、SUP.4 联合评审、SUP.7 文档、SUP.8 配置管理、SUP.9 问题解决管理、SUP.10 变更请求管理 | 横切所有过程的质量与受控性 |
| MAN 管理（Management） | MAN.3 项目管理、MAN.5 风险管理、MAN.6 度量 | 计划、风险与量化管理 |
| PIM / REU | PIM.3 过程改进、REU.2 复用管理 | 组织级能力建设 |

VDA QMC 的 Automotive SPICE Guidelines 定义了评估的最小过程集合，也就是常说的 VDA scope，通常覆盖 ACQ.4、SPL.2、SYS.1–SYS.5、SWE.1–SWE.6、SUP.1、SUP.8、SUP.9、SUP.10、MAN.3 等过程；具体清单、裁剪规则和最低评级要求以最新版指南为准。合同里常见的写法是“VDA scope，目标 CL2”，个别安全相关项目会点名要求 SWE 全组达到 CL3。

## 4. 软件 V 模型：SYS 与 SWE 的对应

V 模型不是“先写完文档再写代码”的瀑布，而是一种对应关系：左侧每往下走一层，就回答更细的问题；底部是把设计落到可执行的单元；右侧每往上一层，就用左侧对应的产物作为验证依据。迭代开发里，每个迭代都可能跑一遍小 V，ASPICE 评的是这个过程能力，不是阶段门禁。

<p style="text-align:center;color:#888;font-size:14px;">图 2 软件 V 模型：实线是工作产品流，虚线是双向追溯与验证关系</p>

| 左侧（分解） | 右侧（集成与验证） | 对应关系 |
| --- | --- | --- |
| SYS.1 系统需求获取 | SYS.5 系统合格性测试 | 系统需求必须有系统级测试覆盖 |
| SYS.2 系统需求分析 | SYS.4 系统集成与集成测试 | 系统需求分配到架构元素，集成后逐条验证 |
| SYS.3 系统架构设计 | SYS.4 系统集成与集成测试 | 架构决定集成顺序与接口测试范围 |
| SWE.1 软件需求分析 | SWE.6 软件合格性测试 | 每条软件需求至少对应一条合格性测试用例 |
| SWE.2 软件架构设计 | SWE.5 软件集成与集成测试 | 接口先定义再集成，集成后测接口 |
| SWE.3 详细设计与单元构建 | SWE.4 软件单元验证 | 单元测试覆盖详细设计中的每个单元行为 |

读图时注意两点。第一，SWE.1 的输入不只是 SYS.2 的系统需求，还包括 SYS.3 分配下来的架构约束，所以软件需求里会有“周期 10 ms”“栈不超过 4 KB”这类非功能条目。第二，右侧不是“最后集中测试”：SWE.4 在编码阶段持续发生，SWE.5 每次集成后回归，SWE.6 才面向完整软件判定。评估看的是活动有没有按计划发生、结果有没有回链，不是报告有多厚。

## 5. 六个 SWE 过程逐项拆解

六个软件过程是工程师日常打交道的地方，下表先给全貌，再逐项说容易走样的地方。

| 过程 | 目的 | 关键输入 | 核心活动 | 主要输出与评估证据 |
| --- | --- | --- | --- | --- |
| SWE.1 软件需求分析 | 把系统需求与变更请求转成可验证的软件需求 | 系统需求、系统架构、变更请求 | 分析、分类、优先级排序、与利益相关方协商、评审、建立追溯 | 软件需求规格、需求属性（唯一 ID、状态、验证准则）、双向追溯、评审记录 |
| SWE.2 软件架构设计 | 把软件需求分配到软件组件并定义接口 | 软件需求、系统架构、非功能约束 | 定义静态结构与动态行为、接口、资源消耗预算、安全相关分配 | 软件架构文档、接口规格、组件-需求映射、架构评审记录 |
| SWE.3 详细设计与单元构建 | 把组件细化到单元并实现 | 软件架构、接口规格、编码规范 | 详细设计、单元规格、编码、静态分析、代码评审 | 详细设计文档、单元规格、源码与提交记录、静态分析报告、评审记录 |
| SWE.4 软件单元验证 | 证明每个单元符合详细设计 | 详细设计、单元规格、测试环境 | 制定单元测试规格、执行、覆盖率分析、缺陷记录与回归 | 单元测试规格与结果、覆盖率报告、静态分析结果、缺陷单 |
| SWE.5 软件集成与集成测试 | 按架构顺序集成并验证接口 | 软件架构、集成策略、组件 | 定义集成顺序、集成、接口测试、回归测试 | 集成计划、集成测试规格与结果、接口覆盖记录 |
| SWE.6 软件合格性测试 | 证明软件满足软件需求 | 软件需求、集成后的软件、测试环境 | 制定合格性测试规格、执行、需求覆盖分析、偏差处理 | 合格性测试规格与结果、需求覆盖率、偏差与变更记录 |

SWE.1 最容易出的问题是需求不可验证。“系统应快速响应”不是需求，“从收到报文到输出控制量不超过 20 ms，95 分位”才是。评估员会随机抽一条需求，问它的验证准则是什么、对应哪条测试用例；答不上来，这个过程的证据链就断了。另一个问题是需求 ID 在需求、缺陷、测试三个工具里不一致，追溯矩阵看着完整，一抽样就对不上。

SWE.2 的重点是接口和资源预算。很多团队的架构文档只有模块框图，没有接口的时序、单位、范围和错误处理，也没有 CPU、内存、总线负载的预算。集成阶段必然返工，因为顺序无从推导。评估时看的是架构是否足以指导 SWE.3 和 SWE.5，而不是图好不好看。

SWE.3 的详细设计不等于给代码加注释，它要说明每个单元的责任、输入输出、状态机或算法、异常路径和资源约束；编码规范、静态分析规则、代码评审记录是常规证据。常见问题是“代码改了设计没改”，抽一个近期变更的单元对照版本日期就能看出来。

SWE.4 的误区是把覆盖率当目的。语句覆盖、分支覆盖、MC/DC 各有适用场景，选哪个取决于安全等级和项目约定；关键是目标事先定义、未覆盖分支有理由和风险说明、缺陷闭环并回归。只有一张 100% 截图而没有测试规格，反而会被追问。

SWE.5 的集成顺序必须来自架构，而不是“谁先写完谁先上”；集成测试覆盖接口的正常路径、边界和错误处理，每次集成后回归。评估最关注集成计划与实际执行记录是否一致。

SWE.6 面向完整软件，对照 SWE.1 的需求集合：测试规格在执行前评审，结果回链到需求，偏差有处理结论。最常见的缺口是“测了但没覆盖”——用例很多，需求覆盖率却算不出来，因为两者没有链接。

## 6. 双向追溯与一致性

追溯（traceability）是 ASPICE 里被问得最多、也最容易被做成形式的一件事。它有两个方向：正向从需求出发，回答“这条需求被哪些设计、代码、测试覆盖”；反向从代码或测试出发，回答“这个单元、这条用例为什么存在”。两个方向都通，才算双向。

| 追溯层次 | 上游 | 下游 | 典型证据 |
| --- | --- | --- | --- |
| 系统到软件 | SYS.2 系统需求、SYS.3 系统架构 | SWE.1 软件需求 | 需求分配矩阵、软件需求条目上的来源链接 |
| 需求到架构 | SWE.1 软件需求 | SWE.2 软件组件 | 组件-需求映射表 |
| 架构到详细设计与代码 | SWE.2 组件、接口 | SWE.3 单元、源码文件 | 单元-组件映射、提交记录中的需求/变更单号 |
| 设计到测试 | SWE.1 需求、SWE.3 单元规格 | SWE.4 单元测试、SWE.6 合格性测试 | 测试用例与需求的链接、覆盖率报告 |
| 问题与变更 | SUP.9 问题单、SUP.10 变更单 | 受影响的全部工作产品 | 缺陷单关联的变更单、变更影响分析记录 |

一致性（consistency）是追溯的孪生要求：同一条需求在需求库、设计文档、测试用例里的描述不能互相矛盾，术语和单位要统一。做法上先建术语表和命名规则，让工具做机械比对，人只判断差异是否有意为之。常见工具组合是需求管理（DOORS、Polarion、Codebeamer 等）加缺陷与变更（Jira 等）加代码托管与流水线，通过唯一 ID 串起来。

追溯矩阵不能靠评估前突击补。评估员会做抽样追踪：从一条需求走到测试结果，再从一条失败的测试走回需求，同时核对版本、评审日期和工具历史；手工补的矩阵通常在这几步露馅。省事的做法是把链接变成日常动作：评审建链接、提交写变更单号、执行关联用例，矩阵就是副产品。

## 7. 能力等级、过程属性与 N/P/L/F

能力等级（Capability Level，CL）描述一个过程“被管理到什么程度”，不是重要性排序，也不代表产品质量高低，而是制度化程度。

<img src="/img/aspice/capability-levels.svg" alt="能力等级 CL1 到 CL5 阶梯，标注对应过程属性与已实现、已管理、已建立、可预测、持续优化" loading="lazy" style="width:100%;height:auto;" />

<p style="text-align:center;font-size:14px;"><a href="/img/aspice/capability-levels.svg" target="_blank" rel="noopener">在新窗口打开原图</a></p>

<p style="text-align:center;color:#888;font-size:14px;">图 3 能力等级阶梯：每一级由一组过程属性支撑，等级越高越依赖数据与组织机制</p>

| 等级 | 名称 | 过程属性 | 含义 |
| --- | --- | --- | --- |
| CL0 | 不完整 Incomplete | 无 | 过程未执行，或未达成过程目的 |
| CL1 | 已实现 Performed | PA1.1 过程绩效 | 过程达成目的，产出所需工作产品 |
| CL2 | 已管理 Managed | PA2.1 绩效管理、PA2.2 工作产品管理 | 有计划、有监控、有调整；工作产品受控 |
| CL3 | 已建立 Established | PA3.1 过程定义、PA3.2 过程部署 | 使用组织标准过程，并按项目裁剪落地 |
| CL4 | 可预测 Predictable | PA4.1 过程测量、PA4.2 过程控制 | 用定量数据理解并控制过程 |
| CL5 | 持续优化 Optimizing | PA5.1 过程创新、PA5.2 过程优化 | 持续识别并实施改进 |

每个过程属性单独评分，等级用四个字母表示：N（Not achieved，0–15%）、P（Partially achieved，>15–50%）、L（Largely achieved，>50–85%）、F（Fully achieved，>85–100%）。百分比是达成度，不是考试分数，具体判定还要看是否存在系统性弱点。要判定某个等级达成，通常要求该等级及以下所有 PA 均为 F；所以报告里出现“CL2，其中 PA2.2 为 L”是正常的，它准确说明差距在哪。

实践中，CL1 意味着“事情做了，东西有”，CL2 意味着“有计划、有跟踪、有受控的工作产品”，CL3 意味着“不靠某个能人，组织有标准过程且项目在用”。多数主机厂对普通软件供应商要求 CL2，对安全相关或平台级软件要求 CL3；CL4、CL5 在整车项目里很少被强制要求，因为定量控制需要长期数据积累。

## 8. 一次评估怎么跑

评估不是审计，也不是打分比赛。它的产出是“在抽样的证据范围内，这些过程达到了什么等级、差距在哪里”。一个典型评估两到五天，流程大致如下。

<p style="text-align:center;color:#888;font-size:14px;">图 4 评估与改进闭环：评级只是中间产物，改进和复评才决定能力是否真的提升</p>

**准备**：确定评估范围（哪些项目、哪些过程、哪些场地）、目标等级、评估组构成和时间表。评估组通常由一名主任评估员（Lead Assessor）和若干评估员组成，且不能评估自己参与过的项目。

**就绪检查**：受评方提交工作产品清单和样本，评估组预检文档是否齐套、版本可查、访谈人可约；这一步做扎实，现场就不会变成“找文件”。

**现场评估**：开场会说明范围与规则，然后按过程做文档评审、访谈和抽样追踪。抽样追踪是核心：从需求抽到设计、代码、测试结果，再从一条缺陷或变更反向往回走，检查链路是否真实。

**评级**：每个过程属性由评估组独立评分，再开评级会形成共识。评级依据是证据和 PAM 规则，不是客户期望；受评方可以核对事实，但不能要求改分数。

**差距分析**：按过程列出弱项、缺失的证据、根因和优先级。差距报告要区分“没做”“做了没记录”“记录了但没用于决策”，三类改进动作完全不同。

**改进与复评**：把差距变成带 owner 和截止日期的行动项，改模板、改流程、改工具链、做培训；三到六个月后复评，重点看上次的差距项和新增范围，不必全量重跑。

要记住：评估结论只对抽样证据负责，同一家公司在不同项目、不同评估组手里可能拿到不同等级；别把等级当绝对分数，要看弱项清单。

## 9. 与 ISO 26262、ISO/SAE 21434、ISO 21448 的关系

ASPICE 和功能安全标准不是替代关系，而是骨架与内容的关系。ASPICE 规定“过程怎么管”，功能安全标准规定“安全相关的工作产品必须包含什么”。

| 标准 | 关注点 | 与 ASPICE 的接口 | 常见组合方式 |
| --- | --- | --- | --- |
| ISO 26262:2018 道路车辆功能安全 | 安全生命周期、ASIL 等级、确认措施 | 安全计划、安全需求、安全分析；Part 6 的软件单元与集成测试对应 SWE.4/SWE.5 | 用 ASPICE 的过程框架承载 26262 的活动与证据，做一张工作产品映射表 |
| ISO/SAE 21434:2021 道路车辆网络安全工程 | 威胁分析与风险评估（TARA）、CAL、漏洞管理 | 网络安全需求进入 SWE.1，架构安全措施进入 SWE.2，漏洞与事件进入 SUP.9/SUP.10 | 与 ASPICE 共用需求、变更、问题管理流程，避免两套记录 |
| ISO 21448:2022 预期功能安全（SOTIF） | 场景覆盖、已知/未知不安全场景、验证策略 | 影响 SYS.5 与 SWE.6 的验证策略、场景库与残余风险评估 | 把场景库作为测试资产纳入配置管理，测试结果回链到需求与场景 |
| IATF 16949 / 质量管理体系 | 组织级质量管理、供应商管理 | 管“组织有没有体系”，ASPICE 管“项目过程能力” | 体系文件引用 ASPICE 过程 |

最常见的浪费是为两套标准写两套文档。先建一张映射表：26262 的安全计划、安全需求、安全分析、验证报告分别挂在 MAN.3、SWE.1、SWE.2、SWE.5/SWE.6 下，共用同一套 ID 和评审记录。评估员看证据是否充分，不看文档标题。

## 10. 从 CL1 到 CL3 的最小落地路径

如果团队现在没有体系，不要一上来就铺满全部过程。选一条真实的软件线，按下面的顺序做，通常两三个迭代见效，半年到一年可冲 CL2，CL3 需要组织级投入。

1. 定范围：选一条量产软件线，明确覆盖 SWE.1–SWE.6、SUP.8、SUP.9、SUP.10、MAN.3，其他过程先做接口说明。
2. 定角色与裁剪：明确需求负责人、架构负责人、测试负责人、配置管理员、质量保证，写清楚每个过程的裁剪理由。
3. 建最小工作产品集：每个过程只保留“评估必看 + 项目真用”的模板，如需求条目、接口规格、单元测试规格、变更单。
4. 打通唯一数据源：需求 ID、变更单号、提交记录、用例 ID 必须互相引用；能自动同步的不要手工维护。
5. 跑一个迭代：从需求评审到合格性测试走一遍，记录按日常节奏产生，不补录。
6. 度量与改进：用 MAN.6 定义少量指标（需求覆盖率、缺陷逃逸率、变更返工率），每月看一次并真的调整做法。

CL3 的额外要求是组织级标准过程：先把上面这套做法固化成组织标准过程（PA3.1），再证明每个项目按裁剪规则部署并使用了它（PA3.2）。这一步的关键不是文档，而是“新项目启动时自动拿到这套东西”。

常见坑清单，逐条自查：

- [ ] 需求没有唯一 ID，或 ID 在需求、缺陷、测试三个工具里不一致
- [ ] 追溯矩阵是评估前用 Excel 手工补的，日期和评审记录对不上
- [ ] 软件架构只有模块框图，没有接口时序、单位范围、资源预算
- [ ] 详细设计与代码不同步，代码里存在的单元在设计文档里找不到
- [ ] 单元测试只报覆盖率数字，没有未覆盖分支的理由和风险说明
- [ ] 集成顺序凭经验决定，不是从软件架构推导出来的
- [ ] 合格性测试用例没有回链到 SWE.1 的软件需求
- [ ] 配置管理只有 Git 提交，没有基线、发布标签和变更单关联
- [ ] 问题解决只看关闭率，没有根因分析和影响范围评估
- [ ] 度量指标只为汇报存在，从未驱动过任何决策

## 11. 学习路径与资料

入门建议按“先全景、再单点、最后评估”的顺序：先读 PAM 的 PRM 部分，把每个过程的 purpose 和 outcome 读一遍；再精读 SWE.1 与 SWE.6，因为需求与合格性测试是追溯链的两端；最后读 PA 评级规则和评估指南，理解 N/P/L/F 怎么判。

资料方面，权威来源是 VDA QMC 发布的 Automotive SPICE PAM 与 Automotive SPICE Guidelines：前者定义过程与评级，后者给出 VDA scope、裁剪和评分细则，版本要与合同一致。ISO/IEC 33001、33002、33004、33020 是底层标准，读 33020 能彻底搞清 PA 与 CL 的关系。想当评估员可以了解 INTACS（International Assessor Certification Scheme）的认证路径：Provisional、Competent、Principal 三级，需要培训、考试和评估经历。

实践上最有效的一步是拿自己项目的一个过程做映射：选 SWE.1，列出它的输入、活动、输出，然后逐条问“这条证据现在在哪、谁维护、最近一次更新是什么时候”。做完这一步，你会对“过程能力”有具体的体感，而不是停留在名词上。

ASPICE 不是目的，而是一套让复杂协作可预期的方法。值得投入的不是评估前突击，而是把追溯、评审、配置管理变成日常习惯；评估来临时，只需把已有的东西整理出来。
