# 汽车软件与AUTOSAR

汽车软件的独特之处，不在于代码有多复杂，而在于它必须在十年生命周期里、在几十家供应商之间、在零下四十度到一百多度的环境里，保持可预测。一个手机 App 崩了，用户重启就好；一个刹车控制器里的任务错过截止时间，后果不可逆。AUTOSAR 正是为这种约束而生的一套标准化尝试：它不发明功能，它规定功能之间怎么说话、怎么被调度、怎么被验证。

## 1. 领域定位与边界：把硬件能力变成可验证的功能

软件在整车上的角色，是把传感器信号变成执行器动作，并在中间完成判断、仲裁与降级。这条链上有三个层次的问题：**功能逻辑**（该不该刹车、刹多重）、**运行时**（任务何时被调度、通信何时到达）、**基础设施**（怎么编译、怎么刷写、怎么诊断）。AUTOSAR 主要解决后两个层次，第一个层次仍然由应用开发者负责。

边界必须说清。AUTOSAR 不定义你的车辆动力学算法，不决定你用几个核，也不保证你的功能是安全的——它只提供机制，让安全机制有可能被实现。功能安全（ISO 26262）要求的安全机制，最终要落在具体的软件设计上，而不是"用了 AUTOSAR 就安全了"。这一点在评审中经常被混淆：架构合规不等于产品安全。

另一个边界是实时性。AUTOSAR 经典平台（Classic Platform，CP）面向硬实时控制，自适应平台（Adaptive Platform，AP）面向高算力、面向服务的计算。把两者混为一谈，会得到错误的时间预算：CP 的周期任务以毫秒计，AP 的进程调度以操作系统的调度策略为准，抖动特性完全不同。

## 2. 在整车开发流程中的位置

软件开发的节奏与硬件不同。硬件以月为单位冻结，软件以周为单位迭代，但两者的耦合点（接口、时序、资源）必须提前锁定。

| 阶段 | 软件侧输入 | 关键输出 | 门禁关注点 |
| --- | --- | --- | --- |
| 需求分析 | 整车功能需求、法规与安全目标 | 软件需求规格、变体矩阵 | 需求是否可验证、是否覆盖降级 |
| 架构设计 | EEA 拓扑、算力与网络预算 | 软件架构、SWC 划分、接口定义（ARXML） | 接口是否稳定、资源是否够用 |
| 详细设计 | 架构与安全需求 | 模块设计、状态机、时序预算 | 每个安全机制是否有实现方案 |
| 编码与单元测试 | 设计文档、编码规范 | 源码、单元测试报告、静态分析报告 | MISRA 违规是否闭环 |
| 集成与测试 | 各模块交付物 | 集成测试报告、HIL 测试报告 | 时序与故障注入是否覆盖 |
| 标定与验证 | 整车标定需求 | 标定数据、参数集、版本清单 | 标定版本与软件版本是否绑定 |
| 量产与运维 | 产线刷写规范 | 刷写规范、OTA 包、SBOM | 回滚策略、签名校验、版本可追溯 |

关键时点是**接口冻结**。ARXML 一旦发给多家供应商，任何字段变更都要走变更流程，周期以周计。所以架构阶段必须把"预留"写进接口：预留几个信号、预留多少周期、预留多少内存，而不是等需求来了再加。这条经验几乎每次项目都会被重新验证一遍。

## 3. 核心概念与术语表

| 术语 | 英文全称 | 一句话解释 |
| --- | --- | --- |
| AUTOSAR 经典平台 | Classic Platform (CP) | 面向硬实时控制的标准化软件架构，静态配置 |
| AUTOSAR 自适应平台 | Adaptive Platform (AP) | 面向高算力与面向服务的运行时，支持动态部署 |
| 基础软件 | Basic Software (BSW) | 与硬件无关或弱相关的标准化服务层 |
| 运行时环境 | Runtime Environment (RTE) | 应用软件组件与 BSW 之间的通信中间层 |
| 软件组件 | Software Component (SWC) | 应用功能的最小封装单元，通过端口通信 |
| 微控制器抽象层 | Microcontroller Abstraction Layer (MCAL) | 直接操作寄存器的驱动层，屏蔽芯片差异 |
| 操作系统 | AUTOSAR OS | 基于 OSEK/VDX 的静态优先级抢占式实时内核 |
| 诊断通信管理 | Diagnostic Communication Manager (Dcm) | 实现 UDS 服务，处理诊断请求与响应 |
| 诊断事件管理 | Diagnostic Event Manager (Dem) | 记录故障码与冻结帧，管理故障状态 |
| 非易失存储管理 | Non-Volatile Memory Manager (NvM) | 统一管理掉电保持数据的读写与校验 |
| 面向服务架构 | Service-Oriented Architecture (SOA) | 以服务契约组织功能，支持动态发现与调用 |
| 可扩展的面向服务的 IP 中间件 | Scalable service-Oriented MiddlewarE over IP (SOME/IP) | 车载以太网上的服务通信协议 |
| 数据分发服务 | Data Distribution Service (DDS) | 以数据为中心的发布订阅中间件，常用于智驾 |
| 统一诊断服务 | Unified Diagnostic Services (ISO 14229, UDS) | 诊断与刷写用的标准服务集 |
| 基于 IP 的诊断 | Diagnostics over IP (ISO 13400, DoIP) | 以太网上的诊断传输协议 |
| 闪存引导程序 | Flash Bootloader (FBL) | 独立于应用的刷写程序，负责接收与写入新软件 |
| 空中升级 | Over-the-Air Update (OTA) | 通过无线网络分发与安装软件更新 |
| 汽车软件过程能力评定 | Automotive SPICE (ASPICE) | 评价开发过程成熟度的模型 |
| 软件物料清单 | Software Bill of Materials (SBOM) | 列出所有开源与第三方组件的清单 |

## 4. 主流方案与取舍

| 方案 | 优势 | 代价与限制 |
| --- | --- | --- |
| AUTOSAR CP | 硬实时、标准化接口、供应商可替换、工具链成熟 | 静态配置复杂、学习曲线陡、资源开销固定，迭代不灵活 |
| AUTOSAR AP | 支持 SOA、动态部署、可复用 POSIX 生态 | 实时性弱于 CP，启动与资源管理复杂，量产经验仍在积累 |
| 自研裸机/RTOS | 资源占用小、启动快、完全可控 | 复用性差，接口私有，供应商协同与人员流动风险高 |
| 商用 BSW 栈 | 经过量产验证、认证材料齐全、支持度高 | 授权费高，配置受工具约束，深度定制困难 |
| 开源/自建 BSW | 成本低、可控性强 | 认证与质量证据需自建，长期维护负担重 |
| 静态 RTE 通信 | 时序确定、可分析、资源可预算 | 变更需重新生成，跨域灵活性差 |
| SOA 服务通信 | 松耦合、可动态发现、便于跨域复用 | 时延与抖动不确定，需额外的服务质量机制 |
| 单 ECU 有线刷写 | 简单可靠、带宽充足 | 召回成本高，必须到店 |
| 整车 OTA | 修复快、可增量交付、用户体验好 | 依赖网络与电量，需回滚与签名机制，法规合规要求高 |
| 严格 MISRA 全量合规 | 降低语言层面风险，便于审查 | 偏离项审批成本高，特殊优化写法受限 |

选择的判断标准是"时间确定性要求"与"变更频率"。制动、转向、电机控制这类毫秒级闭环，CP 是更稳的选择；座舱、智驾感知、车云协同这类高算力、频繁迭代的场景，AP 或通用操作系统更合适。真正的难点不在单个域，而在跨域边界：CP 域与 AP 域之间的信号怎么映射、时延怎么预算、故障怎么传播。

## 5. 关键交付物与评审要点

**架构类**：软件架构文档、SWC 划分与接口定义、ARXML 文件、变体管理方案、资源预算表（CPU、内存、总线负载、堆栈）。**实现类**：源码、编码规范符合性报告（MISRA C 等）、静态分析报告、单元测试报告与覆盖率。**验证类**：集成测试报告、HIL 测试报告、故障注入结果、时序分析报告。**运维类**：刷写规范、诊断数据库（CDD/ODX）、OTA 包与回滚方案、软件版本清单与 SBOM。

评审要点有四个。第一，**接口是否可追溯**。每条信号应该能追到需求、追到发送方与接收方、追到测试用例。ARXML 只是载体，追溯链才是证据。第二，**时序预算是否闭合**。端到端时延要拆成采样、传输、处理、执行四段，每段有预算与实测，不能只给一个总数。第三，**故障传播是否定义**。一个 ECU 掉线，依赖它的功能是降级、保持还是关闭，必须有明确策略，且策略要能在整车上被验证。第四，**版本是否可复现**。给定一个软件版本号，能否还原出全部源码、配置、工具版本与编译参数。做不到这一点，三年后的缺陷分析会变成考古。

一个常见的形式主义：单元测试覆盖率达标，但测试用例只覆盖正常路径。评审时应抽查故障路径的用例，特别是初始化失败、通信超时、存储损坏这三类。

## 6. 标准法规与工具链

规范体系：AUTOSAR 官方规范按 CP 与 AP 分册发布，版本以 R 加年份与月份命名（如 R21-11），具体版本与文档编号以 AUTOSAR 官网最新发布为准。诊断与刷写：ISO 14229（UDS）、ISO 15765（DoCAN）、ISO 13400（DoIP）。功能安全：ISO 26262-6 对软件层面提出要求，对应国内 GB/T 34590 系列。过程模型：Automotive SPICE 4.0（2023 年发布），评级时需确认客户采用的版本。编码规范：MISRA C:2012 及其修订。网络安全与更新：ISO/SAE 21434:2021、UN R155/R156，软件更新管理体系（SUMS）的合规要求以目标市场法规为准。

工具链是 AUTOSAR 项目最容易被低估的成本。配置工具：Vector DaVinci Configurator、ETAS ISOLAR、Elektrobit tresos；BSW 栈：Vector MICROSAR、ETAS RTA、EB tresos 配套；编译与调试：Tasking、Green Hills、Lauterbach TRACE32；测试：CANoe、vTESTstudio、dSPACE HIL；需求与追溯：Polarion、DOORS、Jama；版本与构建：Git 加 CI 流水线，配合制品库管理二进制与配置。工具之间的数据交换主要靠 ARXML，这也意味着 ARXML 的版本兼容性是一个真实的工程风险——不同工具版本生成的模型可能无法互读。

## 7. 与其他领域的接口与常见冲突

**与 EEA 的接口**：软件架构必须落在电子电气架构给定的算力、网络与供电边界内（见 [EEA 学习笔记](/note/eea/) 中的[面向服务架构与软件平台](/pages/7e2a9c4b1f8d3605/)与 [AUTOSAR 平台章节](/pages/0b6f3d8c2a7e9145/)）。典型冲突是"功能增加但预算不变"：新功能要求更多核、更多带宽，而架构阶段预留不足。处理办法是把预算表作为架构交付物的一部分，任何超预算必须走显式审批并给出补偿方案。

**与三电的接口**：电机控制、BMS 状态机、能量管理策略都是软件密集区（见[动力总成与三电](/note/powertrain/)）。冲突在于控制周期与安全机制的耦合：扭矩监控需要独立于功能路径的第二条通道，而这条通道往往在项目后期才被提出，导致资源与接口重新分配。

**与热管理的接口**：热管理的模式切换本质上是状态机，阀位、泵速、压缩机转速之间存在互锁（见[热管理](/note/thermal/)）。冲突是诊断覆盖率：一个阀卡滞，软件能否在合理时间内识别并降级，取决于是否设计了位置反馈与合理性检查。

**与整车集成的接口**：标定参数与软件版本必须绑定（见[整车集成与性能属性](/note/vehicle-integration/)）。常见事故是"标定数据串版"：A 车的参数刷进了 B 车，动力或制动表现异常却查不出原因。解决办法是把标定数据集纳入版本管理，并在 EOL 阶段做校验和比对。

**与安全法规的接口**：功能安全要求的安全机制需要软件实现，网络安全法规要求更新包签名与回滚（见[整车安全与法规](/note/vehicle-safety/)）。冲突在于资源竞争：签名校验与安全监控都吃 CPU，而在低成本控制器上预算很紧。取舍办法是把安全监控放在高优先级分区，签名校验放到后台任务，并接受启动时间的增加。

## 8. 常见坑与检查清单

- [ ] 接口定义是否已冻结并纳入变更管理，ARXML 是否有版本与兼容性说明
- [ ] 端到端时延是否拆分到采样、传输、处理、执行四段并有实测数据
- [ ] 每个安全机制的检测时间加响应时间是否小于 FTTI
- [ ] 单元测试是否覆盖初始化失败、通信超时、存储损坏等故障路径
- [ ] 软件版本能否仅凭版本号复现（源码、配置、工具、编译参数）
- [ ] 刷写流程是否包含签名校验、断电保护与失败回滚
- [ ] 标定数据是否与软件版本绑定，EOL 是否有校验和比对
- [ ] SBOM 是否覆盖开源组件及其许可证与已知漏洞状态

## 9. 学习路径与资料

建议按"运行时—通信—工具—流程"的顺序学，而不是一上来读规范全集。AUTOSAR 规范有数千页，通读的性价比极低。

第一步理解实时系统的骨架：任务、优先级、抢占、优先级反转、堆栈预算。这些概念在 AUTOSAR OS 里被具体化，但底层逻辑是通用的。推荐用一个低成本开发板跑一遍周期任务与中断，观察抖动。

第二步理解通信：CAN 报文到信号组的映射、PDU 路由、SOME/IP 的服务发现与方法调用、DDS 的 QoS。重点不是背协议字段，而是理解"时延与确定性如何被牺牲换取灵活性"。

第三步动手配置：用任一商用或评估版工具走一遍"新建工程—配置 BSW—生成 RTE—编译—HIL 验证"的完整链路。走通一次，比读十篇架构文章更能理解 RTE 到底在做什么。

第四步读流程：ASPICE 的过程域划分、ISO 26262-6 的软件要求、ISO/SAE 21434 的威胁分析。流程不是为了审计，而是为了让多人协作时的证据可复用。

资料优先级：AUTOSAR 官方规范与工具厂商的应用笔记高于教材，高于博客。规范要按需查阅，带着具体问题去读某一册的某一章，效率最高。国内可参考主机厂公开的软件平台白皮书，但要注意其版本与量产状态的差距。

最后一条经验：汽车软件的复杂度主要不在算法，而在集成。一个人能写出功能，十个人能写出系统，一百个人能写出可维护十年、能通过审计、能在四个供应商之间交接的系统——那才是这个领域真正的手艺。
